# 구조 — automation-idea (n8n 자동화 아이디어 모음)

검색의도: "이런 것도 자동화가 되나?" 궁금한 사람, n8n으로 뭘 만들지 아이디어가 필요한 사람.
**읽고 바로 만들어볼 수 있어야 한다** — 막연한 "자동화하세요" 말고, 트리거부터 결과물까지 흐름이
손에 잡혀야 한다.

## 이 구조가 dev-tool(review)과 다른 점

- dev-tool 은 "도구 하나를 며칠 써본 후기"다. 이건 "이 도구로 만들 수 있는 아이디어 여러 개"다.
- **써봤다고 하지 마라.** 아이디어를 제시하는 글이지 체험기가 아니다. "저는 이렇게 씁니다" 대신
  "이렇게 만들 수 있어요"로 쓴다.
- **완전한 워크플로 JSON을 지어내지 마라.** n8n 워크플로는 노드 타입·파라미터·연결 구조가 정확해야
  임포트가 된다. 검증 안 된 JSON은 그대로 못 쓰거나 에러가 난다 — 이건 이 카테고리에서 가장 위험한
  환각 지점이다. 블루프린트(트리거→단계→결과)가 본체이고, 코드블록은 **검증 가능한 조각만**
  (Cron 표현식, HTTP 요청 헤더, 짧은 Function 노드 코드 등 — 그 자체로 맞는지 판단 가능한 수준).

## 뼈대

### 1. 왜 이 모음인가 (3문장)
어떤 반복 업무·불편함을 겨냥하는지. "오늘은 ~에 대해 알아보겠습니다" 금지.

### 2. 아이디어마다 (H2: 번호 + 짧은 이름)

같은 틀을 반복한다 — 하나라도 비면 "아이디어"가 아니라 "제목"만 있는 것이다:

- **한 줄 정의**: 무엇을 자동화하는지 한 문장.
- **트리거**: 무엇이 이 흐름을 시작시키는가(Cron 시간·웹훅·폼 제출·이메일 수신 등).
- **흐름**: 트리거 → 중간 단계(몇 개) → 결과물. 화살표로 짧게, 그다음 각 단계를 1~2문장씩.
- **왜 유용한가**: 정확히 뭘 줄여주는지 구체적으로("시간 절약" 금지 — "매일 아침 수동으로 하던
  집계 작업 하나를 없앤다" 처럼 구체적으로).
- **필요한 것**: n8n 노드 이름·외부 서비스/API 나열. 조사에서 실재 확인된 것만.
- **(있으면) 코드 조각**: Cron 표현식이나 짧은 설정값 — 조사 파일에 근거가 있을 때만. 없으면
  이 항목 자체를 생략해라.
- **난이도**: 초급/중급/고급 중 하나 + 왜(예: "API 키 발급이 필요해서 중급").
- `[IMG: 이 흐름을 보여줄 다이어그램 설명]`

### 3. 시작 전에 알아둘 것
n8n 셀프호스팅이 필요한지 클라우드로 되는지, 계정·API 키 준비가 필요한 항목이 있는지 한 문단.

### 4. 정리 — 하나만 골라 시작한다면
난이도가 가장 낮은 것부터 추천 + 이유.

## 검증 원칙 — 이 카테고리의 핵심

- **노드 이름·연동 가능 여부는 조사 단계에서 실제 n8n 문서(docs.n8n.io)나 커뮤니티 워크플로로
  확인한 것만 쓴다.** 확인 안 됐으면 "~노드로 되는 것으로 보인다"처럼 헤지하거나 그 아이디어를 뺀다.
- **"이대로 임포트하면 끝"이라고 쓰지 마라.** 실제로 안 써봤으면(대부분 그렇다) 그렇게 주장할 근거가
  없다. "이 흐름대로 노드를 연결하면 됩니다" 정도로.
- 특정 API의 요금제·무료 한도를 언급하려면 시점을 명시해라(자주 바뀐다).
- 안 써본 걸 써본 것처럼 쓰지 마라 — 다른 카테고리와 같은 원칙.
