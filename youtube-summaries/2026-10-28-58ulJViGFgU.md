# Who Is Making This Request? Agent Auth 101 - Kamil Potrec, Keycard

🔗 https://youtu.be/58ulJViGFgU · 📅 2026-10-28 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 다양한 시스템과 안전하게 상호작용하기 위한 인증 및 권한 부여 문제를 해결하기 위해 에이전트 아이덴티티, 위임, 짧은 수명 자격 증명, 연동, 브로커링, 정책 및 승인, 감사 기능을 갖춘 통합 플랫폼이 필요하다는 내용입니다.

## 발표자·소속
Kamil Potrec, Keycard

## 핵심 주장
- **에이전트 인증은 더 이상 선택 사항이 아닙니다.** 에이전트가 실제 자격 증명을 사용하여 실제 데이터에 접근하고 작업을 수행하므로, 각 에이전트는 고유한 아이덴티티, 범위가 지정된 접근 권한 및 감사 추적 기능을 가져야 합니다.
- **현실은 복잡하므로 표준을 기반으로 구축해야 합니다.** 수많은 클라이언트, 서버, 인증 서버를 통제할 수 없는 환경에서 OAuth, 토큰 교환, 연동(federation)과 같은 표준 기술을 활용하여 상호 운용성을 유지해야 합니다.
- **"YOLO" 방식으로 접근하지 마세요.** 에이전트 인증은 복잡하고 중요하므로, 에이전트 외부에서 인증을 강제하고 LLM(대규모 언어 모델)에 인증 처리를 맡기지 않아야 합니다.

## 세부 내용
발표는 "누가 이 요청을 하고 있는가?"라는 질문으로 시작합니다. 기존 시스템에서는 Alice(사용자)가 LangChain 에이전트를 통해 MCP 서버에 최신 인보이스를 요청합니다. 에이전트는 LLM API 키를 사용하고, MCP 서버는 Alice의 PAT(Personal Access Token), 정적 키 또는 OAuth를 사용하여 Invoices API에 접근합니다. 여기서 MCP 서버는 서비스 계정을 사용하여 Invoices API를 호출합니다. 문제는 각 단계에서 누가 요청을 하는지(Alice, 에이전트, MCP 서버) 명확하지 않다는 것입니다.

이러한 방식의 문제점은 다음과 같습니다.
1.  **오래 지속되는 비밀(Long-lived secret):** Alice의 PAT는 노트북에 저장되어 쉽게 유출될 수 있으며, 회전 주기가 길어 악용될 위험이 있습니다.
2.  **공유 비밀 또는 통과(Shared secret or passthrough):** 에이전트가 Alice의 PAT를 전달하면, 에이전트가 Alice의 모든 권한을 갖게 되어 권한 범위가 너무 넓어집니다.
3.  **과도한 권한의 서비스 계정(Overprivileged service account):** MCP 서버의 서비스 계정은 여러 사용자의 요청을 처리하기 위해 과도한 권한을 가질 수 있으며, 이는 보안 위험을 초래합니다.
4.  **체인 내 식별 불가(Nothing in the chain identifies the agent):** 요청 체인 내에서 에이전트의 고유한 아이덴티티가 없어 접근 범위를 지정하거나, 권한을 취소하거나, 감사를 수행하기 어렵습니다.

"올바른 방법"은 모든 홉(hop)이 사용자(Alice)와 에이전트 모두를 인지하도록 하는 것입니다.
1.  **짧은 수명 사용자 토큰(Short-lived user token):** Alice는 한 번 로그인하여 짧은 수명의 토큰을 받으며, 이 토큰은 디스크에 비밀로 저장되지 않고 몇 분 내에 만료됩니다.
2.  **토큰 교환, 통과 금지(Token exchange, not passthrough):** 에이전트는 자신의 아이덴티티를 증명하고, 사용자(Alice)와 에이전트에 바인딩된 특정 대상 및 범위에 대한 토큰을 받습니다. 비밀은 LLM 모델 컨텍스트에 절대 들어가지 않습니다.
3.  **위임되고 범위가 축소된 접근(Delegated, downscoped access):** MCP 서버는 Alice의 인보이스에만 접근할 수 있는 범위가 지정된 다운스트림 토큰을 교환합니다. 서비스 계정이 필요 없습니다.

이러한 에이전트 인증 시스템이 제공해야 할 기능은 다음과 같습니다.
-   **에이전트 아이덴티티(Agent identity):** 에이전트별, 또는 실행/세션별로 고유한 아이덴티티를 가지며, 이를 시작한 주체와 분리됩니다.
-   **위임(Delegation):** 사용자 X가 에이전트 Y에게 Z를 수행하도록 승인했음을 증명할 수 있는 기록입니다.
-   **범위가 지정된, 짧은 수명 자격 증명(Scoped, short-lived credentials):** 도구, 리소스 및 작업에 필요한 시간 범위로 제한되며, 구성 파일에 마스터 키가 없습니다.
-   **연동(Federation):** 모든 통합 지점에서 새로운 클라이언트 없이 여러 권한 부여 서버 간에 아이덴티티를 신뢰합니다.
-   **브로커링(Brokering):** 토큰(API 키 등)으로 교환할 수 없는 자격 증명을 보유하고, 대신 범위가 지정된 접근 권한을 제공합니다.
-   **정책 및 승인(Policy and approval):** 에이전트가 행동할 때 무엇이 자동으로 실행되고 무엇이 사람의 승인을 필요로 하는지 결정합니다.
-   **감사(Audit):** 에이전트가 누구의 권한으로 무엇을 했는지, 그리고 그 이유를 기록합니다.

이러한 복잡한 과정을 매번 호출마다 올바르게 처리하는 것은 어렵습니다.
1.  클라이언트는 401 응답을 통해 권한 부여 서버를 발견하고, PKCE를 사용하여 클라이언트로 등록하고 사용자를 로그인시킵니다.
2.  에이전트는 자신의 아이덴티티를 워크로드 아이덴티티로 증명하고, 대상 및 범위에 바인딩된 토큰을 받습니다.
3.  MCP 서버는 토큰을 받아 서명, 발급자, 만료, 대상, 토큰 바인딩을 검증합니다.
4.  서버 SDK는 정책 시행 지점으로서 런타임 인증(Runtime Auth)에서 정책을 동기화하고 로컬에서 권한을 부여합니다.
5.  Invoices API를 위해 MCP 서버는 저장된 비밀 대신 범위가 지정된 다운스트림 토큰을 교환합니다.
6.  모든 것이 감사됩니다. 클라이언트는 필요할 때 캐시, 새로 고침, 단계별 동의를 처리합니다.

SDK를 통한 구현의 문제점은 다음과 같습니다.
1.  **모든 팀이 채택해야 합니다.** 수백 개의 서비스가 각자의 일정에 따라 업그레이드됩니다.
2.  **모든 언어에 포트가 필요합니다.** 각 런타임은 다른 SDK를 빌드, 테스트 및 동기화해야 합니다.
3.  **모든 곳에 임베드할 수 없습니다.** 기성 에이전트와 벤더 MCP 서버는 자체 코드를 배포합니다.
4.  **패치가 마이그레이션이 됩니다.** SDK의 버그 수정은 이를 사용하는 모든 저장소에서 수정해야 합니다.
5.  **자격 증명이 에이전트에 남아 있습니다.** SDK는 에이전트 프로세스 내에서 실행되며, 토큰은 모델과 도구가 접근할 수 있는 곳에 있습니다.

이러한 문제를 해결하기 위해 **게이트웨이**를 도입하여 키를 에이전트의 접근 범위 밖으로 이동시키는 방안을 제시합니다. 에이전트는 게이트웨이에 요청하고, 게이트웨이는 런타임 인증 서버와 정책을 확인하여 필요한 자격 증명을 가져와 요청에 주입한 후 대상 API로 전달합니다.
이 방식의 장점은 다음과 같습니다.
-   **키가 접근 범위 밖에 있습니다.** 자격 증명은 주입되어 전달될 뿐, 유출되거나 재사용될 수 없습니다.
-   **즉각적인 취소(Revoke instantaneously):** 작업이 거부된 후 다음 요청부터 즉시 취소됩니다.
-   **모든 요청에 대한 감쇠(Attenuation on every request):** 각 호출은 에이전트의 범위를 넘어 작업의 범위로 좁혀집니다.
-   **하나의 감사 추적(One audit trail):** 모든 호출, 사용자 및 에이전트가 하나의 로그에 기록됩니다.
-   **다운스트림 변경 없음(No changes downstream):** 변경할 수 없는 기존 시스템에 적용됩니다.

하지만 게이트웨이에도 다음과 같은 문제점이 있습니다.
1.  **모든 호출에 또 다른 홉(Another hop on every call):** 지연 시간이 추가되고, 새로운 종속성이 발생합니다.
2.  **트래픽이 통과해야 합니다.** 로컬 도구, 스티키 MCP 서버, 에이전트 간 호출은 게이트웨이를 우회할 수 있습니다.
3.  **아이덴티티는 여전히 도착해야 합니다.** 어떤 에이전트가 어떤 사용자를 위해 작동하는지 알아야 합니다.
4.  **새로운 왕관 보석(A new crown jewel):** 모든 자격 증명을 보유하거나 가져오므로, 게이트웨이가 손상되면 모든 것을 잃게 됩니다.
5.  **TLS 프록싱(TLS proxying):** 자격 증명을 주입하기 위해 TLS를 종료해야 하며, 모든 클라이언트는 CA를 신뢰해야 합니다.
6.  **구성 관리(Configuration management):** 라우팅, 정책, 업스트림 커넥터 및 환경 간 동기화가 필요합니다.
7.  **누군가 운영해야 합니다.** HA(고가용성), 스케일링, 업그레이드 및 요청당 온콜(on-call)이 필요합니다.

Keycard는 이러한 모든 단계를 하나의 플랫폼에서 처리합니다. 사용자 및 에이전트 아이덴티티, 짧은 수명 자격 증명, 연동, 브로커링, 정책, 감사를 제공합니다. 클라이언트 SDK는 에이전트 내에서 발견, 등록, 워크로드 아이덴티티 증명, 에이전트 바인딩 토큰, 캐싱 등을 처리합니다. 서버 SDK는 서비스 내에서 리소스 메타데이터 게시, 바인딩 검증, 사용자 및 에이전트 식별, 도구별 범위 적용, 정책 동기화 등을 처리합니다. 게이트웨이는 변경할 수 없는 시스템 앞에서 자격 증명 관리, 대상 수락, 홉 간 전달, 정책 시행 등을 담당합니다.

## 실무 적용 포인트
- **에이전트 아이덴티티 및 짧은 수명 자격 증명 도입:** 에이전트가 고유한 아이덴티티를 가지고 필요한 최소한의 권한만 부여받도록 설계하고, PAT나 정적 키 대신 짧은 수명의 토큰을 사용하도록 합니다.
- **토큰 교환 및 위임 패턴 활용:** 에이전트가 사용자 자격 증명을 직접 전달하는 대신, 자신의 아이덴티티를 증명하고 필요한 범위의 토큰을 교환하여 사용하도록 합니다. 이는 권한 축소 및 책임 분리에 도움이 됩니다.
- **표준 기반의 상호 운용성 확보:** OAuth, 워크로드 아이덴티티 연동 등 개방형 표준을 사용하여 다양한 시스템과 에이전트 간의 인증 및 권한 부여를 구현하여 유연성과 확장성을 높입니다.
- **게이트웨이 또는 브로커링 계층 고려:** 기존 시스템을 수정하기 어렵거나 에이전트의 자격 증명 접근을 엄격하게 통제해야 하는 경우, 게이트웨이 또는 브로커링 계층을 도입하여 자격 증명 관리, 정책 시행, 감사 추적을 중앙 집중화합니다.
