# Agents in Orbit: Workflows, Not Autopilot — Eduardo Simon & Javier Casal, Flywire

## 핵심 주장
*   **워크플로 중심 자동화**: AI 에이전트가 개방형 루프에서 자유롭게 실행되도록 하는 대신, Orbit은 LLM을 구조화된 워크플로에 직접 통합하여 예측 가능한 부분은 코드로 처리하고 추론이 필요한 부분에만 LLM을 호출합니다.
*   **규제 준수 및 보안**: 금융 기업으로서 PCI DSS, SOC II와 같은 엄격한 규제 프레임워크를 준수하며, 민감한 데이터가 통제된 환경을 벗어나지 않도록 하고, 모든 변경 사항은 코드와 마찬가지로 병합 요청 검토를 거쳐 안전성과 신뢰성을 보장합니다.
*   **확장성 및 효율성**: Orbit은 AWS Fargate 컨테이너와 MicroVM 런타임을 활용하여 에이전트를 탄력적으로 확장하고, 개별 LLM 단계에 대한 격리된 평가를 통해 성능 회귀를 저렴하게 포착하며, 대규모 코드베이스에 걸쳐 대량 변경을 동시에 실행하여 엔지니어링 효율성을 극대화합니다.

## 세부 내용

Flywire는 전 세계에서 가장 복잡한 결제를 처리하는 기업으로, 교육, 헬스케어, 여행, B2B 서비스 등 다양한 산업 분야에서 5,300개 이상의 고객과 240개 이상의 국가에 서비스를 제공합니다. 이들은 PCI DSS 및 SOC II와 같은 엄격한 규제 프레임워크에 따라 운영되므로, 고객 데이터, 개인 식별 정보(PII), 결제 세부 정보의 보안과 개인 정보 보호가 핵심 요구사항입니다. 약 400명의 소프트웨어 엔지니어가 Java, Ruby, Go, Python, .NET, PHP 등 다양한 기술 스택을 사용하며, 모든 빌드 및 배포는 내부 PaaS인 Victoria(GitLab 및 AWS 인프라 기반)를 통해 이루어집니다.

Flywire의 AI 여정은 6개월 전 AI 플랫폼 경험 팀이 공식적으로 구성되기 전부터 시작되었습니다. 엔지니어들은 이미 AI 도구를 실험하고, 스킬을 만들고, MCP 서버를 구축하고, 초기 코드 검토 봇을 조립하는 등 자발적인 활동을 해왔습니다. 이러한 유기적인 활동은 엔지니어들이 AI 자동화를 원하며, 안전한 기반이 필요하다는 것을 입증했습니다. 이후 6개월 동안 Claude Code는 160개 이상의 릴리스를, 주요 AI 연구소는 20개 이상의 새로운 모델을 출시하는 등 빠르게 발전했습니다.

이러한 배경에서 Flywire는 'Orbit'이라는 자체 '고된 작업 제거자(toil killer)'를 구축했습니다. Orbit은 LLM을 구조화된 워크플로에 직접 통합하여 일상적인 엔지니어링 반복 작업을 제거하는 내부 플랫폼입니다. AI 에이전트가 개방형 루프에서 자유롭게 실행되도록 하는 대신, Orbit은 결정론적 코드와 작은 LLM 단계를 결합합니다. 반복적인 절차 로직은 코드로 결정화하고, 추론이 실제로 필요한 경우에만 모델을 호출합니다.

Orbit을 직접 구축하기로 결정한 이유는 여러 가지입니다. 프론티어 모델 덕분에 기능 개발이 매우 빨라져 맞춤형 플랫폼 구축 비용이 크게 절감되었습니다. 더 중요한 것은, PCI, PII, PHI 데이터를 다루는 금융 기업으로서 기존 Victoria 인프라 내에서 실행을 유지하여 민감한 데이터가 통제된 환경을 벗어나지 않도록 보장할 수 있다는 점입니다. 또한, 긴 공급업체 보안 검토 및 추가 규제 준수 작업을 피할 수 있습니다.

워크플로는 YAML 파일로 정의되며, 이는 트리거, 결정론적 단계, LLM 단계로 구성됩니다. 트리거는 API 호출, 웹훅, 스케줄된 작업 등 세 가지 방식으로 시작될 수 있습니다. 예를 들어, 코드 검토 에이전트는 엔지니어가 병합 요청에서 검토 봇을 언급할 때 GitLab 웹훅을 통해 트리거됩니다. 이후 결정론적 활동(메타데이터 가져오기, 위험 등급 분류, 이전 발견 사항 로드, 저장소 복제)이 수행된 후, LLM 단계가 호출됩니다. LLM은 코드를 읽을 수 있지만 수정할 권한은 없으며, 엄격한 출력 스키마에 따라 응답해야 합니다. 마지막으로 결정론적 단계가 발견 사항을 병합 요청에 다시 게시합니다. 이는 '오토파일럿이 아닌 워크플로'라는 접근 방식을 보여줍니다. 코드는 예측 가능한 부분을 처리하고, 모델은 추론이 필요한 경우에만 호출됩니다.

YAML 파일을 먼저 사용한 것은 엔지니어들에게 친숙하고, AI 친화적인 코드베이스를 유지하며, 다른 코드와 마찬가지로 병합 요청 검토를 통해 관리되기 때문입니다. 향후에는 기업 사용 사례를 위한 UI 저작 도구를 Orbit UI에 도입하여 드래그 앤 드롭 방식으로 워크플로를 구축할 수 있도록 할 계획입니다.

초기 성공 사례로는 코드 검토, 린터 수정, 번역, 지원 티켓 분류, AI 준비도 점수표 및 수정, Sentry 조사관, Jira 구현자(소규모 소프트웨어 공장 역할) 등이 있습니다. 특히, 대규모 코드베이스 변경을 위해 Orbit을 활용하여 마이그레이션, 라이브러리 업데이트, 사용 중단, 코드 상태 진단(Claude Doctor), AI 준비도 점수표 등의 작업을 수백 개의 저장소에 걸쳐 동시에 실행하여 엔지니어링 효율성을 높였습니다.

아키텍처 측면에서 초기에는 ECS Fargate 컨테이너 내에서 오케스트레이션 및 런타임이 함께 있었지만, 현재는 오케스트레이션, 에이전트 런타임, 세션 상태를 별도의 계층으로 분리했습니다. 이는 더 나은 격리, 각 계층의 독립적인 확장, 추론 오류가 샌드박스를 종료시키지 않는다는 장점을 제공합니다. Fargate의 컨테이너 제한을 극복하기 위해 현재는 MicroVM 런타임을 사용하고 있으며, 향후에는 Docker-in-Docker와 같은 완전한 샌드박싱을 통해 모든 저장소에서 빌드 및 테스트를 실행할 수 있도록 할 계획입니다.

LLM 단계에서는 자체 하네스를 구축하는 대신 Claude Agent SDK를 재사용합니다. 이를 통해 도구 사용, 서브 에이전트, 스킬을 기본적으로 활용할 수 있습니다. Flywire는 네트워크 접근, 호출 가능한 도구, 로드 가능한 스킬, 사용할 수 있는 MCP 서버(특정 서버에서 허용된 도구만) 등 네 가지를 제한하여 통제력을 강화합니다. 이 모든 것은 YAML 파일에 선언됩니다.

스킬은 중앙 스킬 저장소에서 관리되며, Flywire 마켓플레이스를 통해 내부적으로 Claude Code 플러그인으로 게시됩니다. Orbit은 빌드 시점에 이 마켓플레이스에 연결하여 스킬을 가져옵니다. 이는 동일한 스킬이 엔지니어의 노트북에서 Claude Code로 실행되거나 Orbit 워크플로 내에서 자동화되어 실행될 수 있음을 의미합니다.

팀에 대한 권장 사항은 스킬로 시작하여 가치를 입증한 다음 워크플로로 전환하는 것입니다. 예측 가능한 부분은 코드가 되고, 모델은 가치를 더하는 경우에만 호출됩니다. 워크플로는 더 저렴하고, 더 안정적으로 실행되며, 백그라운드에서 실행되어 컨텍스트 전환을 줄여줍니다.

신뢰성 패턴을 위해 모든 LLM 단계는 모델 응답에 대한 엄격한 JSON 스키마를 강제합니다. 유효성 검사에 실패하면 Orbit은 재시도 또는 폴백 경로를 자동으로 트리거합니다. 또한, 워크플로 전체가 아닌 개별 LLM 단계를 격리하여 평가합니다. 이는 정확한 과거 상태를 주입하여 프롬프트 변경 사항을 측정하고 성능 회귀를 저렴하게 포착하는 데 도움이 됩니다.

현재 평가 과정은 '바이브 체크'로 시작하여 프로덕션에 배포하고, 모든 실행에 대한 실시간 추적(OpenTelemetry)을 통해 실제 사례를 추출하여 '골든 데이터셋'에 추가합니다. 이 데이터셋은 저장소에 버전 관리되며 필요에 따라 실행됩니다. 이를 통해 프롬프트를 개선하거나 모델을 변경합니다. 향후에는 Orbit UI 또는 Orbit MCP 서버를 통해 배포, 모니터링 및 평가, 개선의 전체 루프를 실행하는 것을 목표로 합니다.

지난 30일간의 수치를 보면, 코드 검토 에이전트는 9,000회 이상 실행되었고, 병합 요청당 평균 2분 45초가 소요되었습니다. 감사 수정자는 150개 이상의 병합 요청을 열어 취약한 종속성을 수정했고, AI 준비도 수정자는 약 80개의 저장소를 개선했습니다. Victoria 린터 수정자는 400개 이상의 프로젝트를 수정했으며, 병합 충돌 해결사는 900회 이상 실행되었습니다. 이 모든 워크플로를 통틀어 11,000회 이상의 실행과 99%의 성공률을 기록했습니다.

배운 점은 다음과 같습니다. 첫째, 셀프 서비스 모델이 효과적입니다. 공유된 가드레일은 SRE, 보안, IT, 지원 팀의 엔지니어들이 안전하게 구축할 수 있도록 합니다. 둘째, 단계별로 적절한 모델을 선택하는 것이 중요합니다. 모든 단계에 가장 강력한 모델이 필요한 것은 아니므로, 각 LLM 단계는 자체 모델을 선언하여 비용을 통제합니다. 셋째, 데이터 분리는 지속적인 과제입니다. 엔지니어링 SDLC 데이터, 기업 운영 데이터, 민감한 결제 생산 데이터 간의 엄격한 격리를 유지해야 합니다. 넷째, 자동화에 대한 높은 수요 속에서 높은 영향력을 가진 작업에 집중하고 우선순위를 정하는 것이 필수적입니다.

향후 Orbit의 로드맵은 플랫폼 기능을 확장하고 아키텍처 유연성을 높이는 데 중점을 둡니다. 완전한 샌드박싱을 통해 에이전트가 모든 프로젝트 유형에서 복잡한 빌드, 로컬 환경 및 테스트 스위트를 원활하게 처리할 수 있도록 할 것입니다. 또한, 복잡한 다단계 작업을 처리하기 위한 재개 가능한 세션을 도입하고, Orbit에 더 많은 평가 도구를 내장할 것입니다. 마지막으로, 오케스트레이션 계층을 모델 및 하네스에 구애받지 않도록 리팩토링하여 다양한 모델 공급업체에 걸쳐 유연한 라우팅을 가능하게 하고, 각 작업에 가장 비용 효율적인 모델을 선택하는 자동화된 모델 라우터를 포함할 것입니다.

## 실무 적용 포인트
*   **작게 시작하고 가치를 입증**: AI 자동화를 도입할 때는 작고 반복적이며 잘 정의된 작업부터 시작하여 실제 가치를 입증한 후 워크플로로 확장하는 것이 효율적입니다.
*   **LLM 사용 최적화**: 모든 작업에 가장 강력하고 비싼 LLM을 사용할 필요는 없습니다. 각 워크플로 단계의 요구 사항에 맞춰 적절한 모델을 선택하여 비용을 통제하고 효율성을 높이세요.
*   **엄격한 데이터 분리 및 통제**: 민감한 데이터를 다루는 환경에서는 엔지니어링 데이터, 기업 운영 데이터, 결제 데이터 등 데이터 유형별로 엄격한 격리를 유지하고, 모든 AI 기반 자동화가 기존의 보안 및 규제 준수 프레임워크 내에서 작동하도록 설계해야 합니다.
*   **인간 중심의 자동화**: AI 에이전트가 자율적으로 모든 것을 처리하게 하기보다는, 병합 요청 검토와 같이 중요한 결정 지점에는 항상 인간이 개입하여 통제력을 유지하고 안전성을 확보하는 'Human in the Loop' 접근 방식을 채택하세요.
