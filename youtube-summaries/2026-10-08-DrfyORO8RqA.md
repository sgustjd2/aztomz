# Why Bigger Context Windows Won't Save Your Agent — Elizabeth Fuentes Leone, AWS

🔗 https://youtu.be/DrfyORO8RqA · 📅 2026-10-08 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트의 컨텍스트 윈도우 오버플로우와 성능 저하 문제를 해결하기 위해, 데이터 외부화, 선택적 검색, 압축, 에이전트 간 컨텍스트 격리 등 네 가지 컨텍스트 엔지니어링 전략을 활용하여 에이전트의 효율성과 신뢰성을 향상시킬 수 있습니다.

## 발표자·소속
Elizabeth Fuentes Leone, Developer Advocate/SDE, GenAI (AWS)

## 핵심 주장
*   **무한 컨텍스트 윈도우는 신화**: 컨텍스트 윈도우 크기를 늘리는 것만으로는 AI 에이전트의 성능 저하 문제를 해결할 수 없습니다. 너무 많은 토큰은 "Lost in the Middle" 현상으로 이어져 에이전트가 중요한 정보를 놓치게 만듭니다.
*   **컨텍스트 엔지니어링의 중요성**: 에이전트가 필요한 정보를 필요할 때만 제공하고, 컨텍스트 윈도우를 최적의 결과와 토큰 소비를 위해 큐레이션하는 것이 중요합니다. 이는 프롬프트 주입과 같은 문제도 방지합니다.
*   **네 가지 핵심 전략**: 대량 데이터 처리, 다중 에이전트 간 정보 공유, 에이전트 루프 및 타임아웃 문제 해결을 위해 외부화(Externalize), 선택(Select), 압축(Compress), 격리(Isolate)의 네 가지 컨텍스트 엔지니어링 전략을 적용할 수 있습니다.
*   **Strands Agents 활용**: AWS의 오픈소스 프레임워크인 Strands Agents는 이러한 컨텍스트 엔지니어링 전략을 쉽게 구현할 수 있도록 돕습니다.

## 세부 내용

발표는 AI 에이전트 시스템이 도구가 많은 양의 데이터를 반환할 때 발생하는 문제, 즉 컨텍스트 윈도우 오버플로우로 인해 에이전트가 환각을 일으키거나 추론 능력이 저하되는 현상으로 시작됩니다. 과거에는 단순히 더 많은 토큰을 추가하여 컨텍스트 윈도우를 확장하는 것이 해결책이라고 생각했지만(4K → 32K → 128K → 1M → 2M 토큰), 이는 사실이 아니었습니다.

**"Lost in the Middle" 현상**
발표자는 "Attention U-curve"를 통해 컨텍스트 윈도우가 너무 커지면 에이전트가 컨텍스트의 중간에 있는 정보를 잊어버리고 처음과 끝 부분만 기억하는 경향이 있음을 설명했습니다. 이는 더 많은 토큰이 반드시 더 유용한 신호로 이어지지 않는다는 것을 의미합니다.

**컨텍스트 엔지니어링의 정의**
컨텍스트 엔지니어링은 모델에 필요한 정보를 필요할 때만 제공하고, 최적의 결과와 토큰 소비를 위해 컨텍스트 윈도우를 큐레이션하는 것을 목표로 합니다. 때로는 컨텍스트 윈도우가 에이전트를 "오염"시킬 수도 있으므로(예: 프롬프트 주입), 신중한 관리가 필요합니다.

**네 가지 컨텍스트 엔지니어링 전략**
발표자는 다음과 같은 네 가지 전략을 소개했습니다.

1.  **외부화(Externalize)**: 대량의 데이터를 영구 스토리지로 이동합니다.
2.  **선택(Select)**: 관련 있는 정보만 검색합니다.
3.  **압축(Compress)**: 토큰을 줄이기 위해 요약하거나 압축합니다.
4.  **격리(Isolate)**: 에이전트 간 컨텍스트를 분리합니다.

**1. 압축: 대화 관리 (Strands Agents)**
Strands Agents는 AWS의 오픈소스 프레임워크로, 모델에 구애받지 않고 에이전트를 구축할 수 있습니다. Strands Agents는 세 가지 대화 관리 전략을 기본으로 제공합니다.
*   **슬라이딩 윈도우(Sliding Window)**: 가장 최근 메시지만 유지합니다.
*   **요약(Summarization)**: 오래된 메시지를 요약하고 최근 메시지를 유지합니다.
*   **조합(Combination)**: 오래된 메시지의 요약과 최근 메시지를 결합합니다.

코드 예시로, `agent = Agent(system_prompt="You are a coding agent.", tools=(file_read, editor, shell))`와 같이 단 한 줄의 코드로 에이전트 루프를 생성할 수 있음을 보여주었습니다. 요약 기능을 사용하려면 `SummarizingConversationManager`를 `conversation_manager`로 지정하고 `summary_ratio` (예: 0.5로 50% 요약)와 `preserve_recent_messages` (예: 4개 메시지 유지)를 설정할 수 있습니다.

**계층형 메모리(Tiered Memory)**
에이전트가 모든 메모리를 잃지 않으면서 많은 양의 메모리를 관리해야 할 때, 계층형 메모리를 사용할 수 있습니다.
*   **단기 메모리(Short-term memory)**: 최근 대화 기록(슬라이딩 윈도우 + 요약).
*   **장기 메모리(Long-term memory)**: 대화 기록에서 추출된 사실(벡터 데이터베이스를 통해 검색).
*   **관계형 메모리(Relational memory)**: 엔티티 그래프, 순회 기반, 사물 간의 연결(그래프 데이터베이스).

**2. 외부화 & 선택: 메모리 포인터 패턴**
에이전트가 214KB와 같은 대량의 로그를 반환하는 경우, 이 모든 로그를 컨텍스트 윈도우에 직접 넣는 것은 비효율적입니다.
*   **해결책**: 로그를 `agent.state`에 외부화하고, 컨텍스트 윈도우에는 "Stored at logs-payment"와 같은 포인터(약 50 토큰)만 전달합니다. 필요한 경우에만 다른 도구가 이 포인터를 사용하여 전체 데이터를 검색합니다.
*   **코드 예시**: `fetch_application_logs` 함수는 로그를 생성하고 `tool_context.agent.state.set(pointer, logs)`를 통해 저장한 후 포인터를 반환합니다. `analyze_error_patterns` 함수는 `tool_context.agent.state.get(logs_pointer)`를 통해 필요할 때 로그를 가져옵니다.
*   **결과**: 이 방법을 통해 토큰 사용량을 약 97% 줄이면서 정보 손실은 없었습니다.

**3. 격리: Strands Swarm: 에이전트 간 메모리 포인터**
여러 에이전트가 동일한 대량의 데이터를 필요로 할 때, 모든 에이전트가 전체 데이터를 공유하는 것은 비효율적입니다.
*   **해결책**: `invocation_state`를 사용하여 에이전트 간에 메모리 포인터를 공유합니다. 각 에이전트는 필요한 데이터에 대한 포인터만 가지고 있으며, 실제 데이터는 공유 상태에 저장됩니다.
*   **예시**: Collector, Analyzer, Reporter 세 에이전트가 로그 데이터를 공유할 때, Collector는 로그를 가져와 `invocation_state`에 저장하고 포인터를 Analyzer에게 넘깁니다. Analyzer는 이 포인터로 로그를 읽고 분석 결과를 `invocation_state`에 저장하며, Reporter는 분석 결과 포인터로 최종 보고서를 생성합니다.

**4. 압축: 에이전트가 멈추지 않을 때**
에이전트가 무한 루프에 빠져 동일한 도구를 계속 호출하거나, 불필요한 호출로 토큰을 낭비하는 문제가 발생할 수 있습니다.
*   **해결책**:
    *   **명확한 상태(Clear States)**: 도구가 `SUCCESS` 또는 `FAILED`와 같은 명확한 신호를 반환하여 에이전트가 루프를 종료하도록 합니다.
    *   **하드 제한(Hard Limit)**: `LimitToolCounts`와 같은 기능을 사용하여 특정 도구의 최대 호출 횟수를 제한합니다.
*   **코드 예시**: `book_hotel` 도구는 성공 시 `SUCCESS` 메시지를 반환합니다. `LimitToolCounts`를 사용하여 `search flights` 및 `check hotel price` 도구의 호출 횟수를 각각 3회로 제한할 수 있습니다.

**5. 격리: 도구가 응답하지 않을 때 (MCP 타임아웃)**
에이전트가 외부 API와 같은 도구를 호출했을 때, 응답이 지연되거나 타임아웃이 발생하여 에이전트가 멈추는 문제가 발생할 수 있습니다.
*   **해결책**: 비동기 핸들(Async Handle) 패턴을 사용합니다.
    *   **동기 방식**: 에이전트가 외부 API 호출에 대해 17.2초 동안 블록되어 기다리다가 404 에러로 타임아웃될 수 있습니다.
    *   **비동기 핸들 방식**: `start_long_job`과 같은 비동기 함수가 즉시 작업 ID를 반환하고, 에이전트는 `check_job_status`를 통해 작업 상태를 폴링합니다. API 호출은 백그라운드에서 실행되므로 에이전트가 블록되지 않습니다.
*   **결과**: 응답 시간이 17.2초에서 1.7초로 단축되었고, 424 타임아웃이 발생하지 않았습니다.

**안티 패턴 (피해야 할 것)**
*   **컨텍스트 스터핑(Context Stuffing)**: 모든 것을 컨텍스트 윈도우에 포함시키려고 하는 것. 항상 가장 큰 윈도우를 사용하는 것.
*   **순진한 요약(Naive Summarization)**: 중요한 세부 정보가 누락될 수 있으며, 성능이 조용히 저하됩니다.
*   **컨텍스트 오염(Context Pollution)**: 에이전트 간에 모든 것을 전달하는 것. 한 에이전트가 모든 것을 처리하는 것.

**실패에 대한 전략 매칭**
*   도구가 대량 데이터(로그, 문서, 데이터셋)를 반환하는 경우: 외부화 + 선택 + 메모리 포인터.
*   여러 에이전트가 동일한 대량 데이터를 필요로 하는 경우: 공유된 `invocation_state` + 스코프된 컨텍스트.
*   에이전트 루프 또는 도구 정지 현상이 발생하는 경우: 명확한 상태 / `LimitToolCounts` / 비동기 핸들.

## 인상적인 대목
*   "The Infinite Context Window Is a Myth." (무한 컨텍스트 윈도우는 신화이다.)
*   "More tokens ≠ more useful signal!" (더 많은 토큰이 반드시 더 유용한 신호로 이어지는 것은 아니다!)
*   "Sometimes, the context window is poisoning the agent." (때로는 컨텍스트 윈도우가 에이전트를 오염시키기도 합니다.)

## 실무 적용 포인트
*   **컨텍스트 윈도우 최적화**: 단순히 더 큰 컨텍스트 윈도우를 사용하는 대신, 에이전트가 필요한 정보만 효율적으로 접근하고 처리할 수 있도록 컨텍스트 엔지니어링 전략(외부화, 선택, 압축, 격리)을 적용해야 합니다.
*   **Strands Agents 활용 고려**: AWS Strands Agents와 같은 오픈소스 프레임워크를 사용하여 대화 관리, 메모리 포인터, 에이전트 스웜, 도구 호출 제한 등 복잡한 컨텍스트 엔지니어링 패턴을 쉽게 구현할 수 있습니다.
*   **비동기 도구 호출 구현**: 외부 API 호출 시 에이전트가 블록되거나 타임아웃되는 것을 방지하기 위해 비동기 핸들 패턴을 사용하여 에이전트의 응답성을 높이고 안정적인 운영을 보장합니다.
*   **안티 패턴 회피**: 컨텍스트 스터핑, 순진한 요약, 컨텍스트 오염과 같은 안티 패턴을 인지하고 피함으로써 에이전트의 성능 저하와 비효율성을 방지해야 합니다.
