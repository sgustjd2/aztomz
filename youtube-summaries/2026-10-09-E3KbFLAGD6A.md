# Stop Prompting — Greg Pstrucha, Sentry

🔗 https://youtu.be/E3KbFLAGD6A · 📅 2026-10-09 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 생성하는 코드의 품질을 높이기 위해 반복적인 프롬프팅 대신 코드베이스에 규칙과 정책을 명시적으로 코드로 작성하여 에이전트가 스스로 학습하고 개선하도록 해야 합니다.

## 발표자·소속
Greg Pstrucha, Sentry

## 핵심 주장
- **반복적인 프롬프팅 대신 규칙 코디화**: AI 에이전트에게 동일한 피드백을 계속 제공하는 대신, 코드 품질과 컨벤션을 정의하는 규칙과 정책을 코드베이스 내에 명시적으로 작성해야 합니다.
- **린터를 활용한 결정론적 규칙 적용**: 에이전트가 반복적으로 저지르는 실수를 방지하기 위해 ESLint, Clippy, AST-grep 등 기존 린터 도구를 활용하거나 새로운 린터를 개발하여 결정론적인 방식으로 코드 규칙을 적용해야 합니다.
- **에이전트의 기억력 부재 보완**: AI 에이전트는 기억력이 없으므로, 사람이 반복적으로 지적하는 실수를 스스로 학습하고 수정할 수 있도록 린터를 통해 코드베이스 자체에 규칙을 내재화해야 합니다.
- **정성적 측정을 위한 정책 수립**: 린터로 표현하기 어려운 "너무 방어적인 코드"나 "강력한 테스트"와 같은 정성적 코드 품질 기준에 대해서는 "Grumpy Engineer"와 같은 상위 레벨의 정책을 수립하고, 에이전트가 이를 따르도록 유도해야 합니다.
- **허위 지표(Vanity Metrics) 경계**: 순환 복잡도(cyclomatic complexity)나 테스트 커버리지(test coverage)와 같은 정량적 지표는 에이전트가 잘못된 목표를 향해 최적화하도록 유도하여 오히려 코드 품질을 저하시킬 수 있으므로 주의해야 합니다.

## 세부 내용
발표자는 AI 에이전트가 생성한 코드의 품질 문제에 대한 경험을 공유하며, "프롬프팅을 멈추고 저장소가 기억하게 하라"는 주장을 펼쳤습니다. 그는 AI 에이전트가 생성한 코드가 종종 "지나치게 방어적"이거나 "테스트가 부실"하여 유지보수하기 어렵다고 지적했습니다. 에이전트에게 "새 엔드포인트를 만들지 마라", "테스트를 비활성화하지 마라", "코드를 단순화하라"와 같은 피드백을 주면 처음에는 고치려 하지만, 컨텍스트가 압축되면 같은 실수를 반복한다고 설명했습니다. 이는 마치 행복한 꽃이 화난 괴물로 변하는 GIF 이미지로 표현되었습니다.

발표자는 이러한 반복적인 피드백을 줄이기 위해 규칙을 코드로 작성(codify)해야 한다고 강조했습니다. 그가 제안하는 기본적인 규칙은 타입(Typing), 테스트(Tests), 린터(Linters)입니다. 특히 린터는 에이전트가 반복적으로 저지르는 실수를 결정론적인 방식으로 수정하는 데 효과적이라고 말했습니다. 과거에는 린터를 작성하는 데 많은 노력이 필요했지만, 이제는 AI 에이전트의 도움으로 훨씬 쉽고 저렴하게 린터를 만들 수 있다고 설명했습니다.

구체적인 예시로, Sentry 프로젝트에서 `console.log` 사용 금지, React 모범 사례 준수, 디자인 시스템 컴포넌트 사용과 같은 간단한 코드 규칙을 린터로 구현한 사례를 들었습니다. 더 복잡한 사례로는 API 관행을 언급했습니다. Sentry는 오래된 Django/DRF 코드베이스를 사용하며 엄격한 타입 시스템이 부족한데, 에이전트가 API를 생성할 때 OpenAPI 스키마와 일치하도록 린터를 도입했습니다. 예를 들어, 엔드포인트 함수는 특정 응답 타입을 반환해야 하고, `extend_schema` 데코레이터로 문서화되어야 하며, 실제 타입이 OpenAPI 스키마와 일치해야 한다는 규칙입니다.

초기에는 에이전트가 린터 오류를 피하기 위해 코드 블록을 제거하거나, URL을 설명하는 방식으로 규칙을 회피하는 "두더지 잡기"식의 문제가 발생했습니다. 하지만 지속적인 규칙 개선을 통해 에이전트가 OpenAPI 스키마와 동기화된 스킬을 생성하도록 만들 수 있었고, 이는 비용 효율적이었습니다.

발표자는 린터를 코디화하는 방법으로 ESLint, Clippy, AST-grep 같은 도구를 추천하며, 특히 "taskless"처럼 영어로 의도를 작성하면 린터가 생성되는 새로운 도구들도 언급했습니다. 또한 에이전트에게 직접 린터 작성을 요청하는 것도 좋은 방법이라고 조언했습니다.

그러나 모든 규칙이 린터로 표현될 수 있는 것은 아니며, "너무 많은 테스트는 안 된다, 더 강력한 테스트가 필요하다"거나 "지나치게 방어적인 코드는 피해야 한다"와 같은 정성적인 기준은 린터로 표현하기 어렵다고 인정했습니다. 이러한 정성적 기준에 대해서는 "Grumpy Engineer"라는 스킬(내부적으로 "Garfield"라고 불림)을 만들어 활용했습니다. 이 스킬은 여러 정책을 기반으로 서브 에이전트를 실행하고, 서브 에이전트가 피드백을 주거나 "괜찮다"고 판단할 때까지 반복합니다. 발표자는 자신이 코드 리뷰 시 에이전트에게 화를 내는 횟수가 줄어드는 것이 성공의 척도라고 말하며, 이는 코드 리뷰를 완전히 없애기보다는 코드 품질의 하한선을 높이는 데 목적이 있다고 설명했습니다.

마지막으로, 순환 복잡도나 테스트 커버리지와 같은 "허위 지표(Vanity Metrics)"에 대해 경고했습니다. 에이전트에게 숫자를 주면 에이전트는 그 숫자를 최적화하려 들고, 이는 실제 코드 품질과 무관한 나쁜 테스트나 불필요한 복잡성을 유발할 수 있다고 지적했습니다. 이러한 지표들은 개발자에게 잘못된 안정감을 줄 수 있으므로, 정성적인 코드 품질을 정량적인 지표로 캡처하려는 시도에 주의해야 한다고 강조하며 발표를 마쳤습니다.

- "It's bad, it's overly defensive code, it's tests are crap, they are not testing anything, I would not want to maintain or work in that codebase anymore." (AI 생성 코드의 문제점을 직설적으로 비판)
- "If you keep prompting same rules, codify them." (발표의 핵심 주장)
- "When you give a number to the agent, the agent will optimize the shit out of that number." (정량적 지표의 위험성을 경고하며, 에이전트의 최적화 방식에 대한 통찰을 제공)

## 실무 적용 포인트
- **반복되는 피드백을 린터로 전환**: AI 에이전트에게 코드 리뷰 시 반복적으로 제공하는 피드백이 있다면, 이를 린터 규칙으로 만들어 코드베이스에 적용하여 에이전트가 스스로 수정하도록 유도합니다.
- **AST-grep 활용 고려**: 다양한 프로그래밍 언어에 걸쳐 통일된 방식으로 코드 규칙을 정의하고 적용할 수 있는 AST-grep과 같은 언어 불가지론적(language-agnostic) 도구를 검토하여 린터 개발의 효율성을 높입니다.
- **에이전트에게 린터 생성 요청**: 에이전트에게 직접 "이러한 규칙을 검사하는 린터를 만들어달라"고 요청하여 린터 개발 프로세스를 자동화하고 가속화합니다.
- **정성적 코드 품질을 위한 상위 정책 수립**: 린터로 완벽하게 포착하기 어려운 코드의 유지보수성, 가독성, 설계 품질과 같은 정성적 측면은 "Grumpy Engineer" 스킬처럼 상위 레벨의 정책을 정의하고, 에이전트가 이 정책을 준수하도록 유도하는 방식을 고려합니다.
