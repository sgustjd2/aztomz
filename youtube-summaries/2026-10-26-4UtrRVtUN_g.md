# How to Build an AI Code Review Agent - Daksh Gupta, Greptile

🔗 https://youtu.be/4UtrRVtUN_g · 📅 2026-10-26 · 🎙 AI Engineer

## 한 줄 요약
Greptile의 공동 창업자가 AI 코드 리뷰 에이전트를 구축하는 데 필요한 5가지 핵심 요소와 그 구현 방법을 설명하며, 코드베이스 컨텍스트, 모델 인버전, 자율 테스트, 프롬프트 최적화, 비용 효율적인 모델 사용의 중요성을 강조합니다.

## 발표자·소속
Daksh, Greptile

## 핵심 주장
- **코드베이스 컨텍스트 이해:** AI 에이전트가 코드베이스의 전체 맥락을 이해하도록 돕는 것이 중요하며, 이를 위해 '리빙 위키(Living wiki)'와 같은 지식 기반을 구축하여 코드, 문서, 인시던트 데이터를 통합해야 합니다.
- **모델 인버전을 통한 버그 탐지율 향상:** 코드를 작성한 AI 모델과 다른 종류의 AI 모델을 사용하여 코드를 리뷰하면 버그 탐지율이 약 10% 증가하여, 모델의 편향을 상쇄하고 더 다양한 유형의 오류를 발견할 수 있습니다.
- **자율 테스트로 기능적 오류 발견:** 단순히 코드 변경 사항을 검토하는 것을 넘어, 개발 서버에 PR 브랜치를 배포하고 브라우저 에이전트를 통해 사용자 흐름을 테스트하여 실제 애플리케이션의 기능적 버그를 자동으로 찾아내야 합니다.
- **프롬프트 최적화 및 데이터셋 활용:** 특정 버그 유형을 찾고 불필요한 잔소리(nitpicks)를 피하도록 프롬프트를 명확하게 최적화하고, 과거의 PR 데이터셋과 알려진 버그를 활용하여 에이전트의 성능을 지속적으로 튜닝해야 합니다.
- **비용 효율적인 모델 사용 전략:** 모든 작업에 최신 프론티어 모델을 사용하는 대신, 컨텍스트 찾기와 같은 간단한 작업에는 저렴한 소형 모델을, 버그 분석과 같은 복잡한 작업에는 프론티어 모델을 사용하는 다중 모델 전략으로 비용을 절감해야 합니다.

## 세부 내용

발표자는 Greptile이 풀 리퀘스트(PR)를 검토하고 테스트하여 AI 생성 코드에서 버그, 논리적 오류, 코드 품질 문제를 찾아내는 AI 에이전트를 구축한다고 소개합니다. 현재 GitHub PR의 1% 이상이 Greptile을 거치며, NVIDIA, Coinbase, Scale 등 다양한 기업들이 사용하고 있습니다. 발표자는 특정 요구사항을 가진 기업들이 자체 AI 코드 리뷰 에이전트를 구축하거나 기존 도구를 선택할 때 도움이 될 정보를 공유하고자 합니다.

**기본 워크플로우와 문제점:**
간단한 AI 코드 리뷰 에이전트는 GitHub PR 웹훅을 샌드박스의 에이전트로 보내고, 에이전트가 리뷰 코멘트를 GitHub으로 다시 보내는 방식으로 하루 만에 구축할 수 있습니다. 하지만 이 방식에는 다음과 같은 문제점이 있습니다.
1.  **버그 누락:** 버그는 '프랙탈적으로 무한'하며, 에이전트는 버그의 존재는 알 수 있지만 부재는 알 수 없습니다.
2.  **컨텍스트 부족:** 에이전트가 코드베이스의 특정 부분이나 라이브러리 작동 방식을 이해하지 못해 오해할 수 있습니다. 특히 마이크로서비스 아키텍처에서는 수천 개의 리포지토리에 대한 컨텍스트가 필요합니다.
3.  **비용:** PR당 3달러에서 25달러까지 비용이 발생할 수 있으며, 토큰 사용량이 빠르게 증가합니다.
4.  **잔소리 같은 코멘트:** 기술적으로는 맞지만 지나치게 세세한 코멘트가 많아 개발자들이 중요한 문제와 사소한 문제를 구분하기 어렵게 만들고, 코드베이스를 '과도하게 방어적'으로 만들 수 있습니다.
5.  **재실행 시 새로운 버그 발견:** 동일한 PR을 여러 번 실행할 때마다 새로운 버그를 찾아내어 일관성이 부족합니다.

**개선 방안:**

1.  **프롬프트 최적화:**
    *   에이전트에게 특정 버그 유형을 찾도록 지시하고, 잔소리 같은 코멘트는 건너뛰도록 명시해야 합니다.
    *   과거의 PR과 알려진 버그를 포함하는 데이터셋을 구축하여 프롬프트를 튜닝하고 에이전트의 성능을 평가해야 합니다. 이는 버그가 매우 드물기 때문에 중요합니다.

2.  **모델 인버전:**
    *   코드를 생성한 모델과 다른 모델을 사용하여 코드를 리뷰해야 합니다. 예를 들어, Claude가 작성한 코드는 GPT/Codex 모델로 리뷰하고, GPT/Codex가 작성한 코드는 Claude 모델로 리뷰하는 식입니다.
    *   Greptile의 연구에 따르면 이 방식은 버그 탐지율을 약 10% 높입니다. 이는 모델마다 다른 유형의 버그를 생성하는 경향이 있기 때문입니다 (예: Claude는 원-오프 오류, GPT는 인증 우회 오류).

3.  **코드베이스 컨텍스트:**
    *   단순히 코드 변경 사항(diff)만 보는 것을 넘어, 에이전트가 전체 코드베이스를 이해하도록 해야 합니다.
    *   Greptile은 코드베이스, 리버트(reverts) 및 인시던트, 원격 측정(telemetry) 데이터를 주기적으로 크롤링하여 '리빙 위키(Living wiki)'를 구축합니다. 이 위키는 코드베이스의 세계 모델 역할을 하며, 에이전트가 애플리케이션의 작동 방식, 로드맵, 인증 흐름 등을 이해하는 데 도움을 줍니다.
    *   이를 통해 에이전트는 불필요한 파일을 읽지 않아 검색이 더 정확해지고, 컨텍스트를 더 잘 이해하여 오탐(false positives)과 버그 누락을 줄일 수 있습니다.

4.  **자율 테스트:**
    *   "올바른 코드도 잘못된 일을 할 수 있다"는 전제하에, 에이전트가 코드를 실행하고 테스트해야 합니다.
    *   **개발 박스(Dev box) 구축:** PR 브랜치와 모든 종속성이 포함된 실행 중인 애플리케이션 환경을 제공합니다.
    *   **흐름 맵(Flow map) 구축:** 인증 코드와 로그인 흐름, 결제 코드와 구매 흐름 등 코드와 해당 비즈니스 흐름 간의 매핑을 정의합니다.
    *   브라우저 에이전트를 사용하여 개발 서버에서 앱을 실행하고, 모바일 뷰포트에서 사용자 흐름을 클릭하여 테스트하고 버그 보고서를 생성합니다. 컴퓨터 비전 모델을 활용하여 UI 변경 사항이나 숨겨진 버튼 등을 감지할 수 있습니다.

5.  **일부 작업에 저렴한 모델 사용:**
    *   모든 작업에 비싼 프론티어 모델을 사용할 필요는 없습니다.
    *   PR diff를 입력받아 리뷰를 계획하고, 컨텍스트를 찾는 작업에는 소형 모델을, 사용자 흐름 테스트에는 브라우저 에이전트를, 버그 분석에는 프론티어 모델을 사용하는 등 각 서브태스크에 적합한 모델을 사용합니다.
    *   후보 파일들을 저렴한 모델로 필터링하여 관련 컨텍스트만 프론티어 모델에 전달함으로써 불필요한 파일 읽기를 줄이고 비용을 절감합니다.

발표자는 이러한 방법들을 통해 AI 코드 리뷰 에이전트의 성능을 크게 향상시키고 비용을 절감할 수 있다고 결론지으며, Greptile.com을 통해 더 많은 정보를 얻거나 도움을 받을 수 있다고 언급합니다.

## 실무 적용 포인트
- **프롬프트 엔지니어링 강화:** 단순히 "이 PR을 리뷰해줘"가 아니라, 과거 인시던트 데이터를 분석하여 회사에 자주 발생하는 특정 버그 유형을 명시하고, 스타일 가이드와 같은 '잔소리'성 코멘트는 피하도록 프롬프트를 구체적으로 작성합니다.
- **모델 다양성 확보:** AI 코파일럿으로 코드를 생성하는 경우, 코드 리뷰에는 다른 종류의 LLM을 사용하여 모델의 고유한 편향으로 인한 버그를 상호 보완적으로 탐지하는 전략을 고려합니다.
- **코드베이스 지식 그래프 구축:** 코드, 문서, 과거 인시던트, 프로덕션 원격 측정 데이터 등을 통합하여 에이전트가 활용할 수 있는 '리빙 위키' 또는 지식 그래프를 구축하여 컨텍스트 이해도를 높입니다.
- **단계별 모델 활용:** PR 변경 사항을 분석하는 초기 단계에는 저렴하고 빠른 모델을 사용하고, 심층적인 버그 분석이나 복잡한 추론이 필요한 단계에는 더 강력한 프론티어 모델을 활용하는 다단계 모델 아키텍처를 설계하여 비용 효율성을 극대화합니다.
