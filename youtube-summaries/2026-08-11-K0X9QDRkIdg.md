# Evolution of agentic surfaces — Gagan Bhat & Isabella Kai He, Anthropic

🔗 https://youtu.be/K0X9QDRkIdg · 📅 2026-08-11 · 🎙 AI Engineer

## 한 줄 요약
앤트로픽은 모델의 빠른 발전 속도에 맞춰 에이전트 개발의 복잡성을 줄이고 생산성을 높이기 위해, 모델의 기능과 인프라 관리를 통합한 '클로드 관리형 에이전트(Claude Managed Agents)'를 개발하여 개발자들이 제품 개발에 집중할 수 있도록 돕고 있다.

## 발표자·소속
- Gagan Bhat, Applied AI, Anthropic
- Isabella He, Applied AI, Anthropic

## 핵심 주장
- **AI 발전 가속화와 태스크 복잡성 증가:** AI 모델의 역량이 빠르게 발전함에 따라, 모델에 부여되는 태스크의 복잡성도 질문 답변에서 전체 결과물 소유로 진화하고 있으며, 이에 맞춰 에이전트 개발 표면(agentic surface)도 함께 발전해야 한다.
- **에이전트 개발의 인프라 복잡성 해소:** 초기 Messages API를 사용한 에이전트 개발은 세션 관리, 관측 가능성, 자격 증명, 호스팅 인프라, 샌드박싱 등 수많은 생산 인프라 과제를 개발자가 직접 처리해야 하는 부담이 있었다.
- **클로드 관리형 에이전트의 통합 솔루션:** 클로드 관리형 에이전트는 에이전트 루프, 메모리, 세션 관리, 캐싱, 압축 등 핵심 에이전트 하네스 기능과 샌드박스 같은 실행 환경을 앤트로픽이 관리하여 개발자가 제품과 도메인 전문성에 집중할 수 있도록 한다.
- **모델 진화에 대응하는 하네스 설계:** 모델의 빠른 진화로 인해 하네스에 모델 특정 가정을 인코딩하면 금방 구식이 되어 에이전트 성능을 저하시킬 수 있으므로, 클로드 관리형 에이전트는 독립적인 구성 요소를 통해 유연하게 진화할 수 있도록 설계되었다.

## 세부 내용
발표는 AI 발전의 가속화와 이에 따른 에이전트 개발 표면의 진화 과정을 설명하는 것으로 시작한다. 2017년 트랜스포머 아키텍처 정의부터 현재까지 AI 모델의 역량이 기하급수적으로 증가했으며, 이에 따라 모델에 부여되는 태스크의 복잡성도 단순한 질문 답변에서 복잡한 태스크 완료, 나아가 전체 결과물 소유로 발전했다. 이러한 변화에 발맞춰 에이전트 개발 표면도 진화해야 한다고 강조한다.

**에이전트 개발 표면의 진화:**
1.  **Messages API:** 초기 클로드 3 출시 당시에는 Messages API가 첫 번째 에이전트 개발 표면이었다. 이는 단순히 토큰을 입력하고 텍스트 완성을 출력하는 방식이었다. 하지만 태스크 복잡성이 증가하면서 모델이 정보를 가져오고 컨텍스트를 관리해야 하는 필요성이 생겼고, 개발자들은 직접 '에이전트 루프'를 구축하기 시작했다. 이 루프는 클로드를 호출하고, 도구를 실행하며, 컨텍스트를 관리하는 역할을 했다. 또한, 세션 관리, 관측 가능성, 자격 증명, 호스팅 인프라, 샌드박싱 등 다양한 생산 인프라 과제를 개발자가 직접 해결해야 하는 어려움이 있었다.
2.  **Claude Agent SDK:** 두 번째 진화 단계는 클로드 에이전트 SDK였다. 이 SDK는 에이전트 루프를 포함한 '클로드 코드 하네스'를 패키징하여 제공했으며, 파일 시스템 접근, 도구, 샌드박싱 시스템을 내장했다. 이를 통해 개발자는 세션 관리 및 관측 가능성과 같은 일부 기본 기능을 얻었지만, 자격 증명, 호스팅 인프라 등 여전히 많은 생산 인프라 과제를 직접 구축하고 확장해야 했다.
3.  **Claude Managed Agents:** 최신 진화 단계인 클로드 관리형 에이전트는 개발자가 제품, 태스크, 컨텍스트, 도메인 지식에만 집중할 수 있도록 앤트로픽이 에이전트 루프, 캐싱, 압축, 도구 등 '두뇌' 부분과 필요할 때 동적으로 스핀업되는 샌드박스 '손' 부분을 포함한 모든 생산 인프라를 관리한다.

**관리형 에이전트의 엔지니어링 원칙:**
- **하네스 프리미티브의 모델 가정 인코딩:** 하네스 프리미티브(예: 컨텍스트 리셋, 압축 전략, 도구 재시도 정책, 프롬프트 캐싱, 서브에이전트 팬아웃)는 클로드가 스스로 할 수 없는 것에 대한 가정을 인코딩한다. 하지만 모델이 빠르게 발전하면서 이러한 가정은 구식이 될 수 있으며, 이는 에이전트 성능 저하로 이어진다. 예를 들어, Sonnet 4.5 모델은 '컨텍스트 불안(context anxiety)' 현상을 보여 컨텍스트 창이 끝나기 전에 작업을 서둘러 마무리하려는 경향이 있었고, 이를 해결하기 위해 하네스에 컨텍스트 리셋 기능을 추가했다. 그러나 Opus 4.5 모델에서는 이 현상이 사라져 해당 하네스 수정 사항이 불필요한 오버헤드가 되었다.
- **진화하도록 구축된 하네스:** 클로드 관리형 에이전트는 도구, 세션, 하네스, 샌드박스, 오케스트레이션 등 독립적인 구성 요소로 설계되어, 개별 구성 요소를 쉽게 교체하고 반복할 수 있으면서도 전체 아키텍처는 안정적으로 유지된다.
- **두뇌와 손의 분리:** 에이전트의 '두뇌'(에이전트 루프)와 '손'(도구 실행 환경인 샌드박스)을 분리함으로써 신뢰성을 향상시키고, 필요할 때만 샌드박스를 동적으로 스핀업하여 효율성을 높였다. 샌드박스가 죽어도 두뇌는 살아남아 새로운 샌드박스를 스핀업하고 작업을 재시도할 수 있다.
- **장기적인 작업을 위한 프리미티브:** 관리형 에이전트는 에이전트, 환경, 세션의 세 가지 핵심 프리미티브를 중심으로 설계되었다. 에이전트는 모델, 프롬프트, 도구, MCP 서버, 가드레일, 스킬 등 에이전트의 기능을 정의하고, 환경은 샌드박스(클라우드 또는 자체 호스팅) 및 연결된 리소스 등 에이전트가 실행되는 곳을 정의한다. 세션은 실행 중인 에이전트 인스턴스로, 사용자 이벤트, 모델 계획, 도구 실행, 결과 등 모든 상호작용이 내구성 있게 기록된다. 이는 관측 가능성과 재개 가능한 장기 실행 에이전트를 가능하게 한다.
- **세션 상태 머신을 통한 신뢰성:** 관리형 에이전트는 유휴(idle), 실행 중(running), 재스케줄링(rescheduling), 종료됨(terminated)의 네 가지 세션 상태를 통해 신뢰성을 모델링한다. 상태는 세션 로그에 저장되므로, 하네스나 샌드박스가 중간에 교체되더라도 마지막 이벤트부터 작업을 재개할 수 있다.
- **세션은 클로드의 컨텍스트 창이 아니다:** 세션 로그는 컨텍스트 창 외부에 영구적으로 저장되며, 하네스는 필요에 따라 세션 로그에서 컨텍스트를 읽어와 클로드의 컨텍스트 창에 주입하는 '컨텍스트 엔지니어링'을 수행한다. 이는 모델이 컨텍스트를 잃어버리더라도 세션 로그에서 복구할 수 있게 한다.
- **컨텍스트 관리 및 도메인 전문성:** 관리형 하네스 내부에 에이전트 루프, 메모리, 세션 관리, 관측 가능성, 캐싱, 압축 등 핵심 기능이 내장되어 있으며, 개발자는 컨텍스트 관리 및 도메인 전문성(시스템 프롬프트, 도구, 스킬 등)을 사용자 정의하는 데 집중할 수 있다.

**데모 - 프로덕션 등급 에이전트 구축:**
발표자는 P99 지연 시간이 10배 이상 급증하는 가상의 체크아웃 서비스 인시던트를 해결하는 SRE 조사 에이전트를 구축하는 데모를 시연했다.
1.  **에이전트 정의:** `SRE Investigator`라는 이름으로 `claude-opus-4-8k` 모델을 사용하고, 시스템 프롬프트와 함께 `bash`, `grep` 등의 에이전트 툴셋과 `atlas`라는 MCP 서버에 연결하는 툴셋을 정의했다.
2.  **환경 정의:** `sre-sandbox`라는 이름의 클라우드 환경을 생성하고, 네트워킹을 제한하며 `mcp.atlas.dev` 호스트만 허용하도록 설정했다.
3.  **증거 업로드:** 문제가 발생한 애플리케이션 로그 파일(`app.log`)을 샌드박스에 마운트할 리소스로 업로드했다.
4.  **세션 생성 및 실행:** 정의된 에이전트, 환경, 업로드된 리소스를 결합하여 세션을 시작했다. 에이전트는 즉시 클라우드에서 스핀업되어 로그를 분석하고, MCP 도구를 사용하여 메트릭과 최근 배포를 확인했다. 에이전트는 로그에서 타임아웃 오류와 인벤토리 서비스 문제를 발견하고, 배포 변경 사항을 분석하여 캐시 제거가 P99 지연 시간 급증의 원인임을 파악했다. 최종적으로 롤백을 권장하는 해결책을 제시했다.

데모 후, 관리형 에이전트 콘솔에서 여러 세션과 각 세션의 상세 이벤트 로그(도구 사용, 결과, 에이전트 메시지 등)를 확인할 수 있음을 보여주며 관측 가능성을 강조했다.

**현장에서 얻은 교훈:**
1.  **자격 증명은 에이전트로부터 멀리 유지:** 에이전트 루프와 도구 실행을 분리하고, 자격 증명을 암호화된 볼트(Vaults)에 저장하여 필요할 때만 도구 실행 시점에 복호화하여 사용함으로써 모델이 민감한 정보에 직접 접근하는 것을 방지한다.
2.  **컨테이너 시작 시 추론을 차단하지 말 것:** 과거에는 하네스가 컨테이너 내부에 결합되어 있어 컨테이너 시작이 완료될 때까지 모델 추론이 지연되었다. 두뇌와 손을 분리함으로써 모델 추론을 즉시 시작하고 컨테이너 설정은 병렬로 실행하거나 필요 없을 경우 건너뛸 수 있어, P50에서 60%, P95에서 90% 이상의 시간-첫 토큰(Time-to-First-Token) 지연 시간 개선을 달성했다.
3.  **세션 로그는 관측 가능성과 자가 개선을 모두 제공:** 세션 로그는 에이전트 실행의 모든 이벤트를 상세히 기록하여 개발자에게 granular한 추적(granular trace)을 제공한다. 이 로그는 관측 가능성뿐만 아니라 '드리밍(Dreaming)'이라는 주기적인 배치 프로세스를 통해 에이전트의 메모리 상태를 업데이트하고 새로운 통찰력과 조직화된 구조를 추출하여 다음 세션에서 에이전트가 자동으로 더 지능적으로 작동하도록 돕는다.
4.  **도구 실행을 위한 보안:** 자체 호스팅 샌드박스 기능을 통해 개발자는 자신의 실행 환경을 완벽하게 제어하고, MCP 터널을 통해 에이전트 루프가 사설 네트워크 내의 MCP 서버와 안전하게 통신할 수 있도록 아웃바운드 전용 터널을 제공한다.

**프론티어에서의 구축:**
발표는 클로드 관리형 에이전트가 볼트, 드리밍, 아웃컴, 멀티 에이전트 오케스트레이션, 스케줄링된 배포, 자체 호스팅 샌드박스, 메모리, MCP 터널, 웹훅 등 다양한 프론티어 기능을 통해 모델 역량과 제품 간의 격차를 줄이는 데 기여하고 있음을 강조하며 마무리된다. 관리형 에이전트는 정적 하네스를 사용하는 제품보다 모델이 할 수 있는 것과 제품이 제공하는 것 사이의 격차를 크게 줄여준다.

## 인상적인 대목
- "모델이 움직이고 하네스가 움직이지 않으면 에이전트가 저하됩니다." (When the model moves and the harness doesn't, it degrades the agent.) - 모델의 빠른 발전 속도에 맞춰 에이전트 하네스도 지속적으로 진화해야 한다는 점을 명확히 보여준다.
- "드리밍은 세션 간 메모리를 정제합니다." (Dreaming refines memory between sessions) - 에이전트가 과거 경험을 통해 스스로 학습하고 개선하는 메커니즘에 대한 흥미로운 개념이다.

## 실무 적용 포인트
- **인프라 관리 부담 경감:** 클로드 관리형 에이전트를 활용하여 세션 관리, 관측 가능성, 호스팅 등 복잡한 생산 인프라 구축 및 유지보수 부담을 덜고, 핵심 제품 기능 개발에 집중할 수 있다.
- **보안 강화된 도구 실행:** 자격 증명을 에이전트 코드로부터 분리하고, 자체 호스팅 샌드박스 및 MCP 터널을 활용하여 에이전트의 도구 실행 환경을 안전하게 제어하고 민감한 시스템 접근을 보호할 수 있다.
- **에이전트 성능 최적화:** 에이전트의 '두뇌'와 '손'을 분리하는 아키텍처를 통해 컨테이너 시작 지연 없이 모델 추론을 즉시 시작하고, 컨테이너 설정을 병렬로 실행하여 시간-첫 토큰(Time-to-First-Token) 지연 시간을 크게 단축할 수 있다.
- **자가 개선 에이전트 구축:** 세션 로그를 활용하여 에이전트의 모든 실행 이벤트를 기록하고, '드리밍'과 같은 메커니즘을 통해 에이전트가 과거 경험으로부터 학습하여 시간이 지남에 따라 자동으로 성능을 개선하도록 설계할 수 있다.
