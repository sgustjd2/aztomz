# Every Company Is Building Agents That Can't Work Together - Justin Schroeder, Standard Agents

🔗 https://youtu.be/3Krz7Rdd4JI · 📅 2026-11-10 · 🎙 AI Engineer

## 한 줄 요약
모든 기업이 AI 에이전트를 구축하고 있지만, 서로 호환되지 않아 발생하는 문제점을 지적하고, 이를 해결하기 위한 오픈소스 표준 에이전트 사양(Standard Agent Specification)을 제안합니다.

## 발표자·소속
Justin Schroeder, AI Engineer, Code Summit

## 핵심 주장
- **모든 기업이 에이전트를 구축하고 있지만, 기존 방식은 비효율적입니다.** 현재 많은 기업이 비즈니스 프로세스를 AI로 자동화하기 위해 에이전트를 만들고 있지만, 이는 기존의 "MCP 서버 + 마크다운 파일 + 스마트 범용 에이전트"라는 일반적인 AI 통합 방식과 상반됩니다. 기업들은 여전히 맞춤형 에이전트를 구축하고 있으며, 이는 현재의 지배적인 AI 통합 방식이 비즈니스의 실제 요구사항을 충족하지 못하고 있음을 시사합니다.
- **비즈니스는 제어, 신뢰, 반복 가능성, 비범용성을 요구합니다.** 기업은 에이전트가 비즈니스 프로세스에 깊이 통합되어 정확히 지시받은 대로만 작동하며, 예측 가능하고 반복 가능한 결과를 제공하고, 비즈니스 고유의 특성을 반영하기를 원합니다. 범용 에이전트는 이러한 요구사항을 충족하기 어렵고, 잘못된 작업을 수행할 위험이 있어 비즈니스에 큰 부담이 됩니다.
- **에이전트 개발의 복잡성과 상호 운용성 부족이 문제입니다.** 현재 에이전트 개발은 다양한 언어와 도구로 파편화되어 있으며, 각 에이전트는 고유한 하네스(harness)를 구축해야 하므로 배포, 구성, 확장이 어렵습니다. 이러한 맞춤형 하네스는 다른 시스템과의 호환성이 낮아 에이전트 생태계의 성장을 저해합니다.
- **표준 에이전트 사양(Standard Agent Specification)이 해결책입니다.** 이 사양은 에이전트가 벤더에 구애받지 않고, 도메인에 특화되며, 특정 모델과 연결되고, 구성 가능하며, 이식 가능하도록 설계되었습니다. 이를 통해 에이전트 개발을 표준화하고, 상호 운용성을 높여 에이전트 생태계의 발전을 촉진할 수 있습니다.

## 세부 내용

발표자는 먼저 "모든 기업이 에이전트를 구축하고 있다"는 흥미로운 관찰로 시작합니다. 하지만 이는 현재 AI 업계의 지배적인 지혜, 즉 MCP(Microservices Control Plane) 서버와 마크다운 파일(스킬 파일 또는 에이전트 MD 파일)을 스마트 범용 에이전트(예: Grok Bot, Muse, ChatGPT)에 연결하여 비즈니스를 AI로 강화하는 방식과 대조됩니다. 발표자는 이러한 방식이 충분하고 효과적이라고 여겨지지만, 실제로는 많은 기업이 여전히 맞춤형 에이전트를 구축하고 있다고 지적합니다.

발표자는 사람들이 맞춤형 에이전트를 구축하는 세 가지 주요 요인을 제시합니다.
1.  **통합(Integration):** 비즈니스 프로세스와 시스템에 깊이 통합되어야 합니다. HVAC 수리점, 대학, 클라우드 제공업체 등 모든 조직은 보증 청구 관리, 직원 스케줄링, 허가 관리, 재무 관리, 고객 지원 등 수많은 핵심 프로세스를 가지고 있습니다. 이러한 프로세스는 비즈니스의 가치를 결정하며, AI 에이전트가 이러한 프로세스에 제대로 통합되어야 합니다.
2.  **신뢰(Trust):** 에이전트가 지시받은 대로만 수행하고 다른 작업을 수행하지 않도록 신뢰할 수 있어야 합니다. "에이전트가 무엇이든 할 수 있다면, 무엇이든 할 수도 있다"는 말처럼, 너무 광범위한 기능을 가진 범용 에이전트는 예측 불가능한 행동을 할 위험이 있습니다. 기업은 에이전트가 특정 워크플로우에 따라 제한된 범위 내에서 정확하게 작동하기를 원합니다.
3.  **효능(Efficacy):** 에이전트가 주어진 작업을 효율적으로 수행하고 비즈니스 성과를 향상시켜야 합니다. 단순히 스마트한 모델이 아니라, 특정 작업을 효율적으로 수행하고 비즈니스 프로세스의 전반적인 성능을 개선하는 데 기여해야 합니다. 예를 들어, 보증 청구 에이전트는 특정 작업을 위해 미세 조정되어야 하며, 높은 평가 통과율, 낮은 비용, 짧은 지연 시간을 보여야 합니다.

발표자는 현재 에이전트 개발의 문제점을 지적합니다. 모든 기업이 에이전트를 구축하고 있지만, 이들은 파편화되어 "엉망진창"입니다. 다양한 언어, 도구, 에이전트 루프, 컨텍스트 관리, 병렬 실행 등 수많은 복잡한 요소들이 존재합니다. 에이전트를 구축한다는 것은 사실상 하네스(harness)를 구축하는 것과 같습니다. 이러한 맞춤형 하네스는 배포, 구성, 상호 운용성 측면에서 어려움을 겪습니다.

이러한 문제에 대한 해결책으로 **표준(standards)**을 제시합니다. 이미 도구 접근(MCP), 패키지화된 노하우(스킬), 프로젝트 지침(AGENTS.md), 에이전트 간 통신(A2A), 에디터-에이전트 통신(ACP), 결제(AP2-x402) 등 다양한 표준이 존재하지만, 에이전트 자체의 런타임에 대한 표준은 아직 없습니다.

발표자는 표준이 제공하는 이점을 설명합니다.
1.  **속도(Speed):** 코딩 에이전트가 이미 구축 방법을 알고 있으므로 개발 속도가 빨라집니다.
2.  **일관성(Consistency):** 모든 에이전트가 동일한 방식으로 구축됩니다.
3.  **이식성(Portability):** 에이전트가 어떤 런타임에서도 동일하게 실행됩니다.
4.  **구성 가능성(Composability):** 작은 에이전트들이 더 큰 에이전트로 조립될 수 있습니다.

이러한 표준의 부재를 해결하기 위해 **"표준 에이전트 사양(The Standard Agent Specification)"**을 오픈소스로 공개한다고 발표합니다. 이 사양은 에이전트 구축에 대한 오픈소스, 엔지니어링 우선 접근 방식을 제시합니다.

표준 에이전트의 핵심 원칙은 다음과 같습니다.
1.  **벤더에 구애받지 않아야 합니다.** 특정 클라우드 제공업체나 모델에 종속되지 않고 어디서든 호스팅하고 실행할 수 있어야 합니다.
2.  **도메인에 특화되어야 합니다.** 특정 비즈니스 프로세스에 최적화되어야 합니다.
3.  **모델과 연결되어야 합니다.** 에이전트는 특정 모델에 최적화되어야 합니다.
4.  **구성 가능해야 합니다.** 작은 에이전트들이 계층적으로 결합될 수 있어야 합니다.
5.  **이식 가능해야 합니다.** 어떤 런타임에서도 실행될 수 있도록 패키징되어야 합니다.

사양의 세부 구성 요소는 다음과 같습니다.
-   **모든 것은 코드입니다:** 모델, 프롬프트, 도구, 핸들러, 에이전트, 서브에이전트, 훅, 효과, 타입 레지스트리 등 모든 정의는 TypeScript 코드로 작성됩니다. 이는 에이전트를 에이전트로 작성하고, 빌드 및 컴파일 단계 없이 즉시 실행 가능하게 합니다.
-   **모델 정의:** 정확한 모델을 지정하고, 대체 모델을 설정하며, 비용을 보고하고, 제공업체 옵션을 타입으로 정의합니다.
-   **프롬프트 정의:** 프롬프트는 대화의 한 측면을 소유하며, 공유된 부분에서 프롬프트를 구성하고, 타입이 지정된 입력을 가질 수 있으며, 도구(함수, 다른 프롬프트, 에이전트)를 자유롭게 혼합하여 사용할 수 있습니다.
-   **도구 정의:** 함수 도구(런타임 내에서 실행되는 일반 코드), 프롬프트 도구(하나의 작업에 대한 다른 모델 및 지침), 선언된 변수(비밀은 타입으로 지정), 범위 지정(변수는 부모에게 절대 누출되지 않음)의 세 가지 유형이 있습니다.
-   **에이전트 정의:** 에이전트는 두 가지 측면(Side A, Side B)을 가지며, 인간-프롬프트, 프롬프트-프롬프트, 핸들러-인간, 프롬프트-인간(자식 에이전트) 등 다양한 방식으로 상호작용할 수 있습니다. 핸들러는 모델 호출 없이 결정론적으로 작동합니다.
-   **서브에이전트:** 자체 스레드, 메시지, 파일, 큐 및 라이프사이클을 가진 완전한 에이전트입니다. 내구성이 있어 메시지를 기억하고, 별칭을 통해 하나의 정의를 여러 번 다른 자격 증명으로 사용할 수 있습니다.
-   **훅(Hooks):** 컨텍스트, 메시지, 도구 실행을 요청하는 12개의 훅 지점이 있습니다. 압축, 컨텍스트 주입, 수정, 원격 측정 등에 사용됩니다.
-   **효과(Effects):** 나중에 발생하는 작업을 예약하는 방법입니다. 내구성이 있어 재시작 후에도 예약된 작업이 유지되고, 타입이 지정된 인수를 가지며, 에이전트와 함께 패키징되어 이동합니다.
-   **스레드:** 모든 스레드는 메시지, 파일 시스템, 코드 실행(샌드박스), 서브에이전트, 환경 변수, 도구, 효과, 이벤트, 키-값 저장소, 결정 등 완전한 환경을 제공합니다.
-   **코드 실행:** 샌드박스 환경에서 실행되며, 명시적인 브리지를 통해서만 외부 자원에 접근할 수 있고, 호출자가 예산을 설정하여 종료할 수 있습니다.
-   **결정(Decisions):** 선택, 점수, 부울 질문 등 타입이 지정된 질문을 통해 모델이 결정을 내릴 수 있도록 합니다.
-   **엔드포인트:** 에이전트가 서비스로서 자체 HTTP API를 노출할 수 있도록 합니다. 각 스레드는 자체 엔드포인트를 가질 수 있으며, 파일 기반 라우팅을 지원합니다.
-   **패키징:** 에이전트는 npm 패키지처럼 모든 필요한 것을 포함하는 하나의 모듈로 패키징됩니다. 지연 로딩되며, 사설 런타임 RPC, 스토리지 스키마 또는 사이드카 서비스를 요구하지 않아야 합니다.

발표자는 **Standard Agent Builder**라는 첫 번째 공개 런타임을 소개합니다. 이를 통해 사용자는 사양에 따라 에이전트를 복제하고, 코딩 에이전트에게 에이전트 구축을 요청하며, 어디서든 실행할 수 있습니다.

데모에서는 Claude Code를 사용하여 배터리 보증 청구를 처리하는 에이전트를 구축하는 과정을 보여줍니다. Claude Code는 PDF 문서와 기존 API 서버 소스 코드를 읽고, 사양에 따라 에이전트, 모델, 프롬프트, 도구 파일을 자동으로 생성합니다. 이 과정은 5분 21초 만에 완료됩니다. 생성된 에이전트는 AgentBuilder UI에서 확인하고 직접 상호작용할 수 있으며, 각 단계의 로그, 모델 호출 비용, 토큰 사용량 등 상세한 정보를 제공합니다. 최종적으로 이 에이전트는 웹사이트의 온라인 지원 챗봇으로 통합되어 사용자와 상호작용하며 배터리 보증 청구를 처리합니다.

발표자는 마지막으로 커뮤니티에 참여하여 런타임을 구축하고, 에이전트를 구축하며, 사양을 개선하는 데 기여해 줄 것을 요청합니다.

## 실무 적용 포인트
- **도메인 특화 에이전트 개발:** 범용 에이전트 대신 특정 비즈니스 프로세스에 최적화된 소규모 에이전트를 구축하여 효율성과 신뢰성을 높이는 전략을 고려해야 합니다.
- **에이전트 개발 표준화:** Standard Agent Specification과 같은 표준을 활용하여 에이전트 개발의 일관성을 확보하고, 재사용 가능한 구성 요소를 만들어 개발 속도를 높일 수 있습니다.
- **에이전트의 투명성과 제어:** 에이전트의 작동 방식(모델 호출, 도구 사용, 비용 등)에 대한 상세한 로그와 제어 기능을 제공하여 비즈니스 신뢰도를 높이고 위험을 관리해야 합니다.
- **TypeScript 기반 에이전트 개발:** TypeScript를 사용하여 에이전트를 코드로 정의함으로써, 에이전트의 이식성, 구성 가능성, 그리고 에이전트가 에이전트를 작성하고 즉시 실행할 수 있는 능력을 확보할 수 있습니다.
