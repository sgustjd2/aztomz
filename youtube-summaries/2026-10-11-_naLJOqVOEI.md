# Same Model, Different Speed: Why Your Inference Provider Matters — FriendliAI

🔗 https://youtu.be/_naLJOqVOEI · 📅 2026-10-11 · 🎙 AI Engineer

## 한 줄 요약
FriendliAI는 오픈웨이트 모델이 실제 AI 애플리케이션에 실용적이게 되면서, 빠른 속도와 높은 신뢰성을 갖춘 풀스택 추론 엔진을 제공하여 생산 환경에서의 모델 채택을 가속화한다.

## 발표자·소속
Yunmo Koo, Founding Engineer @FriendliAI

## 핵심 주장
-   **오픈웨이트 모델의 경쟁력**: GLM-5.2와 같은 오픈웨이트 모델은 코딩, 추론, 에이전트 워크로드 벤치마크에서 GPT나 Claude와 같은 선도적인 독점 모델과 동등하거나 더 나은 성능을 보여주며, 더 이상 성능 면에서 타협점이 아니다.
-   **비용 효율성**: 동일한 작업에 대해 GLM-5.2는 Claude Opus 4.8보다 5.6배 저렴하고 요청당 7.2배 저렴하여, 특히 여러 번 반복해야 하는 에이전트 워크로드에서 비용 절감 효과가 크다.
-   **추론 제공자의 중요성**: 모델 가중치가 같더라도 추론 제공자에 따라 지연 시간, 처리량, 신뢰성이 크게 달라지므로, 모델 선택뿐 아니라 어떤 제공자를 통해 추론을 실행할지가 중요하다.
-   **풀스택 최적화의 필요성**: 빠른 추론은 KV 캐시 재사용, 요청 라우팅, 스케줄링 및 배치, 추측 디코딩, 양자화, GPU 커널 최적화 등 여러 계층에 걸친 조정이 필요한 풀스택 문제이다.
-   **신뢰성의 중요성**: 에이전트 워크로드와 같이 여러 단계로 구성된 작업에서는 단 한 번의 실패도 전체 사용자 경험을 저해할 수 있으므로, 평균 속도뿐 아니라 타임아웃, 오류율, 가동 시간 등 전반적인 API 경험의 신뢰성이 중요하다.

## 세부 내용

발표는 오픈웨이트 모델의 발전과 함께 시작되었다. 발표자는 GLM-5.2와 같은 오픈웨이트 모델이 코딩, 추론, 에이전트 워크로드 벤치마크에서 GPT나 Claude와 같은 독점 모델과 경쟁할 수 있는 수준에 도달했음을 강조했다. 특히, Code Arena WebDev 리더보드에서 GLM-5.2가 Claude Opus 4.8보다 높은 순위를 기록한 점을 예시로 들었다.

이어서 발표자는 타워 디펜스 게임을 만드는 간단한 핸즈온 실험을 통해 GLM-5.2(FriendliAI)와 Anthropic/Opus-4.8 모델의 실제 성능을 비교했다. 두 모델 모두 유사한 구조와 품질로 작동하는 게임을 생성했지만, 비용 면에서는 큰 차이를 보였다. GLM-5.2는 Claude Opus 4.8보다 동일 작업에 대해 5.6배, 요청당 7.2배 저렴했다. 이는 특히 여러 번의 모델 호출이 필요한 에이전트 워크로드에서 비용 효율성이 매우 중요함을 시사한다.

발표자는 같은 모델을 사용하더라도 추론 제공자에 따라 성능이 크게 달라질 수 있음을 지적했다. OpenRouter의 GLM-5.2 제공자 스냅샷을 통해 FriendliAI가 99.99%의 가동 시간과 40 TPS(초당 토큰 수)를 기록하며 다른 제공자들보다 우수한 성능을 보였다. 또 다른 데모에서는 GLM-5.2와 Kilo Code를 사용하여 캔디 크러시 스타일의 모바일 게임("Model Crush Saga")을 생성하는 과정을 시연했는데, FriendliAI는 1분 47초 만에 게임을 생성한 반면, 다른 제공자는 3분 25초가 걸렸다. 이는 추론 제공자의 품질이 개발자 경험에 직접적인 영향을 미친다는 것을 보여준다.

발표자는 빠른 추론이 단순히 하나의 최적화 문제가 아니라 KV 캐시 재사용, 요청 라우팅, 스케줄링 및 배치, 추측 디코딩, 양자화, GPU 커널 최적화 등 여러 요소를 아우르는 풀스택 문제라고 설명했다. FriendliAI는 이러한 모든 계층을 처음부터 설계하고 최적화하여 Gen AI 모델을 대규모로 서비스하기 위한 풀스택 추론 엔진을 구축했다.

최적화 전략으로는 크게 두 가지를 소개했다. 첫째, **긴 컨텍스트 최적화**이다. 에이전트 애플리케이션은 긴 입력(10K+ 토큰)과 짧은 출력(1K 미만 토큰)을 사용하며, 입력의 50~90%가 요청 간에 반복되거나 공유된다. 이를 위해 FriendliAI는 이미 계산된 내용을 재계산하지 않고, 요청을 캐시로 라우팅하며, GPU 메모리의 한계를 고려한 캐시 계층(GPU VRAM, CPU RAM, NVMe)을 활용하여 KV 캐시를 효율적으로 관리한다. 둘째, **대화형 속도 최적화**이다. 표준 자기회귀 디코딩은 한 번에 하나의 토큰을 생성하여 GPU 활용도가 낮다. 이를 개선하기 위해 추측 디코딩(Speculative Decoding)을 사용하는데, 이는 여러 토큰을 미리 제안하고 타겟 모델이 이를 병렬로 검증하는 방식이다. FriendliAI는 모델 기반(작은 드래프트 모델 사용)과 모델 프리(패턴 매칭 사용) 추측 방식을 동적으로 선택하는 적응형 하이브리드 라우팅과, 실제 트래픽을 기반으로 예측을 지속적으로 개선하는 자기 진화 추측(Self-evolving speculation) 방식을 사용한다.

마지막으로 발표자는 **신뢰성**이 속도의 일부임을 강조했다. 타임아웃, 오류, 실패한 스트림은 사용자 경험을 저해하며, 특히 에이전트 워크로드에서는 하나의 실패한 호출이 전체 다단계 워크플로우를 무효화할 수 있다. FriendliAI는 단순히 TPS(초당 토큰 수)가 아닌, 오류율과 가동 시간을 포함한 전체 API 경험을 최적화한다. 발표자는 청중에게 일반적인 벤치마크는 불완전하므로, 실제 프롬프트, 컨텍스트, 트래픽 패턴을 가져와 FriendliAI와 함께 속도, 신뢰성, 비용, 품질 측면에서 전체 API 경험을 비교해 볼 것을 권유하며 발표를 마쳤다.

## 인상적인 대목
-   "오픈웨이트 모델은 더 이상 타협점이 아니다." (Open-Weight Is No Longer a Compromise)
-   "생산 환경에서의 채택은 빠르고 신뢰할 수 있는 추론에 달려 있다." (But production adoption depends on fast and reliable inference.)
-   "빠른 추론은 하나의 최적화가 아니다. 이는 KV 캐시 재사용, 요청 라우팅, 스케줄링 및 배치, 추측 디코딩, 양자화, GPU 커널 최적화 등 전반에 걸친 조정을 필요로 한다." (Fast inference is not one optimization. It requires coordination across: KV cache reuse, Request routing, Scheduling and batching, Speculative decoding, Quantization, GPU kernel optimization.)
-   "신뢰성은 속도의 일부이다." (Reliability Is Part of Speed)
-   "최고의 벤치마크는 당신의 애플리케이션이다." (The Best Benchmark Is Your Own Application)

## 실무 적용 포인트
-   **오픈웨이트 모델 적극 활용**: 코딩, 추론, 에이전트 작업 등에서 독점 모델과 유사하거나 더 나은 성능을 제공하면서도 훨씬 저렴한 오픈웨이트 모델을 적극적으로 검토하고 도입한다.
-   **추론 제공자 신중한 선택**: 모델 자체의 성능 외에도 추론 제공자가 제공하는 지연 시간, 처리량, 신뢰성, 비용을 종합적으로 고려하여 실제 워크로드에 가장 적합한 제공자를 선택한다.
-   **풀스택 최적화 접근**: 추론 성능 최적화 시, 모델 아키텍처뿐만 아니라 캐싱, 스케줄링, 디코딩 전략, GPU 커널 최적화 등 전체 추론 스택을 통합적으로 고려하고 개선한다.
-   **실제 워크로드 기반 벤치마킹**: 일반적인 벤치마크 점수보다는 실제 애플리케이션의 프롬프트, 컨텍스트 길이, 트래픽 패턴을 사용하여 속도, 신뢰성, 비용, 품질 측면에서 전체 API 경험을 직접 테스트하고 비교한다.
