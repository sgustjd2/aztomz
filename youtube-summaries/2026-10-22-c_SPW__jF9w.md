# How to Test AI Agents When No Benchmark Exists — Nathanael Weill, Air Canada

🔗 https://youtu.be/c_SPW__jF9w · 📅 2026-10-22 · 🎙 AI Engineer

## 한 줄 요약
벤치마크가 없는 상황에서 AI 에이전트를 효과적으로 평가하기 위해, 정답을 먼저 정의하고 이를 기반으로 테스트를 자동화하는 새로운 접근 방식을 제시합니다.

## 발표자·소속
Nathanael Weill, Air Canada

## 핵심 주장
- **정답 우선 접근 방식**: 벤치마크가 없는 AI 에이전트 평가 환경에서, 에이전트가 찾아야 할 정답을 먼저 정의하고 이를 기반으로 테스트를 구축하여 평가 프로세스를 자동화할 수 있습니다.
- **테스트 속도 향상**: 이 방법을 통해 에이전트 변경 사항에 대한 피드백 주기를 4주에서 5분으로 단축하여 개발 속도를 크게 높일 수 있습니다.
- **전문가 의존도 감소**: 도메인 전문가의 시간 제약과 주관적인 평가 문제를 해결하기 위해, 코드를 통한 자동화된 검증을 도입하여 전문가의 직접적인 개입 없이도 에이전트의 품질을 확인할 수 있습니다.
- **다양한 테스트 기법 활용**: 과거 의사결정 활용, 정답 기반 계약서 생성, 계약서 고의 파손, 변경 불가능한 요소 확인, 템플릿을 통한 대량 생성 등 다양한 테스트 기법을 통해 에이전트의 견고성을 확보합니다.

## 세부 내용
발표자는 에어 캐나다에서 AI 솔루션을 개발하며 겪는 문제점을 공유했습니다. 에어 캐나다는 운영, 기업, 상업, 로열티 등 다양한 부서에서 챗봇, AI 워크플로우, ML 및 최적화 파이프라인에 AI 에이전트를 활용하고 있지만, 각 비즈니스 영역의 특수성 때문에 공개된 벤치마크가 없다는 것이 가장 큰 어려움입니다. 또한, AI 엔지니어는 도메인 전문가가 아니며, 바쁜 도메인 전문가들은 에이전트의 답변을 평가할 시간이 부족합니다.

발표자는 2024년 통신 회사에서 Q&A 어시스턴트를 개발할 때도 비슷한 문제를 겪었다고 언급했습니다. 당시 여러 팀이 경쟁했지만, 발표자의 팀만이 성공적으로 에이전트를 작동시켰습니다. 성공의 핵심은 "테스트 세트"를 가졌다는 점이었습니다. 발표자는 "변화가 도움이 되었는지 알 수 없다면, 에이전트를 더 좋게 만들 수 없다"는 원칙을 강조했습니다.

이전 RAG(Retrieval-Augmented Generation) 방식에서는 질문-검색-답변의 과정을 거쳤고, 더 나은 파싱, 재랭킹, 쿼리 재작성, 추론 단계 등 다양한 복잡한 기술을 추가했지만, 답변 품질은 개선되지 않았습니다. 오히려 복잡성을 추가할수록 다른 부분이 망가지는 문제가 발생했습니다. 더 큰 문제는 전문가의 피드백을 받기 위해 일주일에 한 번 회의를 해야 했고, 한 번의 변경 사항을 테스트하는 데 1주일이 걸렸다는 점입니다.

이러한 문제를 해결하기 위해 발표자는 새로운 방법을 도입했습니다: **"정답을 먼저 작성하는 것(So we wrote the answer first)"**.
기존에는 질문 → 에이전트 답변 → 전문가 검토(1주 소요) 방식이었지만, 새로운 방식은 다음과 같습니다.
1.  **페이지 선택**: 에이전트가 찾아야 할 "정답 페이지"를 먼저 선택합니다.
2.  **LLM이 질문 작성**: LLM(Large Language Model)에게 해당 페이지에 대한 질문을 작성하도록 합니다. 이는 쉬운 작업입니다.
3.  **에이전트 검색**: 에이전트가 이 질문에 대해 검색합니다.
4.  **정답 페이지 확인**: 에이전트가 찾아낸 페이지가 미리 정해둔 "정답 페이지"와 일치하는지 코드로 확인합니다.

이 방법의 장점은 테스트 실행 전에 어떤 페이지가 정답을 포함하고 있는지 알기 때문에, 코드로 몇 초 만에 확인이 가능하며 전문가의 개입이 필요 없다는 것입니다. 이를 통해 일주일에 한 번의 테스트에서 하루에 수십 번의 테스트를 실행할 수 있게 되었고, 답변 품질이 꾸준히 향상되는 것을 확인했습니다.

2026년 에어 캐나다에서 새로운 프로젝트인 "공급업체 계약서 분석"에 직면했을 때도 비슷한 문제가 발생했습니다. 계약서가 많고, 전문가들은 바쁘며, 벤치마크가 없었습니다. 에이전트는 계약서의 각 조항을 규칙에 따라 확인하고, 변경 사항을 제안하거나 그대로 둘지 결정해야 합니다. 이 에이전트는 '문제점 발견(Spot)', '규칙/과거 계약서 찾기(Find)', '변경 사항 작성(Write)', '결정(Decide)'의 네 단계를 거칩니다. RAG 테스트는 '찾기(Find)' 단계만 검증할 수 있었고, 나머지 단계는 테스트하기 어려웠습니다.

발표자는 이 문제를 해결하기 위해 다섯 가지 새로운 테스트 기법을 제시했습니다.
1.  **과거 의사결정을 정답으로 사용**: 과거의 계약서(수정 전/후)를 제공하고, 코드로 변경 사항을 비교한 후 에이전트가 동일한 변경 사항을 제안하는지 확인합니다. 하지만 에어 캐나다에서는 과거 계약서 쌍을 찾기 어려워 이 방법은 적용하지 못했습니다.
2.  **정답을 선택하고 계약서를 작성**: 특정 규칙(예: 자본금 100만 달러 이상)과 그에 대한 정답(예: 자본금 50만 달러는 플래그)을 먼저 정하고, 이 규칙을 위반하는 계약서를 생성하여 에이전트가 올바르게 플래그를 지정하는지 확인합니다. 이 방법으로 43개의 규칙에서 275개의 테스트 케이스를 생성할 수 있었습니다.
3.  **좋은 계약서를 가져와 파손**: 잘 작성된 실제 계약서에서 특정 조항을 고의로 삭제하고, 에이전트가 이 누락된 부분을 감지하는지 확인합니다. 이는 에이전트가 "무언가 빠졌다"고 인식하는지 테스트하는 강력한 벤치마크입니다.
4.  **정답이 없는 경우, 답변이 어떻게 움직이는지 확인**: 계약서의 당사자 이름을 바꾸거나 조항 순서를 변경하는 등 에이전트의 결과에 영향을 주지 않아야 하는 작은 변경을 가합니다. 코드를 통해 에이전트의 두 답변이 동일한 플래그를 생성하는지 비교합니다.
5.  **하나의 예시를 여러 개로 변환**: 템플릿을 사용하여 계약서의 특정 부분(예: 통지 기간, 지불 조건)을 빈칸으로 만들고, 이 빈칸을 다양한 값으로 채워 여러 가지 계약서 버전을 생성합니다. 코드로 각 계약서가 규칙을 위반하는지 확인합니다.

이러한 방법을 통해 에이전트의 평가 주기를 4주에서 5분으로 단축할 수 있었습니다. 가장 저렴한 검사(정확한 일치, 코드)를 먼저 수행하고, 필요한 경우에만 AI 심사 또는 인간 전문가를 활용합니다. 발표자는 "정답을 먼저 작성하면 검증은 코드가 되고, 모든 변경 사항을 테스트할 수 있다"고 강조했습니다. 또한, "생성된 테스트는 시작점일 뿐, 배포 결정이 아니다. 사람이 여전히 모든 변경 사항을 확인하며, 실제 피드백이 그 역할을 대신한다"고 덧붙였습니다.

## 인상적인 대목
- "If you can't tell whether a change helped, you can't make the agent better." (변화가 도움이 되었는지 알 수 없다면, 에이전트를 더 좋게 만들 수 없다.)
- "Because we wrote the answer first, the check is just code, and you can test every change." (우리가 정답을 먼저 작성했기 때문에, 검증은 단지 코드가 되고, 모든 변경 사항을 테스트할 수 있습니다.)
- "Generated tests are a starting point, not a ship decision. A person still checks every change. Real feedback takes over." (생성된 테스트는 시작점일 뿐, 배포 결정이 아닙니다. 사람은 여전히 모든 변경 사항을 확인하며, 실제 피드백이 그 역할을 대신합니다.)

## 실무 적용 포인트
- **정답 기반 테스트 자동화**: 도메인 전문가의 시간 제약이 있거나 공개된 벤치마크가 없는 경우, 에이전트가 찾아야 할 정답(예: 특정 문서의 특정 페이지, 특정 규칙 위반 여부)을 먼저 정의하고, 이를 코드로 검증하는 테스트를 구축하여 평가 프로세스를 자동화합니다.
- **테스트 주기의 극적인 단축**: 수동 검토에 의존하는 대신 자동화된 테스트를 통해 에이전트 변경 후 피드백을 몇 분 내로 받을 수 있도록 시스템을 설계하여 개발-테스트-개선 주기를 가속화합니다.
- **다양한 테스트 케이스 생성 전략**: 과거 데이터 활용, 규칙 기반 계약서 생성, 고의적인 오류 주입, 불변성 테스트, 템플릿 기반 대량 생성 등 여러 방법을 조합하여 에이전트의 다양한 측면을 검증할 수 있는 테스트 세트를 구축합니다.
- **LLM을 테스트 생성 도구로 활용**: LLM을 직접적인 평가자(judge)로 사용하기보다, 특정 정답에 대한 질문이나 테스트 시나리오를 생성하는 데 활용하여 테스트 세트 구축의 효율성을 높입니다.
