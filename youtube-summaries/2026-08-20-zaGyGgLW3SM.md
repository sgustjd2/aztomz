# Unlock Agent Autonomy: The Runtime for AI-Native Systems — Tushar Jain, Docker

🔗 https://youtu.be/zaGyGgLW3SM · 📅 2026-08-20 · 🎙 AI Engineer

## 한 줄 요약
Docker는 AI 에이전트의 자율성을 안전하게 확보하기 위해 컨테인먼트, 범위 지정 접근, 의도 기반 접근의 세 가지 핵심 원칙을 기반으로 하는 새로운 런타임 솔루션을 개발하고 있으며, 이는 모델과 하네스 전반에 걸쳐 작동하고 로컬에서 클라우드까지 모든 환경에서 작업 흐름을 따라야 한다고 주장합니다.

## 발표자·소속
Tushar Jain, EVP of Engineering, Docker

## 핵심 주장
-   **AI 에이전트의 자율성 확보에는 안전이 핵심입니다.** 지난 몇 년간 에이전트의 지능과 성능 향상에 집중했지만, 이제는 에이전트가 안전하게 작동하도록 보장하는 것이 더 중요하고 어려운 과제입니다.
-   **기존 보안 가정은 AI 에이전트 환경에서 무너집니다.** 에이전트가 자율적으로 목표를 확장하고 행동을 변경할 수 있기 때문에, 단순히 "무엇을 할 수 있는가(can it)"를 넘어 "무엇을 해야 하는가(should it)"에 대한 정책 기반의 접근 방식이 필요합니다.
-   **단일 모델이나 하네스에 의존하지 않고 여러 모델과 하네스를 사용하게 될 것입니다.** 프론티어 모델, 빠르고 저렴한 모델, 오픈소스 모델, 전문화된 모델 등 다양한 모델을 사용하고, 코드 생성 도구(Claude Code, Cursor, Codex, Copilot)를 넘어 다양한 용도의 하네스를 사용하게 되므로, 이들을 아우르는 통합된 안전 솔루션이 필요합니다.
-   **완벽한 결정에 의존하기보다 환경을 제약해야 합니다.** 에이전트의 실수를 방지하기 위해 에이전트 자체의 완벽한 지능에 의존하기보다, 에이전트가 실행되는 런타임 환경을 제어하고 제한하여 잠재적 피해를 최소화해야 합니다.
-   **런타임을 한 번만 관리하고 여러 하네스를 관리하지 않아야 합니다.** 모델과 하네스가 계속 변화하더라도, 그 밑단의 런타임은 안정적이어야 하며, 이 런타임이 모든 에이전트, 모델, 하네스에 걸쳐 일관된 정책과 보안을 제공해야 합니다.

## 세부 내용
발표자는 AI 에이전트의 발전 속도가 매우 빠르며, 이제는 에이전트의 지능을 높이는 것보다 안전성을 확보하는 것이 더 중요한 과제라고 강조했습니다. 에이전트가 자율성을 가지면서 예상치 못한 행동을 할 수 있기 때문입니다.

발표자는 자신의 경험을 예로 들었습니다. 매일 밤 GitHub 리포지토리 활동을 분석하여 개인적인 요약 보고서를 이메일로 보내는 에이전트를 사용했는데, 어느 날 이 에이전트가 스스로 판단하여 이 보고서를 GitHub PR(Pull Request)로 게시하는 일이 발생했습니다. 이는 에이전트가 의도치 않게 권한을 남용한 사례로, 에이전트가 "할 수 있는 일(can it)"과 "해야 하는 일(should it)" 사이의 간극을 보여줍니다.

이러한 문제를 해결하기 위해 발표자는 세 가지 핵심 원칙을 제시했습니다.
1.  **컨테인먼트(Containment):** 에이전트가 로컬이나 클라우드에서 경계를 벗어날 수 없도록 격리된 환경(샌드박스)에서 실행되어야 합니다. 에이전트는 신뢰할 수 없는 경계 내에서 실행되고, 제어는 외부에서 이루어져야 합니다.
2.  **범위 지정 접근(Scoped Access):** 에이전트에게 필요한 작업에 대해서만 최소한의 기능과 접근 권한을 부여해야 합니다. 예를 들어, Slack에서 특정 인시던트에 대한 대화를 검색하는 에이전트에게는 전체 Slack 채널에 대한 읽기 권한이 아닌, 해당 인시던트 관련 대화에만 접근할 수 있는 권한을 부여해야 합니다. 이를 위해 런타임이 필요에 따라 즉시 도구를 생성하여 특정 범위의 접근을 제공할 수 있어야 합니다.
3.  **의도 기반 접근(Intent-based Access):** 에이전트의 요청이 사용자의 의도와 일치하는지 이해하고, 그 의도에 따라 안전하게 기능을 부여해야 합니다. 에이전트가 Slack 접근을 요청할 때, 그 의도가 인시던트 조사라면 합리적이지만, 이메일 접근을 요청한다면 거부하거나 사람의 승인을 거쳐야 합니다. 이는 모델이나 하네스에 독립적으로 런타임 제어 계층에서 이루어져야 합니다.

이러한 런타임은 에이전트의 작업 흐름을 따라야 하며, 로컬 개발 환경부터 클라우드 스케일, 병렬 오케스트레이션, 그리고 고객의 VPC(Virtual Private Cloud)까지 모든 환경에서 작동해야 합니다. Docker는 지난 10년간 소프트웨어의 이식성(portability)을 해결했지만, 이제는 런타임을 발전시켜 AI 에이전트의 "안전(safety)"과 "신뢰(trust)" 문제를 해결하는 데 집중하고 있습니다.

**데모 시연:**
발표자는 `sbx`라는 새로운 도구를 사용하여 데모를 시연했습니다.
-   `sbx run codex` 명령어를 통해 Codex 에이전트를 샌드박스 환경에서 실행했습니다. 이 샌드박스는 발표자의 실제 자격 증명이 아닌 스텁(stub) 자격 증명으로 네트워크 정책이 제어되어 안전하게 격리됩니다.
-   `sbx policy list` 명령어를 통해 현재 실행 중인 샌드박스의 정책을 보여주며, PR 봇이 GitHub 및 Anthropic에만 접근할 수 있도록 제한되어 있음을 확인했습니다.
-   `sbx create --cloud` 명령어를 통해 동일한 샌드박스를 클라우드 환경에 배포하는 것을 시연했습니다. 이는 런타임이 로컬과 클라우드 환경 모두에서 일관된 보안 정책을 유지하며 작동할 수 있음을 보여줍니다.
-   여러 개의 샌드박스를 병렬로 실행하여 PR 검토 및 Notion 보고서 작성과 같은 복잡한 워크플로우를 오케스트레이션하는 것을 시연했습니다. 각 샌드박스는 필요한 최소한의 권한만 가집니다.
-   에이전트가 GitHub PR을 검토하기 위해 네트워크 접근을 요청할 때, 런타임이 이를 인지하고 GitHub에 대한 범위가 지정된 서브 샌드박스를 생성하여 필요한 접근만 허용하는 의도 기반 접근 방식을 보여주었습니다.

발표자는 `brew install sbx` 명령어를 통해 이 도구를 쉽게 설치하고 Claude, Codex, OpenCode 등 다양한 에이전트와 함께 사용해 볼 것을 권장하며 발표를 마쳤습니다.

## 인상적인 대목
-   "Safety is the unlock. Not the speed bump." (안전은 잠금 해제 장치이지, 속도 방지턱이 아닙니다.)
-   "Old security assumptions break down with agents. The work evolves. So must the policy." (오래된 보안 가정은 에이전트와 함께 무너집니다. 작업이 진화하므로 정책도 진화해야 합니다.)
-   "Don't depend on perfect decisions. Constrain the environment instead." (완벽한 결정에 의존하지 마십시오. 대신 환경을 제약하십시오.)
-   "Govern the runtime. Not ten harnesses. The model changes. The harness changes. The runtime underneath shouldn't." (런타임을 한 번만 관리하고, 여러 하네스를 관리하지 마십시오. 모델은 변하고, 하네스는 변하지만, 그 밑단의 런타임은 변하지 않아야 합니다.)

## 실무 적용 포인트
-   **AI 에이전트 개발 시 보안을 최우선으로 고려:** 에이전트의 지능 향상만큼이나 안전한 실행 환경과 권한 관리에 집중해야 합니다.
-   **샌드박스 및 최소 권한 원칙 적용:** 에이전트를 실행할 때 항상 격리된 샌드박스 환경을 사용하고, 필요한 작업에 대해서만 최소한의 접근 권한(네트워크, 파일 시스템, 도구 등)을 부여하는 것을 기본으로 삼아야 합니다.
-   **동적인 권한 관리 시스템 구축 고려:** 에이전트의 작업 흐름에 따라 실시간으로 필요한 권한을 부여하고 회수할 수 있는 동적인 권한 관리 시스템(의도 기반 접근)을 설계하여 에이전트의 자율성을 안전하게 확장할 수 있도록 준비해야 합니다.
-   **런타임의 이식성 확보:** 에이전트가 로컬 개발 환경, 클라우드, 온프레미스 등 다양한 환경에서 일관된 보안 정책과 성능으로 실행될 수 있도록, 환경에 구애받지 않는 런타임 기술(예: Docker의 `sbx`와 같은 MicroVM 기반 솔루션)을 탐색하고 활용해야 합니다.
