# Computer-use models will agentify the web, not APIs — Dhruv Batra, Yutori

🔗 https://youtu.be/Ki980nV0__0 · 📅 2026-08-14 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 웹에서 행동을 주도할 것이라는 주장은 맞지만, 이는 API를 통해서가 아니라 인간의 눈처럼 웹을 보고 상호작용하는 컴퓨터 사용 모델을 통해 이루어질 것이며, 특히 웹의 롱테일 부분에서 이러한 변화가 두드러질 것입니다.

## 발표자·소속
Dhruv Batra, Yutori

## 핵심 주장
*   **AI 에이전트가 웹 행동의 주요 동력이 될 것:** 발표자는 AI 에이전트가 인간보다 더 많은 웹 활동을 수행할 것이라는 온라인의 일반적인 주장에 동의합니다. 이는 에이전트가 클릭, 읽기, 구매 등 다양한 작업을 자동화할 것이기 때문입니다.
*   **웹은 API가 아닌 컴퓨터 사용 에이전트에 의해 '에이전트화'될 것:** 발표자는 웹이 에이전트 친화적인 API를 통해 에이전트화될 것이라는 주장에 반대합니다. 대신, 그는 웹이 인간의 시각과 유사하게 작동하는 컴퓨터 사용 에이전트에 의해 에이전트화될 것이라고 주장합니다.
*   **웹의 롱테일은 API를 제공하지 않을 것:** 특히 웹의 롱테일(덜 인기 있는 수많은 웹사이트)은 에이전트가 호출할 수 있는 표준화된 API를 제공하지 않을 것이며, 이는 인프라 변화가 느리기 때문입니다.
*   **기계는 웹을 탐색하기 위해 '시각'이 필요하다:** 웹은 본질적으로 인간의 눈을 위해 설계되었기 때문에, 에이전트가 웹사이트와 효과적으로 상호작용하려면 픽셀 기반의 시각적 이해와 인간과 유사한 행동 능력이 필수적입니다.

## 세부 내용

발표자는 온라인에서 흔히 제기되는 세 가지 주장을 소개하며 발표를 시작합니다.
1.  AI 에이전트가 웹에서 인간이 아닌 행동의 동력이 될 것이다.
2.  어떻게? 웹이 "에이전트화"될 것이다.
3.  어떻게? 에이전트가 특정 프로토콜(예: MCP/WebMCP, ACP/UCP)을 통해 호출할 API를 제공할 것이다.

발표자는 첫 두 주장에는 동의하지만, 세 번째 주장은 "망상적"이라고 일축합니다. 그의 핵심 주장은 "컴퓨터 사용 에이전트가 웹을 에이전트화할 것이며, API가 아닐 것이다. 특히 웹의 롱테일을 에이전트화할 것이다"입니다.

그는 비즈니스 클래스 항공편을 찾는 예시를 들어, `flights.google.com`과 같은 웹사이트에서 에이전트가 버튼을 클릭하는 대신, `curl -X POST https://flights.google.com -H 'X-API-Key: YOUR_API_KEY' -d '{ "origin": "MIA", "destination": "PMI", "departureDate": "2026-08-15", "passengers": [{ "type": "ADT" }], "cabin": "Business" }'`와 같은 API 호출을 하는 것이 더 합리적이라고 설명합니다.

그러나 그는 레스토랑 메뉴에서 글루텐 프리 항목을 찾는 더 복잡한 예시를 제시하며 현실을 보여줍니다.
*   **쉬운 모드:** 텍스트 기반의 메뉴가 있는 웹사이트. (예: `https://xn--rainbownrnberg-7yb.com/`) 이는 스크래핑하기 쉽습니다.
*   **중간 모드:** 메뉴 버튼을 클릭하면 PDF 파일로 연결되는 웹사이트. (예: `https://www.eiscafe-baek.de/`) 이는 PDF 리더와 OCR(광학 문자 인식)이 필요합니다.
*   **어려운 모드:** 메뉴가 갤러리에 임베드된 픽셀화된 JPEG 이미지로 제공되는 웹사이트. (예: `https://www.vegandveg.es/`) 여기에는 텍스트가 없어 OCR조차 어렵습니다.

이어서 그는 미국 내 15,000~20,000개의 학군 웹사이트를 예시로 들어, 노트북 조달 정보를 찾는 시나리오를 보여줍니다.
*   **쉬운 모드:** 정보가 명확히 텍스트로 제공되는 웹사이트. (예: `https://www.ithacaschools.net/`)
*   **중간 모드:** 메뉴를 통해 구매 부서로 이동해야 하고, 조달 공고가 스캔된 PDF로 제공되는 웹사이트. (예: `https://www.mcps.org/`)
*   **궁극의 보스 모드:** 정보에 접근하려면 정보 자유법(FOIA) 요청을 제출해야 하고, 그 결과로 스캔된 이메일과 Google Drive에 업로드된 PDF 파일이 제공되는 웹사이트. (예: `https://www.bbrsd.org/`)

발표자는 웹이 방대하고(총 13억 4천만 개의 웹사이트 중 2억 1백만 개가 활성 상태), 인프라 변화가 매우 느리다는 점을 강조합니다. 그는 "여전히 팩스를 주고받는 곳도 있다"고 언급하며, 웹이 갑자기 에이전트 친화적인 API로 전환될 것이라는 생각은 비현실적이라고 말합니다.

그는 HTML을 읽는 코딩 에이전트의 한계를 지적합니다. NBA 경기 점수를 보여주는 웹사이트를 예로 들면, 초기 HTML에는 점수가 없고, 브라우저가 비동기 호출을 통해 JSON 데이터를 가져와 렌더링한 후에야 점수가 화면에 나타납니다. 즉, HTML만으로는 모든 정보를 얻을 수 없습니다.

발표자는 웹이 인간의 눈을 위해 만들어졌으며, 픽셀이 진실의 원천이라고 강조합니다. 따라서 기계는 웹과 상호작용하기 위해 '시각'이 필요합니다.

그는 Yutori 팀이 개발한 '내비게이터(Navigator)'라는 모델을 소개합니다.
*   **입력:** 브라우저의 스크린샷
*   **출력:** 인간과 유사한 행동 (클릭, 타이핑, 스크롤, URL 이동)

내비게이터는 전자상거래 웹사이트에서 특정 제품을 장바구니에 담고 할인 코드를 적용하는 데모를 보여줍니다. 이 모델은 스크린샷을 기반으로 버튼을 클릭하고, 텍스트를 입력하며, 할인 적용 여부를 확인합니다. 또한, 여러 양식 필드를 동시에 채우기 위해 JavaScript 코드를 작성하고 실행하는 능력도 보여줍니다. 이는 스크린샷을 통해 결과를 확인하므로 성공 여부를 알 수 있습니다.

발표자는 이러한 컴퓨터 사용 모델이 멀티 에이전트 시스템으로 확장될 수 있다고 설명합니다. 예를 들어, 개인 쇼핑 에이전트가 여러 내비게이터 인스턴스를 병렬로 실행하여 여러 웹사이트에서 정보를 수집하고 비교하는 시나리오를 보여줍니다.

마지막으로 그는 컴퓨터 사용 모델의 성능(정확도, 단계당 지연 시간, 작업당 비용)을 다른 최신 모델(Opus 4.7, GPT 5.5)과 비교한 그래프를 제시합니다. 내비게이터 1.5는 정확도에서 89.7%로 약간 우수하며, 단계당 지연 시간(2.935ms)과 작업당 비용($0.81)에서 훨씬 효율적입니다. 그는 이러한 추세가 계속될 것이며, 웹을 에이전트화하는 방식은 결국 인간이 웹을 사용하는 방식 위에 또 다른 '혼란의 층'을 쌓는 것이 될 것이라고 결론짓습니다. 즉, API를 기다리는 것이 아니라, 인간처럼 웹을 보고 행동하는 에이전트가 웹을 변화시킬 것이라는 주장입니다.

## 실무 적용 포인트
*   **시각 기반 에이전트 개발에 집중:** 웹의 롱테일이 API를 제공하지 않을 가능성이 높으므로, 스크린샷을 입력으로 받아 인간처럼 웹과 상호작용하는 시각 기반 에이전트(예: 내비게이터) 개발에 리소스를 집중하는 것이 효과적입니다.
*   **JavaScript 실행 능력 활용:** 에이전트가 단순히 클릭하고 타이핑하는 것을 넘어, 필요에 따라 JavaScript 코드를 생성하고 실행하여 동적인 웹 페이지와 상호작용할 수 있도록 설계해야 합니다. 이는 복잡한 양식 채우기나 동적 콘텐츠 로딩에 유용합니다.
*   **멀티 에이전트 시스템 설계:** 단일 에이전트로는 처리하기 어려운 복잡한 작업을 위해 여러 에이전트를 병렬로 실행하고 조율하는 오케스트레이터 기반의 멀티 에이전트 시스템을 고려해야 합니다. 이는 부동산 검색과 같은 광범위한 정보 수집 작업에 특히 적합합니다.
*   **비용 및 지연 시간 최적화:** 컴퓨터 사용 모델은 여전히 느리고 비용이 많이 들 수 있으므로, 모델의 크기를 줄이거나 추론 효율성을 높이는 등 성능 최적화에 주력하여 실제 서비스에 적용 가능하도록 만들어야 합니다.
