# Large clusters for small models — Daniel Svonava, Superlinked

🔗 https://youtu.be/g4SsanB0gMc · 📅 2026-09-19 · 🎙 AI Engineer

## 한 줄 요약
발표자는 작고 오픈소스인 AI 모델들이 비용 효율성, 속도, 성능 면에서 큰 모델에 필적하며, 이러한 모델들을 효율적으로 서빙하기 위한 Superlinked의 오픈소스 클러스터 아키텍처를 소개합니다.

## 발표자·소속
Daniel Svonava, Superlinked

## 핵심 주장
- **작은 모델의 성능 향상**: 작은 오픈소스 모델들이 특정 작업에서 GPT-5.1과 같은 최첨단 대규모 모델에 필적하는 성능을 보여주며, 비용과 속도 면에서 큰 이점을 제공합니다.
- **오픈소스 모델 생태계의 성장**: Hugging Face와 같은 플랫폼에서 수많은 오픈소스 모델이 다양한 작업에 대해 미세 조정되어 제공되고 있으며, 이는 특정 에이전트 작업에 필요한 모델을 찾는 데 유리합니다.
- **기존 클라우드 서빙 솔루션의 한계**: AWS Bedrock과 같은 독점 클라우드 서비스는 모델 카탈로그가 제한적이고, 구식이며, 미세 조정된 모델에 대한 소유권을 제공하지 않아 오픈소스 모델의 잠재력을 완전히 활용하기 어렵습니다.
- **작은 모델 서빙의 새로운 도전 과제**: 많은 수의 작은 모델을 효율적으로 서빙하는 것은 기존의 대규모 모델 서빙 방식(모델당 풀, 맹목적인 라우팅, 어댑터 관리)으로는 비효율적이며, 새로운 아키텍처 접근 방식이 필요합니다.
- **Superlinked의 오픈소스 클러스터 솔루션**: Superlinked는 Rust 기반의 스테이트리스 게이트웨이, 공유 작업 스트림 큐, GPU를 활용하는 워커 파드로 구성된 클러스터 아키텍처를 개발하여, 이러한 작은 모델들을 높은 처리량과 낮은 지연 시간으로 효율적으로 서빙할 수 있도록 합니다.

## 세부 내용

발표는 "Small Models Win"이라는 주제로 시작하며, 작은 모델들이 비용, 속도, 지능 면에서 큰 모델에 비해 우위를 점하고 있다고 강조합니다. 예를 들어, 텍스트 임베딩 모델의 경우 50배 저렴하고 2.7배 빠르며, 27B 오픈 모델은 GPT-5.1의 96%에 해당하는 지능 지수를 보입니다. 발표자는 오픈소스 모델의 지능 지수가 시간이 지남에 따라 빠르게 발전하여 최첨단 성능에 근접하고 있음을 그래프로 보여줍니다.

발표자는 실제 에이전트(예: 계약 검토 에이전트)가 이미 9개의 작은 모델을 필요로 한다고 설명하며, 문서 분류, 엔티티 추출, 조항 검색, 의무 질의 등 각기 다른 전문화된 작업을 수행하는 모델들이 조합되어 사용되는 방식을 보여줍니다. Hugging Face와 같은 플랫폼에는 이미 수백만 개의 오픈소스 모델이 존재하며, 이는 모든 에이전트 작업에 대한 오픈 모델이 이미 존재함을 의미합니다.

그러나 이러한 작은 모델들을 기존의 클라우드 서비스(예: AWS Bedrock)에서 서빙하는 데는 여러 가지 어려움이 있습니다. Bedrock은 모델 유형이 제한적이고, 제공되는 모델들은 최신 기술보다 2~3년 뒤처져 있으며, 미세 조정된 모델에 대한 소유권을 제공하지 않습니다. 또한, "지원됨"이라는 것은 단순히 모델이 로드된다는 의미일 뿐, 최적의 성능을 보장하지 않습니다.

많은 수의 작은 모델을 서빙하는 것은 표준적인 서빙 플레이북을 무너뜨립니다.
1.  **모델당 풀은 유휴 상태**: 모델당 하나의 프로비저닝된 엔드포인트는 유휴 상태일 때도 비용이 청구되어 비효율적입니다.
2.  **라우터는 맹목적으로 커밋**: 라우터가 각 요청을 복제본에 고정하면, 워커 배치가 로컬 슬라이스만 처리하게 되어 작은, 빈번한 배치로 인해 슬롯이 지연됩니다.
3.  **사용자가 어댑터를 가져옴**: 작은 모델은 LoRA(Low-Rank Adaptation)를 통해 적응력을 높이지만, 모든 도메인과 언어 쌍에 대해 LoRA를 공유 기반에 적용하면 카탈로그가 100배 증가하여 관리하기 어렵습니다.

Superlinked는 이러한 문제를 해결하기 위해 "The Gluster"라는 오픈소스 클러스터 아키텍처를 제안합니다. 이 아키텍처는 전체 카탈로그를 서빙하는 하나의 클러스터로 구성되며, Rust로 구현된 스테이트리스 게이트웨이, 풀 워크 스트림을 위한 큐(NATS JetStream), 그리고 GPU를 공급받는 워커 파드로 이루어져 있습니다.

요청의 핫 패스는 하나의 디코드 비용으로 종단 간 처리됩니다.
-   **SDK**: msgpack을 사용하여 numpy 배열을 반환합니다.
-   **게이트웨이**: 요청을 한 번 파싱하고 응답을 분할하여 오버헤드를 최소화합니다.
-   **큐**: 메모리 기반의 작업 스트림을 사용하며, 1987년 이후 1000개 이상의 객체 크기에서 50ms의 지연 시간을 보입니다.
-   **Rust 풀, 통합, 배치**: Rust 기반의 워커는 큐에서 작업을 풀링하고, 배치 비용을 예측하여 효율적인 배치를 구성합니다.
-   **하나의 소켓, 모든 엔진**: PyTorch, SGLang, Candle 등 다양한 런타임을 하나의 소켓 뒤에서 지원하며, 동일한 배치에서 넘피(numpy) 바이트를 전송하여 차이를 없앱니다.

이러한 아키텍처는 하나의 공유 큐에서 전체 배치를 처리하여 GPU당 처리량을 1.8배 향상시킵니다. 발표자는 기존의 "라우트-후-배치" 방식이 GPU 효율성 51%에 그치는 반면, "풀-후-배치" 방식은 89%의 GPU 효율성을 달성함을 시뮬레이션으로 보여줍니다.

어떤 런타임이든 하나의 소켓 뒤에서 작동하며, Superlinked는 PyTorch, SGLang, Candle을 지원합니다. PyTorch 어댑터는 80개 이상의 Python 어댑터를 포함하며, SGLang은 모델당 자식 프로세스를 사용하여 감독되고, Candle은 Rust 기반의 드롭인 솔루션입니다. Superlinked의 자동 연구(Auto-research) 시스템은 PyTorch 및 Candle 코드를 작성하고 SGLang 플래그를 스윕하여 벤치마크 결과에 따라 최적의 구성을 결정합니다.

측정 결과에 따르면, Superlinked의 프로파일은 SGLang보다 우수한 성능을 보이며, 테일 지연 시간까지 포함합니다. "The Knee"라는 개념은 추가된 부하가 처리량이 아닌 지연 시간을 증가시키는 지점을 나타냅니다. 하나의 GPU가 초당 682,000개의 임베딩 토큰을 처리할 수 있으며, 이는 텍스트 임베딩 작업에서 엄청난 효율성을 의미합니다. 워커를 추가하면 토큰 처리량이 선형적으로 증가하여, 하나의 큐에서 선형적인 스케일링이 가능합니다.

발표자는 모델을 공유 GPU에 패킹하여 유휴 비용을 절감하는 방법을 설명합니다. 모든 모델이 GPU에 고정되는 대신, 핫 모델은 상주하고 콜드 모델은 메모리 압력에 따라 제거됩니다. 이를 통해 GPU 활용률을 95% 이상으로 높일 수 있습니다.

마지막으로, Superlinked는 두 개의 에이전트 루프를 통해 모델 카탈로그를 최신 상태로 유지합니다. 하나는 새로운 오픈 모델을 온보딩하고 어댑터 코드를 작성하며 벤치마크를 수행하는 루프이고, 다른 하나는 공개 데이터에 대해 도메인 및 언어 어댑터를 훈련하여 모델을 적응시키는 루프입니다. 이 모든 과정은 자동화되어 있으며, 80센트의 GPU 시간으로 독일 법률 검색에서 18%의 품질 향상을 달성한 사례를 보여줍니다.

## 인상적인 대목
- "Small models are cheaper, faster, and match the frontier on the task. The rest is an engineering problem: serve them, adapt them, keep up with them." (작은 모델은 더 저렴하고 빠르며, 작업의 최전선에 필적합니다. 나머지는 엔지니어링 문제입니다: 서빙하고, 적응시키고, 따라잡는 것입니다.)
- "A real agent already needs nine small models." (실제 에이전트는 이미 9개의 작은 모델을 필요로 합니다.)
- "You can't run a small-model catalog on Bedrock." (Bedrock에서는 작은 모델 카탈로그를 실행할 수 없습니다.)
- "Full batches from one shared queue: 1.8x the throughput per GPU." (하나의 공유 큐에서 전체 배치를 처리하면 GPU당 처리량이 1.8배 증가합니다.)
- "One GPU serves 682,000 embedding tokens per second." (하나의 GPU가 초당 682,000개의 임베딩 토큰을 처리합니다.)

## 실무 적용 포인트
- **작은 모델 활용 전략**: 특정 작업에 대해 대규모 범용 모델 대신, 작고 전문화된 오픈소스 모델들을 조합하여 사용함으로써 비용 절감, 지연 시간 단축, 처리량 증가를 꾀할 수 있습니다.
- **오픈소스 인프라 구축**: 클라우드 제공업체의 관리형 서비스에 의존하기보다, Rust 기반의 게이트웨이, NATS JetStream과 같은 오픈소스 큐, 다양한 런타임(PyTorch, SGLang, Candle)을 지원하는 워커 파드를 활용하여 자체적인 모델 서빙 클러스터를 구축하는 것을 고려할 수 있습니다.
- **"풀-후-배치" 방식 도입**: 작은 모델의 효율적인 서빙을 위해, 라우터가 요청을 특정 워커에 푸시하는 대신, 워커가 중앙 공유 큐에서 작업을 풀링하여 자체적으로 배치를 구성하는 "풀-후-배치" 방식을 도입하여 GPU 활용률과 처리량을 극대화할 수 있습니다.
- **자동화된 모델 관리 및 최적화**: 새로운 모델 온보딩, 성능 벤치마킹, 미세 조정 및 어댑터 훈련, 그리고 런타임 최적화를 위한 자동 연구(Auto-research) 루프를 구축하여 모델 카탈로그를 지속적으로 업데이트하고 성능을 개선할 수 있습니다.
