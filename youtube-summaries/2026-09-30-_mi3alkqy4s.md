# The Death of the Code Review: What the Data Actually Says — Laurie Voss, Arize AI

🔗 https://youtu.be/_mi3alkqy4s · 📅 2026-09-30 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 코드 생성 속도를 획기적으로 높였지만, 인간의 코드 리뷰 속도는 그대로여서 새로운 병목 현상이 발생하고 있으며, 이 문제를 해결하기 위해 리뷰 자동화가 시도되고 있지만 여전히 인간의 개입이 필수적이고, 미래에는 더 높은 추상화 수준에서 코드 품질을 정의하고 검증하는 역할로 전환될 것입니다.

## 발표자·소속
Laurie Voss, Arize AI 개발자 관계 책임자 (NPM Inc. 공동 창립자)

## 핵심 주장
- **AI는 코드 생성 속도를 획기적으로 높였지만, 출하 속도는 크게 늘리지 못했습니다.** AI 에이전트를 사용하는 개발자는 741% 더 많은 코드를 작성했지만, 실제 출하된 소프트웨어는 30%만 증가했습니다. 이는 코드 리뷰가 새로운 병목 현상이 되었음을 의미합니다.
- **기존의 인간 중심 코드 리뷰 방식은 AI 시대에 비효율적입니다.** 인간은 한 번에 400줄 이상의 코드를 효과적으로 리뷰하기 어렵고, 대규모 AI 생성 코드에 대해 "더 열심히 리뷰"하는 것은 불가능하며, 리뷰어의 번아웃을 초래합니다.
- **테스트 통과가 코드의 병합 가능성을 보장하지 않습니다.** 모델이 테스트를 통과하더라도, 실제 유지보수자가 코드를 병합할 수 있다고 판단하는 기준(코드 품질, 다른 코드에 미치는 영향 등)은 테스트 스위트가 포착하지 못하는 경우가 많습니다.
- **완전한 자동화는 아직 불가능하며, 인간은 여전히 루프 안에 있습니다.** OpenAI와 같은 선도 기업들도 리뷰 프로세스에서 인간을 완전히 배제하지 못했으며, 자동화된 리뷰어는 프롬프트 주입 공격에 취약하거나 잘못된 코드를 88%의 확률로 놓칠 수 있습니다.
- **미래의 성공적인 팀은 "무엇을 출하했는지 신뢰할 수 있는" 팀이 될 것입니다.** 코드 생성과 리뷰의 자동화가 가속화됨에 따라, 개발자는 코드를 직접 리뷰하는 대신, 코드 품질의 정의를 코드로 작성하고, 자동화된 리뷰 시스템을 설계 및 튜닝하며, 프로덕션 환경에서 실제 동작을 검증하는 더 높은 추상화 수준의 역할로 이동해야 합니다.

## 세부 내용
발표자는 AI 에이전트의 등장으로 개발자들이 코드를 작성하는 속도가 획기적으로 빨라졌지만, 소프트웨어 출하 속도는 그에 미치지 못하고 있다고 지적했습니다. 최근 연구에 따르면, AI 에이전트를 사용한 개발자들은 741% 더 많은 코드를 작성했지만, 출하된 소프트웨어는 30%만 증가했습니다. 이는 코드 리뷰가 새로운 병목 현상이 되었음을 보여줍니다. 발표자는 "그럴듯한 코드를 생산하는 비용은 급감했지만, 그것을 신뢰할 수 있는지 아는 비용은 그렇지 않다"고 강조했습니다.

이러한 병목 현상을 해결하기 위한 몇 가지 시도가 있습니다. 첫째, "더 열심히 리뷰"하는 방법은 인간의 한계 때문에 효과적이지 않습니다. Cisco의 20년 전 연구에 따르면, 리뷰어는 한 번에 400줄 이상의 코드를 효과적으로 리뷰할 수 없으며, 450줄/시간을 넘으면 효율성이 급격히 떨어집니다. AI 에이전트가 수만 줄의 코드를 생성할 수 있는 상황에서, 인간이 이를 모두 리뷰하는 것은 불가능하며 번아웃을 초래합니다.

둘째, "코드를 읽는 것을 완전히 멈추는" 시도도 있습니다. OpenAI는 내부 제품 개발에서 수동으로 작성된 코드가 전혀 없으며, 에이전트가 모든 것을 작성했다고 보고했습니다. 5개월 만에 100만 줄의 코드를 3명의 엔지니어가 1500개의 병합된 PR로 만들었습니다. OpenAI는 "인간이 풀 리퀘스트를 리뷰할 수도 있지만, 그럴 필요는 없다"고 말했습니다. 그러나 발표자는 OpenAI가 이 방법론을 공개하지 않은 점을 들어 여전히 허점이 있을 수 있다고 지적했습니다.

셋째, 리뷰를 완전히 자동화하는 방법입니다. 그러나 "테스트 통과가 병합 가능성과 동일하지 않다"는 것이 문제입니다. Meter 연구 그룹은 Fable 5 모델이 SWE-Bench Pro 벤치마크에서 80.3%를 통과했지만, 실제 유지보수자의 병합 가능성 기준을 반영한 FrontierCode 벤치마크에서는 29.3%만 통과했음을 보여주었습니다. 이는 테스트 스위트가 코드 품질, 회귀 안전성, 유지보수성 등 모든 것을 포착하지 못하기 때문입니다. 발표자는 "병합 가능성을 알아내면, 모델이 그것을 학습할 것"이라며, "무엇이든 검증하기 쉬운 것은 학습되어 능가된다"고 말했습니다. 즉, "좋음의 정의를 쓰는 사람이 다음 해의 모델을 쓰는 것"입니다.

현재 GitHub Copilot의 리뷰어는 6천만 건의 리뷰를 수행하며 GitHub 전체 코드 리뷰의 5분의 1 이상을 차지하고 있습니다. Cursor와 CodeRabbit 같은 도구들도 수백만 건의 코드 리뷰를 자동화하고 있습니다. 이들 도구의 주요 과제는 "오탐(false positives) 관리"입니다. Cursor는 모델이 코드를 "덜 신뢰"하도록 훈련시켰고, 리뷰어가 버그를 발견하면 패치를 작성하는 기능까지 제공합니다.

그러나 인간의 개입 없이 완전히 자동화된 리뷰는 아직 불가능합니다. Anthropic의 Nicholas Carlini는 16개의 에이전트가 C 컴파일러를 Rust로 작성하는 실험을 했지만, 테스트 하니스와 피드백 시스템은 여전히 인간이 작성했습니다. Bun의 100만 줄 코드 포팅 실험에서는 아무도 diff를 읽지 않았고, 결과적으로 13,044개의 안전하지 않은 블록이 포함되었는데, 이는 인간이 작성한 유사한 프로젝트의 73개에 비해 세 자릿수 높은 수치입니다. OpenAI도 한동안 매주 금요일마다 AI가 생성한 "슬롭(slop)"을 수동으로 정리해야 했습니다. Dexter Horthy는 작년 AI Engineer 컨퍼런스에서 "코드를 읽지 말라"고 주장했지만, 올해는 "제발 코드를 읽어달라. 6개월 동안 코드를 읽지 않으려 했지만, 결과가 좋지 않았다"며 입장을 철회했습니다.

결론적으로, "테스트는 누군가가 인코딩한 것을 검증할 뿐"이며, 테스트 스위트 외부의 맥락을 포착하지 못합니다. 인간의 역할은 사라지지 않고, "더 높은 수준으로 이동"하고 있습니다. 코드를 직접 검사하는 대신, 코드를 검사하는 시스템을 설계하고 튜닝하며, "좋음의 정의"를 설계하는 역할로 변화하고 있습니다. "누군가는 리뷰어를 리뷰해야 합니다." Anthropic의 자동화된 보안 리뷰어조차 "이 작업은 프롬프트 주입 공격에 대해 강화되지 않았으며 신뢰할 수 있는 PR을 리뷰하는 데만 사용해야 한다"는 경고를 담고 있습니다. 자동화된 리뷰어는 자신감 있게 구성된 나쁜 코드에 88%의 확률로 속을 수 있습니다. 결국 "마지막 리뷰어는 프로덕션"입니다.

## 인상적인 대목
- "The cost of producing plausible code has collapsed. The cost of knowing whether to trust it has not." (그럴듯한 코드를 생산하는 비용은 급감했지만, 그것을 신뢰할 수 있는지 아는 비용은 그렇지 않다.)
- "Humans may review pull requests, but aren't required to." (인간이 풀 리퀘스트를 리뷰할 수도 있지만, 그럴 필요는 없다.)
- "You can't just review harder." (그냥 더 열심히 리뷰할 수는 없다.)
- "If you figure out mergeability, the models will train on it." (병합 가능성을 알아내면, 모델이 그것을 학습할 것이다.)
- "Whoever writes the definition of good writes next year's models." (좋음의 정의를 쓰는 사람이 다음 해의 모델을 쓰는 것이다.)
- "They had to tell it to trust the code less." (그들은 코드에게 코드를 덜 신뢰하라고 말해야 했다.)
- "No, we can't get away without humans." (아니요, 우리는 인간 없이 해낼 수 없습니다.)
- "Please, please read the code. We tried not reading the code for ~6 months. It did not end well." (제발 코드를 읽어달라. 6개월 동안 코드를 읽지 않으려 했지만, 결과가 좋지 않았다.)

## 실무 적용 포인트
- **코드 리뷰의 초점을 변경하세요:** AI가 생성한 코드의 양이 폭증함에 따라, 모든 줄을 수동으로 검토하는 것은 비효율적입니다. 대신, 자동화된 도구가 놓칠 수 있는 고수준의 아키텍처적 문제, 시스템 간의 상호작용, 비기능적 요구사항(보안, 성능) 등에 집중하여 인간 리뷰의 가치를 높이세요.
- **자동화된 리뷰 시스템을 구축하고 튜닝하세요:** 코드 품질, 회사 표준, 도메인 지식 등을 반영하는 자체적인 리뷰 하니스(harness)를 구축하고, 이를 통해 AI 에이전트가 생성한 코드의 초기 검증을 자동화해야 합니다. 오탐(false positives)을 줄이는 것이 핵심 과제입니다.
- **"좋음의 정의"를 명확히 코드로 작성하세요:** 모델이 학습하고 개선될 수 있도록, "병합 가능한 코드"가 무엇인지에 대한 명확하고 측정 가능한 기준(벤치마크, 분류기, 규칙 등)을 정의하고 코드로 구현하는 데 시간을 투자하세요. 이는 다음 세대 AI 모델의 행동을 결정하는 중요한 작업입니다.
- **프로덕션 환경에서의 평가(Evals)를 강화하세요:** 코드가 배포된 후 실제 환경에서 어떻게 작동하는지 모니터링하고 평가하는 시스템을 구축하여, 자동화된 리뷰 시스템이 놓친 문제를 식별하고 개선하는 마지막 방어선으로 활용하세요.
