# AI Writes Code Faster Than Uber Can Merge It - Preetam Dwivedi & Manjari Akella, Uber

🔗 https://youtu.be/hX140a5klW0 · 📅 2026-11-09 · 🎙 AI Engineer

## 한 줄 요약
우버는 AI가 생성하는 코드 변경사항의 급증에 대응하기 위해 SubmitQueue와 Stovepipe라는 하이브리드 검증 시스템을 도입하여, 병합 전 투기적 검증과 병합 후 지속적인 검증을 통해 처리량을 233% 증가시키면서도 코드 통합 시간을 30분으로 유지하고 있다.

## 발표자·소속
*   Preetam Dwivedi: Staff Software Engineer, Developer Platform, Uber
*   Manjari Akella: Senior Software Engineer, Developer Platform, Uber

## 핵심 주장
*   **AI 코드 생성으로 인한 통합 속도 변화:** AI가 코드를 생성하기 시작하면서, 우버의 코드 변경사항 병합 속도가 급증(2개월 만에 44% 증가)하여 기존 SubmitQueue의 처리량 최적화만으로는 개발자 대기 시간이 3~4시간으로 늘어나는 문제가 발생했습니다.
*   **SubmitQueue 최적화를 통한 처리량 개선:** SubmitQueue는 타겟 분석, 확률적 추측, 대규모 변경 우회 등의 최적화를 통해 초기에는 인간 개발자의 요구사항을 충족시켰으며, AI 도입 후에도 추가적인 최적화를 통해 처리량을 크게 늘렸습니다.
*   **개발자 경험 개선을 위한 디퍼럴(Deferrals) 도입:** 피크 시간대에 비용이 많이 드는 변경사항을 즉시 거부하는 대신, 디퍼럴 큐에 보관하여 시스템 부하가 적을 때 자동으로 재시도함으로써 개발자가 수동으로 재제출할 필요 없이 대기 시간을 자동화했습니다.
*   **병렬 처리를 위한 충돌 완화(Conflict Relaxation) 구현:** 코드 변경 간의 의존성 강도를 평가하여 약한 의존성을 가진 연결을 끊고 여러 개의 독립적인 가상 큐를 생성함으로써 병렬 처리량을 극대화했습니다.
*   **병합 후 검증 시스템 Stovepipe로 트렁크 안정성 유지:** 충돌 완화로 인해 발생할 수 있는 병합 후 트렁크 오류를 감지하고 복구하기 위해 Stovepipe 시스템을 도입했습니다. 이는 메인 브랜치와 검증된 메인 브랜치 두 개의 포인터를 관리하며, 오류 발생 시 온콜팀에게 알리고 복구 프로세스를 시작합니다.

## 세부 내용

**우버의 모노레포 환경**
우버는 Go, Java, Web, Python, iOS, Android 등 6개의 주요 모노레포를 사용하며, 5천 명 이상의 개발자가 매주 3만 6천 건 이상의 커밋과 2만 7천 건의 PR을 생성하고 4억 4천만 줄 이상의 코드를 관리합니다. 이 발표에서는 주로 Go 코드에 초점을 맞춥니다.

**통합 문제: 두 개의 그린 PR, 하나의 테스트되지 않은 조합**
기존의 CI/CD 파이프라인에서는 PR A와 PR B가 각각 베이스 H에 대해 독립적으로 CI를 통과하여 "그린" 상태로 표시될 수 있습니다. 하지만 PR A가 먼저 메인 브랜치에 병합된 후 PR B가 병합될 때, H+A+B 조합이 실패하여 메인 브랜치를 "레드" 상태로 만들 수 있습니다. 이는 PR B가 H+A 상태에서 테스트되지 않았기 때문입니다. 수천 명의 개발자가 모노레포에서 매일 수백, 수천 건의 변경사항을 생성하는 환경에서는 이러한 문제가 빈번하게 발생하여 트렁크가 자주 깨지고 복구에 많은 비용이 듭니다.

**SubmitQueue: 미래를 투기하는 우버의 병합 큐**
이러한 문제를 해결하기 위해 우버는 SubmitQueue라는 병합 큐를 도입했습니다. SubmitQueue는 여러 PR이 메인 브랜치에 병합될 수 있는 가능한 미래 상태(예: H+A, H+B, H+A+B)를 투기적으로 빌드하고 테스트합니다. 모든 조합이 성공적으로 빌드 및 테스트될 때만 변경사항을 메인 브랜치에 병합하여 항상 "그린" 트렁크를 유지하는 것을 목표로 합니다.

**SubmitQueue의 확장 방식**
SubmitQueue는 세 가지 주요 최적화를 통해 확장성을 확보했습니다.
1.  **타겟 분석 (Target analysis):** 독립적인 작업을 분리하여 처리합니다. 빌드 타겟 간의 관계를 분석하여 서로 영향을 주지 않는 작업은 가상 큐로 분리하여 병렬로 빌드 및 테스트함으로써 처리량을 높이고 불필요한 직렬화를 방지합니다.
2.  **확률적 투기 (Probabilistic speculation):** 가장 가능성 있는 미래 상태를 먼저 빌드합니다. 과거 빌드 정보와 변경 특성을 사용하여 특정 변경사항의 성공 확률을 예측하고, 병합에 필요한 빌드를 우선순위화하여 자원 낭비를 줄입니다.
3.  **대규모 변경 우회 (Bypass large changes):** 대규모 변경사항이 큐에 오래 머무르더라도, 작고 빠르게 빌드되는 변경사항들이 먼저 병합될 수 있도록 허용하여 큐의 처리량을 유지합니다.

**AI의 등장과 통합 속도 변화**
2026년 1월에는 시간당 약 90건의 피크 병합이 이루어졌으나, 2026년 3월에는 시간당 약 130건으로 44% 증가했습니다. 이는 주로 AI가 생성한 코드 변경사항 때문이었습니다. 이로 인해 개발자들의 코드 통합 대기 시간은 기존 30분에서 피크 시 3~4시간으로 급증했습니다. SubmitQueue는 트렁크를 "그린" 상태로 유지했지만, 개발자들은 긴 대기 시간으로 인해 불편을 겪었습니다.

**우버의 대응: 세 가지 주요 변경사항**
우버는 이러한 문제에 대응하기 위해 세 가지 추가 최적화를 도입했습니다.
1.  **입장 게이팅 (Admission gating):** 피크 시간대에 큐로 들어오는 트래픽을 제어합니다. 변경사항을 "작은 변경"과 "비용이 많이 드는 변경"으로 분류하고, 피크 시간에는 비용이 많이 드는 변경을 거부하여 개발자가 피크 시간 외에 재시도하도록 유도했습니다. 이로 인해 처리량은 23% 증가하여 시간당 약 160건의 병합을 달성했지만, 개발자가 직접 스케줄러 역할을 해야 하는 부담이 생겼습니다.
2.  **디퍼럴 (Deferrals):** 개발자 경험을 개선하기 위해 도입되었습니다. 피크 시간에 거부된 비용이 많이 드는 변경사항을 "지연 큐(Deferred queue)"에 보관하고, 시스템 용량이 허용될 때 자동으로 메인 큐에 재제출합니다. 개발자는 한 번만 제출하면 되므로 수동 재제출의 번거로움이 사라졌지만, 여전히 대기 시간 자체는 존재합니다.
3.  **충돌 완화 (Conflict relaxation):** 병렬 처리를 극대화하기 위해 도입되었습니다. 기존에는 어떤 타겟이라도 겹치면 변경사항들이 직렬화되어야 했지만, 충돌 완화는 변경사항 간의 의존성 강도를 점수화(Jaccard 유사성 기반)하여 약한 의존성을 가진 연결을 끊고 여러 개의 독립적인 가상 큐를 생성합니다. 예를 들어, 6개의 변경사항을 3개의 가상 큐로 분리하여 병렬 처리량을 56% 증가시켜 시간당 약 250건의 병합을 달성했습니다.

**충돌 완화의 트레이드오프와 Stovepipe**
충돌 완화는 처리량을 크게 늘렸지만, 일부 조합이 테스트되지 않은 채 병합될 수 있다는 트레이드오프가 있습니다. 이는 개별적으로 "그린"이었던 변경사항들이 병합 후 상호작용하여 트렁크를 "레드"로 만들 수 있음을 의미합니다.

이러한 문제를 해결하기 위해 우버는 **Stovepipe**라는 병합 후 검증 시스템을 사용합니다. Stovepipe는 메인 브랜치의 헤드(main HEAD)와 마지막으로 알려진 "그린" 상태를 가리키는 검증된 메인 헤드(verified/main HEAD)라는 두 개의 포인터를 유지합니다.
*   새로운 커밋이 메인 브랜치에 병합되면 main HEAD가 이동합니다.
*   Stovepipe는 main HEAD와 verified/main HEAD 사이의 모든 커밋 범위를 가져와 빌드 및 테스트를 수행합니다.
*   만약 이 범위의 검증이 실패하면 verified/main HEAD는 이동하지 않고 마지막 "그린" 상태에 머무릅니다.
*   검증이 성공하면 verified/main HEAD도 main HEAD로 이동합니다.
*   트렁크가 "레드" 상태가 되면 Stovepipe가 이를 감지하고 온콜팀에게 알립니다. 온콜팀은 수정사항을 준비하거나 변경사항을 되돌리고, SubmitQueue를 통해 이를 병합합니다. Stovepipe는 복구된 상태를 다시 검증하여 트렁크의 건강을 확인합니다.

**결과 및 향후 계획**
2026년 10월 기준으로 우버는 피크 시간당 약 300건의 병합을 처리하며, 이는 1월 대비 233% 증가한 수치입니다. 동시에 P95 통합 시간은 약 30분으로 유지되고 있습니다.

향후 계획은 다음과 같습니다.
*   **더 나은 처리량:** SubmitQueue에 배치 처리를 도입하여 반복 작업을 줄이고 더 많은 변경사항을 함께 검증합니다.
*   **더 나은 신뢰도:** 프로젝트 스코프를 검증하여 "내 프로젝트가 그린인가?"라는 질문에 답하고, 모든 실패를 전역적인 문제로 취급하지 않도록 합니다.
*   **더 빠른 복구:** 자동화된 진단 및 수정 조치에 투자하여 트렁크 상태를 더 빠르게 복구합니다.

**결론**
우버는 병합 전 필요한 검사와 강력한 의존성 제약을 유지하면서, 병합 후 통합된 트렁크 상태를 지속적으로 검증하는 하이브리드 접근 방식을 채택했습니다. 이를 통해 높은 코드 통합 처리량을 지원하면서도 합리적인 통합 시간을 유지할 수 있는 유연성을 확보했습니다. SubmitQueue와 Stovepipe는 오픈 소스로 공개되어 있습니다.

## 인상적인 대목

## 실무 적용 포인트
*   **하이브리드 검증 모델 고려:** 병합 전 투기적 검증(SubmitQueue)과 병합 후 지속적인 검증(Stovepipe)을 결합하여 높은 처리량과 안정성을 동시에 추구하는 모델을 도입할 수 있습니다.
*   **AI 코드 생성에 대한 CI/CD 전략 재고:** AI가 코드 생성 속도를 가속화함에 따라, 기존 CI/CD 파이프라인의 병목 현상을 예측하고 이에 대응하는 확장성 있는 전략(예: 입장 게이팅, 디퍼럴, 충돌 완화)을 수립해야 합니다.
*   **개발자 경험과 시스템 안정성 균형:** 개발자 대기 시간을 줄이기 위한 자동화된 대기 관리(디퍼럴)를 도입하여 개발자 생산성을 높이면서도, 시스템 안정성을 위한 병합 후 검증(Stovepipe)을 통해 트렁크의 건강을 유지하는 균형 잡힌 접근이 중요합니다.
*   **오픈 소스 프로젝트 활용 및 기여:** 우버의 SubmitQueue 및 Stovepipe 프로젝트가 오픈 소스로 공개되어 있으므로, 유사한 문제를 겪는 조직은 이를 활용하거나 기여하여 자체 CI/CD 시스템을 개선할 수 있습니다.
