# From 15% to 90% GPU Utilization: Fix the Data Pipeline, Not the Model

🔗 https://youtu.be/tNAV259UhCM · 📅 2026-10-10 · 🎙 AI Engineer

## 한 줄 요약
멀티모달 대규모 언어 모델(LLM) 훈련 파이프라인에서 GPU 활용률을 15%에서 90%로 높이기 위해 모델 최적화 대신 데이터 파이프라인의 병목 현상을 해결하는 방법을 제시합니다.

## 발표자·소속
Tarun Sunkaraneni, Member of Technical Staff - ML Systems, Amazon AGI Labs

## 핵심 주장
- **GPU 활용률 최적화의 중요성**: GPU는 가장 비싼 자원이므로, 훈련 루프가 GPU에 의해 막히지 않고 지속적으로 데이터를 공급받도록 하는 것이 중요합니다. 멀티모달 처리에서 CPU 작업이 많아 GPU가 유휴 상태에 빠지기 쉽습니다.
- **데이터 파이프라인 병목 현상 해결**: 데이터 로딩, 전처리, 전송 과정에서 발생하는 병목 현상을 해결하는 것이 모델 커널 최적화보다 훈련 처리량 향상에 더 큰 영향을 미칩니다.
- **점진적 최적화의 필요성**: 하나의 병목 현상을 해결하면 다른 병목 현상이 드러나므로, 단계별로 프로파일링하고 해결하는 접근 방식이 효과적입니다.
- **스케일 변화에 따른 최적화 전략 변화**: 소규모 실험에서는 효과가 없던 최적화 기법(예: SPREAD 스케줄링)이 대규모에서는 큰 효과를 발휘할 수 있으므로, 스케일에 따라 적절한 전략을 선택해야 합니다.

## 세부 내용

발표자는 멀티모달 지도 미세 조정(SFT) 데이터 파이프라인을 최적화하여 GPU 활용률을 높이는 방법에 대해 설명했습니다. 발표의 핵심 질문은 "훈련 루프가 정말 GPU에 의해 막혀 있는가?"였습니다.

**문제 정의 및 배경:**
GPU는 매우 비싼 자원이므로 활용률을 극대화해야 합니다. 그러나 멀티모달 데이터(이미지, 오디오, 비디오) 처리는 이미지 로딩/리사이징/정규화(PIL), 오디오 로딩/크롭핑(NumPy) 등 GPU가 아닌 CPU에서 수행되는 무거운 작업이 많습니다. 일반적으로 훈련 클러스터는 GPU보다 CPU가 훨씬 많음에도 불구하고, GPU는 데이터 부족으로 인해 유휴 상태에 빠지는 경우가 많습니다. 발표자는 이를 측정하기 위해 '대기 시간 비율(Wait Time Ratio)'이라는 지표를 도입했습니다. 이 지표는 (데이터 준비 시간 + 데이터 전송 시간)을 (데이터 준비 시간 + 데이터 전송 시간 + 훈련 단계 시간)으로 나눈 값입니다. 초기 베이스라인에서는 이 대기 시간 비율이 약 85%에 달했습니다.

훈련 스택은 NVIDIA Megatron-LM 모델/옵티마이저 병렬 처리, Qwen3-VL-52B-Base VLM 모델, S3에 호스팅된 JSONL 채팅 메시지 및 상대 이미지 경로 데이터 형식, KubeRay 및 Ray Cluster 인프라, 16개의 데이터 병렬 랭크, 512,000개 예제/실행 규모를 사용했습니다. 데이터는 JSONL 파일에 텍스트와 이미지 경로가 포함되어 S3에 저장됩니다. GPU가 실제 계산을 수행하기 전에 데이터 로딩, 데이터 변환(정규화, 토큰화, 손실 마스크), 데이터 전송의 세 가지 주요 단계가 필요합니다.

**베이스라인 문제점:**
나이브한 베이스라인 파이프라인은 각 샘플을 순차적으로 처리합니다. 즉, 객체 스토리지에서 이미지를 하나씩 가져와 블로킹 방식으로 처리하고, 트레이너가 한 번에 하나의 배치를 가져와 훈련한 다음 다음 배치를 요청합니다. 텐서는 드라이버를 통해 값으로 인라인 전송됩니다. 이 모든 단계가 GPU의 크리티컬 패스에 있습니다. 결과적으로, 배치당 데이터 가져오기 시간이 100초 이상으로 치솟아 GPU 활용률이 15%에 불과했습니다. 프로파일링 결과 S3 GET 및 PIL 이미지 로딩이 대부분의 시간을 차지했습니다.

**해결책 1: 동시성 (Concurrency)**
각 샘플 작업은 독립적이며 CPU 집약적입니다. 데이터 가져오기(I/O 바운드)와 처리(CPU 바운드)라는 두 가지 비용이 있습니다.
- **데이터 가져오기**: `asyncio`를 사용하여 I/O 바운드 작업을 비동기적으로 처리합니다.
- **데이터 처리**: `ray.Actor`를 사용하여 CPU 바운드 작업을 병렬 처리합니다. `ray.Actor`는 파이썬 GIL(Global Interpreter Lock)을 해제하는 스레드와 달리 프로세스 기반으로 완전한 격리를 제공하여 여러 코어를 활용할 수 있습니다.
이 최적화를 통해 대기 시간 비율은 약 40-50%로 감소했으며, 25%의 속도 향상을 달성했습니다.

**해결책 2: 미리 가져오기 (Prefetching)**
다음 배치에 대한 대기 시간을 없애기 위해 미리 가져오기 기법을 도입했습니다. 백그라운드 스레드가 트레이너보다 앞서 미리 데이터를 가져와 유한한 크기의 큐를 채웁니다. 이는 프로듀서(데이터 생성자)가 컨슈머(트레이너)보다 빠를 때만 효과적입니다. 이를 통해 배치당 데이터 가져오기 시간이 거의 0초에 가까워졌고, 대기 시간 비율은 약 20%로 추가 감소했습니다. 데이터 로딩 및 변환 병목 현상을 효과적으로 해결했습니다.

**해결책 3: 객체 저장소 (Object Store)**
이전 최적화 후에도 데이터 전송 비용이 여전히 남아있었습니다. 멀티모달 텐서는 샘플당 메가바이트 단위로 크기 때문에, 워커에서 피클링되고, 코디네이터로 복사된 다음, 트레이너로 다시 피클링되는 과정에서 데이터 생성자(Data generator)의 메모리 부족(OOM) 문제가 발생했습니다. 해결책으로 Ray Object Store를 사용했습니다. 각 샘플은 실제 데이터 대신 `ObjectRef`(포인터)를 전달하며, 트레이너는 필요할 때 Ray Store에서 직접 데이터를 가져옵니다. 이로써 불필요한 데이터 복사 및 직렬화/역직렬화 오버헤드를 제거하여 대기 시간 비율을 10-15% 수준으로 낮췄습니다.

**해결책 4: 프레임워크 최적화 (Framework Optimizations)**
대규모로 확장할 때 새로운 병목 현상이 나타났습니다. 워커 액터가 몇몇 노드에 집중되어 S3 트래픽과 JIT 풀이 해당 노드의 네트워크 인터페이스 카드(NIC)를 포화시켰습니다. 이를 해결하기 위해 두 가지 Ray 프레임워크 최적화를 적용했습니다.
- **제로-카피 검색 (Zero-copy retrieval)**: 소비하는 랭크가 공유 메모리에서 텐서를 직접 매핑하여 불필요한 복사를 줄입니다. (호스트에서 GPU로의 복사는 불가피). `RAY_ENABLE_ZERO_COPY_TORCH_TENSORS=1` 플래그를 사용합니다.
- **SPREAD 스케줄링**: 노드당 하나의 워커를 할당하여 객체 및 S3 트래픽이 모든 노드 스토어/NIC에 분산되도록 합니다. `scheduling_strategy="SPREAD"`를 사용합니다.
이 두 가지 최적화는 소규모 실험에서는 오히려 성능 저하를 가져왔지만, 대규모에서는 시너지 효과를 발휘하여 NIC 대역폭 병목 현상을 해소하고 교차 노드 풀링 비용을 낮췄습니다. 최종적으로 전체 처리량을 50% 이상 향상시켰습니다.

**학습 내용:**
- GPU는 비싸지만, 때로는 GPU로 가는 경로에서 가장 큰 병목 현상이 발생합니다. CPU 바운드인지, GPU 바운드인지, I/O 바운드인지, 컴퓨팅 바운드인지 먼저 파악해야 합니다.
- 하나의 병목 현상을 해결하면 종종 다른 병목 현상이 드러납니다. 처리량 -> 대기 시간 -> 메모리 -> 검색 비용 -> NIC 순으로 병목 현상이 이동했습니다.
- 고전적인 최적화 기법(병렬 처리, 미리 가져오기)이 중요하지만, 데이터 지역성(locality)과 복사 의미론(copy semantics)도 여전히 중요합니다.
- 스케일은 답을 바꿉니다. 제로-카피 낭비 및 워커 분산과 같은 튜닝 매개변수는 대규모에서만 중요해지며, 소규모에서는 오히려 역효과를 낼 수 있습니다.
- "베이스라인을 프로파일링하는 것이 변화를 이끄는 데 도움이 됩니다."

## 인상적인 대목
- "GPUs aren't the goal - Never letting data be the bottleneck is." (GPU가 목표가 아니라, 데이터가 병목 현상이 되지 않도록 하는 것이 목표입니다.)
- "The same config can lose at a small scale and win at a large scale." (동일한 설정이 소규모에서는 실패하고 대규모에서는 성공할 수 있습니다.)
- "Premature optimization is the root of all evil." (성급한 최적화는 모든 악의 근원입니다.)

## 실무 적용 포인트
- **초기 프로파일링의 중요성**: GPU 훈련 파이프라인 최적화를 시작하기 전에, 현재 시스템의 병목 현상이 CPU, GPU, I/O 중 어디에 있는지 정확히 파악하기 위한 철저한 프로파일링을 수행해야 합니다.
- **단계별 최적화 접근**: 한 번에 모든 것을 최적화하려 하지 말고, 가장 큰 병목 현상부터 순차적으로 해결하고 각 단계마다 효과를 측정하여 다음 병목 현상을 식별하는 반복적인 접근 방식을 사용합니다.
- **Ray Actors 및 Object Store 활용**: 멀티모달 데이터 전처리 및 전송 시, Ray Actors를 사용하여 CPU 집약적 작업을 병렬화하고, Ray Object Store를 통해 대용량 데이터 전송 시 포인터 기반 접근 방식을 사용하여 메모리 복사 오버헤드를 최소화합니다.
- **스케일 고려한 최적화 전략**: 소규모 개발 환경에서 효과가 없던 최적화 기법이라도 대규모 프로덕션 환경에서는 필수적일 수 있음을 인지하고, 스케일업 시 네트워크 대역폭, 노드 간 통신 비용 등을 고려하여 `SPREAD` 스케줄링과 같은 분산 최적화 기법을 적용합니다.
