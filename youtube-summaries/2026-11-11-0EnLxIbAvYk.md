# Your Spec Has Bugs. Catch Them Before Your Agent Codes. - Rajath Mahendrappa Kotyal, AWS

🔗 https://youtu.be/0EnLxIbAvYk · 📅 2026-11-11 · 🎙 AI Engineer

## 한 줄 요약
AWS의 Rajath Kotyal은 LLM(대규모 언어 모델) 기반 코딩 에이전트가 코드를 작성하기 전에 사양(specification)의 모호성, 충돌, 누락된 부분을 SMT(만족도 모듈 이론) 솔버를 활용한 자동화된 추론으로 탐지하고 해결하는 Kiro Specification Analyzer 프로젝트를 소개합니다.

## 발표자·소속
Rajath Kotyal, Automated Reasoning Group, Amazon Web Services (AWS)

## 핵심 주장
- **불분명한 사양은 코드 정확도를 저해합니다:** 불분명한 프롬프트는 LLM의 코드 생성 정확도를 20-40% 감소시키고, 유효한 코드의 60-90%가 여전히 잘못될 수 있으며, 버전 간 회귀가 2배 더 발생할 수 있습니다.
- **사양 버그는 두 가지 방식으로 숨어 있습니다:** 단일 문장 내의 모호성(잘못된 세부 수준)과 여러 문장 간의 충돌이나 누락된 부분(gaps)으로 나타납니다.
- **LLM과 SMT 솔버를 결합하여 사양을 분석합니다:** LLM이 자연어 사양을 정제하고 SMT(만족도 모듈 이론) 공식으로 형식화한 다음, SMT 솔버가 이 공식에서 충돌, 누락, 시나리오를 분석하여 버그를 탐지합니다.
- **인간의 개입을 통해 모호성을 해결합니다:** LLM이 여러 해석을 내놓을 경우, 논리적 동등성을 기준으로 해석들을 클러스터링하고, 사용자에게 명확한 질문을 던져 모호성을 해소하거나 특정 구현을 보류하도록 합니다.

## 세부 내용
발표자는 AI Engineer Code Summit 2026에서 'Specs Have Bugs Too'라는 주제로 LLM이 코드를 작성하기 전에 SMT 솔버를 사용하여 사양의 버그를 잡아내는 프로젝트인 Kiro Specification Analyzer에 대해 설명했습니다.

**문제점:**
발표자는 전자상거래 웹사이트의 사양에서 발생할 수 있는 버그를 예시로 들었습니다.
- R2: "주문이 제출되고 재고가 없을 경우, 주문은 백오더로 처리되어야 한다." (WHEN order submitted AND inventory unavailable SHALL place the order on backorder)
- R3: "어떤 주문도 백오더로 처리되어서는 안 된다." (SHALL NOT place any order on backorder)
이 두 규칙은 개별적으로는 타당해 보이지만, 함께 읽으면 모순됩니다. LLM이 이 두 규칙을 동시에 처리할 때 모호성이 발생하여 코드를 잘못 작성할 수 있습니다. 이러한 불분명한 프롬프트는 LLM의 코드 정확도를 20-40% 떨어뜨리고, 생성된 유효한 코드 중 60-90%가 여전히 잘못될 수 있으며, 코드 배포 시 2배 더 많은 회귀를 유발할 수 있습니다.

**버그가 숨는 곳:**
사양 버그는 크게 두 가지 유형으로 나뉩니다.
1.  **단일 문장 내:** 모호성, 잘못된 세부 수준. (예: "기록을 삭제하라"는 문장이 기록을 완전히 지우는 것인지, 아니면 사용자에게만 숨기고 감사 목적으로 보관하는 것인지 불분명)
2.  **여러 문장 간:** 충돌(conflict) 또는 누락(gap). (예: R2와 R3의 모순, 특정 상황에 대한 규칙이 전혀 없는 경우)

**해결 아이디어: LLM 번역 및 솔버 검사 (3단계 프로세스)**
1.  **LLM 정제 (Refine):** LLM이 사양의 워딩을 자체적으로 정리하려고 시도합니다.
2.  **LLM 형식화 (Formalize):** LLM이 영어 사양을 SMT(만족도 모듈 이론) 공식으로 변환합니다. 예를 들어, R2는 `(=> (and submitted (not in_stock)) backordered)`와 같은 수학 공식 형태로 인코딩됩니다.
3.  **SMT 솔버 분석 (Analyze):** SMT 솔버가 형식화된 규칙들 간의 충돌, 누락된 부분, 가능한 시나리오를 분석합니다.

**세부 단계:**
-   **1단계: 규칙을 논리로 변환:** 자연어 규칙을 SMT 형식의 논리적 표현으로 바꿉니다.
-   **2단계: 샘플링 후 클러스터링:** LLM에게 여러 번 번역을 요청하여 다양한 해석을 얻습니다. 이 번역들을 논리적 동등성을 기준으로 클러스터링합니다. 만약 여러 클러스터가 존재한다면, 이는 모호성이 있음을 의미합니다.
-   **3단계: 명확한 질문:** 모호성이 감지되면, 시스템은 사용자에게 명확한 질문을 던져 어떤 해석이 올바른지 확인합니다. 예를 들어, "기록을 삭제하라"는 지시에 대해 "A: 기록은 사라진다" 또는 "B: 기록은 보존되지만 사용자에게는 숨겨진다"와 같은 두 가지 옵션을 제시하여 사용자가 선택하도록 합니다.
-   **4단계: 모든 규칙을 한 번에 확인:**
    -   **충돌(Conflict):** R2와 R3 예시처럼 재고가 소진되었을 때 두 규칙이 충돌하는 경우를 탐지합니다.
    -   **누락(Gap):** 특정 상황(예: 유휴 주문)을 다루는 규칙이 없는 경우를 탐지합니다.
    이것은 예측 문제가 아니라 탐색 문제입니다.

**한계점:**
-   **오라클 부재:** 사양의 정확성에 대한 궁극적인 오라클은 사용자 자신입니다.
-   **암묵적 도메인 지식 (Dark matter):** LLM은 암묵적인 도메인 지식을 알지 못합니다.
-   **비결정론적 특성 (No guarantee nondeterministic):** LLM의 비결정론적 특성 때문에 항상 동일한 결과를 보장할 수 없습니다.
-   **형식화에 대한 증거 부족 (Thin evidence for formalization):** 형식화 및 에이전트에서의 활용에 대한 연구는 아직 초기 단계입니다.

## 인상적인 대목
"There is no oracle for specification correctness other than the user." (사양 정확성에 대한 오라클은 사용자 외에는 없습니다.)

## 실무 적용 포인트
-   **LLM 기반 코드 생성 전 사양 검토 필수:** LLM 에이전트를 사용하여 코드를 생성하기 전에, 사양의 모호성, 충돌, 누락된 부분을 반드시 확인해야 합니다.
-   **다중 해석 샘플링 및 클러스터링:** LLM의 비결정론적 특성을 고려하여, 사양 번역을 여러 번 샘플링하고 논리적 동등성으로 클러스터링하여 잠재적 모호성을 식별하는 접근 방식을 고려할 수 있습니다.
-   **사용자 주도적 모호성 해결:** 시스템이 모호성을 탐지하면, 사용자에게 명확한 선택지를 제공하여 사양의 의도를 명확히 하도록 유도하는 인터페이스를 설계해야 합니다.
-   **SMT 솔버를 활용한 형식 검증:** 중요한 사양의 경우, SMT 솔버와 같은 형식 검증 도구를 활용하여 규칙 간의 충돌이나 누락된 부분을 자동으로 분석하고 검증하는 파이프라인을 구축하는 것을 고려해야 합니다.
