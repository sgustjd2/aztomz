# How to Kill the Code Review — Ankit Jain, Aviator

🔗 https://youtu.be/YgEv7IQzGdM · 📅 2026-08-17 · 🎙 AI Engineer

## 한 줄 요약
코드 리뷰는 단순한 코드 검토를 넘어 팀의 정렬(alignment)과 의미론적 정확성(semantic accuracy)을 확보하는 것이 중요하며, AI를 활용한 의도 기반 리뷰 시스템과 AI Slop Register를 통해 이 과정을 자동화하고 효율화할 수 있습니다.

## 발표자·소속
Ankit Jain, Aviator 공동 창립자

## 핵심 주장
- **코드 리뷰는 단순히 코드 검토가 아니다:** 코드 리뷰의 본질은 버그, 컨벤션, 보안 등의 '의미론적 정확성'뿐만 아니라, '지식 공유', '멘토링', '아키텍처 피드백'과 같은 팀 '정렬'에 있다.
- **AI는 코드 리뷰의 병목 현상을 심화시켰다:** AI가 코드를 작성하고 리뷰하는 시대에도 여전히 인간이 UI에서 AI의 리뷰를 '훑어보는' 비효율적인 과정이 반복되며, 이는 코드 변경량 증가, 인시던트-PR 비율 증가, 리뷰 시간 증가, 리뷰 없이 병합되는 PR 증가로 이어진다.
- **의도(Intent) 기반 개발로 전환해야 한다:** 기존의 사양(spec) 기반 개발은 피드백 루프가 없어 사양과 구현 간의 불일치(spec drift)가 발생한다. AI 시대에는 Jira 티켓, 디자인 문서, 그리고 AI 에이전트와의 프롬프트 대화에서 드러나는 '의도'를 중심으로 개발해야 한다.
- **AI Slop Register로 반복적인 피드백을 자동화하라:** 코드 리뷰에서 반복적으로 발생하는 코멘트(예: 특정 타입 사용, 로거 사용, 직접적인 DB 접근 금지 등)를 'AI Slop Register'라는 불변값(invariant)으로 코디파이(codify)하여 자동화된 검사로 전환함으로써 의미론적 정확성을 높일 수 있다.
- **리뷰어는 코드 차이(diff)가 아닌 의도를 리뷰해야 한다:** AI가 의도와 불변값을 기반으로 테스트 계획을 생성하고 검증한 후, 리뷰어는 생성된 코드의 동작 증거와 아키텍처적 결정 사항을 검토하여 팀의 정렬을 유지하는 데 집중해야 한다.

## 세부 내용

발표자는 AI 엔지니어링 컨퍼런스에서 '코드 리뷰를 없애는 방법'이라는 주제로 강연을 시작했습니다. 그는 자신이 Aviator의 공동 창립자이며 AI 코드 검증 플랫폼을 구축하고 있다고 소개했습니다.

발표자는 먼저 몇 달 전 자신이 작성했던 '5단계 신뢰 모델'에 대한 글을 언급하며, 이 모델이 라인별 코드 리뷰 없이 코드 병합에 대한 신뢰를 구축하는 데 초점을 맞췄다고 설명했습니다. 그는 이 모델에서 일부는 맞고 일부는 틀렸으며, 이번 강연에서는 그 개념들을 더 깊이 탐구할 것이라고 말했습니다.

**문제점: 오늘날 코드 리뷰의 현실**
발표자는 현재 코드의 양이 매일 증가하고 있으며, 우리는 이를 따라잡기 위해 고군분투하고 있다고 지적했습니다. 그는 Focus.ai의 2023년 4월 보고서 데이터를 인용하며, 코드 변경량(code churn)이 861% 증가했고, 인시던트-PR 비율이 243% 증가했으며, 리뷰에 걸리는 중앙값이 441% 증가했다고 밝혔습니다. 심지어 PR의 31.3%는 전혀 리뷰 없이 병합되고 있다고 강조하며, 이는 우리가 이미 코드 리뷰를 제대로 하지 못하고 있음을 의미한다고 주장했습니다.

**리뷰 극장: AI가 코드를 작성하고 AI가 리뷰하는데 왜 UI가 필요한가?**
발표자는 AI가 코드를 작성하고 AI가 리뷰하는 상황에서 왜 여전히 인간이 UI를 통해 리뷰를 해야 하는지 의문을 제기했습니다. 그는 AI 에이전트가 코드를 작성하고, AI가 이를 리뷰하며, 인간은 그저 '훑어보고(skins)' 병합하는 과정이 반복된다고 설명했습니다. AI가 AI를 UI에서 리뷰하는데 아무도 읽지 않는다면, 우리는 잘못된 것을 설정하고 있는 것이라고 비판했습니다.

**핵심 전환점: 코드 리뷰는 코드 리뷰에 관한 것이 아니다**
발표자는 코드 리뷰의 역사가 15~20년 정도로 길지 않으며, Google이 2006년에 Mondrian을 출시하면서 공식적인 코드 리뷰가 시작되었다고 언급했습니다. 그는 코드 리뷰가 단순히 '의미론적 정확성'(버그 포착, 컨벤션 준수, 보안 취약점 식별, 회귀 감지, 명명 규칙, 엣지 케이스 처리)만을 위한 것이 아니라고 강조했습니다.

그는 코드 리뷰의 또 다른 중요한 측면으로 '정렬(Alignment)'을 제시했습니다. 이는 '지식 공유', '멘토링', '아키텍처 피드백', '온보딩', '공동 소유권', 'API 설계'와 같은 요소들을 포함합니다. 발표자는 의미론적 정확성을 위해서는 더 나은 도구가 필요하지만, 정렬은 반드시 살아남아야 한다고 주장했습니다.

**첫 번째 과제: 정렬 (대화를 유지하고 상위 단계로 이동)**
발표자는 '사양 기반 개발'이 '새 옷을 입은 폭포수 모델'과 같다고 비판했습니다. 1970년대의 폭포수 모델(요구사항 → 설계 → 구현 → 검증)과 2020년대의 사양 기반 개발(사양 → 아키텍처 → 생성 → 검증)은 유사하며, 둘 다 '피드백 루프'가 없다는 공통적인 문제점을 가지고 있다고 설명했습니다. 사양은 작업이 시작되기 전에 작성되므로, 구현 과정에서 발생하는 새로운 통찰력이 사양에 반영되지 않아 '사양 드리프트(specs drift)'가 발생합니다.

발표자는 '의도(Intent)'가 사양에만 존재하는 것이 아니라고 강조했습니다. 의도는 Jira 티켓(코드를 건드리기 전에 작성된 목표), PR/디자인 문서(첫 커밋부터 이미 달라지는 계획), 그리고 가장 중요한 '프롬프트'(실제 결정이 이루어지는 세션 내 대화)에 존재한다고 설명했습니다. 그러나 현재는 이 프롬프트들이 세션이 끝나면 버려지고 있다고 지적했습니다.

**두 번째 과제: 의미론적 정확성 (기계가 코드를 증명하게 하라)**
발표자는 반복되는 코드 리뷰 코멘트를 'AI Slop Register'로 코디파이(codify)하는 개념을 소개했습니다. 예를 들어, "통화 금액에는 Money 타입을 사용하고 float를 사용하지 마세요", "구조화된 로거를 사용하고 print를 사용하지 마세요", "user.* 테이블에 직접 쓰지 마세요", "오류 경로는 메트릭 카운터를 증가시키세요", "하드코딩된 비밀번호는 안 됩니다"와 같은 코멘트들을 불변값(invariant)으로 정의하여 자동화된 검사로 만들 수 있습니다. 이 AI Slop Register는 병합된 PR 코멘트로부터 주간 단위로 자동으로 구축되며, 인간이 승인하면 라이브로 적용됩니다. 이는 반복되는 모든 코멘트가 더 이상 수동으로 리뷰할 필요 없는 '가드레일'이 되는 것을 의미합니다.

**시스템: 두 가지 과제를 함께 해결**
발표자는 정렬과 의미론적 정확성이라는 두 가지 문제를 하나의 루프(loop)로 통합하는 시스템을 제시했습니다.
1. **캡처(Capture):** 사용자의 프롬프트 세션에서 '의도'를 캡처하여 '승인 기준(Acceptance criteria)'으로 만듭니다. 이 승인 기준은 LLM을 활용하여 생성될 수 있습니다.
2. **구축(Build):** AI Slop Register의 불변값들과 캡처된 승인 기준을 결합하여 '테스트 계획(Test plan)'을 생성합니다.
3. **실행(Run):** 시스템은 이 테스트 계획을 기반으로 '프리뷰 환경'을 띄워 시나리오를 테스트하고, '결과'(통과/실패 및 증거)를 생성합니다. 이 과정은 코드를 읽고 추측하는 것이 아니라, 실제 동작을 실행하고 기록합니다.
4. **리뷰(Review):** '리뷰어'는 이제 코드의 '차이(diff)'가 아닌, '의도'와 '아키텍처'를 리뷰합니다. 즉, 의사결정, 아키텍처의 형태, 인간이 판단해야 할 트레이드오프, 그리고 지속되어야 할 대화에 집중합니다.

발표자는 시스템이 완벽할 필요는 없다고 강조했습니다. '결정론적 검사(Deterministic check)'는 스캔, 어설션, 상태 코드, 스크린샷 등을 통해 동일한 코드가 항상 동일한 결과를 내도록 보장합니다. 반면, '런타임 + LLM 판단(Runtime + LLM judge)'은 스크린샷과 같은 '퍼지한 동작'이나 진정으로 판단이 필요한 기준에 대해 LLM을 활용합니다. 모델은 도구일 뿐, 기록의 심판관이 아니라는 점을 분명히 했습니다.

**리뷰는 의도를 리뷰하는 것이지, 차이를 리뷰하는 것이 아니다.**
결론적으로, 리뷰어는 이제 '의도 및 결정'(무엇을 만들려고 했는지, 시도하고 거부한 것, 세션에서 캡처된 것)과 '아키텍처'(변경의 형태, 인간이 판단할 가치가 있는 트레이드오프, 지속되는 대화)를 리뷰합니다. '검증 결과'(판단 + 증거, 결정론적이고 재현 가능하며, 동작이 실제로 발생했는지)는 리뷰의 중요한 근거가 됩니다. 발표자는 "리뷰어는 그 어느 때보다 중요하다. 그들은 더 이상 차이를 읽지 않는다."고 말했습니다.

**숙제: 레지스터를 구축하라. 첫날부터 리뷰를 없애려 하지 마라.**
발표자는 청중에게 숙제를 주며 강연을 마무리했습니다. "지난 1000개의 리뷰 코멘트를 분석하여 반복되는 패턴에 대한 AI Slop Register를 구축하라." 그는 이 과정이 J-커브를 따른다고 설명했습니다. 처음에는 고통스럽지만(Pain is real), 시간이 지남에 따라 보상(Payoff is real too)이 커진다고 했습니다. 병합된 모든 PR은 새로운 불변값을 제안하고, 다음 PR은 더 많은 것을 포착하며, 리뷰는 줄어들고, 피드백 루프는 더욱 강화됩니다.

마지막으로, 발표자는 "오늘 한 가지를 기억한다면, 코드 리뷰는 코드 리뷰에 관한 것이 아니다"라고 다시 한번 강조하며, Aviator의 새로운 제품 'Verify'의 얼리 디자인 파트너가 되어달라고 요청했습니다.

## 인상적인 대목
- "When AI reviews AI in a UI nobody reads, you've configured the wrong thing." (AI가 UI에서 AI를 리뷰하는데 아무도 읽지 않는다면, 당신은 잘못된 것을 설정하고 있는 것입니다.)
- "Semantic accuracy needs better tools. But alignment must survive!" (의미론적 정확성은 더 나은 도구를 필요로 합니다. 하지만 정렬은 반드시 살아남아야 합니다!)
- "Intent doesn't *only* live in a spec." (의도는 사양에만 존재하는 것이 아닙니다.)
- "It doesn't read the code and guess. It runs the behavior and records what happened." (그것은 코드를 읽고 추측하지 않습니다. 그것은 동작을 실행하고 무슨 일이 일어났는지 기록합니다.)
- "The model is a tool inside the harness — never the judge of record." (모델은 하네스 안의 도구일 뿐, 기록의 심판관이 아닙니다.)
- "The reviewer is more important than ever. They're just not reading diffs anymore." (리뷰어는 그 어느 때보다 중요합니다. 그들은 더 이상 차이를 읽지 않습니다.)

## 실무 적용 포인트
- **AI Slop Register 구축:** 팀 내에서 반복적으로 발생하는 코드 리뷰 코멘트나 가이드라인을 수집하여 불변값(invariant) 형태로 정의하고, 이를 자동화된 검사 도구(예: 린터, 정적 분석 도구)에 통합하는 것을 고려해볼 수 있습니다.
- **의도 기반의 테스트 계획 전환:** 개발 초기 단계에서 Jira 티켓이나 디자인 문서, AI 에이전트와의 대화에서 도출된 '의도'를 명확히 정의하고, 이를 기반으로 테스트 계획(acceptance criteria)을 수립하는 방식으로 전환하여 사양 드리프트를 줄이고 팀 정렬을 강화합니다.
- **LLM을 활용한 테스트 계획 자동화:** 반복적이고 시간이 많이 소요되는 테스트 계획 작성에 LLM을 활용하여 초기 테스트 스위트를 빠르게 생성하고, 인간 리뷰어는 생성된 테스트 계획의 품질과 의도 부합 여부를 검토하는 데 집중합니다.
- **리뷰의 초점 변경:** 코드의 라인별 차이(diff) 검토에서 벗어나, 변경의 '의도', '아키텍처적 결정', '트레이드오프' 등 상위 수준의 논의와 검증 결과(행동 증거)에 집중하여 리뷰의 가치를 높입니다.
