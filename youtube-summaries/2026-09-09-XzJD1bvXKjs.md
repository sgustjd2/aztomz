# How long can your skills be before your agent forgets what you told it? — Laurie Voss, Arize AI

🔗 https://youtu.be/XzJD1bvXKjs · 📅 2026-09-09 · 🎙 AI Engineer

## 한 줄 요약
LLM 기반 에이전트가 많은 도구(기술)를 효과적으로 기억하고 활용하도록 돕기 위해, 사용자 질의에 따라 관련 도구 설명만 검색하여 제공하는 RAG(Retrieval Augmented Generation) 패턴을 적용하는 방법을 제안한다.

## 발표자·소속
Laurie Voss, Arize AI

## 핵심 주장
*   **LLM 에이전트는 많은 도구를 기억하는 데 어려움을 겪습니다.** LLM은 고정된 컨텍스트 창을 가지며, 긴 대화나 많은 도구 목록 속에서 특정 정보를 찾아내는 "건초 더미 속 바늘 찾기" 문제와 "최신 정보 편향(recency bias)" 때문에 에이전트가 자신의 모든 기술을 효과적으로 기억하고 활용하기 어렵습니다.
*   **모든 도구 설명을 프롬프트에 넣는 것은 비효율적이고 확장성이 떨어집니다.** 에이전트가 사용할 수 있는 모든 도구의 설명을 프롬프트에 직접 제공하는 전통적인 방식은 도구 수가 늘어날수록 컨텍스트 창을 빠르게 소모하고, LLM의 성능을 저하시키며, 비용을 증가시키고, 정확도를 떨어뜨립니다.
*   **"기술 검색(Skill Retrieval)"을 위한 RAG 패턴이 해결책입니다.** 일반적인 RAG가 사실 정보 검색에 중점을 둔다면, 이 발표에서는 에이전트가 "무엇을 할 수 있는지"와 "어떻게 하는지"를 기억하도록 돕는 "기술 검색"에 RAG를 적용합니다. 이는 사용자 질의에 따라 관련 도구 설명만 동적으로 검색하여 LLM에 제공하는 방식입니다.
*   **RAG 기반 기술 검색은 에이전트의 확장성, 정확성, 비용 효율성을 크게 향상시킵니다.** 관련 도구만 선별하여 LLM에 제공함으로써, 에이전트는 수백, 수천 개의 도구를 혼란 없이 관리하고, 더 정확하게 올바른 도구를 선택하며, 프롬프트 길이가 짧아져 비용을 절감할 수 있습니다.

## 세부 내용
발표는 LLM 기반 에이전트가 많은 "기술" 또는 "도구"를 기억하고 적절히 사용하는 데 겪는 문제점을 지적하며 시작됩니다. 발표자는 LLM이 고정된 컨텍스트 창을 가지고 있으며, 긴 컨텍스트 내에서 특정 정보를 찾아내는 "건초 더미 속 바늘 찾기" 문제와 최근 정보에 더 집중하는 "최신 정보 편향" 때문에 에이전트가 자신의 모든 능력을 잊어버리는 경향이 있다고 설명합니다. 이는 마치 매번 모든 것을 다시 알려줘야 하는 비효율적인 인간 비서에 비유됩니다.

기존의 에이전트 도구 호출 방식은 에이전트가 사용할 수 있는 모든 도구의 상세한 설명을 LLM 프롬프트에 직접 포함하는 것입니다. 하지만 이 방식은 도구의 수가 늘어날수록 다음과 같은 문제점을 야기합니다.
1.  **컨텍스트 창 한계:** 도구 설명이 길어지면 LLM의 컨텍스트 창을 빠르게 소모합니다.
2.  **성능 저하:** 너무 많은 선택지나 관련 없는 정보가 주어지면 LLM의 추론 성능이 저하되고 혼란스러워합니다.
3.  **비용 증가:** 프롬프트 길이가 길어지면 API 호출 비용이 증가합니다.

이러한 문제에 대한 해결책으로 발표자는 "도구를 위한 RAG(Retrieval Augmented Generation)" 또는 "기술 검색(Skill Retrieval)" 패턴을 제안합니다. 이는 일반적인 RAG가 문서에서 사실 정보를 검색하는 것과 유사하게, 에이전트가 사용할 수 있는 도구 목록에서 사용자 질의에 가장 적합한 도구 설명을 검색하여 LLM에 제공하는 방식입니다.

제안된 아키텍처는 다음과 같습니다.
1.  **도구 임베딩:** 에이전트가 사용할 수 있는 모든 도구(예: `book_flight`, `get_weather`, `get_stock_price` 등)의 상세한 설명(기능, 매개변수 등)을 임베딩하여 벡터 데이터베이스에 저장합니다.
2.  **사용자 질의:** 사용자가 에이전트에게 요청을 보냅니다 (예: "SFO에서 JFK로 내일 비행기를 예약하고 싶어").
3.  **도구 라우터(Tool Router):** 사용자 질의를 받아 어떤 도구가 관련될 수 있는지 결정합니다. 이 라우터는 별도의 소형 LLM이거나, 질의를 임베딩하여 벡터 데이터베이스에서 가장 유사한 도구 임베딩을 검색하는 역할을 합니다.
4.  **관련 도구 검색:** 도구 라우터가 식별한 관련 도구 또는 벡터 검색을 통해 상위 K개(예: 3~5개)의 가장 유사한 도구 설명을 벡터 데이터베이스에서 검색합니다.
5.  **LLM에 전달:** 검색된 소수의 관련 도구 설명만 사용자 질의와 함께 메인 LLM에 전달됩니다.
6.  **도구 호출:** 메인 LLM은 제공된 관련 도구 설명과 사용자 질의를 바탕으로 가장 적절한 도구를 선택하고 호출합니다.

발표자는 데모를 통해 이 접근 방식의 효과를 시연합니다. 수많은 도구(비행기 예약, 날씨 확인, 주식 가격 조회, 이메일 전송, 캘린더 이벤트 생성 등)를 가진 에이전트가 있다고 가정합니다.
*   **RAG 없는 경우:** 모든 도구 설명을 LLM에 제공하면, LLM이 혼란스러워하거나 잘못된 도구를 선택할 가능성이 커집니다.
*   **RAG 있는 경우:** 사용자 질의("SFO에서 JFK로 내일 비행기를 예약하고 싶어")가 들어오면, 질의 임베딩을 통해 벡터 데이터베이스에서 `book_flight` 도구 설명이 가장 관련성이 높다고 판단되어 검색됩니다. 이후 `book_flight` 도구 설명만 LLM에 전달되고, LLM은 명확한 컨텍스트 내에서 정확하게 `book_flight` 도구를 선택하고 필요한 매개변수를 추출합니다.

이러한 RAG 기반 기술 검색은 에이전트가 수백, 수천 개의 도구를 확장성 있게 관리하고, 더 정확한 도구 선택을 가능하게 하며, 프롬프트 길이를 줄여 비용 효율성을 높이고, 도구 추가/제거 시 LLM을 재학습할 필요 없이 유지보수를 용이하게 하는 장점이 있습니다.

## 인상적인 대목
*   "How long can your skills be before your agent forgets what you told it?" (에이전트가 당신이 알려준 것을 잊어버리기까지 얼마나 많은 기술을 가질 수 있을까요?) — 발표 제목 자체가 LLM 에이전트의 핵심적인 한계를 명확히 짚어줍니다.
*   "It's like having a human assistant who you have to remind of everything every single time." (매번 모든 것을 다시 알려줘야 하는 인간 비서를 두는 것과 같습니다.) — LLM의 컨텍스트 한계를 인간적인 비유로 쉽게 설명합니다.
*   "The needle in the haystack problem." (건초 더미 속 바늘 찾기 문제.) — LLM이 긴 컨텍스트에서 특정 정보를 찾아내는 데 겪는 어려움을 간결하게 표현합니다.

## 실무 적용 포인트
*   **도구 수가 많은 에이전트 개발 시 RAG for Tools 패턴 적용:** 에이전트가 관리해야 할 도구(기능)의 수가 많아질 것으로 예상된다면, 모든 도구 설명을 프롬프트에 직접 넣는 대신, 도구 설명을 임베딩하여 벡터 데이터베이스에 저장하고 사용자 질의에 따라 관련 도구만 검색하여 LLM에 제공하는 RAG for Tools 아키텍처를 구현해야 합니다.
*   **도구 라우터(Tool Router) 설계 고려:** 사용자 질의에서 관련 도구를 효율적으로 식별하기 위한 "도구 라우터" 컴포넌트를 설계해야 합니다. 이는 간단한 키워드 매칭, 규칙 기반 시스템, 또는 별도의 소형 LLM을 활용하여 구현할 수 있으며, 벡터 검색과 결합하여 정확도를 높일 수 있습니다.
*   **도구 설명의 명확성과 구조화:** 각 도구의 기능, 입력 매개변수, 출력 형식 등을 명확하고 간결하게 설명하여 임베딩의 품질을 높이고, LLM이 도구를 정확하게 이해하고 활용할 수 있도록 해야 합니다.
*   **에이전트 성능 평가에 도구 선택 정확도 포함:** 에이전트의 전반적인 성능을 평가할 때, 올바른 도구를 적절한 시점에 선택하는 "도구 선택 정확도"를 핵심 지표 중 하나로 포함하여 RAG for Tools 구현의 효과를 검증해야 합니다.
