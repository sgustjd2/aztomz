# How to avoid disaster when vibe-coding a billing engine — Andrew Garvin, Stripe

🔗 https://youtu.be/mJqwmmOx4WA · 📅 2026-08-27 · 🎙 AI Engineer

## 한 줄 요약
Stripe의 앤드류 가빈은 복잡한 빌링 엔진을 "vibe-coding"하여 재앙을 피하기 위해 상태 머신, 이벤트 기반 아키텍처, 불변성, 멱등성, 철저한 테스트, 관측 가능성, DDD 원칙, 점진적 배포 및 인간 개입의 중요성을 강조한다.

## 발표자·소속
Andrew Garvin, Stripe (Staff Engineer)

## 핵심 주장
-   **빌링 시스템은 본질적으로 복잡한 상태 머신이다:** 단순히 돈을 주고받는 것을 넘어 구독, 사용량, 세금, 할인, 환불 등 다양한 상태와 전환을 포함하는 분산된 상태 기반 프로세스이며, 이를 상태 머신으로 모델링하면 이해와 설계에 도움이 된다.
-   **이벤트 기반 아키텍처와 불변성/멱등성이 필수적이다:** `customer.created`, `invoice.paid`와 같은 이벤트를 통해 시스템의 상태 변화를 유도하고, 모든 변경 사항을 불변의 기록으로 남겨 감사 가능성을 확보하며, 작업이 여러 번 실행되어도 동일한 결과를 보장하는 멱등성을 통해 시스템의 견고성과 신뢰성을 높여야 한다.
-   **철저한 테스트와 관측 가능성으로 프로덕션 환경을 보호해야 한다:** 단위, 통합, E2E 테스트를 통해 복잡한 빌링 로직의 정확성을 검증하고, 모니터링, 로깅, 트레이싱을 통해 시스템의 동작을 실시간으로 파악하여 문제를 조기에 감지하고 해결할 수 있는 능력을 갖춰야 한다.
-   **도메인 주도 설계(DDD) 원칙과 점진적 배포를 통해 복잡성을 관리해야 한다:** 유비쿼터스 언어, 바운디드 컨텍스트, 애그리게이트와 같은 DDD 원칙을 적용하여 도메인 모델을 명확히 하고, 기능 플래그를 활용한 점진적 배포로 위험을 최소화하며 변경 사항을 안전하게 출시해야 한다.
-   **인간의 개입과 시스템의 단순성을 간과해서는 안 된다:** 아무리 자동화된 시스템이라도 복잡한 문제 해결을 위해 고객 지원팀이 시스템을 이해하고 디버깅할 수 있는 도구를 제공해야 하며, 처음부터 과도하게 복잡하게 설계하기보다 단순하게 시작하여 필요에 따라 점진적으로 복잡성을 추가하는 것이 중요하다.

## 세부 내용
발표는 Stripe의 Staff Engineer인 앤드류 가빈이 빌링 엔진 개발의 어려움과 이를 극복하기 위한 전략을 설명하는 것으로 시작한다. 그는 빌링이 단순히 돈을 주고받는 것을 넘어 구독, 사용량 기반 과금, 세금, 할인, 환불, 연체 관리, 보고 등 수많은 복잡한 로직을 포함하는 "분산된 상태 기반 프로세스"라고 강조한다.

첫 번째 핵심 아이디어는 **빌링을 상태 머신으로 생각하는 것**이다. 구독의 생명 주기(예: Trial -> Active -> Past Due -> Canceled)를 예로 들며, 특정 이벤트가 상태 전환을 유발하고 각 상태에서 특정 작업이 수행된다는 모델이 빌링 시스템을 이해하고 설계하는 데 유용하다고 설명한다.

이어서 **이벤트 기반 아키텍처**의 중요성을 강조한다. `customer.created`, `subscription.created`, `invoice.paid`, `payment.failed`, `usage.reported`와 같은 이벤트들이 시스템의 상태 변화를 주도하며, 이는 시스템의 결합도를 낮추고 확장성 및 복원력을 높이는 데 기여한다고 설명한다.

**불변성(Immutability)과 감사 가능성(Auditability)**은 빌링 시스템의 신뢰성을 위한 필수 요소로 제시된다. 모든 변경 사항은 불변의 기록으로 남겨져야 하며, 감사 로그는 디버깅, 규제 준수, 고객 분쟁 해결에 있어 가장 중요한 도구라고 말한다. 인보이스 라인 아이템, 결제 시도, 구독 변경 내역 등이 불변의 기록으로 남아야 하는 예시로 언급된다.

**멱등성(Idempotency)** 또한 분산 시스템에서 재시도가 흔한 만큼 중요하다고 강조한다. `create_invoice`나 `process_payment`와 같은 작업은 여러 번 호출되어도 한 번만 실행되는 것과 동일한 결과를 보장해야 하며, 이를 위해 고유한 요청 ID를 사용하는 방법을 제안한다.

복잡한 빌링 로직의 정확성을 보장하기 위해 **철저한 테스트**가 필수적이라고 말한다. 단위 테스트, 통합 테스트, 종단 간(E2E) 테스트를 모두 활용해야 하며, 윤년, 시간대, 통화 변환과 같은 엣지 케이스를 반드시 테스트해야 한다고 조언한다. 시뮬레이션 환경의 가치도 언급한다.

**관측 가능성(Observability)**은 프로덕션 환경에서 시스템이 어떻게 동작하는지 이해하는 데 핵심적인 역할을 한다. 모니터링, 로깅, 트레이싱을 통해 시스템의 상태를 파악하고, 성공적인 결제, 실패한 결제, 구독 이탈률과 같은 핵심 지표를 대시보드로 시각화하며, 이상 징후 발생 시 알림을 설정해야 한다고 설명한다.

**도메인 주도 설계(DDD) 원칙**도 빌링 시스템의 복잡성을 관리하는 데 도움이 된다. 팀 전체와 코드베이스에서 일관된 용어를 사용하는 유비쿼터스 언어, 시스템의 각 부분에 대한 명확한 경계를 정의하는 바운디드 컨텍스트, 그리고 단일 단위로 처리되어야 하는 관련 객체들을 묶는 애그리게이트(예: `Subscription` 애그리게이트) 개념을 소개한다.

**단순성(Simplicity)**을 추구하는 것도 중요하다. "가장 좋은 코드는 코드가 없는 것이다"라는 격언을 인용하며, 처음부터 과도하게 복잡하게 설계하기보다 단순하게 시작하여 필요에 따라 점진적으로 복잡성을 추가하고 모델을 단순하게 유지할 것을 권장한다.

**점진적 배포(Gradual Rollouts)와 기능 플래그(Feature Flags)**는 변경 사항을 안전하게 출시하는 전략으로 제시된다. 변경 사항을 점진적으로 배포하고 기능 플래그를 사용하여 새로운 기능을 제어함으로써, 소수의 사용자에게만 기능을 노출하여 프로덕션 환경에서 테스트하고 위험을 완화할 수 있다고 설명한다.

마지막으로 **인간 개입(Human in the Loop)**의 중요성을 강조한다. 아무리 자동화된 시스템이라도 복잡한 빌링 문제는 인간의 개입이 필요할 수 있으므로, 고객 지원팀이 문제를 조사하고 수정할 수 있는 도구를 제공해야 한다고 말한다. "시스템을 사용하고 디버깅해야 하는 인간을 잊지 마세요"라는 메시지로 발표를 마무리한다.

## 인상적인 대목
-   "Billing is not just money in, money out. It's a distributed system of stateful processes." (빌링은 단순히 돈을 주고받는 것이 아닙니다. 그것은 상태 기반 프로세스의 분산 시스템입니다.)
-   "Audit logs are your best friend." (감사 로그는 당신의 가장 친한 친구입니다.)
-   "The best code is no code." (가장 좋은 코드는 코드가 없는 것입니다.)
-   "Don't forget about the humans who have to use and debug your system." (시스템을 사용하고 디버깅해야 하는 인간을 잊지 마세요.)

## 실무 적용 포인트
-   **빌링 로직을 상태 머신으로 모델링:** 복잡한 구독, 결제, 환불 프로세스를 상태와 이벤트 기반으로 명확히 정의하여 시스템 설계의 복잡성을 줄이고 이해도를 높인다.
-   **모든 변경 사항에 대한 불변의 감사 로그 구현:** 데이터베이스 변경 시 `created_at`, `updated_at`뿐만 아니라 `event_type`, `old_value`, `new_value`, `actor` 등을 기록하는 별도의 감사 테이블이나 이벤트 소싱 패턴을 활용하여 모든 상태 변화를 추적 가능하게 한다.
-   **멱등성 보장을 위한 고유 요청 ID 활용:** 외부 시스템과의 연동이나 API 호출 시 클라이언트가 제공하는 고유한 요청 ID를 사용하여 중복 요청으로 인한 부작용을 방지하고, 서버 측에서도 이를 검증하는 로직을 구현한다.
-   **기능 플래그를 통한 점진적 배포 및 A/B 테스트:** 새로운 빌링 기능을 개발할 때 기능 플래그를 사용하여 특정 사용자 그룹에만 기능을 노출하고, 프로덕션 환경에서 실제 데이터를 기반으로 테스트하며 위험을 최소화하고 피드백을 수집한다.
