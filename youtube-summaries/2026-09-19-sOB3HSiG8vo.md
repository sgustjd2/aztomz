# Routing LLM Inference in Production: From Engine Signals to Policy — Qianru Lao & Lu Zhang, OpenAI

🔗 https://youtu.be/sOB3HSiG8vo · 📅 2026-09-19 · 🎙 AI Engineer

## 한 줄 요약
OpenAI는 LLM 추론 시스템의 효율성과 안정성을 높이기 위해 엔진 신호에 기반한 주기적 피드백 루프 방식에서 제어 평면과 데이터 평면을 분리하여 전역적으로 최적화된 라우팅 정책을 사용하는 아키텍처로 전환했습니다.

## 발표자·소속
- Qianru Lao, OpenAI (Inference)
- Lu Zhang, OpenAI (Inference)

## 핵심 주장
- **LLM 추론 라우팅의 복잡성:** LLM 추론은 엔진의 이질성(하드웨어, 용량, 상태), 캐시 인식(KV 캐시), 지리적 분산 등으로 인해 단순한 로드 밸런싱보다 훨씬 복잡한 라우팅 문제를 야기합니다. 성능, 안정성, 지역성, 캐시 인식의 균형을 맞추는 것이 중요합니다.
- **초기 피드백 루프의 한계:** 초기 시스템은 엔진 신호(TTFT, TBOT, 상태, 활용도)를 기반으로 가중치를 주기적으로 업데이트하는 PID 제어기 유사 피드백 루프를 사용했습니다. 이는 자체 적응적이었지만, 라우팅 결정의 추론이 어렵고, 부하가 고르지 않게 분산되며, 느린 진동으로 인해 KV 캐시 적중률에 부정적인 영향을 미쳤습니다.
- **분리된 제어/데이터 평면 아키텍처 도입:** 이러한 한계를 극복하기 위해 제어 평면(전역 최적화)과 데이터 평면(로컬 라우팅 결정)을 분리한 아키텍처를 채택했습니다. 이를 통해 요청 처리(동기)와 라우팅 정책 업데이트(비동기)를 분리하여 성능과 최적화 효율성을 동시에 달성했습니다.
- **최적화기의 역할:** 최적화기는 CPU 클러스터의 요청 수요, 각 엔진까지의 네트워크 지연 시간, 엔진 용량 및 상태, TTFT/TBOT 지연 시간 프로필 등 다양한 신호를 입력받아 각 CPU 클러스터가 각 GPU 엔진으로 트래픽을 라우팅해야 하는 비율을 나타내는 라우팅 가중치를 계산합니다. 목표는 모든 라우팅된 트래픽에 걸쳐 예상되는 종단 간 지연 시간을 최소화하고 네트워크 거리와 엔진 측 지연 시간의 균형을 맞추는 것입니다.
- **생산 환경 보호 메커니즘:** 실제 생산 환경의 예측 불가능한 상황(클러스터 장애, 노드 성능 저하, 네트워크 문제)에 대비하여 페널티(이상 엔진의 가중치 감소), 캡이 있는 재시도(재시도 폭주 방지), 로드 셰딩(시스템의 정상적인 성능 저하 유도)과 같은 보호 메커니즘을 구현하여 시스템 안정성을 유지합니다.

## 세부 내용
발표는 OpenAI 추론 팀의 Lu Zhang과 Qianru Lao가 LLM 추론 시스템의 로드 밸런싱 아키텍처 진화를 설명하는 것으로 시작됩니다.

**추론 로드 밸런서(ILB) 소개:**
ILB는 사용자 요청을 처리하는 프론트엔드 CPU 클러스터와 실제 추론을 수행하는 백엔드 GPU 엔진 클러스터 사이에 위치합니다. ILB의 주요 역할은 들어오는 요청에 대해 최적의 추론 엔진을 선택하고 요청을 해당 엔진으로 프록시하는 것입니다. 특히, 엔진 선택은 모델의 종류, TTFT(첫 번째 토큰까지의 시간), TBOT(토큰 간 시간), 엔진 상태, 활용도, KV 캐시 인식(동일 대화의 후속 요청을 동일 엔진으로 라우팅하여 재계산 방지 및 효율성 증대) 등 다양한 실시간 신호를 고려해야 하므로 복잡한 문제입니다.

**초기 로드 밸런싱 방식: 주기적 피드백 루프:**
초기 시스템에서는 추론 요청이 들어오면 먼저 기능(capability)과 같은 제약 조건에 따라 적격 엔진을 필터링합니다. 그런 다음 가중치 일관 해싱(weighted consistent hashing)을 사용하여 최적의 엔진을 선택합니다. 이 가중치는 주기적인 피드백 루프를 통해 업데이트됩니다. 추론 엔진은 TTFT, TBOT, 상태, 활용도 등 다양한 신호를 제어기에 보고합니다. 제어기는 이러한 신호를 지수 가중 이동 평균(EWMA)으로 평활화하고 성능 점수를 계산한 후, 이 점수를 전체 플릿 평균과 비교하여 각 엔진의 가중치를 조정합니다(성능이 좋으면 가중치 증가, 나쁘면 감소). 이는 PID 제어기와 유사하게 시스템을 원하는 상태로 유도하는 제어 루프 역할을 합니다.

**초기 방식의 장단점:**
**장점:** 많은 신호를 고려하고, 라우팅 제약 조건이 자연스럽게 균형을 이루며, 자체 적응적이고, "그냥 작동"하는 경향이 있습니다.
**단점:** 라우팅 결정이나 제어에 대한 추론이 어렵고, 특히 혼합 플릿(다양한 GPU SKU)의 경우 부하가 항상 균등하게 분산되지 않습니다. 또한, 피드백 루프는 느린 진동을 유발하여 KV 캐시 적중률에 부정적인 영향을 미칠 수 있습니다. 가중치 조정이 다른 부분에 의도치 않은 영향을 미칠 수 있어 미세 조정이 어렵습니다.

**새로운 아키텍처: 제어 평면 및 데이터 평면 분리:**
이러한 한계를 극복하기 위해 OpenAI는 제어 평면과 데이터 평면을 분리하는 새로운 아키텍처를 설계했습니다.
- **데이터 평면:** CPU 클러스터에 로컬로 존재하며, 들어오는 요청을 즉시 처리합니다. 엔진 선택기는 제어 평면에서 비동기적으로 가져온 최신 라우팅 상태(후보 엔진 및 라우팅 가중치)를 기반으로 로컬에서 라우팅 결정을 내립니다. 요청은 데이터 평면에서 대기하지 않고 즉시 GPU 플릿으로 전달됩니다.
- **제어 평면:** 시스템 전체에 대한 전역적인 시야를 가지고 라우팅 최적화를 담당합니다. 데이터 로더는 GPU 엔진에서 수집된 실시간 엔진 신호(TTFT, TBOT, 복제본 수, 엔진 상태 등)와 네트워크 오버헤드, 그리고 용량 및 지연 시간 프로필에 대한 오프라인 회귀 분석 결과를 결합합니다. 최적화기는 이 데이터를 사용하여 각 CPU 클러스터가 각 GPU 엔진으로 트래픽을 할당해야 하는 비율을 나타내는 라우팅 가중치를 계산하고 이를 데이터 평면으로 게시합니다.

**시스템의 세 가지 경로:**
1. **추론 요청 경로 (동기, 요청당):** CPU 클러스터에서 요청이 들어오면 데이터 평면의 엔진 선택기가 로컬 라우팅 상태를 기반으로 엔진을 선택하고 요청을 GPU 엔진으로 라우팅합니다. 이 경로는 빠르고 로컬에서 이루어집니다.
2. **엔진 신호 경로 (비동기 피드백):** GPU 엔진은 실시간 신호를 제어 평면으로 보내고, 제어 평면은 이를 집계하여 데이터 로더에 공급합니다.
3. **라우팅 가중치 경로 (비동기 풀):** 제어 평면이 계산한 라우팅 가중치는 게시되고, 데이터 평면은 이를 비동기적으로 풀(pull)하여 로컬 캐시를 업데이트합니다.

이러한 분리를 통해 동기적인 요청 처리 경로의 지연 시간을 최소화하면서도, 비동기적인 제어 루프를 통해 전역적인 최적화를 지속적으로 수행할 수 있습니다.

**"가장 가까운 엔진만" 라우팅 방식의 실패 사례:**
발표자는 지리적으로 분산된 세 지역의 CPU 클러스터와 엔진을 예시로 들어 "가장 가까운 엔진만" 라우팅하는 방식의 한계를 설명합니다.
- **지역 1:** CPU 클러스터 A의 수요(90 RPS)가 엔진 A의 용량(100 RPS)보다 낮아 문제가 없습니다.
- **지역 2:** CPU 클러스터 B의 수요(120 RPS)가 엔진 B의 용량(100 RPS)을 초과하여 20 RPS가 엔진 B에서 대기하게 됩니다.
- **지역 3:** CPU 클러스터 C의 수요(40 RPS)가 엔진 C의 용량(80 RPS)보다 낮아 40 RPS의 여유가 있습니다.
이 경우, 지역 2의 초과 트래픽 20 RPS를 지역 3의 여유 있는 엔진 C로 라우팅하면 네트워크 거리가 늘어나지만, 엔진 B에서의 대기 시간을 피하여 종단 간 지연 시간을 줄일 수 있습니다. 이는 단순히 가장 가까운 엔진으로 라우팅하는 것보다 전역적인 최적화가 필요함을 보여줍니다.

**최적화기: 신호에서 가중치로:**
최적화기는 다음 입력을 받습니다.
- 각 CPU 클러스터의 요청 수요
- 각 엔진까지의 네트워크 지연 시간
- 각 엔진의 가용 용량 및 상태
- 부하 증가에 따른 엔진 측 지연 시간 변화를 나타내는 TTFT/TBOT 지연 시간 프로필
최적화의 목표는 모든 라우팅된 트래픽에 걸쳐 예상되는 종단 간 지연 시간을 최소화하고, 네트워크 거리와 엔진 측 지연 시간의 균형을 맞추는 것입니다. 이는 모든 수요를 라우팅하고, 엔진 용량을 초과하지 않으며, 라우팅 가중치가 음수가 아니어야 한다는 제약 조건을 따릅니다.

**보호 메커니즘:**
시스템의 안정성을 보장하기 위해 다음과 같은 보호 메커니즘이 적용됩니다.
- **페널티:** 특정 엔진이 이상치(높은 오류율, 높은 지연 시간)로 감지되면 해당 엔진으로의 라우팅 가중치를 줄여 트래픽을 분산시킵니다. 이는 엔진이 스스로 복구하거나 수동 개입을 통해 문제를 해결할 시간을 줍니다.
- **캡이 있는 재시도(Retry with cap):** 재시도는 일반적인 문제 해결 기법이지만, 시스템이 과부하 상태일 때 과도한 재시도는 "재시도 폭주(retry storm)"를 유발하여 상황을 악화시킬 수 있습니다. 이를 방지하기 위해 재시도 횟수에 동적인 캡(예산)을 설정합니다. 시스템이 건강할 때는 더 많은 재시도를 허용하고, 과부하일 때는 재시도를 제한합니다.
- **로드 셰딩(Load shedding):** 모든 다른 방법이 실패하고 시스템 용량이 수요를 감당할 수 없을 때 최후의 수단으로 사용됩니다. 트래픽의 일부를 의도적으로 차단하여 시스템이 완전히 붕괴하는 대신 점진적으로 성능이 저하되도록 합니다.

## 인상적인 대목

## 실무 적용 포인트
- **제어 평면/데이터 평면 분리:** 고성능이 요구되는 LLM 추론 시스템에서 요청 처리의 동기 경로와 라우팅 정책 업데이트의 비동기 경로를 분리하여 시스템의 반응성과 최적화 효율성을 동시에 확보할 수 있습니다.
- **종단 간 지연 시간 최적화:** 네트워크 지연 시간뿐만 아니라 엔진 측 지연 시간 프로필(부하에 따른 성능 변화)까지 고려하여 트래픽을 할당하는 최적화 기법을 도입하여 실제 사용자 경험을 개선할 수 있습니다.
- **동적 재시도 캡:** 시스템 부하 상태에 따라 재시도 허용량을 동적으로 조절하는 정책을 구현하여 재시도 폭주를 방지하고 시스템 안정성을 높일 수 있습니다.
- **다양한 신호 활용:** TTFT, TBOT, 엔진 상태, 용량, 네트워크 오버헤드 등 다양한 실시간 및 오프라인 신호를 통합하여 라우팅 결정의 정확성과 적응성을 향상시킬 수 있습니다.
