## 핵심 주장
- **LLM 기반 에이전트의 안전하고 신뢰성 있는 도구 사용 설계**: LLM이 금융 시스템과 같은 고위험 환경에서 API 도구를 사용할 때 환각이나 오류를 방지하기 위해, 단순한 API 호출을 넘어선 정교한 도구 정의, 강력한 유효성 검사, 그리고 인간 개입을 통합해야 한다. 이는 에이전트가 실제 세계와 상호작용할 때 필수적인 요소이다.
- **다단계 유효성 검사를 통한 에이전트 행동 제어**: 에이전트가 제안하는 모든 행동은 구문적, 의미적, 안전성 측면에서 다단계 유효성 검사를 거쳐야 한다. 이는 API 스키마 준수, 비즈니스 로직 적합성, 그리고 잠재적 위험 방지를 포함하여 에이전트의 오작동을 최소화하고 신뢰성을 확보한다.
- **고위험 작업에 대한 인간 개입의 필수성**: 데이터 변경을 수반하는 환불이나 결제와 같은 중요한 금융 작업에는 항상 인간의 명시적인 승인이 필요하다. 에이전트는 제안된 작업을 명확하게 요약하여 인간이 쉽게 검토하고 결정할 수 있도록 제시함으로써, 통제력을 유지하고 잠재적 오류의 영향을 완화한다.
- **에이전트 친화적인 도구 정의 및 관리**: 복잡한 API를 LLM이 이해하고 활용하기 쉽도록 "에이전트 친화적인" 방식으로 래핑하고 설명해야 한다. 이는 OpenAPI 사양을 단순화하고, 각 도구에 대한 명확한 설명과 사용 예시를 제공하는 도구 레지스트리를 통해 이루어지며, LLM의 도구 선택 및 매개변수 추출 정확도를 높인다.

## 세부 내용
발표는 AI 에이전트가 Stripe의 결제 시스템과 같은 실제 금융 환경에서 안전하고 신뢰성 있게 작업을 수행하도록 가르치는 방법에 초점을 맞춘다. 발표자는 LLM의 강력한 능력에도 불구하고, 금융 거래와 같은 고위험 영역에서는 환각(hallucination)이나 오류의 가능성 때문에 추가적인 안전장치가 필수적이라고 강조한다.

Stripe의 접근 방식은 LLM을 "오케스트레이터"로 활용하여 사용자 요청을 해석하고 적절한 도구를 선택하며, 필요한 매개변수를 추출하는 것이다. 이 과정에서 핵심은 **도구 사용(Tool Use)**과 **안전성 및 신뢰성(Safety & Reliability)** 확보이다.

**도구 정의 및 선택**:
Stripe는 자사의 방대한 API를 LLM이 이해하기 쉽도록 "에이전트 친화적인" 도구로 래핑한다. 이는 단순히 OpenAPI 사양을 넘어서, 각 도구의 목적, 사용 방법, 필요한 매개변수 등을 명확하게 설명하는 과정을 포함한다. LLM은 이 설명을 바탕으로 사용자 요청에 가장 적합한 도구를 선택한다. 예를 들어, "고객 X에게 마지막 청구를 환불해 줘"라는 요청이 들어오면, LLM은 `refund_charge`와 같은 도구를 식별한다.

**매개변수 추출 및 유효성 검사**:
도구가 선택되면, LLM은 사용자 요청에서 해당 도구에 필요한 매개변수(예: 고객 ID, 환불 금액)를 추출한다. 이 단계에서 **유효성 검사(Validation)**가 매우 중요하게 작용한다.
1.  **구문적 유효성 검사 (Syntactic Validation)**: 추출된 매개변수가 API 스키마에 정의된 형식과 데이터 타입을 준수하는지 확인한다.
2.  **의미적 유효성 검사 (Semantic Validation)**: 매개변수의 값이 비즈니스 로직상 타당한지 확인한다. 예를 들어, 환불 금액이 원래 청구 금액을 초과하지 않는지, 유효한 고객 ID인지 등을 검사한다.
3.  **안전성 유효성 검사 (Safety Validation)**: 제안된 작업이 보안 정책, 사용자 권한, 속도 제한(rate limits) 등 안전성 기준을 충족하는지 확인한다. 이는 잠재적인 악용이나 의도치 않은 피해를 방지하는 데 필수적이다.

**인간 개입 (Human-in-the-Loop)**:
데이터를 변경하는 환불, 결제 생성, 송장 발행과 같은 고위험 작업의 경우, 에이전트는 최종 실행 전에 반드시 인간의 승인을 요청한다. 에이전트는 제안된 작업을 명확하고 간결하게 요약하여 사용자에게 제시하며, 사용자는 이를 검토하고 승인하거나 거부할 수 있다. 이는 에이전트의 오작동으로 인한 재정적 손실을 방지하는 중요한 안전장치이다.

**데모 예시**:
발표에서는 "고객 X의 마지막 청구를 환불해 줘"라는 시나리오를 통해 에이전트의 작동 방식을 시연한다. 에이전트는 고객을 식별하고, 마지막 청구를 찾아내며, 환불 작업을 제안한다. 이때, 단순히 "환불했습니다"라고 응답하는 것이 아니라, "고객 X의 [청구 ID]에 대해 [금액]을 환불하려고 합니다. 계속하시겠습니까?"와 같이 구체적인 실행 계획을 제시하여 인간의 확인을 받는다. 또 다른 예시로 "고객 Y에게 Z달러짜리 송장을 만들어 줘"라는 요청에 대해 에이전트가 송장 생성 도구를 사용하고 필요한 정보를 추출하여 인간에게 확인을 요청하는 과정을 보여준다.

**아키텍처 및 도구**:
발표에서 구체적인 아키텍처 다이어그램이나 코드 스니펫은 제시되지 않았지만, LLM이 오케스트레이터 역할을 하며, 도구 레지스트리(tool registry)를 통해 에이전트 친화적인 API 정의를 관리하고, 다단계 유효성 검사 모듈을 거쳐 최종적으로 Stripe API를 호출하는 흐름을 설명한다.

## 실무 적용 포인트
- **도구 정의의 명확화 및 단순화**: 복잡한 내부 API를 LLM이 이해하기 쉽도록 간결하고 명확한 설명과 함께 "에이전트 친화적인" 도구로 래핑하여 제공해야 한다. 이는 LLM의 도구 선택 및 매개변수 추출 정확도를 높인다.
- **다단계 유효성 검사 파이프라인 구축**: LLM이 제안하는 모든 작업에 대해 구문적(API 스키마), 의미적(비즈니스 로직), 안전성(보안, 권한) 측면에서 다단계 유효성 검사 로직을 구현하여 에이전트의 오작동 및 위험을 최소화해야 한다.
- **고위험 작업에 대한 인간 개입 설계**: 데이터 변경이나 재정적 영향을 미치는 작업에는 반드시 인간의 명시적인 승인 단계를 포함해야 한다. 이때 에이전트는 제안된 작업을 명확하고 간결하게 요약하여 인간이 쉽게 이해하고 결정할 수 있도록 제시해야 한다.
- **상태 관리 및 컨텍스트 유지**: 에이전트가 다중 턴 대화에서 이전 대화의 맥락을 기억하고 활용할 수 있도록 상태 관리 메커니즘을 설계하여 보다 자연스럽고 효율적인 상호작용을 가능하게 해야 한다.
