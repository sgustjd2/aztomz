# Your Coding Agent Can't Undo Its Own Mistakes - Tanmay Sah & Dolly Sah

🔗 https://youtu.be/BT1Mo-fD-g0 · 📅 2026-11-08 · 🎙 AI Engineer

## 한 줄 요약
코딩 에이전트의 자율성이 증가함에 따라, 단순히 작업을 완료하는 것을 넘어 에이전트가 외부 시스템에 미치는 영향을 추적하고 오류 발생 시 안정적으로 복구할 수 있는 '실행 취소(Undo)' 메커니즘이 필수적이며, 이를 위한 EvoUndo 알고리즘이 제안되었다.

## 발표자·소속
- Tanmay Sah, PhD
- Dolly Sah

## 핵심 주장
- **작업 역량과 복구 능력은 별개**: 코딩 에이전트가 특정 작업을 성공적으로 완료할 수 있다고 해서, 오류 발생 시 시스템을 이전 상태로 안정적으로 복구할 수 있다는 것을 의미하지 않는다.
- **Git만으로는 불충분한 복구**: Git과 같은 버전 관리 시스템은 코드 변경 사항을 되돌릴 수 있지만, 에이전트가 수행하는 외부 API 호출, 런타임 설정 변경, 알림 발송 등 Git 외부의 부수 효과(side effects)는 되돌릴 수 없다.
- **실패 단계에 따른 맞춤형 복구 전략 필요**: 돌연변이(mutation) 발생 전, 발생 중, 또는 커밋 후 응답 없음(no ACK) 등 실패가 발생하는 시점에 따라 필요한 복구 전략(재시도, 복원, 보상, 중단/에스컬레이션)이 달라진다.
- **EvoUndo 알고리즘을 통한 복구 가능성 향상**: EvoUndo는 변경 전 상태를 기록(witness), 돌연변이 적용(mutate), 복구(recover), 그리고 복구된 상태를 검증(verify)하는 구조화된 프로세스를 통해 에이전트의 복구 능력을 크게 향상시킨다.

## 세부 내용

발표는 코딩 에이전트가 `service/config.py` 파일을 수정하여 `timeout` 값을 30에서 600으로 변경하는 데모로 시작한다. 패치가 적용되고 변경 사항이 커밋되었지만, 다운스트림 검사가 실패한다. 에이전트가 `agent.undo()` 명령을 시도하지만, "UNDO NOT AVAILABLE" 메시지와 함께 복구가 불가능함을 보여준다.

발표자는 에이전트가 리포지토리 이슈를 해결하고, 패치를 적용하고, 테스트를 통과하며, 릴리스 태그까지 생성했지만, 다운스트림 통합이 실패하는 시나리오를 제시한다. 여기서 Git이 리포지토리 내의 변경 사항은 추적할 수 있지만, 외부 API 호출, 런타임 도구 레지스트리 수정, 런타임 리스너 변경, 알림 발송 등 Git 외부에서 발생한 변경 사항은 알지 못한다는 문제가 제기된다. 단순히 작업을 재시도하는 것은 이미 발생한 일을 되돌리지 못한다.

"UndoBench"라는 연구를 통해, 에이전트가 작업을 성공적으로 완료하는 능력(83.54%의 성공률)과 실패로부터 복구하는 능력(46.72%의 복구율) 사이에 큰 차이가 있음을 발견했다. 이는 성공적인 에이전트가 반드시 복구 가능한 에이전트는 아니라는 것을 시사한다.

발표자는 타임아웃이 롤백과 동일하지 않다는 점을 강조하며, 에이전트가 외부 시스템에 티켓 생성을 요청했을 때 응답이 손실되는 시나리오를 시각적으로 보여준다. 서버는 티켓을 성공적으로 생성했지만, 에이전트는 응답을 받지 못해 타임아웃으로 인식한다. 에이전트가 이를 알지 못하고 재시도하면, 동일한 티켓이 중복 생성되는 부작용이 발생한다. UndoBench 연구에서 이러한 단순 재시도로 인한 중복 효과가 53.33%의 경우에서 발생했다.

실패의 단계에 따라 복구 전략이 달라져야 한다고 설명한다.
- **돌연변이 발생 전(BEFORE mutation)**: 영구적인 효과가 발생하지 않았으므로 안전하게 재시도할 수 있다.
- **돌연변이 발생 중(DURING mutation)**: 외부 상태가 부분적으로 업데이트되었을 수 있으므로, 상태를 검사하고 조정해야 한다.
- **커밋 후 응답 없음(AFTER commit - no ACK)**: 작업은 완료되었을 수 있지만 에이전트가 알지 못하므로, 검증하거나 중복을 제거해야 한다.
단일한 일반 재시도 정책으로는 이 세 가지 다른 실패 모드를 해결할 수 없다.

Git revert는 리포지토리 상태만 복원할 수 있는 '한 가지 종류의 실행 취소'일 뿐이다. 코딩 에이전트는 런타임 상태(도구 레지스트리, 미들웨어, 프롬프트, 설정)와 외부 효과(배포, DB 쓰기, 메시지, 결제)도 변경한다. Git revert는 이러한 모든 변경 사항을 되돌리지 못한다. 복구 메커니즘은 에이전트가 생성한 효과의 유형과 일치해야 한다.

코딩 에이전트는 프롬프트, 도구, 미들웨어, 리스너, 리소스, 라우팅 설정 등 에이전트 자체의 실행 환경(하네스)도 변경할 수 있다. 이러한 변경은 에이전트의 성능을 향상시킬 수 있지만, 동시에 복구를 더 어렵게 만들 수도 있다. 즉, 에이전트가 더 유능해지면서도 복구 가능성은 낮아질 수 있다.

'실행 취소'는 단순히 역 명령 이상을 필요로 한다. 예를 들어, `timeout` 값을 30에서 60으로 변경하는 경우, 실행 취소를 위해서는 원래 값이 30이었다는 것을 알아야 한다. EvoUndo는 돌연변이 적용 전에 이전 값, 존재 여부, 관련 구조를 캡처하는 '상태 증인(state witness)'을 활용한다. 이 증인은 원래 상태를 복원하는 데 필요한 정보를 제공하고, 나중에 복구가 실제로 작동했는지 검증한다.

개선된 하네스가 얼마나 자주 복구에 실패하는지 조사한 결과, 600개의 자가 진화(self-evolution) 작업 중 478개가 역량 향상 돌연변이를 생성했지만, 이 중 197개(41.2%)는 복구 검증에 실패했다. 이는 에이전트의 역량을 향상시키는 돌연변이가 시스템을 복구 불가능한 상태로 만들 수 있음을 보여준다.

"실행 취소를 고쳐달라"는 요청이 작동하지 않은 이유는, LLM이 런타임 복구 언어가 허용하지 않는 작업을 합성할 수 없기 때문이다. 더 많은 프롬프트를 제공한다고 해서 누락된 의미론이 생성되는 것은 아니다. 병목 현상은 누락된 상태 증거 또는 표현력이 부족한 복구 작업에 있을 수 있다.

두 가지 병목 현상과 두 가지 엔지니어링 지렛대가 확인되었다.
1.  **상태 그라운딩(State Grounding)**: 정확한 상태 위치, 잔여물, 효과 순서를 지적하는 것. 기본 언어 해결 가능 하위 그룹에서 0/48에서 38/48로 복구율이 향상되었다.
2.  **복구 표현력(Recovery Expressivity)**: 미들웨어, 리스너, 파일, 리소스 및 순서가 지정된 역전(reversal)을 표현 가능하게 만드는 것. 풍부한 언어 전용 하위 그룹에서 0/143에서 142/143로 복구율이 크게 향상되었다.

더 나은 실행 취소 메커니즘이 실패한 돌연변이를 구제할 수 있는지에 대한 질문에, EvoUndo는 197개의 복구 결함 돌연변이 중 180개(91.4%)를 성공적으로 복구했다. 이는 원래 언어로는 0/197이었던 것에 비해 큰 발전이다. 결과적으로, 600개 작업 중 초기 허용 가능한 돌연변이 수가 281개에서 L1 복구 후 461개로 증가하여, 총 30%p의 절대적인 수익 증가를 가져왔다.

EvoUndo 알고리즘은 '복구 가능성 제약적 승인(recoverability-constrained admission)'을 따른다.
1.  **제안(PROPOSE)**: 에이전트가 하네스 돌연변이(전방 후보 + 선언된 효과 계약)를 제안한다.
2.  **기록(RECORD)**: 돌연변이 적용 전에 원래 상태를 나타내는 '상태 증인'을 캡처한다.
3.  **테스트(TEST)**: 테스트 환경에서 돌연변이를 적용하고, 복구 계획을 실행하여 원래 상태로 돌아가는지 확인한다.
4.  **독립 검증(INDEPENDENT VERIFICATION)**: 복구된 상태가 원래 상태와 동일한지 독립적으로 검증한다. 효과 범위, ID 및 OOD 복구 테스트, 승인 임계값을 확인한다.
이러한 검증을 통과하면 변경 사항을 **승인(ADMIT)**하고, 그렇지 않으면 복구 사양을 개선하거나 변경 사항을 **수리/거부(REPAIR/REJECT)**한다. 이 방식은 복구 가능성이 에이전트의 변경 승인 결정의 일부가 되도록 한다.

EvoUndo의 작동 예시로, `timeout` 값을 30에서 60으로 변경하는 과정이 다시 시연된다. EvoUndo는 변경 전 `timeout=30`을 상태 증인으로 기록하고, `timeout=60`으로 돌연변이를 적용한다. 이후 `undo.restore(w.timeout)` 명령으로 증인을 사용하여 `timeout=30`으로 복원하고, `verify(recovered == original)`로 복구된 상태가 원래 상태와 일치하는지 검증한다.

복구 전략은 단순히 재시도(RETRY)뿐만 아니라, 상태를 복원(RESTORE)하거나, 외부 효과를 보상(COMPENSATE)하거나, 복구가 불가능할 경우 중단 및 에스컬레이션(STOP / ESCALATE)하는 등 상황에 따라 적절한 메커니즘을 선택해야 한다.

세 가지 주요 연구 결과는 다음과 같다.
1.  UndoBench: 작업 역량 ≠ 복구.
2.  EvoUndo 알고리즘: 증인(witness) → 돌연변이(mutate) → 복구(recover) → 검증(verify).
3.  복구가 통과될 때만 진화(evolution)를 승인한다.

마지막으로, 발표는 처음의 에이전트가 "I NEED AN UNDO BUTTON!"이라고 외치던 장면으로 돌아가, 이제 EvoUndo를 통해 에이전트가 실행 취소 버튼을 갖게 되었음을 보여준다. 에이전트가 잘못된 변경을 저질렀을 때, 실행 취소 버튼을 누르면 원래의 유효한 상태로 복구되고 검증된다. 이는 에이전트가 단순히 작업을 실행하는 것을 넘어, 문제가 발생했을 때 스스로 복구할 수 있는 근본적인 역량을 갖게 되었음을 의미한다.

## 인상적인 대목
- "A successful agent is not necessarily a recoverable agent." (성공적인 에이전트가 반드시 복구 가능한 에이전트는 아니다.)
- "One request. Two tickets. A timeout doesn't mean rollback." (하나의 요청. 두 개의 티켓. 타임아웃이 롤백을 의미하지는 않는다.)
- "One generic retry policy cannot solve three different failure modes." (하나의 일반적인 재시도 정책으로는 세 가지 다른 실패 모드를 해결할 수 없다.)
- "Reverting code does not reverse every action the agent took." (코드를 되돌리는 것이 에이전트가 수행한 모든 작업을 되돌리지는 않는다.)
- "A forward-improving mutation can still destroy the information needed to reverse it." (전방향으로 개선되는 돌연변이가 이를 되돌리는 데 필요한 정보를 파괴할 수도 있다.)
- "An LLM cannot synthesize an operation that the runtime recovery language does not allow. More prompting does not create missing semantics." (LLM은 런타임 복구 언어가 허용하지 않는 작업을 합성할 수 없다. 더 많은 프롬프팅이 누락된 의미론을 생성하지는 않는다.)

## 실무 적용 포인트
- **에이전트 개발 시 복구 가능성 고려**: 에이전트의 기능 개발 단계부터 성공적인 작업 완료뿐만 아니라, 실패 시의 복구 메커니즘을 함께 설계하고 테스트해야 한다.
- **Git 외부 변경 사항 추적 및 관리**: 에이전트가 Git 리포지토리 외부에 영향을 미치는 작업(API 호출, DB 변경, 런타임 설정 등)을 수행할 경우, 이러한 변경 사항의 이전 상태를 기록하고 복구할 수 있는 별도의 메커니즘(예: 상태 증인)을 도입해야 한다.
- **실패 유형별 맞춤형 복구 전략 구현**: 모든 실패에 동일한 재시도 정책을 적용하는 대신, 실패가 발생한 시점(돌연변이 전/중/후)과 외부 시스템의 상태를 고려하여 재시도, 복원, 보상, 중단/에스컬레이션 등 적절한 복구 전략을 선택하고 구현해야 한다.
- **복구 언어의 표현력 확장**: 에이전트의 런타임 환경(하네스) 변경이나 복잡한 외부 효과를 되돌리기 위해서는, 기존의 단순한 역 명령을 넘어선 풍부한 표현력을 가진 복구 언어와 도구를 개발하거나 활용하는 것이 중요하다.
