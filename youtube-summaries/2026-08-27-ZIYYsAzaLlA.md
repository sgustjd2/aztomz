# Building the Engine While Flying the Plane: Launching the Figma MCP Server — Jesse Lumarie, Figma

🔗 https://youtu.be/ZIYYsAzaLlA · 📅 2026-08-27 · 🎙 AI Engineer

## 한 줄 요약
Figma는 실시간 협업 엔진의 확장성 및 안정성 한계를 극복하기 위해 기존 모놀리식 서버를 MCP(Multi-Client Protocol) 기반의 분산 아키텍처로 무중단 전환한 경험을 공유합니다.

## 발표자·소속
Jesse Lumarie, Figma (Staff Engineer)

## 핵심 주장
- **기존 모놀리식 협업 엔진의 한계 극복**: Figma의 기존 "Document Server"는 단일 문서당 하나의 서버로 구성되어 확장성, 안정성, 운영 복잡성 측면에서 한계에 도달했습니다. 사용자 증가와 문서 크기 증대로 인해 새로운 아키텍처가 필수적이었습니다.
- **MCP(Multi-Client Protocol) 기반 분산 아키텍처 도입**: MCP는 문서 상태 관리와 협업 로직을 분리하여, 협업 로직을 처리하는 MCP 서버를 무상태(또는 거의 무상태)로 만들고 스토리지 계층을 통해 문서 데이터를 관리합니다. 이는 수평적 확장성과 안정성 향상을 가능하게 합니다.
- **"비행 중 엔진 교체" 전략으로 무중단 마이그레이션 수행**: Figma는 서비스를 중단할 수 없었으므로, 새로운 MCP 서버와 기존 Document Server가 동시에 작동하는 "이중 쓰기(dual write)" 및 "조정(reconciliation)" 전략을 통해 점진적으로 문서를 마이그레이션했습니다. 이를 통해 데이터 일관성을 유지하며 라이브 시스템을 전환했습니다.
- **초기 관측 가능성(Observability) 투자 및 점진적 접근의 중요성**: 복잡한 시스템 전환 과정에서 성능 문제, 디버깅 어려움 등 예상치 못한 도전 과제에 직면했습니다. 발표자는 초기 단계부터 로깅, 메트릭, 트레이싱 등 관측 가능성 도구에 투자하고, 작은 단위부터 시작하여 점진적으로 확장하는 접근 방식이 성공적인 마이그레이션에 필수적임을 강조했습니다.

## 세부 내용
발표는 Figma의 실시간 협업 엔진인 "멀티플레이어 엔진"의 진화 과정을 다룹니다. Figma는 사용자들이 실시간으로 함께 디자인 작업을 할 수 있도록 하는 핵심 기능으로, 클라이언트가 서버에 작업(operations, ops)을 보내면 서버가 이를 적용하고 다른 클라이언트들에게 브로드캐스트하는 방식으로 작동합니다.

기존 엔진은 "Document Server"라고 불리는 모놀리식 아키텍처였습니다. 각 문서마다 하나의 서버가 할당되어 일관성 유지에는 유리했으나, 사용자 수와 문서 크기가 증가함에 따라 확장성(단일 서버의 부하), 안정성(단일 장애점), 운영 복잡성(수많은 서버 관리) 측면에서 심각한 한계에 봉착했습니다.

이러한 문제를 해결하기 위해 Figma는 MCP(Multi-Client Protocol) 서버를 구축했습니다. MCP의 핵심은 문서 상태 관리(데이터 저장)와 협업 로직(ops 적용, 충돌 해결, 브로드캐스트)을 분리하는 것입니다. 새로운 아키텍처에서 MCP 서버는 주로 협업 로직을 담당하며, 문서 데이터는 별도의 스토리지 계층에 저장됩니다. 이를 통해 MCP 서버는 무상태(stateless) 또는 거의 무상태(near-stateless)가 되어 수평적 확장이 용이해지고, 시스템의 전반적인 안정성과 성능이 향상됩니다.

가장 큰 도전 과제는 "비행 중 엔진 교체"라는 비유처럼, 서비스를 중단하지 않고 기존 시스템에서 새로운 MCP 시스템으로 전환하는 것이었습니다. Figma는 다음과 같은 마이그레이션 전략을 사용했습니다.
1.  **이중 쓰기(Dual Write)**: 새로운 작업(ops)은 기존 Document Server와 새로운 MCP Server 양쪽으로 전송됩니다. MCP Server는 이를 처리하여 새로운 스토리지에 기록합니다.
2.  **점진적 롤아웃**: 처음에는 새로 생성되는 문서만 MCP를 사용하도록 하고, 이후 기존 문서들을 작은 것부터 큰 것 순으로 점진적으로 MCP로 마이그레이션했습니다.
3.  **조정(Reconciliation)**: 마이그레이션 기간 동안 기존 시스템과 새 시스템 간의 데이터 일관성을 유지하기 위해 주기적으로 두 시스템의 상태를 비교하고 불일치가 발견되면 수정하는 조정 프로세스를 운영했습니다.

마이그레이션 과정에서 성능 저하, 분산 시스템 간의 디버깅 어려움, 복잡한 엣지 케이스 처리 등 여러 난관에 부딪혔습니다. 이를 통해 발표자는 초기 단계부터 관측 가능성(Observability) 도구(로깅, 메트릭, 트레이싱)에 투자하고, 작은 단위로 시작하여 점진적으로 반복하며 개선하는 접근 방식, 그리고 팀 간의 긴밀한 소통과 철저한 테스트(단위, 통합, E2E, 부하 테스트)의 중요성을 강조했습니다. 최종적으로 모든 문서가 MCP로 성공적으로 전환되었고, 기존 Document Server는 서비스에서 제외되었습니다.

## 인상적인 대목
- "Building the Engine While Flying the Plane." (비행 중 엔진 교체) - 서비스 중단 없이 핵심 시스템을 재구축하는 도전적인 상황을 명확히 표현하는 비유.
- "Invest in observability early." (관측 가능성에 일찍 투자하라.) - 복잡한 분산 시스템 마이그레이션에서 디버깅과 문제 해결의 핵심임을 강조하는 실용적인 조언.

## 실무 적용 포인트
- **핵심 시스템 재설계 시 무중단 마이그레이션 전략 고려**: 라이브 서비스의 핵심 컴포넌트를 재설계할 때는 "이중 쓰기(dual write)"와 "조정(reconciliation)"과 같은 점진적 마이그레이션 전략을 적극적으로 검토하여 서비스 중단을 최소화해야 합니다.
- **초기 단계부터 관측 가능성(Observability) 도구 구축**: 복잡한 분산 시스템이나 대규모 마이그레이션 프로젝트에서는 로깅, 메트릭, 트레이싱 등 관측 가능성 도구를 프로젝트 초기부터 설계하고 구축하여 문제 발생 시 신속하게 원인을 파악하고 해결할 수 있도록 준비해야 합니다.
- **점진적 롤아웃 및 반복적 개선**: 모든 것을 한 번에 바꾸려 하기보다, 작은 단위부터 시작하여 새로운 시스템을 도입하고, 피드백을 바탕으로 반복적으로 개선하며 점진적으로 적용 범위를 확대하는 것이 위험을 줄이고 성공 확률을 높이는 방법입니다.
- **상태 관리와 비즈니스 로직 분리 검토**: 확장성과 안정성이 중요한 시스템을 설계할 때, 문서 상태나 데이터 저장과 같은 상태 관리 계층과 비즈니스 로직(예: 협업 로직) 계층을 분리하는 아키텍처 패턴을 고려하여 시스템의 유연성과 확장성을 확보할 수 있습니다.
