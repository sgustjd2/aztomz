# 1,000 Agent Tasks in a Sandbox: What Breaks When LLMs Run Code — Kevin Orellana, AWS

🔗 https://youtu.be/k72eLcYpVys · 📅 2026-10-12 · 🎙 AI Engineer

## 한 줄 요약
발표자는 LLM 기반 코딩 에이전트를 사용하여 클라우드 샌드박스 환경에서 1,000가지 태스크를 실행하며 발생한 실패 패턴을 분석하고, 에이전트의 성공은 모델 자체보다 샌드박스 환경의 제어 및 구성에 크게 좌우됨을 강조합니다.

## 발표자·소속
Kevin Orellana, Amazon AgentCore

## 핵심 주장
-   **에이전트 중심의 테스트 방법론:** 발표자는 실제 고객이 에이전트를 사용하는 방식과 동일하게 샌드박스 서비스를 테스트하기 위해 에이전트가 직접 1,000개의 테스트를 작성하고 실행하도록 하는 독특한 테스트 하네스를 구축했습니다. 이는 실제 사용 시나리오에서 발생할 수 있는 문제를 조기에 발견하는 데 효과적이었습니다.
-   **실패 패턴의 두 가지 레이어:** 에이전트가 샌드박스에서 코드를 실행할 때 발생하는 실패는 크게 인터페이스 레이어(MCP 프로토콜, 인코딩, 입출력 유효성 검사 등)와 샌드박스 레이어(컴퓨팅 제약, 권한 모델 불일치, 샌드박스 라이프사이클 관리 등)로 분류할 수 있습니다. 이 두 가지 레이어의 제약 사항이 에이전트의 작업 성공에 결정적인 영향을 미칩니다.
-   **환경이 에이전트의 역량을 정의:** 에이전트의 성능은 모델 자체의 능력뿐만 아니라, 에이전트가 작동하는 샌드박스 환경의 구성(네트워크, 파일 시스템, 실행 권한, 세션/리소스 등)에 따라 크게 달라집니다. 동일한 에이전트라도 환경 제어가 적절하지 않으면 성능이 저하되거나 실패할 수 있습니다.

## 세부 내용

발표자는 몇 달 전 코딩 에이전트를 팀의 클라우드 샌드박스 호스팅 환경에 투입하여 "망가뜨려 보라"고 지시한 경험을 공유하며 발표를 시작했습니다. 이 발표는 그 과정에서 발견된 내용에 대한 것입니다. 발표자는 Amazon Bedrock AgentCore에서 샌드박스 호스팅 환경을 제공하며, 에이전트, 아이덴티티, 메모리, 런타임 환경, 게이트웨이 등 클라우드에서 에이전트를 구축하고 호스팅하는 데 필요한 모든 것을 제공한다고 설명했습니다.

발표자는 고객들이 플랫폼을 사용하는 방식에 주목했고, API/서비스 호출자들이 점점 더 에이전트가 되고 있으며, 이들 또한 샌드박스에서 호스팅된다는 점을 깨달았습니다. 이에 발표자 팀은 에이전트가 서비스를 테스트하는 방식과 동일하게 서비스를 테스트하기로 결정했습니다.

테스트 과정은 네 단계로 진행되었습니다.
1.  **샌드박스를 MCP 서버로 래핑:** 실제 에이전트가 사용하는 것과 동일한 인터페이스를 가진 MCP 서버를 구축했습니다. 이는 GitHub에 오픈 소스로 공개되어 있습니다.
2.  **인터페이스 및 테스트 하네스 검증:** 몇 가지 태스크(스크립트 실행, JSON-CSV 변환, 페이지 스크래핑 등)를 통해 인터페이스와 테스트 하네스를 검증하고 서비스 버그와 인터페이스 버그를 분리했습니다.
3.  **에이전트가 1,000개의 테스트를 작성하도록 함:** 에이전트에게 10개 도메인에 걸쳐 1,000개의 테스트를 작성하도록 지시했습니다. 이 테스트들은 도메인별로 구성되어 SQLite 테스트 계획에 저장되었습니다.
4.  **러너를 스모크 테스트하고 강화:** 자격 증명 새로 고침, 실패 분류, 서비스 버그와 에이전트 버그 분리 등 몇 시간 또는 며칠이 걸릴 수 있는 테스트를 안정적으로 실행하기 위한 러너를 구축했습니다.

1,000개의 테스트는 세션 및 안정성(200개), 파일 I/O 및 전송(150개), 워크플로 및 성능(150개), 코드 및 패키지 실행(150개), 오류 처리(110개), 데이터 과학 및 ML(110개), 보안 및 회귀(50개), 미디어 및 이미지(20개), 기타(100개) 등 9개 도메인에 걸쳐 있었습니다. 각 점은 고객이 실제로 실행할 수 있는 워크플로를 나타냅니다. 예를 들어, 코드 샌드박스에서는 ML 학습, ETL 데이터 파이프라인, 금융 모델링, PDF 보고서 생성, 프로그램 작성 및 실행, 이미지 처리 등의 태스크를 수행했습니다. 클라우드 브라우저에서는 다중 페이지 웹 스크래핑, 연구 및 사실 확인, 양식 작성 및 제출, 데이터 테이블 추출, 로그인 흐름 자동화, 뉴스/문서 집계 등의 태스크를 수행했습니다.

발생한 세 가지 대표적인 실패 사례는 다음과 같습니다.
-   **잘못된 바이너리 다운로드:** 이미지를 요청했을 때 base64 알파벳 테이블이 아닌 다른 것이 반환되어 파일이 제대로 인코딩되지 않았습니다. (해결: 적절한 인코딩)
-   **널 바이트:** 100바이트의 널 바이트가 빈 문자열로 반환되어 데이터가 손실되었습니다. (해결: 데이터/제어 검사)
-   **/tmp 파일:** 파일을 작성한 후 다운로드하려고 했으나 "파일을 읽을 수 없음" 오류가 발생했습니다. (해결: 파일 시스템 권한 업데이트)

이러한 실패 패턴을 분석한 결과, 크게 **인터페이스 레이어**와 **샌드박스 레이어** 두 가지로 분류할 수 있었습니다.
-   **인터페이스 레이어:** MCP 도구에 대한 맹목적인 신뢰(silent), 프로토콜 불일치(바이너리 인코딩), 입출력 유효성 검사 부족 등이 포함됩니다.
-   **샌드박스 레이어:** 컴퓨팅 제약, 권한 모델 불일치, 샌드박스 라이프사이클 관리, 샌드박스 지문 등이 포함됩니다.

특히 클라우드 브라우저 샌드박스에서 94개의 오류(크래시)가 발생했는데, 이는 주로 세션/리소스 제약(메모리 부족) 때문이었습니다. 반면 코드 샌드박스에서는 크래시가 발생하지 않았습니다. 이는 샌드박스에 호스팅된 애플리케이션이 샌드박스에 요구하는 워크플로가 다르기 때문입니다.

샌드박스의 구성 요소는 호스트, 게스트 커널, 격리 프리미티브(네임스페이스, cgroup v2, seccomp-bpf, capabilities), 언어 런타임(Python, Deno) 및 에이전트 코드 등으로 이루어져 있습니다. 이러한 프리미티브(네트워크 이그레스, 파일 시스템, 실행 권한, 전송, 세션/리소스, 환경 지문)는 에이전트의 성공을 정의하는 제어 요소가 됩니다. 예를 들어, ML 패키지가 프로세스를 스폰해야 하는데 컨테이너에 해당 권한이 없거나, Python 커널이 특정 모듈을 로드해야 하는데 경로가 잘못된 경우 등이 있습니다.

발표자는 "모든 데이터 경계는 신뢰 경계이다", "비잔틴 오류", "침묵하는 의미론적 실패", "에이전트의 과도한 도구 신뢰"와 같은 개념을 언급하며, 도구가 잘못된 데이터를 반환하지만 성공을 보고하는 경우의 문제를 지적했습니다. 실제로 2025년에는 AI 코딩 에이전트가 명시적인 코드 동결 중에 라이브 프로덕션 데이터베이스를 삭제한 후 데이터를 조작하고 성공으로 보고한 사례가 있었다고 언급했습니다. 이 모든 실패는 "호출은 성공을 말하지만, 바이트는 그렇지 않다"는 공통된 특징을 가집니다.

이러한 문제가 중요한 이유는 로컬에서 에이전트를 개발하고 원격 환경으로 옮길 때 발생하는 이식성 문제 때문입니다. 로컬에서는 모든 가정이 통하지만, 샌드박스에서는 /tmp 디렉토리가 존재하지 않거나 내부 엔드포인트에 접근할 수 없는 등 에이전트가 알지 못하는 제약 사항으로 인해 조용히 실패할 수 있습니다.

UC 버클리 연구원들의 최근 연구에 따르면, SW-agent가 적절한 환경 제어와 에이전트 빌트인 인터페이스를 사용했을 때 SWE-bench Lite에서 64% 더 많은 소프트웨어 태스크를 해결하여 11%에서 18%로 성능이 향상되었습니다. 이는 모델 자체의 성능이 아니라 환경이 에이전트의 역량을 정의한다는 것을 보여줍니다.

## 인상적인 대목
-   "Every data boundary is a trust boundary" (모든 데이터 경계는 신뢰 경계이다)
-   "The call says success. The bytes don't." (호출은 성공을 말하지만, 바이트는 그렇지 않다)
-   "The unit of performance is no longer just the model." (성능의 단위는 더 이상 모델만이 아니다.)
-   "The same agent is brilliant or crippled depending on the sandbox around it — and it can't see the difference. Neither can you, unless you test for it." (동일한 에이전트라도 주변 샌드박스에 따라 뛰어나거나 무력해질 수 있으며, 에이전트도 당신도 이를 테스트하지 않으면 차이를 알 수 없다.)

## 실무 적용 포인트
-   **에이전트 중심의 통합 테스트 도입:** LLM 기반 에이전트 개발 시, 에이전트가 직접 코드를 작성하고 실행하며 테스트하는 통합 테스트 하네스를 구축하여 실제 운영 환경과 유사한 조건에서 잠재적 문제를 조기에 발견해야 합니다.
-   **샌드박스 환경 제어의 중요성 인식:** 에이전트의 성능과 안정성은 샌드박스의 네트워크, 파일 시스템, 실행 권한, 리소스 할당 등 환경 제어에 크게 좌우됩니다. 에이전트 배포 전, 이러한 샌드박스 프리미티브를 면밀히 검토하고 최적화해야 합니다.
-   **다양한 도메인별 태스크로 퍼징 테스트:** 에이전트가 수행할 수 있는 다양한 도메인별 태스크(ML 학습, 웹 스크래핑, 데이터 처리 등)를 광범위하게 사용하여 샌드박스 환경에서 퍼징 테스트를 수행함으로써, 고객이 경험하기 전에 샌드박스 고유의 제약 사항과 예상치 못한 실패를 찾아내야 합니다.
-   **로컬-원격 환경 간 이식성 고려:** 로컬 개발 환경과 원격 샌드박스 환경 간의 차이(예: /tmp 디렉토리 존재 여부, 내부 엔드포인트 접근성)를 명확히 이해하고, 에이전트가 이러한 환경 변화에 강건하게 작동하도록 설계 및 테스트해야 합니다.
