# Your Agent Is a Lethal Trifecta (And What to Do About It) — Kim Maida, Keycard

🔗 https://youtu.be/ws9XcGGPBDk · 📅 2026-10-12 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트의 유용성을 유지하면서도 보안 위험을 줄이기 위해 토큰 교환(Token Exchange) 및 의도 기반 권한 부여(Intent-Based Authorization)와 같은 오픈 표준을 활용하여 에이전트 접근 제어를 강화해야 합니다.

## 발표자·소속
Kim Maida, Keycard (Founding GTM Engineer & Head of Developer Relations)

## 핵심 주장
- 에이전트의 유용성을 높이는 기능들(데이터 접근, 리서치 능력, 외부 도구 사용)은 동시에 보안 취약점을 야기하는 "치명적인 트라이펙타"를 형성합니다.
- 현재의 에이전트 접근 제어 방식(OAuth, 게이트웨이, 샌드박스)은 단독으로 사용될 경우 에이전트에게 과도한 권한을 부여하거나 유용성을 제한하는 문제를 안고 있습니다.
- 토큰 교환(Token Exchange) 표준을 통해 에이전트의 신원과 사용자 신원을 명확히 하고, 작업 범위에 따라 일시적인(ephemeral) 접근 토큰을 발급하여 권한을 최소화할 수 있습니다.
- 의도 기반 권한 부여(Intent-Based Authorization, IBA)는 에이전트의 행동 의도를 정책에 따라 평가하여 승인 여부를 결정함으로써, 에이전트가 의도치 않은 작업을 수행하는 것을 방지합니다.

## 세부 내용
발표는 온콜 트리아지(on-call triage) 에이전트의 데모로 시작됩니다. 이 에이전트는 인시던트 페이저(Incidex), 클라우드 호스팅 API(Compuhost), 고객 데이터 웨어하우스(Snowflake), 결제 데이터베이스(PostgreSQL)에 대한 완전한 접근 권한을 가지고 있습니다.

**데모 1 (기존 방식)**:
- **청구 이상(Billing anomaly)**: 에이전트가 티켓을 읽고(Incidex API 키 사용), 고객 데이터 웨어하우스(Snowflake 키 사용)에서 고객 PII(개인 식별 정보)를 조회한 후, 이 정보를 인시던트 페이저에 공유하여 보안 위험을 야기합니다.
- **백업 전원 공급 장치 오류**: 에이전트가 티켓을 읽고(API 키 사용), 물리적 문제임을 판단하여 추가 서비스 호출 없이 아침 팀에 에스컬레이션합니다.
- **웹사이트 보안 인증서 만료**: 에이전트가 티켓을 읽고(API 키 사용), 클라우드 호스팅 API(API 키 사용)를 호출하여 인증서를 갱신합니다. 이 과정에서 광범위한 권한을 가진 정적 API 키를 사용하여 잠재적 위험을 내포합니다.
- **결제 데이터베이스 손상**: 에이전트가 티켓을 읽고(API 키 사용), 데이터베이스를 '드롭 앤 리스토어(drop-and-restore)'하는 표준 복구 절차를 따릅니다. 이 과정에서 관리자 비밀번호가 포함된 데이터베이스 연결 문자열을 사용하여 프로덕션 데이터베이스를 삭제하는 심각한 보안 위험을 보여줍니다.
- **주문 정체, 메인 서버 동결**: 에이전트가 티켓을 읽고(API 키 사용), 메인 서버를 재시작합니다. 이로 인해 프로덕션이 일시적으로 오프라인이 됩니다.
- **사이트 방문자 1/3 오류**: 에이전트가 티켓을 읽고(API 키 사용), 클라우드 호스팅 API를 호출하여 서버를 4개에서 40개 포드로 확장합니다. 이로 인해 시간당 420달러의 비용이 발생합니다.

이러한 데모는 에이전트가 데이터 접근, 리서치 능력, 외부 도구 사용이라는 "치명적인 트라이펙타"를 가질 때 발생하는 문제점을 보여줍니다. 에이전트는 작업을 완료하기 위해 모든 권한을 사용하며, 이는 데이터 삭제, 시스템 손상, 비용 발생 등 심각한 결과를 초래할 수 있습니다. 발표자는 이러한 문제가 "인간이 에이전트에게 필요한 것보다 훨씬 많은 접근 권한을 부여하기 때문"이라고 지적합니다. 기존의 OAuth, 게이트웨이, 샌드박스 같은 접근 제어 방식은 단독으로는 작업 범위에 따른 권한 제어, 장기 권한 문제, 샌드박스 탈출 등의 문제를 해결하기 어렵습니다.

**해결책: 토큰 교환(Token Exchange) 및 의도 기반 권한 부여(IBA)**:
- **토큰 교환(RFC 8693)**: OAuth 2.0을 확장한 표준으로, 사용자 인증 후 권한 부여 서버가 에이전트에게 사용자의 권한 중 일부(스코프)를 위임하는 토큰을 발급합니다. 이 토큰은 에이전트의 신원과 사용자 신원을 모두 포함하며, 특정 작업에 필요한 최소한의 권한만을 부여합니다. 토큰은 일시적(ephemeral)이며 저장되지 않습니다.
- **에이전트 실행 경로**: 사용자가 에이전트에게 프롬프트를 제출하면, 에이전트 런타임은 LLM을 호출하고, LLM은 도구 호출을 제안합니다. 이 도구 호출은 MCP(Management Control Plane) 클라이언트를 통해 MCP 서버로 전달됩니다. MCP 서버는 Security Token Service(STS)에 에이전트의 신원, 사용자 신원, 요청된 접근 권한을 포함한 토큰 교환을 요청합니다.
- **정책 평가**: STS는 요청된 접근이 거버넌스 정책에 부합하는지 평가합니다. 정책이 허용하면 STS는 해당 작업에 특화된(task-scoped) 접근 토큰을 발급합니다. 이 토큰은 게이트웨이를 통해 MCP 서버로 전달되고, MCP 서버는 이 토큰을 사용하여 다운스트림 리소스(예: Snowflake)를 호출합니다. 이 과정을 통해 모든 활동이 추적 가능하며, 권한은 필요한 시점에 필요한 만큼만 부여됩니다.
- **의도 기반 권한 부여(IBA)**: 에이전트가 작업을 수행하기 전에 "미션(mission)"을 제안하고, 이 미션은 목표, 허용된 작업, 제한 사항을 포함합니다. STS는 이 미션을 정책에 따라 평가하여 승인, 거부 또는 수정을 결정합니다.

**데모 2 (토큰 교환 및 정책 적용)**:
- **사용자 로그인**: 발표자가 구글, 깃허브, Compuhost에 로그인하여 에이전트에게 필요한 권한을 위임합니다.
- **청구 이상**: 에이전트가 고객 PII를 조회하려 하자, **정책에 의해 거부됩니다**. "보안 정책은 에이전트가 개별 고객 기록을 가져오는 것을 금지합니다. 익명 총계만 볼 수 있습니다. 개인 데이터는 접근되지 않았습니다." 에이전트는 PII 없이 에스컬레이션합니다.
- **웹사이트 보안 인증서 만료**: 에이전트가 인증서 갱신을 요청하자, **허용됩니다**. 에이전트는 클라우드 호스팅 API를 호출하여 인증서를 갱신합니다.
- **결제 데이터베이스 손상**: 에이전트가 데이터베이스 삭제를 시도하자, **정책에 의해 거부됩니다**. "보안 정책은 에이전트가 프로덕션 데이터베이스를 삭제하는 것을 금지합니다. 인간이 수동으로 해야 합니다." 에이전트는 에스컬레이션합니다.
- **주문 정체, 메인 서버 동결**: 에이전트가 메인 서버 재시작을 요청하자, **사용자 승인이 필요합니다**. 발표자가 승인하지만, **정책에 의해 재시작이 차단됩니다**. "보안 정책은 프로덕션 재시작을 위해 프로-관리자 역할이 필요하며, 온콜 운영자는 해당 권한이 없습니다." 에이전트는 에스컬레이션합니다.
- **사이트 방문자 1/3 오류**: 에이전트가 서버 확장을 요청하자, **사용자 승인이 필요합니다**. 발표자가 승인하고, 발표자의 역할이 해당 권한을 가지고 있으므로 **허용됩니다**. 에이전트는 서버를 확장합니다.

이 데모는 토큰 교환과 정책 기반 접근 제어를 통해 에이전트가 필요한 작업을 수행하면서도 보안 위험을 효과적으로 관리할 수 있음을 보여줍니다.

## 인상적인 대목
- "인간이 에이전트에게 필요한 것보다 훨씬 많은 접근 권한을 부여하기 때문"에 AI 에이전트 관련 사고가 발생한다는 지적. 에이전트의 자율성 자체보다 인간의 권한 부여 방식이 문제의 근원임을 명확히 합니다.
- "치명적인 트라이펙타(lethal trifecta)"라는 용어로 에이전트의 유용성과 위험성을 동시에 설명하는 방식이 인상적입니다. 데이터 접근, 신뢰할 수 없는 콘텐츠 노출, 외부 통신이라는 세 가지 요소가 결합될 때 발생하는 위험을 강조합니다.
- 데모에서 에이전트가 프로덕션 데이터베이스를 삭제하려 하거나, PII를 유출하려 할 때 정책에 의해 차단되는 장면은 보안 강화의 효과를 직관적으로 보여줍니다. 특히, 사용자가 승인했음에도 불구하고 역할 기반 정책에 의해 재시작이 차단되는 부분은 인간의 개입만으로는 부족하며 정책의 중요성을 부각합니다.

## 실무 적용 포인트
- **최소 권한 원칙 적용**: 에이전트에게 필요한 최소한의 권한만 부여하고, 광범위한 정적 API 키나 관리자 비밀번호를 직접 사용하는 것을 지양해야 합니다.
- **토큰 교환(Token Exchange) 표준 도입 검토**: 에이전트가 리소스에 접근할 때마다 STS(Security Token Service)를 통해 작업 범위에 특화된(task-scoped) 일시적인(ephemeral) 접근 토큰을 발급받도록 시스템을 설계하여 권한을 동적으로 관리합니다.
- **의도 기반 권한 부여(IBA) 정책 수립**: 에이전트가 수행할 "미션"을 명확히 정의하고, 이 미션의 목표, 허용된 작업, 제한 사항을 포함하는 정책을 수립하여 에이전트의 행동을 제어합니다.
- **감사 로그 및 추적성 강화**: 모든 에이전트의 행동과 권한 요청이 사용자 및 에이전트 신원과 연결되어 감사 로그에 기록되도록 하여, 사고 발생 시 원인 분석 및 책임 추적을 용이하게 합니다.
