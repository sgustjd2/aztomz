# MCP Apps: Give the Model Data, Give the User a UI — Dustin Mihalik, Indeed

## 한 줄 요약
AI 엔지니어링에서 MCP 앱을 구축할 때, 모델의 데이터 처리 능력과 사용자 UI 렌더링을 분리하고, 사용자 상호작용 정보를 모델에 제공하며, 작고 재사용 가능한 도구를 활용하여 모델이 데이터를 효과적으로 탐색하고 사용자에게 최적화된 경험을 제공하도록 해야 합니다.

## 핵심 주장
-   **데이터 우선 접근 방식**: UI를 설계하기 전에 모델이 처리할 데이터와 그 기능을 명확히 정의하는 것이 중요합니다.
-   **모델에 UI 데이터 제공**: 사용자에게 표시되는 모든 UI 요소와 관련 데이터는 모델이 이해할 수 있는 형태로 함께 제공되어야 합니다.
-   **사용자 상호작용 정보 전달**: 사용자의 모든 상호작용(클릭, 선택 등)에 대한 정보를 모델에 전달하여 모델이 대화의 맥락을 파악하고 적절하게 대응하도록 해야 합니다.
-   **데이터 처리와 UI 렌더링 분리**: 데이터 검색 및 처리 로직을 UI 렌더링 로직과 분리하여 모델이 데이터를 자유롭게 탐색하고 조작한 후, 필요한 경우에만 UI 렌더링 도구를 호출하도록 설계해야 합니다.
-   **작고 재사용 가능한 도구**: 복잡한 기능을 하나의 큰 도구로 만들기보다, 작고 명확한 목적을 가진 여러 개의 도구를 만들어 모델이 유연하게 조합하여 사용할 수 있도록 해야 합니다.

## 세부 내용
발표자는 Indeed에서 MCP 앱(Model-Controlled UI Apps)을 구축하며 얻은 실질적인 교훈을 공유했습니다. Indeed는 세계 1위의 채용 사이트이며, 발표자는 AI 플랫폼, 가드레일, 게이트웨이 및 규정 준수 업무를 담당합니다.

초기 텍스트 기반 챗봇 인터페이스의 문제점을 지적하며 발표를 시작했습니다. 예를 들어, "오스틴에서 바리스타 일자리를 찾고 있습니다"라는 질문에 챗봇이 텍스트로 일자리 목록을 제공하지만, Indeed 브랜딩이 없고, 챗봇이 임의로 지역을 분류하며, 가장 중요한 것은 사용자가 목록의 특정 일자리에 대한 자세한 정보를 얻거나 지원하기 위해 외부 링크를 클릭하기 어렵다는 점입니다. 챗봇 제공자(Claude, ChatGPT 등)는 사용자가 자신의 환경을 떠나는 것을 원치 않기 때문에 링크를 일관되게 제공하도록 하는 것이 매우 어려웠다고 합니다.

이러한 문제를 해결하기 위해 MCP 앱을 사용하면 UI를 직접 제어할 수 있습니다. 발표자는 "Apply on Indeed" 및 "View details" 버튼이 있는 직업 카드 UI를 보여주며, 이를 통해 Indeed 브랜딩을 유지하고, 중요한 정보를 강조하며, "View details" 클릭 시 모달 팝업으로 상세 정보를 제공하여 사용자가 챗봇 환경을 떠나지 않고도 정보를 얻을 수 있음을 설명했습니다. 이는 사용자 경험과 기업 모두에게 윈-윈입니다.

하지만 MCP 앱 구축이 단순히 웹사이트를 챗봇 인터페이스에 드래그 앤 드롭하는 것처럼 쉽지 않다고 강조했습니다. 발표자는 세 가지 주요 규칙을 제시했습니다.

**규칙 #1: 사용자에게 표시되는 모든 것은 모델에 데이터로 제공되어야 합니다.**
만약 모델이 API를 호출하여 데이터를 가져오고, 그 데이터를 기반으로 UI를 렌더링하지만, 모델 자체에는 렌더링된 UI에 대한 정보가 없다면, 모델은 해당 UI를 "블랙박스"로 인식합니다. 이 경우, 사용자가 "첫 번째 결과에 대해 알려주세요"와 같은 후속 질문을 하면 모델은 "???" 또는 "IDK"와 같이 응답할 수밖에 없습니다.
해결책은 `structuredContent`와 `resourceUri`를 모두 반환하여 모델이 UI의 경로와 함께 실제 데이터를 이해하도록 하는 것입니다. 이를 통해 모델은 UI에 표시된 내용에 대해 추론하고 응답할 수 있습니다. 또한, 도구 설명(Tool Description)에 "결과는 UI 구성 요소로 사용자에게 자동으로 표시됩니다"와 같은 문구를 추가하여 모델이 텍스트로 중복 설명하는 것을 방지할 수 있습니다.

**규칙 #2: 모든 사용자 상호작용에 대한 정보는 모델에 제공되어야 합니다.**
사용자가 UI에서 "View details" 버튼을 클릭하여 특정 직업의 상세 정보를 보거나, "Apply on Indeed" 버튼을 누르는 등의 상호작용을 할 때, 모델은 어떤 항목이 선택되었는지 알지 못합니다. 이 경우, 사용자가 "이 직업 설명 요약", "이 직업에 대한 자기소개서 작성" 등의 질문을 하면 모델은 다시 "???"와 같이 응답합니다.
해결책은 `app.updateModelContext`와 같은 메서드를 사용하여 사용자의 상호작용(예: 클릭한 직업의 ID)을 모델 컨텍스트에 문자열 형태로 업데이트하는 것입니다. 이를 통해 모델은 사용자가 현재 어떤 정보에 집중하고 있는지 파악하고 관련 질문에 응답할 수 있습니다.

**규칙 #3: 데이터 처리와 UI 렌더링을 분리해야 합니다.**
이것은 다른 모든 규칙을 아우르는 가장 중요한 규칙입니다. 발표자는 복잡한 검색 요청(예: "AI 엔지니어 일자리를 찾고 있습니다. 이사할 의향이 있고, 가장 높은 급여 옵션을 찾고 있으며, 방위, 금융 서비스 또는 의료 산업에서는 일하고 싶지 않습니다.")을 예로 들었습니다. 텍스트 기반 챗봇은 여러 번의 검색과 필터링을 거쳐 최종 결과를 테이블 형태로 잘 요약해 줍니다. 하지만 UI 렌더링이 데이터 처리와 결합된 MCP 앱의 경우, 모델이 한 번 UI를 렌더링하면 더 이상 데이터를 깊이 탐색하거나 필터링하지 않으려는 경향이 있습니다.
해결책은 데이터 검색(`search_jobs(title, location)`)과 UI 렌더링(`render_jobs_widget(job_ids)`)을 별도의 도구로 분리하는 것입니다. `search_jobs` 도구는 UI를 반환하지 않고 순수한 데이터(예: 직업 ID 목록)만 반환하며, 모델은 이 데이터를 여러 번 호출하여 탐색하고 필터링할 수 있습니다. 그런 다음, 모델은 최종적으로 사용자에게 표시할 직업 ID 목록을 `render_jobs_widget` 도구에 전달하여 UI를 렌더링하도록 합니다. 이 접근 방식은 모델에게 데이터 탐색의 유연성을 제공하고, 렌더링 도구에는 ID와 함께 "왜 이 직업이 좋은지"와 같은 추가적인 설명을 포함하여 모델이 더 풍부한 사용자 경험을 제공할 수 있도록 합니다.

## 인상적인 대목
-   "Claude나 ChatGPT가 링크를 만들도록 하는 것은 정말 어렵습니다. 그들은 당신이 그들의 환경을 떠나는 것을 원치 않기 때문입니다." (It's really hard to get Claude or ChatGPT to link to things because they don't want you to leave their environment.)
-   "모델에게 데이터를 주고, 사용자에게 UI를 주십시오." (Give the Model Data, Give the User a UI)
-   "사용자에게 표시되는 모든 것은 모델에 데이터로 제공되어야 합니다." (Anything shown to the user should be provided as data to the model)
-   "데이터 처리와 UI 렌더링을 분리하십시오." (Separate data processing from UI rendering)

## 실무 적용 포인트
-   **도구 설계 시 데이터와 UI 분리**: API를 설계할 때, 데이터를 반환하는 도구와 UI를 렌더링하는 도구를 명확히 분리하여 모델이 데이터에 대한 완전한 제어권을 갖도록 합니다.
-   **모델 컨텍스트 업데이트 활용**: 사용자가 UI와 상호작용할 때마다 `updateModelContext`를 사용하여 모델에게 현재 상태와 사용자 의도를 명확히 전달합니다.
-   **도구 설명 최적화**: 도구 설명에 UI 렌더링에 대한 정보를 포함하여 모델이 텍스트로 중복 설명하는 대신 UI를 활용하도록 유도하고, 도구 간의 의존성(예: `search_jobs`를 먼저 호출해야 함)을 명시합니다.
-   **작은 단위의 재사용 가능한 도구 개발**: 복잡한 기능을 여러 개의 작고 명확한 도구로 나누어 모델이 다양한 시나리오에서 유연하게 조합하고 재사용할 수 있도록 합니다.
