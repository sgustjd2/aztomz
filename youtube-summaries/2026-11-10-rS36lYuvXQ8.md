# Your Agent Hates Your CLI - Ayush Bhardwaj, Allos AI

🔗 https://youtu.be/rS36lYuvXQ8 · 📅 2026-11-10 · 🎙 AI Engineer

## 한 줄 요약
에이전트가 CLI를 사용하는 방식(파이프를 통한 출력 필터링)을 분석하여, 에이전트 친화적인 CLI를 설계하고 문서화하는 방법을 제시하며, 에이전트의 트랜스크립트가 제품 분석 및 테스트 케이스가 될 수 있음을 강조한다.

## 발표자·소속
Ayush Bhardwaj, Tech Lead @ Allos (이전: D. E. Shaw & Co, Arista Networks)

## 핵심 주장
-   **에이전트는 CLI 출력을 필터링하여 사용한다**: 에이전트는 필요한 정보만 얻기 위해 `head`, `grep`, `tail`, `python3` 등의 도구를 파이프하여 CLI 출력을 자르는 경향이 있다. 이는 CLI가 에이전트의 요구사항을 직접적으로 충족시키지 못한다는 신호이다.
-   **에이전트는 버그 리포트를 제출하지 않는다**: 에이전트는 CLI 사용 중 마찰을 겪어도 직접 버그를 보고하는 대신, 자체적으로 스크립트를 작성하여 문제를 우회한다. 이로 인해 개발자는 에이전트가 겪는 어려움을 인지하기 어렵다.
-   **CLI는 에이전트의 요구사항에 맞춰 설계되어야 한다**: 에이전트가 반복적으로 사용하는 파이프 패턴을 CLI 자체 기능으로 흡수하여, 에이전트가 더 효율적으로 정보를 얻고 불필요한 토큰 사용을 줄일 수 있도록 해야 한다.
-   **에이전트의 트랜스크립트는 중요한 제품 분석 데이터다**: 에이전트가 실행한 명령어와 그 다음 행동은 CLI의 사용성, 문제점, 개선점을 파악할 수 있는 실제 사용자 데이터이자 테스트 케이스 역할을 한다.
-   **문서가 에이전트의 인터페이스다**: CLI의 `SKILL.md` 파일, `--help` 메시지, 예제는 에이전트가 도구를 이해하고 사용하는 주요 인터페이스이므로, 최신 정보를 정확하게 반영해야 한다.

## 세부 내용

발표자는 자신이 만든 CLI가 에이전트가 과거 세션의 컨텍스트를 재사용할 수 있도록 돕는다고 소개하며, 이 CLI를 개선하는 과정에서 에이전트가 자신의 CLI를 "싫어하는" 이유를 깨달았다고 말한다.

**에이전트의 CLI 사용 패턴 분석**
발표자는 클로드 코드(Claude Code)가 문서 페이지에서 특정 설정을 찾기 위해 전체 페이지를 다운로드하고 `grep`으로 필터링한 후 `head -40`으로 40줄만 남기는 예시를 보여준다. 코덱스(Codex)는 `npm audit`의 JSON 리포트에서 취약점 총계를 찾기 위해 전체 리포트를 요청하고 `tail -40`으로 마지막 40줄만 남겼다. 커서(Cursor)는 `cargo test`를 실행하여 테스트 실패를 찾고 `tail -80`으로 마지막 80줄만 남겼다. 이 세 가지 예시 모두 에이전트가 출력의 특정 부분에 답이 있을 것이라고 "추측"하여 출력을 잘라냈음을 보여준다.

발표자는 에이전트가 마찰을 겪어도 버그 리포트를 제출하지 않는다고 지적한다. 샌티(Sanity)의 사례를 인용하며, 2만 개 이상의 에이전트가 3백만 건의 툴 호출을 했지만 버그 리포트는 단 한 건도 없었다고 언급한다. 에이전트는 대신 "자신의 프로그램 주변에 작은 프로그램"을 작성하여 문제를 우회한다.

발표자는 자신의 트랜스크립트에서 약 2만 건의 에이전트 호출을 분석했다. `git`, `gh`, `cargo`, `curl`, `npm`, `docker` 등 14개 CLI가 사용되었으며, 이 중 26%가 `head`, `grep`, `tail`, `sort`, `python3` 같은 필터로 출력을 파이프했다. 특히 `git show`와 `cargo test` 같은 읽기 위주 명령어의 경우 62%가 파이프를 사용했다. 이는 에이전트가 필요한 정보만 얻기 위해 불필요한 출력을 잘라내고 있음을 시사한다.

**파이프의 문제점**
파이프는 단순히 노이즈를 제거하는 것 외에 문제를 일으킬 수 있다. Bash에서 `pipefail` 옵션이 없으면 파이프라인은 마지막 명령어의 종료 코드를 반환한다. 예를 들어, `cargo test`가 실패했음에도 불구하고 `head`가 성공적으로 실행되면 파이프라인은 성공으로 보고될 수 있다. 발표자는 컴파일 에러가 발생했지만 `head` 때문에 녹색 점(성공)으로 표시된 `cargo test`의 예시를 보여준다.

더 나쁜 경우, 파이프가 에러 메시지 자체를 잘라낼 수도 있다. `node generate-files.js 2>&1 | tail -3` 명령어의 경우, `ReferenceError`가 발생했지만 `tail -3` 때문에 에러 메시지가 잘리고 클로드(Claude)는 성공으로 보고했다. 에러가 모델에 도달하지 못한 것이다. 발표자는 CLI가 실패할 때 "크게 실패"하고, 마지막 몇 줄에 짧은 요약을 제공하며, 전체 로그 경로를 알려주도록 권장한다.

**`chat-history` CLI 사례 연구**
발표자는 자신이 만든 Rust CLI인 `chat-history`를 사례로 들었다. 이 도구는 에이전트가 클로드 코드, 코덱스, 커서 등에서 과거 세션을 검색할 수 있도록 하며, `SKILL.md`와 함께 제공되어 에이전트가 언제 어떻게 호출할지 결정할 수 있다. 10월 감사에서 약 1,000건의 실제 호출이 기록되었다.

분석 결과, 에이전트가 `chat-history`로 과거 세션을 열 때 5번 중 4번(80%)은 출력을 `grep`, `sed`, `head`, `tail`, `python` 등으로 파이프하여 잘라냈다. 이는 에이전트가 매번 수동으로 동일한 축소 명령어를 작성하는 "파이프 세금(pipe tax)"을 지불하고 있음을 의미한다.

**개선 방안: 파이프가 요구하는 것을 CLI에 내장**
발표자는 에이전트가 반복적으로 사용하는 파이프 패턴을 CLI 기능으로 흡수할 것을 제안한다.
1.  **필터링**: `view <id> --plain | rg -n "..." | head -60` 또는 `view <id> --plain | sed -n '7970,8040p'`와 같은 패턴은 `view <id> --around 42 --grep "..." --tail 6 --max-chars 1500`과 같이 CLI 자체에서 특정 라인 주변, 특정 패턴, 마지막 몇 줄, 최대 문자 수 등을 선택할 수 있는 플래그를 제공하여 대체할 수 있다.
2.  **JSON 처리**: `search "..." --deep --json | python3 -c "for r in d['results']:"`와 같은 패턴은 `search "..." --compact`와 같이 JSON 출력을 한 줄당 하나의 결과로 압축하여 제공하는 모드를 통해 6배 더 작은 출력을 제공할 수 있다.
3.  **반복 작업**: `for id in ...; do chat-history inspect $id | head -45; done`과 같이 여러 세션을 수동으로 반복하는 패턴은 `inspect a b c --brief`와 같이 여러 ID를 한 번에 처리하는 기능을 제공하여 셸 루프 대신 단일 호출로 대체할 수 있다.

인프라코스트(Infracost)도 유사한 문제를 겪었으며, 에이전트가 `jq`와 `python` 파이프라인을 사용하여 JSON 덤프를 처리하는 것을 발견했다. 그들은 CLI에 필터 플래그, 압축 출력 형식, 그리고 이를 에이전트에게 가르칠 스킬을 추가했다. 그 결과, 클로드 단독으로는 6개의 어려운 질문 중 0개를 맞췄지만, 개선된 CLI와 함께는 6개 모두를 맞췄고, 벤치마크 전체 비용도 41% 감소했다.

**문서화의 중요성**
CLI에 새로운 기능이 추가되면, 에이전트에게 이를 가르쳐야 한다. `SKILL.md` 파일이나 `--help` 플래그를 통해 새로운 기능을 명확히 설명해야 한다. 발표자는 `deep` 플래그를 노옵(no-op)으로 변경한 후에도 `SKILL.md`가 여전히 `always use it`이라고 말하자, 에이전트 95개 중 95개가 여전히 `deep` 플래그를 사용했다고 언급한다. `SKILL.md`에서 이 지시를 제거하자, 새로운 플래그를 시도한 9개 세션 중 0개가 `deep` 플래그를 사용했다. 이는 `SKILL.md`, `--help` 텍스트, 에러 메시지가 에이전트의 실제 인터페이스이며, 오래된 문서는 버그와 같다는 것을 의미한다.

**인터페이스 변경 후 결과**
새로운 플래그(예: `search --compact`, 선택/크기 플래그)가 에이전트에게 도달하자, `search` 호출의 99%가 `--compact` 출력을 사용하기 시작했다. 파이프된 읽기(view piped)의 비율은 82%에서 25%로 급감했다.

**트랜스크립트를 테스트 케이스로 활용**
에이전트가 실행한 명령어는 테스트 케이스가 되고, 에이전트가 그 다음으로 한 행동은 대략적인 정답 키가 된다.
-   **새로운 랭킹**: 에이전트가 사용한 결과가 여전히 상위에 나오는지 확인한다.
-   **새로운 출력 형식**: 누락된 것이 없는지 확인한다.
-   **새로운 기본값**: 어떤 실제 명령어가 다르게 동작하는지 확인한다.
다른 인수로 재시도하는 에이전트의 호출은 실패하는 테스트 케이스일 가능성이 높다.

**우선적으로 구축해야 할 것**
발표자는 2만 건의 호출 분석을 바탕으로 다음을 우선적으로 구축할 것을 제안한다.
-   **범위 및 제한 기능 제공**: 측정된 파이프라인의 55%가 `head`, `tail`, `sed`만 사용했다. 이는 더 작은 슬라이스에 대한 수요를 나타낸다.
-   **플래그를 통해 제한 제공**: `gh ... list` 호출의 81%가 `--limit` 플래그를 사용했다. 플래그는 에이전트가 직접 찾아야만 도움이 된다.
-   **기본적으로 적게 출력**: 큰 출력은 기본적으로 제한하고, 더 많은 정보를 얻는 방법을 명시한다. 예: "showing 20 of 300, add --offset 20".

**에이전트 모드**
이러한 기능들을 한 번에 제공하는 한 가지 방법은 "에이전트 모드"이다. CLI가 에이전트가 호출하고 있음을 감지하고 다르게 출력하는 것이다. 클로드 코드와 같은 에이전트는 환경 변수를 설정하여 CLI가 자신을 식별할 수 있도록 한다. 덕DB(DuckDB)는 터미널에서는 보기 좋은 테이블을 제공하지만, 에이전트에게는 누락된 행 수와 얻는 방법을 알려주는 일반 텍스트를 제공한다. 에이전트 모드는 모델이 읽는 출력을 59% 줄였지만, 전체 토큰의 약 0.5%만 절약했다. 그러나 인프라코스트의 에이전트는 정답을 맞추기 시작했고, 덕DB는 이미 그랬다. 중요한 것은 토큰 수가 아니라 "정답"을 측정하는 것이다.

**에이전트는 아직 설계를 잘하지 못한다**
에이전트는 아직 에이전트를 위한 설계, 무엇이 작동하는지 아는 것, 자체 문서 작성에는 능숙하지 않다. 그들은 사람을 상상하고, 흔한 패턴을 복사하며, 대부분의 경우 그 패턴은 좋지 않다. 에이전트가 작성한 컨텍스트 파일은 작업 성공에 도움이 되지 않았다.
반면, 에이전트는 트랜스크립트를 읽고, 여러 세션에서 무엇이 잘못되었는지 찾고, 테스트에 맞춰 도구를 개선하는 데는 이미 능숙하다. 때로는 사람이 수동으로 작성한 것보다 더 잘한다.

**결론**
결론적으로, CLI의 사용자가 에이전트라면 다음 규칙을 따라야 한다.
-   더 적게 요청하도록 한다.
-   기본값을 제한하고, 더 많은 정보를 얻는 방법을 알려준다.
-   마지막 몇 줄에 크게 실패 메시지를 표시한다.
-   에이전트가 실제로 원하는 플래그를 제공한다.
-   정답을 측정하고, 토큰 수를 측정하지 않는다.
-   결과당 한 줄을 출력하고, 루프를 일괄 처리한다.
-   문서가 인터페이스이다.

발표자는 에이전트의 트랜스크립트가 우리가 읽지 않는 제품 분석 데이터라고 강조하며, 트랜스크립트를 읽고 개선점을 찾을 것을 권장한다.

## 실무 적용 포인트
-   **에이전트의 CLI 사용 패턴 분석**: 에이전트가 CLI 출력을 어떻게 파이프하고 필터링하는지 트랜스크립트를 분석하여, 에이전트가 반복적으로 수행하는 작업을 CLI의 내장 기능으로 제공할 수 있는지 파악한다.
-   **명확하고 간결한 출력 및 에러 보고**: CLI는 기본적으로 필요한 정보만 출력하고, 큰 출력은 제한하며, 더 많은 정보를 얻는 방법을 명시해야 한다. 에러 발생 시에는 마지막 몇 줄에 명확한 요약과 함께 전체 로그를 볼 수 있는 경로를 제공하여 에이전트가 문제를 쉽게 진단할 수 있도록 돕는다.
-   **에이전트 모드 구현 고려**: `CLAUDECODE`와 같은 환경 변수를 통해 에이전트 호출을 감지하고, 에이전트에게 최적화된 출력 형식(예: 압축된 JSON, 요약된 텍스트)을 제공하는 "에이전트 모드"를 구현하여 불필요한 토큰 사용을 줄이고 효율성을 높인다.
-   **문서화의 중요성 인식**: `SKILL.md`, `--help` 메시지, 예제 등 CLI의 모든 문서는 에이전트의 주요 인터페이스이므로, 항상 최신 상태로 유지하고 새로운 기능에 대한 설명을 명확히 제공하여 에이전트가 도구를 올바르게 사용할 수 있도록 한다.
