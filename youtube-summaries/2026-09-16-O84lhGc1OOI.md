# If we want them to do Knowledge Work, design them as Knowledge Agents — Benjamin Clavié, Mixedbread

🔗 https://youtu.be/O84lhGc1OOI · 📅 2026-09-16 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 지식 작업을 효과적으로 수행하려면 코딩 에이전트가 아닌 지식 에이전트로 설계되어야 하며, 이를 위해 도구와 조직화된 워크플로를 활용하는 것이 중요하다.

## 발표자·소속
Benjamin Clavié, MTS @ Mixedbread

## 핵심 주장
-   **지식 작업의 본질 이해**: 지식 작업은 정보가 주요 입력이고 실행 가능한 판단이 주요 출력인 모든 작업을 의미하며, 코딩은 지식 작업의 한 형태일 뿐 전체를 대변하지 않는다.
-   **도구와 조직화의 중요성**: 역사적으로 지식 작업은 더 나은 도구와 조직화된 워크플로를 통해 발전해왔으며, 이는 AI 에이전트 설계에도 동일하게 적용되어야 한다.
-   **코딩과 지식 작업의 차이**: 코드는 명확하고 안정적인 식별자를 가지며 작업이 미리 정의되어 있지만, 일반적인 지식 작업은 의미가 암묵적이고 맥락 의존적이며 의도에서 시작되는 광범위한 탐색을 요구한다.
-   **에이전트 성능 향상**: 적절한 검색 도구와 작업 분할(조직화)을 통해 에이전트의 지식 작업 정확도를 크게 향상시키고, 인간과 에이전트 간의 성능 격차를 줄일 수 있다.

## 세부 내용

발표자는 AI 에이전트가 코딩 에이전트가 아닌 지식 에이전트로 설계되어야 한다고 주장하며 강연을 시작했습니다. 초기 에이전트(2022년경)는 주로 일반 도메인 질의응답(QA)에 사용되었으며, 툴 호출 기능도 없어 PDF와 대화하는 수준의 제한적인 지식 작업만 수행했습니다. 이후 코딩 에이전트가 등장하여 툴 호출을 통해 검색, 이해, 작업 수행이 가능해지면서 큰 인기를 얻었습니다.

발표자는 코딩 에이전트가 지식 작업의 한 형태이지만, 지식 작업의 전체 범위에 비하면 매우 작은 부분이라고 강조했습니다. 지식 작업은 법률, 의료, 금융, 학술 등 다양한 분야에 걸쳐 있으며, 코딩 역시 그중 하나입니다.

지식 작업은 "주요 입력이 정보이고 주요 출력이 (광범위하게) 실행 가능한 판단인 모든 작업"으로 정의됩니다. 또한, 검색이 필요한 문제라면 지식 문제이고, 지식 문제라면 검색이 필요하다는 자기 참조적인 정의도 제시했습니다. 현실 세계에서 변호사, 학자, 소프트웨어 엔지니어, 법률 보조원, 의사, 보험 계리사 등 많은 직업이 매일 지식 작업을 수행합니다. 각 지식 산업은 지식 작업의 구조화를 개선하는 데 기여해왔지만, 에이전트는 소프트웨어 엔지니어링이라는 특정 사례에만 집중해왔습니다.

발표자는 "코드는 지식이다. 하지만 지식이 코드는 아니다"라는 점을 설명하며 코딩과 일반 지식 작업의 차이를 강조했습니다.
-   **코드의 고유한 특징**:
    1.  **영구적인 단서**: 식별자, 파일, 메서드 등 코드 내 참조는 비교적 안정적입니다.
    2.  **좁고 검색 가능한 표면**: 키워드, 메서드 정의 등 코드는 특정 요소를 쉽게 검색할 수 있습니다.
    3.  **미리 정의된 작업**: 기능 구현, 버그 수정 등 코딩 작업은 명확하게 정의된 경우가 많습니다.
-   **지식 작업의 광범위한 특징**:
    1.  **암묵적인 의미**: 정보의 의미가 명확하지 않고 맥락에 따라 달라질 수 있습니다. 예를 들어 "30일"은 마감일, 유예 기간, 보존 규칙 등 다양한 의미를 가질 수 있습니다.
    2.  **다양한 의미를 가질 수 있는 단서**: 동일한 단서가 여러 가지를 의미할 수 있습니다.
    3.  **의도에서 시작되는 검색**: 작업이 미리 정의되지 않고 사용자의 광범위한 의도에서 시작됩니다.
    *   비(非)코드 지식은 종종 맥락적이고 의미 중심적입니다.

지식 작업은 두 가지 자기 최적화 루프를 통해 발전해왔습니다.
1.  **도구 루프**: 더 많은 지식 -> 찾기/사용하기 어려움 -> 더 나은 도구 -> 더 많은 사람이 지식을 생산/사용 -> 더 많은 지식. (구술 문화 -> 알렉산드리아 도서관 -> 수도원 필사실 -> 초기 산업 시대 -> 19세기 말 -> 웹 + AI 시대)
2.  **조직화 루프**: 낮은 전문성 -> 서기 및 사무원 -> 수도원 필사실 -> 대학/길드/전문직 -> 관료주의 -> 전문 서비스 회사 -> 법률 보조원/비서.
이 두 루프는 사실 하나의 자기 최적화 루프이며, 새로운 지식은 더 나은 도구의 필요성을 낳고, 새로운 도구, 워크플로, 규칙은 지식 작업을 재훈련하고 재조직화하여 더 많은 지식을 창출하는 순환을 이룹니다.

발표자는 검색 도구가 단순한 추가 기능이 아니라 작업을 수행 가능하게 만드는 핵심 요소라고 설명했습니다. 도구는 작업의 가능성뿐만 아니라 비용 효율성까지 결정합니다. 예를 들어, 도서관 목록은 특정 책을 찾는 것을 가능하게 하고, 지도 디렉토리는 세계 탐험을 합리적으로 만들며, 멀티모달 검색 플랫폼은 수백만 개의 PDF를 저렴하게 검색할 수 있게 합니다.

실제 딥 리서치(DeepResearch) 작업 예시를 통해 도구의 영향력을 보여주었습니다. BrowseComp-Plus 리더보드 데이터에 따르면, BM25(최적화되지 않음)는 51.8%의 정확도와 평균 25.1회의 검색을 기록하며 성능이 매우 낮았습니다. 반면, 최적화된 BM25는 73.2% 정확도와 13.4회 검색, Queen3-Embed-3B와 같은 시맨틱 검색은 89.8% 정확도와 10.2회 검색을 보여주었습니다. Lexical + Mixedbread Search와 같은 하이브리드 방식은 90.2% 정확도와 8.6회 검색으로 가장 좋은 성능을 보였습니다. 이는 도구의 품질이 향상될수록 LLM이 올바른 답변에 도달할 가능성이 높아지며, 비용(검색 횟수)은 급격히 감소한다는 것을 의미합니다. 특히, 최적화된 도구는 성능을 크게 향상시키면서도 툴 호출 횟수를 줄여 비용 효율성을 높입니다.

마지막으로, 적절한 지식 작업에는 조직화가 필요하다고 강조했습니다. 도구의 발전과 함께 노동 분업이 이루어져 정보의 폭과 효율성이 증대됩니다. 프로그래밍의 경우, 사용자가 기술적이고 터미널 인터페이스가 문제를 완화하며, 작업이 대부분 자체 포함되어 검증 가능하기 때문에 조직화가 덜 중요할 수 있습니다. 하지만 실제 지식 작업에서는 "빅 샷(Big Shot)"이라는 오케스트레이터가 클라이언트의 요청을 받아 쿼리를 세분화하고 여러 "어시스턴트"에게 작업을 위임하며, 어시스턴트들은 검색 도구를 사용하여 메모와 노트를 작성하고 이를 빅 샷에게 다시 전달하는 복잡한 워크플로가 필요합니다.

MadQA 벤치마크(PDF 기반 기업 QA 벤치마크) 결과는 도구와 조직화의 중요성을 다시 한번 입증했습니다. BM25를 사용했을 때 인간과 Gemini 3 Pro 에이전트 모두 82.2%의 정확도로 동일한 한계에 도달했습니다. 이는 더 나은 도구가 필요하다는 것을 의미합니다. 하지만 "모든 것을 하는 에이전트"에서 "분리된 어시스턴트" 패러다임(Mixedbread Search Agent)으로 전환함으로써 에이전트와 인간 간의 격차를 3분의 1 이상 줄였습니다 (Gemini 3.5 Flash + Mixedbread Search Tool 88.9% -> Gemini 3.5 Flash + Mixedbread Search Agent 93.4%). 이는 에이전트가 실수를 줄이는 데 약 40%의 개선 효과를 가져왔습니다.

## 인상적인 대목
-   "Knowledge work is all work where the main input is information and the main output is a (broadly) actionable judgement." (지식 작업은 주요 입력이 정보이고 주요 출력이 (광범위하게) 실행 가능한 판단인 모든 작업이다.)
-   "Code is Knowledge, but Knowledge isn't Code." (코드는 지식이다. 하지만 지식이 코드는 아니다.)
-   "Search Tools are not a neutral add-on. In fact, tooling is what decides whether or not a task can be carried out cheaply at all." (검색 도구는 중립적인 추가 기능이 아니다. 사실, 도구는 작업이 저렴하게 수행될 수 있는지 여부를 결정한다.)
-   "For organisation, moving from an 'everything-agent' to a decoupled assistants paradigm narrows the gap between agents and humans by over a third!" (조직화에 있어서, '모든 것을 하는 에이전트'에서 분리된 어시스턴트 패러다임으로 전환하는 것은 에이전트와 인간 간의 격차를 3분의 1 이상 줄인다!)

## 실무 적용 포인트
-   **에이전트 설계 시 지식 작업의 광범위한 특성 고려**: 코딩 문제에만 국한하지 않고, 암묵적인 의미, 맥락 의존성, 의도 기반 검색 등 일반적인 지식 작업의 특징을 반영하여 에이전트를 설계해야 합니다.
-   **도구의 지속적인 최적화 및 에이전트의 도구 활용 능력 강화**: 에이전트가 다양한 검색 도구(렉시컬, 시맨틱, 멀티모달 등)의 원시 기능을 이해하고 적절히 활용하도록 훈련시켜야 합니다. 이는 성능 한계를 극복하고 비용 효율성을 높이는 데 필수적입니다.
-   **작업 분할 및 오케스트레이션 도입**: 복잡한 지식 작업은 단일 에이전트가 아닌, 오케스트레이터 에이전트가 상위 목표를 설정하고 여러 하위 에이전트(어시스턴트)에게 세분화된 작업을 위임하는 방식으로 조직화해야 합니다. 이는 인간의 전문 서비스 조직과 유사한 구조로, 효율성과 정확도를 높일 수 있습니다.
-   **컨텍스트 관리의 중요성 인식**: 컨텍스트는 유한한 자원이므로, 에이전트가 불필요한 정보를 처리하지 않도록 검색 작업을 효율적으로 오케스트레이션하고 관련성 높은 컨텍스트만 활용하도록 설계해야 합니다.
