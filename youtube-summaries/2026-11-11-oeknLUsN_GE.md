# Agents Made Code Free. Maintaining It Didn't Get Cheaper. - Dmitry Buykin, Maersk

🔗 https://youtu.be/oeknLUsN_GE · 📅 2026-11-11 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 코드를 저렴하게 만들었지만, 코드베이스의 엔트로피 증가로 인한 유지보수 비용은 더 비싸졌으며, 이를 해결하기 위해 6가지 핵심 원칙(시간, 공간, 현실, 정신, 힘, 영혼)을 기반으로 한 주간 정비 시스템을 구축하여 코드베이스의 혼란을 관리하고 통제하는 방법을 제시합니다.

## 발표자·소속
Dmitry Buykin · Maersk

## 핵심 주장
- **AI 에이전트가 코드 생성 비용을 낮췄지만, 엔트로피를 증가시켜 유지보수 비용을 높였다:** 코딩 에이전트의 사용은 코드 생성을 저렴하게 만들었지만, 이로 인해 코드베이스의 복잡성과 무질서(엔트로피)가 빠르게 증가하여 유지보수와 관리가 어려워지는 새로운 딜레마를 초래했습니다.
- **"브리치 라인" 아래로 엔트로피를 유지하는 것이 핵심이다:** 시스템의 변경 사항을 사람이 감당할 수 있는 수준인 "브리치 라인" 아래로 유지하기 위해, 매주 작은 규모의 정비(weekly sweeps)와 피드백 루프를 시스템에 내장하여 지속적으로 엔트로피를 관리해야 합니다.
- **코드와 산문(prose) 모두 엔지니어링이 필요하며, 인간의 판단이 여전히 중요하다:** 시스템의 대부분이 에이전트가 작성한 산문(prose instructions)으로 이루어져 있어, 코드뿐만 아니라 산문에도 테스트와 엔지니어링 원칙을 적용해야 합니다. 특히, 복잡한 시스템에서는 에이전트가 일관성을 깨뜨릴 수 있으므로, 인간 전문가의 판단이 필요한 영역을 명확히 하고 그들의 개입을 시스템에 통합하는 것이 중요합니다.
- **변화에 대한 증거를 체계적으로 수집하고 검증해야 한다:** 에이전트가 생성한 변경 사항의 진실성을 확인하기 위해, 실제 작업의 리플레이, 프로덕션 측정, 코드 라인 단위의 검증 등 다양한 증거를 계층적으로 활용하고, 새로운 검증 메커니즘은 의도적으로 한 번 실패하도록 설계하여 신뢰성을 확보해야 합니다.
- **시스템은 개발자와 전문가의 지식과 편향을 복제한다:** 시스템의 설계는 누가 시스템을 구축하고 수정하는지에 따라 그들의 습관과 편향을 반영합니다. 따라서 시스템이 올바른 방향으로 발전하도록 하려면, 개발자와 전문가의 판단과 지식을 시스템 설계에 의도적으로 통합하는 것이 중요합니다.

## 세부 내용

발표는 코딩 에이전트가 코드를 저렴하게 만들었지만, 이로 인해 엔트로피가 증가하여 유지보수 비용이 더 비싸지는 "타노스 딜레마"를 소개하며 시작됩니다. 발표자는 자신의 프로젝트에서 코드가 무질서하게 성장하여 결국 테스트와 사용되지 않는 코드를 삭제하고 프로젝트를 다시 작성해야 했던 경험을 공유합니다. 이는 "혼돈에 빠지거나 사람들이 사용하는 것을 망가뜨리는" 딜레마로 이어졌고, 발표자는 세 번째 옵션인 "브리치 라인" 아래로 엔트로피를 유지하는 방법을 찾았다고 말합니다.

이러한 목표를 달성하기 위해 6가지 "인피니티 스톤"에 비유되는 질문들을 제시합니다.

**1. 시간(Time): 브리치 라인 아래로 유지하는 방법은?**
프로젝트는 에이전트가 계속 코드를 작성하면서 다시 혼란스러워졌습니다. 발표자는 "브리치 라인"을 설정하여, 그 이상으로 변경이 발생하면 누구도 검토할 수 없게 됩니다. 해결책은 매주 작은 정비(weekly sweeps)를 통해 엔트로피를 브리치 라인 아래로 유지하고, 시스템에 피드백 루프를 구축하는 것입니다.

**2. 공간(Space): "옳다"는 무엇에 달려 있는가? 변화는 어디로 이동할 수 있는가?**
발표자는 "옳다"는 것이 테스트에 달려 있다고 생각했지만, 실제로는 팀의 판단에 달려 있었습니다. 시스템은 110개국에서 약 10,000개의 산문 지시 시나리오로 실행됩니다. 각 작업은 하나의 프로세스와 하나의 국가를 나타내는 "슬라이스"에 할당됩니다. 변경은 기본적으로 해당 슬라이스 내에 머무릅니다.

**3. 현실(Reality): 시스템의 4분의 1은 코드, 4분의 3은 산문이다. 둘 다 엔지니어링이 필요하다. 그것이 사실인가?**
시스템의 대부분은 산문(prose)으로 구성되어 있어, 산문에도 엔지니어링이 필요합니다. 발표자는 코드의 TDD(테스트 주도 개발)와 BDD(행동 주도 개발)에서 영감을 받아 산문에 "변이 테스트(mutation tests)"를 적용했습니다. 그러나 산문은 쉽게 깨지지 않았고, 이는 테스트가 산문의 "옳음"을 결정하지 못한다는 것을 보여주었습니다. 에이전트가 복잡한 시스템을 스스로 구축할 수 없으며, 일관성을 깨뜨릴 수 있기 때문에 인간의 판단이 필요합니다. 비즈니스 전문가들은 규칙을 보지만, 개발자들은 계약, 와이어 포맷, 레거시 시스템 등 "물 아래"의 연결을 봅니다. 개발자는 코딩 에이전트를 사용하여 이러한 연결을 기록하고 런타임에 검증합니다.

**4. 정신(Mind): 결정이 행동이 된다. 통제 상태를 유지한다는 것은 무엇을 의미하는가?**
통제는 모델이 무엇을 아는지에서 시작됩니다. 모델이 무엇을 로드할지 선택하게 했을 때, 모델은 모든 것을 로드하고 불필요한 작업(예: 가격 확인)을 발명했습니다. 런타임은 모델이 보는 것을 결정하고, 모델은 몇 가지 사실만 보고 결정을 내립니다. 모델에게 전체 데이터 뭉치(haystack) 대신 핸들(handle)을 제공하여 컨텍스트 블로트(context bloat)를 최소화하고 일관성을 검증합니다. 변경은 개발 중에 한 번, 런타임에 한 번, 총 두 번 통제됩니다. 런타임 시에는 라우트 정책, 지시 허용 목록, 쓰기 게이팅, 동의, 저널, 읽기 백 등 6가지 제어 장치가 작동합니다.

**5. 힘(Power): 한 사람의 주의력을 넘어선다. 언제 통제력을 잃고 있는지 어떻게 아는가?**
발표자는 자신의 인지적 과부하가 첫 번째 경고 신호였다고 말합니다. 모든 변경 사항을 읽을 수 없을 때, 병렬 작업을 중단하고, 변경 사항을 설명 가능하게 만들고, 핸드오프를 복원하는 조치를 취했습니다. 변화의 속도가 주의력을 넘어설 때, 도메인별 변화율, 경계 누출, 계약 차이, 폭발 반경(blast radius)과 같은 파생 지표를 모니터링했습니다. 문제가 발생하면, 단일 신호가 돌아올 때까지 기다리거나, 여러 슬라이스에 걸쳐 클러스터가 형성될 때까지 기다립니다. 클러스터가 형성되면, 에이전트가 추가한 조건을 제거하고 개념을 한 번에 수정합니다. 빨간색 슬라이스(오류 발생)는 모든 관련 슬라이스에 걸쳐 정비를 시작하며, 수정 사항은 오류가 확인된 곳에만 적용됩니다.

**6. 영혼(Soul): 무엇이 살아남을 가치가 있는가?**
에이전트는 하나의 프로세스를 여러 버전으로 분기시켰습니다. 어떤 브랜치는 다시 병합되었고, 어떤 브랜치는 여전히 표류하며, 어떤 브랜치는 죽었지만 살아있는 것처럼 보입니다. 매주 실제 사용(real use)을 기반으로 무엇이 남을지 결정합니다. 실제 작업이 도달하지 않는 모든 것은 이름과 증거를 부여받은 후 제거됩니다. 테스트는 죽은 변형을 살려두는 경향이 있어, 실제 사용만이 무엇이 살아남을 가치가 있는지 결정합니다. 전체 방법론은 주간 프로세스로 요약됩니다: 월요일에 신호를 분류하고, 화요일에 클러스터를 확인하며, 수요일에 개념을 수정하고, 목요일에 관련 슬라이스를 정비하며, 금요일에 원장을 닫고 가지치기를 합니다.

결론적으로, 발표자는 6가지 스톤을 모두 사용하여 두 번째 스냅(대규모 삭제) 없이 시스템을 유지할 수 있었다고 말합니다. 시스템은 이를 구축하고 수정한 사람들의 지식과 편향을 복제합니다. 발표자는 "아마도 타노스는 정원에서 시작했어야 했고, 스냅으로 끝내지 말았어야 했다"고 말하며, 모든 변화를 읽을 수 있을 때 자신의 스톤(원칙)을 사용하라고 조언합니다.

## 인상적인 대목
- "Agents made code cheap. They made entropy cheaper." (0:08) - 에이전트가 코드 생성 비용을 낮췄지만, 시스템의 무질서(엔트로피)를 증가시켜 유지보수 비용을 더 비싸게 만들었다는 역설적인 통찰.
- "Drawn in chaos or break what people use." (0:48) - 코드베이스 유지보수에서 겪는 딜레마를 명확하게 표현한 문장.
- "A rewrite is easy. Knowing what must survive is the hard part." (2:51) - 에이전트 시대에 코드 재작성은 쉬워졌지만, 진정으로 중요한 비즈니스 로직과 기능을 식별하는 것이 더 어려워졌다는 점을 지적.
- "Developers hold what experts can't see." (3:45) - 비즈니스 전문가는 규칙을 보지만, 개발자는 시스템 내부의 복잡한 연결과 숨겨진 버그를 본다는 아이스버그 비유.
- "My own sanity is the gauge that fires first." (10:09) - 시스템의 통제력을 잃고 있다는 첫 번째 신호가 개인의 인지적 과부하라는 점을 솔직하게 표현.
- "Maybe Thanos should start in the garden, not finish with the snap." (17:52) - 문제 발생 후 대규모 조치(스냅)를 취하기보다, 일상적으로 작은 규모의 관리를 통해 문제를 예방해야 한다는 비유적인 조언.

## 실무 적용 포인트
- **산문(Prose)에 대한 엔지니어링 접근 방식 도입**: AI 에이전트가 생성하는 비즈니스 규칙이나 지시사항(산문)에 대해서도 코드와 유사하게 테스트(변이 테스트), 컴파일러, 린터 등을 적용하여 품질과 일관성을 관리합니다.
- **인간의 판단과 자동화의 명확한 경계 설정**: 시스템 내에서 인간 전문가의 판단이 필수적인 영역(예: 복잡한 비즈니스 결정)과 자동화할 수 있는 영역을 명확히 구분하고, 개발자가 데이터와 증거를 기반으로 이 경계를 결정하도록 합니다.
- **주간 엔트로피 관리 및 가지치기 프로세스 구현**: "브리치 라인"을 설정하고, 매주 시스템의 변경 사항을 검토하여 사용되지 않거나 불필요한 코드/산문을 제거(가지치기)하는 루틴을 만듭니다. 이때 실제 사용(real use) 데이터를 기반으로 무엇을 유지할지 결정합니다.
- **변경 검증을 위한 다단계 제어 및 피드백 루프 구축**: 개발 단계와 런타임 단계에서 여러 제어 장치(라우트 정책, 동의, 저널, 읽기 백 등)를 통해 변경 사항을 검증하고, 에이전트가 변경을 생성하면 다른 에이전트가 이를 검증하는 이중 검증 시스템을 도입하여 신뢰성을 높입니다.
