## 세부 내용
발표는 Codex 에이전트의 내부 작동 방식을 설명하며 시작됩니다. 에이전트 루프는 대화 기록을 조합하고, 최신 사용자 입력을 받아 모델 추론을 수행한 후, 에이전트 응답을 생성하거나 도구를 호출하는 방식으로 진행됩니다. OpenAI의 `openai/codex` GitHub 저장소는 Apache 2 라이선스로 공개되어 있으며, Rust로 작성된 하네스를 포함합니다. 발표자는 이 모든 내용이 현재 시점의 스냅샷이며, 모델 및 API는 빠르게 진화한다고 강조합니다.

Codex 에이전트는 두 가지 주요 프로토콜을 통해 작동합니다. 첫째, **앱 서버(App server)**는 UI(Codex 데스크톱 앱, TUI/CLI, 웹 런타임 등)와 에이전트 간의 통신을 JSON-RPC를 통해 처리합니다. 이는 JetBrains IDE, VS Code, Xcode와 같은 서드파티 통합도 지원하는 개방형 생태계를 목표로 합니다. 둘째, **Responses API**는 에이전트와 LLM 추론 간의 통신을 담당하며, 에이전트 사용 사례를 염두에 두고 Chat Completions API를 재설계한 것입니다. 웹 검색, 이미지 생성과 같은 내장 기능이 포함되어 있으며, Ollama, LM Studio, Nvidia 등 다양한 호스팅 제공업체와 함께 OpenResponses 프로토콜을 기반으로 합니다.

**하네스(Harness)** 내부에서는 컨텍스트 구성이 중요합니다. 컨텍스트 크기(비용 및 혼란 방지), 유연성(다양한 스킬 및 플러그인 지원), 캐시 가능성(성능 및 비용 제어) 세 가지 요소가 고려됩니다. 컨텍스트 크기를 관리하기 위해, 중요도가 낮은 도구는 "지연 로딩(deferred loading)"으로 표시되어 필요할 때만 도구 검색을 통해 로드됩니다. 또한, 사용 가능한 스킬 목록은 최대 컨텍스트 창의 2%로 제한하여 불필요한 토큰 사용을 줄입니다.

에이전트의 **액션(Actions)**은 세 가지 유형으로 나뉩니다.
1.  **비동기 액션(Async actions)**: 서브에이전트(subagents)를 통해 구현됩니다. `spawn_agent` 도구를 사용하여 새로운 에이전트 인스턴스를 생성하고, `send_input` 도구를 사용하여 이들에게 입력을 전달하며, 메인 에이전트는 작업을 계속 진행할 수 있습니다. 이는 백그라운드 터미널에도 적용됩니다.
2.  **컴퓨터 사용(Computer use)**: 초기에는 제한된 고정 명령을 사용했지만, 이제는 모델이 직접 코드를 실행하여 복잡한 작업을 수행할 수 있도록 **코드 실행(Code execution)**으로 발전했습니다. JavaScript나 Python과 같은 언어로 컴퓨터 인터페이스를 스크립팅할 수 있어 유연성이 높습니다. 데모에서는 Playwright 코드를 사용하여 브라우저와 상호작용하고 웹 페이지에서 정보를 스크랩하는 과정을 보여줍니다.
3.  **파일 시스템(Filesystem)**: `apply_patch` 도구를 사용하여 파일 변경을 수행하고, `shell` 도구를 통해 `rip_grep` 같은 명령어를 실행하여 파일 검색 및 기타 파일 시스템 작업을 처리합니다. 모든 파일 시스템 상호작용은 샌드박스(sandbox)를 통해 이루어집니다. macOS에서는 Seatbelt, Linux에서는 Bubblewrap, Windows에서는 자체 개발한 오픈 소스 샌드박스를 사용합니다.

**승인 피로도(Approval fatigue)** 문제를 해결하기 위해 **자동 검토(Auto-review)** 모드가 도입되었습니다. 이는 에이전트가 잠재적으로 위험한 작업을 수행하기 전에 사용자 승인을 요청하는 대신, 별도의 서브에이전트가 에이전트의 행동을 검토하고 승인 여부를 결정하는 방식입니다. 자동 검토 에이전트는 사용자 권한 부여, 위험 수준 분류(낮음, 중간, 높음, 치명적), 그리고 행동의 맥락을 고려하여 판단을 내립니다. 이를 통해 사용자는 안전하면서도 효율적인 에이전트 경험을 얻을 수 있습니다.

에이전트의 **속도(Speed)**는 LLM 추론 속도뿐만 아니라 네트워크 통신에도 크게 좌우됩니다. GPT-5.3-Codex-Spark와 같은 모델이 초당 1000개 이상의 토큰을 생성할 정도로 빨라지면서, 네트워크가 병목 현상이 되었습니다. 이를 해결하기 위해 **웹소켓 모드(Websocket Mode)**가 도입되었습니다. Responses API가 HTTP 대신 영구적인 웹소켓 연결을 사용하고, 전체 컨텍스트 대신 변경된 데이터만 전송하는 상태 저장(stateful) 방식을 통해 네트워크 오버헤드를 줄이고 처리 속도를 크게 향상시킵니다.

마지막으로, 에이전트가 장시간 실행될 때 컨텍스트 창이 너무 커지는 것을 방지하기 위해 **압축(Compaction)** 기능이 제공됩니다. 이는 Responses API를 통해 수동 또는 자동으로 트리거될 수 있으며, 이전 대화 기록을 압축하여 새로운 컨텍스트를 생성함으로써 모델의 성능을 일정하게 유지합니다.
