# How to Build a Software Factory That Improves Itself - Zach Lloyd, Warp

🔗 https://youtu.be/nKjPBAw_N_0 · 📅 2026-11-09 · 🎙 AI Engineer

## 한 줄 요약
소프트웨어 팩토리는 개방적이고 적응 가능하며 코드로 정의되어야 하며, 측정과 자체 개선을 통해 개발 프로세스를 자동화하고 최적화하는 데 중점을 두어야 합니다.

## 발표자·소속
Zach Lloyd, Warp 창립자 겸 CEO

## 핵심 주장
-   **에이전트 개발의 진화와 현재의 한계:** 현재 대부분의 기업은 대화형 프롬프팅(ChatGPT, Claude Code 등) 단계에 머물러 있으며, 이는 비즈니스 가치 창출에 한계가 있습니다. 상호작용적 사용은 자동화가 부족하고, 비용 및 품질 최적화가 체계적이지 않으며, 거버넌스와 통제를 위한 중앙 레이어가 없습니다.
-   **로컬 에이전트의 보안 및 관리 문제:** 로컬 환경에서 실행되는 에이전트는 보안에 취약하며(사용자 권한 탈취 가능성), 개별 설정으로 인해 관리 및 감사(governance)가 어렵습니다.
-   **클라우드 소프트웨어 팩토리의 필요성:** 이러한 문제를 해결하기 위해 에이전트를 샌드박스 처리하고 클라우드로 이동시켜야 합니다. 클라우드 소프트웨어 팩토리는 인간과 에이전트가 협력하여 소프트웨어 개발 라이프사이클(트리아지, 사양, 구현, 검증, 배포, 모니터링)을 자동화하는 루프를 만듭니다.
-   **팩토리 인프라의 핵심 특성:** 소프트웨어 팩토리는 개방적이고(다양한 모델 및 하네스 지원), 적응 가능하며(기존 인프라와 연동), 코드로 정의되어야 합니다(버전 관리, 테스트 가능성). 이는 AI 주권(데이터, 컴퓨팅, 추론 게이트웨이 소유)을 보장하고 옵션 선택의 유연성을 제공합니다.
-   **측정 기반의 개선:** "측정 > 분위기(Vibes)"라는 원칙 하에, 팩토리의 성능을 측정하고(생산성, 비용, 스코어링), 이 데이터를 기반으로 에이전트가 팩토리 자체를 개선하는 "자체 개선 루프"를 구축해야 합니다.

## 세부 내용

발표자는 자신을 구글의 Principal Engineer였으며 GDocs 엔지니어링을 이끌었고, 현재는 Warp의 창립자 겸 CEO라고 소개했습니다. Warp는 에이전트 개발 분야의 회사로, 기업들이 자체 소프트웨어 팩토리를 구축하도록 돕는 Warp Factories 플랫폼과 에이전트 터미널인 Warp Terminal을 운영하고 있습니다.

발표자는 에이전트 개발의 진화를 설명하며 현재 대부분의 기업이 "대화형 프롬프팅(Interactive Prompting)" 단계에 있다고 언급했습니다. 이 단계에서는 개발자들이 랩톱에서 Claude Code나 Codex와 같은 도구를 사용하여 기능 개발이나 버그 수정을 위해 에이전트에게 대화형으로 프롬프트를 제공합니다. 그러나 발표자는 기업들이 궁극적으로 "자동화된 개발(Automated Development)"로 나아가기를 원한다고 강조했습니다.

현재의 대화형 프롬프팅 방식의 문제점은 다음과 같습니다.
1.  **애드혹(Ad hoc) 사용, 자동화 부족:** 상호작용적 사용은 자동화가 부족하여 비즈니스 가치 창출에 한계가 있습니다.
2.  **체계적인 비용 및 품질 최적화 부재:** 각 엔지니어가 개별적으로 에이전트를 사용하므로 비용을 최적화하거나 품질을 체계적으로 관리하기 어렵습니다.
3.  **거버넌스 및 통제 중앙 레이어 부재:** 로컬 에이전트는 보안에 취약하며(사용자 권한 탈취 가능성), 각 엔지니어가 자신만의 MCP(Model, Context, Prompt), 스킬, 도구를 구성하므로 무엇이 진행되고 있는지 파악하거나 감사하기 어렵습니다.

발표자는 이러한 문제에 대한 해결책으로 에이전트를 샌드박스 처리하고 클라우드로 이동시키는 것을 제안했습니다. 이를 통해 "클라우드 소프트웨어 팩토리"라는 새로운 개념이 등장합니다. 이 팩토리는 소프트웨어 개발 라이프사이클(새로운 제품 아이디어/버그 보고 -> 트리아지 -> 사양 -> 구현 -> 검증 -> 배포 -> 모니터링)을 인간과 에이전트가 협력하여 자동화하는 루프입니다. 인간은 작업 투입, 사양 검토, 코드 검토, 제품 검토 등 핵심적인 의사결정 및 검토 단계에 참여하고, 에이전트는 트리아지, 구현, 검증 등 반복적이고 자동화 가능한 작업을 수행합니다.

이러한 소프트웨어 팩토리는 개방적이고, 적응 가능하며, 코드로 정의된 인프라 스택 위에 구축되어야 합니다.
-   **개방성(Open):** OpenAI, Frontier와 같은 다양한 모델과 하네스를 지원해야 합니다.
-   **적응성(Adaptable):** 기존 인프라와 원활하게 연동되어야 합니다.
-   **코드로 정의(Defined in code):** 팩토리의 모든 구성 요소(워크플로, 스킬, 도구, MCP, 실행 환경 등)는 코드로 정의되고 버전 관리되어야 합니다. 이를 통해 팩토리의 다양한 버전을 테스트하고, 코딩 에이전트가 팩토리를 업데이트할 수 있습니다.

또한, "AI 주권(AI Sovereignty)"이 중요하다고 강조했습니다. 기업은 데이터, 컴퓨팅 자원, 추론 게이트웨이를 소유하고, 어떤 모델이나 하네스든 사용할 수 있는 유연성을 확보해야 합니다.

"측정 > 분위기(Vibes)" 원칙도 중요합니다. 팩토리의 성능을 측정하고 개선하는 것이 핵심입니다.
-   **스코어링(Scoring):** 코딩 에이전트의 성능을 평가합니다.
-   **자체 개선(Self-improvement):** 스코어링 결과를 바탕으로 에이전트가 팩토리 자체를 개선합니다.
-   **벤치마킹(Benchmarking):** 실제 워크플로 데이터를 기반으로 자체 벤치마크를 생성하여 다양한 모델과 하네스의 성능을 비교합니다.

발표자는 소프트웨어 팩토리를 사용하는 두 가지 유형의 엔지니어를 제시했습니다.
1.  **제품 엔지니어(Product Engineer):** 고객을 위한 유용한 기능을 구축하고 버그를 수정하는 데 집중하며, 팩토리를 통해 작업을 수행합니다.
2.  **팩토리 엔지니어(Factory Engineer):** 팩토리 자체를 개선하는 데 집중합니다. 스킬 개선, 컨텍스트 설정, 모델 믹스 변경 등 팩토리의 효율성과 성능을 높이는 작업을 합니다.

**데모 시연:**
발표자는 Warp Factories 플랫폼의 대시보드를 시연했습니다.
-   **생산성(Productivity) 탭:** PR당 인간 상호작용 횟수, 평균 사이클 시간(PR 생성부터 병합까지), 에이전트 유형별 총 실행 횟수 등을 보여줍니다.
-   **지출(Spending) 탭:** PR당 비용, 소스별 지출(Black, Warp, Factory MCP 등)을 그래프로 시각화하여 보여줍니다.
-   **스코어러(Scorers) 탭:** "Redundant Tests"와 같은 스코어러들이 에이전트의 실행 결과를 평가하여 합격률과 실패율을 보여줍니다. 예를 들어, 에이전트가 불필요한 테스트를 작성했는지 여부를 LLM이 판단하여 점수를 매깁니다.
-   **실행(Runs) 탭:** 팀의 모든 엔지니어와 자동화 에이전트가 수행한 모든 작업(PR 생성, 코드 검토, 버그 수정 등)의 목록을 보여줍니다. 각 작업은 GitHub, Slack, Linear 등 관련 도구와 연결되어 있으며, 모든 에이전트 트레이스(대화 내용, 실행 단계, 아티팩트)가 저장됩니다.
-   **에이전트(Agents) 탭:** 팩토리 워크플로를 오케스트레이션하는 "Wilson Foreman" 에이전트와 "code-review", "implementation", "spec", "triage", "design" 에이전트들의 정의를 보여줍니다. 각 에이전트의 정의는 GitHub 리포지토리(`factory.yaml`)에 코드로 저장되어 버전 관리가 가능합니다.
-   **자체 개선(Self-Improvement) 탭:** 스코어러에서 발견된 실패 모드들을 에이전트가 집계하고 패턴을 분석하여 팩토리 정의를 개선하는 PR을 제안하는 과정을 보여줍니다. 예를 들어, "Read matching repository skills before implementing"이라는 문제에 대해 에이전트가 PR을 생성하여 팩토리의 스킬 정의를 업데이트하는 모습을 시연했습니다.
-   **벤치마크(Benchmarks) 탭:** 과거 실행 데이터를 기반으로 벤치마크를 생성하고, 다양한 모델 구성(예: gpt-5.6-sol, gpt-5.3-flash, gemini-1.7-flash)에 대한 정확성(Correctness)과 평균 비용(Average cost) 간의 트레이드오프를 시각화한 그래프를 보여줍니다. 이를 통해 특정 워크플로에 가장 적합한 모델 라우팅 전략을 수립할 수 있습니다.

발표자는 결론적으로, 세계는 팩토리로 움직이고 있으며, 팩토리는 개방적이고, 적응 가능하며, 코드로 정의되어야 한다고 재차 강조했습니다. 이를 위해 에이전트를 샌드박스 처리하고, 데이터를 소유하며, 측정 기반의 접근 방식을 채택해야 합니다.

## 인상적인 대목
-   "More AI usage != more business value." (더 많은 AI 사용이 더 많은 비즈니스 가치를 의미하지는 않는다.) - AI 도구의 단순한 도입을 넘어 실제 가치 창출을 위한 체계적인 접근의 중요성을 강조하는 문장.
-   "Local agents are insecure agents. Local agents are ungovernable agents." (로컬 에이전트는 안전하지 않은 에이전트이다. 로컬 에이전트는 관리 불가능한 에이전트이다.) - 로컬 환경에서 에이전트를 사용하는 것의 근본적인 보안 및 거버넌스 문제를 명확히 지적.
-   "Software factories should be built on an infrastructure stack that is open, adaptable, and defined in code." (소프트웨어 팩토리는 개방적이고, 적응 가능하며, 코드로 정의된 인프라 스택 위에 구축되어야 한다.) - 소프트웨어 팩토리 구축의 핵심 원칙을 한 문장으로 요약.
-   "Measurement > Vibes" (측정 > 분위기) - AI 개발 및 팩토리 개선에 있어 주관적인 느낌보다는 객관적인 데이터와 측정을 우선시해야 한다는 강력한 메시지.
-   "The key thing here is like, it's saying I saw this fail 37 times, and then it's saying, okay, we can actually fix this with a PR to the factory definition." (핵심은 이것이 37번 실패했다고 말하고, 그 다음 팩토리 정의에 대한 PR로 이것을 실제로 고칠 수 있다고 말하는 것이다.) - 에이전트가 스스로 문제를 식별하고, 팩토리의 코드를 수정하여 개선하는 "자체 개선 루프"의 구체적인 작동 방식을 설명하는 대목.

## 실무 적용 포인트
-   **팩토리 정의의 코드화:** 소프트웨어 팩토리의 모든 구성 요소(에이전트 정의, 워크플로, 스킬, 자동화, 벤치마크 등)를 코드로 정의하고 Git과 같은 버전 관리 시스템에 저장하여 변경 사항을 추적하고 관리할 수 있도록 합니다. 이는 팩토리의 투명성과 재현성을 높입니다.
-   **측정 및 모니터링 시스템 구축:** PR당 비용, 사이클 시간, 에이전트별 실행 횟수, 스코어링 결과 등 팩토리의 생산성, 비용, 품질 지표를 지속적으로 측정하고 모니터링하는 대시보드를 구축합니다. 이를 통해 팩토리의 성능을 객관적으로 파악하고 개선점을 식별할 수 있습니다.
-   **자체 개선 루프 도입:** 스코어링 시스템을 통해 에이전트의 실패 모드를 식별하고, 이를 분석하여 팩토리 정의를 개선하는 에이전트(자체 개선 에이전트)를 도입합니다. 이 에이전트는 실패 패턴을 찾아 팩토리의 코드를 수정하는 PR을 생성하여 지속적인 개선을 유도합니다.
-   **실제 데이터 기반 벤치마킹:** 공개된 벤치마크보다는 실제 팀의 과거 작업 데이터를 활용하여 자체 벤치마크 스위트를 구축합니다. 이를 통해 다양한 LLM 모델과 하네스의 조합이 실제 워크플로에서 어떤 정확성과 비용 트레이드오프를 가지는지 측정하고, 최적의 모델 라우팅 전략을 수립할 수 있습니다.
