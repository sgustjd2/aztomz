# The unreasonable effectiveness of BM25 for agentic search — Jo Kristian Bergum, Hornet.dev

🔗 https://youtu.be/fZH97QHHYjY · 📅 2026-09-16 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트의 검색 성능을 최적화하기 위해 BM25와 같은 30년 된 어휘 기반 검색 함수가 새로운 사용자(GPT-5와 같은 대규모 언어 모델)의 능력과 결합하여 강력한 도구로 재부상하고 있으며, 이는 에이전트 검색의 평가 방식과 인프라 구축에 변화를 가져온다.

## 발표자·소속
Jo Kristian Bergum, CEO, Hornet.dev

## 핵심 주장
-   **새로운 사용자(AI 에이전트)의 등장으로 검색 패러다임이 변화했습니다.** GPT-5와 같은 대규모 언어 모델(LLM)은 일반 지식을 활용하여 복잡하고 상세한 쿼리를 생성하며, 검색 결과를 바탕으로 쿼리를 재구성하는 능력을 갖추고 있습니다. 이는 기존의 짧고 단일한 인간 쿼리 방식과는 다른 새로운 검색 워크로드를 만들어냅니다.
-   **BM25는 에이전트 검색을 위한 강력하고 해석 가능한 기본 도구입니다.** BM25는 정확한 매칭(이름, 날짜, 구문 등)에 강점을 가지며, 임베딩 추론 비용이 없어 저렴하고, 모델이 검색 결과를 이해하고 다음 단계를 결정하는 데 도움이 되는 설명 가능성을 제공합니다.
-   **검색 품질은 에이전트의 최종 답변 정확도에 결정적인 영향을 미칩니다.** BrowseComp-Plus 벤치마크에서 BM25의 매개변수를 최적화하여 검색 품질을 향상시키면 에이전트의 답변 정확도가 64.0%에서 82.0%로 크게 증가하는 것을 보여주며, 이는 모델의 추론 능력만큼이나 적절한 증거를 검색하는 것이 중요함을 시사합니다.
-   **BM25와 grep 같은 단순한 도구의 조합이 에이전트 검색에 효과적입니다.** 방대한 문서에서 BM25로 후보 문서를 검색하고, 이를 가상 파일 시스템(VFS)에 노출한 뒤, 에이전트가 grep과 같은 셸 도구를 사용하여 문서를 검사하고 정제하는 '점진적 공개(progressive disclosure)' 방식은 높은 정확도를 달성하며 효율적인 에이전트 루프를 가능하게 합니다.

## 세부 내용
발표는 AI Engineer World's Fair에서 진행되었으며, Jo Kristian Bergum은 Hornet.dev의 CEO로서 "에이전트 검색을 위한 BM25의 비합리적인 효과"라는 주제로 발표했습니다. 그는 20년 이상 검색 및 검색 문제에 종사해 왔으며, Hornet.dev는 에이전트를 위한 검색 인프라를 구축하고 있다고 소개했습니다.

**에이전트 검색의 정의와 구성 요소:**
에이전트 검색은 "에이전트 루프 내에서 이루어지는 검색"으로 정의됩니다. 이를 위해서는 세 가지 핵심 요소가 필요합니다.
1.  **모델 (LLM)**: 언제 검색할지 선택하고 쿼리를 구성하는 능력을 갖춘 모델입니다.
2.  **하네스 (Harness)**: 에이전트 루프를 실행하고 검색 쿼리 같은 도구 계약을 정의하며, 컨텍스트, 호출, 비용 등의 예산을 관리합니다.
3.  **검색 엔진 (Retrieval Engine)**: 효율적으로 검색을 수행하고 후보를 순위화하며, 결과를 노출하고 반복적인 검색을 처리할 수 있어야 합니다. 이는 잠재적으로 수십억 개의 문서에 걸쳐 이루어질 수 있습니다.

**BM25란 무엇인가?**
BM25는 "Best Match 25"의 약자로, 1990년대 Okapi TREC에서 개발된 어휘 기반 순위 함수입니다. 이는 쿼리와 문서 간의 점수를 계산하는 함수로, 용어 희소성, 용어 빈도, 문서 길이 정규화 등을 고려하여 단일 숫자를 산출합니다. BM25는 상위 K개 문서 검색(top-k retrieval)을 위해 역색인 및 WAND와 같은 알고리즘을 사용하여 가장 관련성 높은 후보를 효율적으로 반환합니다.

**BM25의 재부상: 사용자의 변화**
BM25 자체는 변하지 않았지만, 사용자가 더 강력해졌습니다. 기존의 단일 샷(single-shot) 검색에서는 짧은 인간 쿼리, 단일 순위 목록, nDCG@10과 같은 지표로 BM25를 평가했습니다. 그러나 GPT-5와 같은 LLM 에이전트는 모델 내에 풍부한 일반 지식(엔티티, 회사, 날짜 등)을 가지고 있으며, 이를 활용하여 상세한 쿼리를 생성하고, 검색 결과에 대한 관련성 피드백을 통해 쿼리를 지속적으로 재구성할 수 있습니다. 이는 BM25를 단순히 이겨야 할 '기준선'이 아닌, '해석 가능한 기본 도구'로 만듭니다.

**에이전트 검색 벤치마크: BrowseComp-Plus**
BrowseComp-Plus는 딥 리서치 에이전트를 위한 벤치마크로, 수수께끼 같은 다중 홉(multi-hop) 질문에 대한 답변을 찾는 것이 목표입니다. 에이전트는 '생각(think)'하고, '검색(search)' 도구를 호출하며, BM25를 통해 상위 5개 문서를 검색하고, '읽고 재구성(read + reformulate)'한 후 최종 답변을 제출하는 루프를 반복합니다. 이 벤치마크는 830개의 질문과 100,195개의 웹 페이지로 구성된 고정된 문서 세트를 사용합니다.

**검색 품질의 중요성:**
발표자는 컨텍스트 윈도우를 플로피 디스크에 비유하며, 현재 LLM의 컨텍스트 윈도우가 약 350K-370K 토큰(약 1.44MB 플로피 디스크 하나 분량)에 불과하다고 설명했습니다. BrowseComp-Plus 코퍼스(736M 토큰)의 0.05%에 불과한 양입니다. 따라서 모델이 추론할 '플로피 디스크 크기'의 슬라이스를 결정하는 것이 검색의 역할입니다.

BrowseComp-Plus 벤치마크에서, 기본 BM25를 사용했을 때 답변 정확도는 55.9%였으나, 더 강력한 검색 증거를 사용했을 때 70.1%로 증가했습니다. 만약 모델에 정답을 찾기 위한 '오라클 증거(oracle evidence)'를 직접 제공하면 정확도는 93%에 달합니다. 이는 모델의 추론 능력이 충분하더라도, 검색 품질이 최종 답변 정확도에 결정적인 영향을 미친다는 것을 보여줍니다.

**쿼리 세션으로서의 질문:**
에이전트 검색에서는 하나의 질문이 여러 번의 쿼리 재구성을 포함하는 '쿼리 세션'이 됩니다. 예를 들어, 초기에는 넓은 범위의 쿼리(`site:newsroom 2017 acquisition founder`)를 사용하다가, 검색 결과를 읽은 후 쿼리를 좁히고(`"appointment" 2019 founder`), 최종적으로 답변을 검증하기 위한 상세 쿼리(`"person name" "role" "date"`)를 생성합니다. GPT-5는 인간의 평균 쿼리(2개 용어)보다 훨씬 긴 10개 용어의 쿼리를 생성하며, `site:` 필터, 연도, 엔티티, 구문 매칭 등 고급 검색 연산자를 활용합니다. 이는 새로운 유형의 워크로드입니다.

**어떤 BM25를 사용할 것인가?**
BM25는 k1과 b라는 두 개의 하이퍼파라미터를 가지고 있습니다. BrowseComp-Plus 벤치마크에서 기본 BM25(k1=0.9, b=0.4)는 64.0%의 답변 정확도를 보였지만, 튜닝된 BM25(k1=2.5, b=1)는 82.0%로 18%p 향상되었습니다. 이는 BM25의 구현과 매개변수 튜닝이 성능에 큰 영향을 미친다는 것을 의미합니다.

**BM25가 효과적인 이유:**
1.  **정확성 (EXACT)**: 이름, 날짜, ID, 구문과 같은 정확한 매칭에 강합니다. LLM은 이러한 엔티티를 잘 알고 쿼리에 포함할 수 있습니다.
2.  **저렴함 (CHEAP)**: 임베딩 추론이 필요 없어 비용 효율적입니다.
3.  **설명 가능성 (EXPLAIN)**: 모델이 검색 결과를 쉽게 검사하고 이해할 수 있어, 어떤 용어가 매칭되었는지 파악하고 다음 쿼리 재구성으로 이어질 수 있습니다.

**에이전트를 위한 SERP: 점진적 공개 (Progressive Disclosure)**
"BM25 + grep이면 충분하다"는 주장은 수십억 개의 문서에서 BM25를 통해 후보 문서를 검색한 다음, 이 후보들을 가상 파일 시스템(VFS)에 노출하는 방식을 제안합니다. 에이전트는 이 VFS 내에서 `rg`(ripgrep) 및 `read`와 같은 간단한 셸 도구를 사용하여 문서를 검사하고, 쿼리를 좁히고, 답변을 검증하는 루프를 실행합니다. 이 방식은 BrowseComp-Plus에서 73.3%의 정확도를 달성하여, 기존의 DCI read + grep 방식(61%)보다 우수함을 보여줍니다. 이는 LLM이 코딩, 셸 도구 사용에 능숙하다는 점을 활용하여 검색 인프라를 구축하는 강력한 방법입니다.

**에이전트 + 검색 시스템 평가:**
전통적인 정보 검색(IR)에서는 단일 쿼리, 단일 순위 목록, nDCG와 같은 지표로 평가했지만, 에이전트 검색에서는 '트랙토리(trajectory)' 전체를 시스템으로 평가해야 합니다. 성공률, 호출 횟수, 지연 시간, 비용 등이 새로운 평가 지표가 됩니다. Hornet.dev는 BM25에 투자하여 1억 개의 웹 문서를 단일 노드에서 처리할 때 다른 엔진보다 훨씬 효율적인(낮은 지연 시간, 높은 처리량) 성능을 달성했습니다.

## 인상적인 대목
-   "BM25 did not become magic. The user changed." (BM25가 마법이 된 것이 아니라, 사용자가 변했다.)
-   "Retrieval decides which floppy-sized slice the model gets to reason over." (검색은 모델이 추론할 플로피 디스크 크기의 조각을 결정한다.)
-   "Oracle evidence reaches 93%. Retrieval quality is core to answer quality." (오라클 증거는 93%에 도달한다. 검색 품질이 답변 품질의 핵심이다.)
-   "BM25 + grep is all you need." (BM25 + grep이면 충분하다.)

## 실무 적용 포인트
-   **에이전트 쿼리 특성 이해 및 활용**: LLM 에이전트가 인간보다 훨씬 상세하고 복잡한 쿼리(예: 10개 용어 중앙값, `site:` 연산자, 엔티티, 구문 매칭 포함)를 생성한다는 점을 인지하고, 검색 시스템이 이러한 '파워 유저 쿼리'를 효과적으로 처리할 수 있도록 설계해야 합니다.
-   **BM25 매개변수 튜닝의 중요성**: BM25의 기본 매개변수가 특정 작업에 최적화되지 않을 수 있으므로, 대상 문서의 특성(예: 문서 길이)을 고려하여 k1, b와 같은 하이퍼파라미터를 튜닝하는 것이 에이전트의 최종 답변 정확도를 크게 향상시킬 수 있습니다.
-   **점진적 공개(Progressive Disclosure) 검색 아키텍처 고려**: 방대한 코퍼스에서 에이전트가 필요한 정보를 효율적으로 찾도록 돕기 위해, BM25로 초기 후보를 검색하고 이를 가상 파일 시스템(VFS)에 노출한 뒤, 에이전트가 `grep`과 같은 셸 도구를 사용하여 점진적으로 정보를 탐색하고 정제하는 아키텍처를 구축하는 것을 고려할 수 있습니다.
-   **시스템 단위 평가 지표 도입**: 에이전트 검색 시스템의 성능을 평가할 때는 단일 쿼리 기반의 전통적인 지표(nDCG)를 넘어, 전체 쿼리 트랙토리(trajectory)에 대한 성공률, 호출 횟수, 지연 시간, 비용 등 시스템 전반의 지표를 활용하여 에이전트와 검색기의 상호작용을 종합적으로 평가해야 합니다.
