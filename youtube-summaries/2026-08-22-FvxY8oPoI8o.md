# Preferences Over Benchmarks: Model Routing — Archana Kamath & Tyler Gillam, DigitalOcean

## 한 줄 요약
DigitalOcean은 비용, 적합성, 위험이라는 세 가지 요인으로 인해 단일 모델로는 모든 AI 작업을 처리할 수 없게 되면서, 사용자의 선호도에 따라 요청별로 가장 적합한 모델을 지능적으로 선택하는 오픈소스 추론 라우터인 'Plano'를 개발했습니다.

## 발표자·소속
*   **Archana Kamath**: DigitalOcean 추론 엔진 및 AI 인프라 엔지니어링 부사장
*   **Tyler Gillam**: DigitalOcean 소프트웨어 엔지니어 II

## 핵심 주장
*   **단일 모델의 한계와 모델 라우팅의 필요성**: AI 모델 사용 비용 폭증, 모든 작업에 최신 모델을 사용하는 비효율성, 단일 모델 의존에 따른 위험 증가로 인해 요청별로 적합한 모델을 선택하는 모델 라우팅이 필수적입니다.
*   **모델 선택의 기준은 벤치마크가 아닌 선호도**: 공개 벤치마크 점수만으로는 특정 작업에 가장 적합한 모델을 알 수 없으며, 실제 작업의 종류, 시스템 프롬프트, 비용 제한, 지연 시간 요구 사항, 최종 사용자 선호도 등 복합적인 요소를 고려해야 합니다.
*   **오픈소스 기반의 맞춤형 라우팅 솔루션**: DigitalOcean은 벤더 종속성 없이 사용자가 직접 라우팅 규칙을 정의하고, 평가 및 개선할 수 있는 오픈소스 라우팅 모델 'Plano'를 개발하여 투명성과 유연성을 제공합니다.
*   **비용 절감 및 성능 최적화 효과**: 데모를 통해 라우터가 작업에 따라 더 작고 저렴한 모델을 선택함으로써, 최신 고성능 모델을 직접 사용하는 것보다 훨씬 낮은 비용으로 유사하거나 더 나은 성능을 달성할 수 있음을 입증했습니다.

## 세부 내용
발표는 AI 엔지니어링 컨퍼런스에서 DigitalOcean의 Archana Kamath와 Tyler Gillam이 진행했습니다. Archana는 "Preferences > Benchmarks: Model Routing for How Teams Actually Build"라는 주제로 발표를 시작하며, DigitalOcean이 인프라부터 관리형 에이전트까지 5개 계층으로 구성된 AI-Native Cloud를 제공하며, 그 중심에 추론 엔진(Inference Engine)이 있다고 설명했습니다.

그녀는 현재 많은 기업이 단일 모델에 의존하는 방식에서 벗어나 모델 라우팅을 도입하려는 세 가지 주요 이유를 제시했습니다. 첫째, **비용(Cost)**이 폭증하고 있어 Uber, Microsoft, Walmart와 같은 대기업들도 추론 비용을 통제하기 위해 사용량을 제한하고 있습니다. 둘째, **적합성(Fit)** 측면에서 모든 작업에 하나의 모델을 사용하는 것은 과도하며, 더 작은 모델로도 충분히 처리할 수 있는 작업에 최신 모델의 높은 비용을 지불하는 것은 비효율적입니다. 셋째, **위험(Risk)** 관리 차원에서 단일 모델에 제품과 프로덕션을 의존할 경우, 모델 성능 저하 시 대체할 수 있는 페일오버(failover)가 없다는 문제가 있습니다.

Archana는 "모델 오케스트레이션(Model orchestration)이 새로운 FinOps"라고 강조하며, 클라우드 비용 최적화가 정착하는 데 15년이 걸렸지만, 모델 오케스트레이션은 몇 달 만에 빠르게 발전하고 있다고 말했습니다. 또한, "단 하나의 최고의 모델은 없다"고 주장하며, 올바른 모델은 요청에 따라 달라진다고 설명했습니다. 예를 들어, 분류 및 라벨링과 같이 대량이고 비용에 민감한 작업에는 작은 오픈 모델이 적합하고, 코드 완성(인라인)처럼 지연 시간에 민감한 작업에는 빠른 라우팅 모델이 필요하며, 코드 생성과 같이 트래픽이 많고 오픈 가중치를 사용하는 작업에는 중간 규모의 오픈 가중치 모델이, 코드 검토 및 보안처럼 정확도가 중요한 작업에는 프론티어 모델이 적합하다고 언급했습니다. 모델을 "올바르게" 만드는 요소는 작업 자체, 시스템 프롬프트 및 도구, 비용 제한, 지연 시간, 최종 사용자 선호도 등 여러 요소의 조합이며, 이는 어떤 공개 리더보드도 인코딩할 수 없는 부분이라고 강조했습니다.

이어서 Tyler Gillam이 DigitalOcean의 접근 방식을 설명했습니다. 그는 기존의 자동 라우팅 솔루션이 블랙박스처럼 느껴져 성능 개선이 어려웠던 문제를 지적하며, DigitalOcean은 이를 다르게 구축했다고 밝혔습니다. 그들의 아키텍처는 요청이 오픈 프록시인 'Plano'와 목적에 맞게 구축된 라우팅 모델을 거치도록 설계되었습니다. 이 모든 것은 오픈소스이며, 벤더 종속성이 없습니다. 사용자는 워크플로우에 중요한 요소(비용, 지연 시간, 품질, 선호 모델 등)를 정의할 수 있으며, 라우터는 이러한 맥락을 사용하여 요청별로 올바른 모델을 선택합니다. 라우팅 모델은 200ms 미만으로 매우 빠르며, 추가 비용이 발생하지 않습니다. 평가 결과, 그들의 라우팅 모델은 GPT-5 시리즈와 같은 프론티어 모델보다 라우팅 작업 자체에서 훨씬 빠른 속도를 보였습니다.

Tyler는 라우팅 규칙을 설정하는 세 가지 원칙을 제시했습니다. **선언(Declare)**: 자연어로 작업을 설명하고 비용, 지연 시간, 작업 유형 등 중요한 요소를 설정하여 선호도를 존중합니다. **제어(Control)**: 의사결정 트리 규칙을 계층화하고, 사전 설정에서 시작하여 한 줄의 코드로 원하는 것을 변경할 수 있습니다. **신뢰(Trust)**: 다른 사람의 리더보드가 아닌 자체 평가를 통해 모델 선택을 확인합니다. 라우팅, 평가, 조정, 그리고 다시 피드백하는 이 루프가 핵심이라고 강조했습니다.

라이브 데모에서 Tyler는 DigitalOcean의 추론 라우터(Inference Router) UI를 보여주었습니다. 그는 소프트웨어 엔지니어링을 위한 라우터 구성을 시연했는데, 버그 수정, 코드 생성, 테스트 작성 및 코드 검증, 코드 성능 최적화 등 다양한 작업을 위한 모델과 선택 정책(예: 코드 생성에는 GLM 5.2를 우선하고 GPT 5.2를 페일오버로, 버그 수정에는 가장 빠른 모델 선택)을 설정했습니다.

플레이그라운드 데모에서는 "기본 피보나치 함수 작성" 프롬프트를 Opus 4.0과 소프트웨어 엔지니어링 라우터에 동시에 입력했습니다. 라우터는 "코드 스니펫" 작업에 매칭되어 Maverick 모델을 사용했고, Opus 4.0보다 토큰 사용량(520 vs 43), 비용($0.01 vs $0.00), 시간(1.5s vs 0.3s) 면에서 훨씬 효율적이었습니다. "함수 최적화" 프롬프트에서는 라우터가 "코드 성능 최적화" 작업에 매칭되어 GPT 5.2를 사용했고, Opus 4.0보다 훨씬 빠르고 저렴했습니다. "단위 테스트 작성" 프롬프트에서도 라우터는 "테스트 작성 및 코드 검증" 작업에 매칭되어 Claude 5 Sonnet 모델을 사용하며 Opus 4.0보다 빠르고 저렴했습니다.

실제 워크플로우 데모에서는 'opencode'라는 코딩 에이전트를 두 개의 터미널에서 실행했습니다. 왼쪽 터미널은 Claude Opus 4.7을 직접 사용하고, 오른쪽 터미널은 소프트웨어 엔지니어링 라우터를 사용하도록 설정했습니다. "회전하는 휠 앱을 만들어줘"라는 프롬프트를 입력하자, 오른쪽 라우터는 코드 생성에는 GLM 5.2를, 테스트 작성에는 Claude 5 Sonnet을 사용하는 등 작업에 따라 모델을 전환하며 진행했습니다. 반면 왼쪽 Opus는 모든 작업에 Opus 4.7을 사용했습니다. 최종적으로 라우터를 사용한 세션의 총 비용은 14센트였고, Opus를 직접 사용한 세션의 총 비용은 44센트로, 라우터가 약 3배의 비용 절감 효과를 보였습니다. 두 경우 모두 유사한 품질의 결과물을 생성했습니다.

Archana는 요약하며, 라우팅 결정은 200ms 미만으로 이루어지며, 라우터는 라우팅을 위해 특별히 구축된 전문가 혼합(Mixture of Experts) 모델을 사용한다고 강조했습니다. 또한, 애플리케이션 코드 변경 없이 채택할 수 있고, 무료로 제공되며, 오픈소스(Plano)로 공개되어 벤더 종속성 없이 사용할 수 있다고 덧붙였습니다. 라우팅은 목적지가 아닌 기반이며, 그 위에 평가(Evals), 캐싱(Caching), 개인화(Personalization)의 세 가지 계층을 구축하여 지속적인 개선 루프를 통해 워크로드에 대한 라우터의 성능을 향상시킬 수 있다고 설명했습니다.

## 인상적인 대목
*   "Cloud cost optimization took fifteen years. This isn't waiting." (클라우드 비용 최적화는 15년이 걸렸습니다. 이것은 기다리지 않습니다.)
*   "There's no single best model. The right one depends on the request." (단 하나의 최고의 모델은 없습니다. 올바른 모델은 요청에 따라 달라집니다.)
*   "This is routing you can customize, evaluate, and improve without vendor lock-in." (이것은 벤더 종속성 없이 사용자 정의하고, 평가하고, 개선할 수 있는 라우팅입니다.)

## 실무 적용 포인트
*   **비용 및 성능 최적화를 위한 모델 라우팅 도입 고려**: 모든 AI 작업에 최신 고성능 모델을 사용하는 대신, 작업의 특성(비용 민감도, 지연 시간 요구 사항, 정확도 요구 사항 등)에 따라 적절한 크기와 성능의 모델을 선택하도록 라우팅 전략을 수립하여 비용을 절감하고 성능을 최적화할 수 있습니다.
*   **자체 평가(Evals) 시스템 구축**: 공개 벤치마크에만 의존하지 않고, 실제 사용 사례와 데이터에 기반한 자체 평가 시스템을 구축하여 모델 라우터의 성능을 지속적으로 검증하고 개선해야 합니다.
*   **오픈소스 라우팅 모델 활용**: DigitalOcean의 'Plano'와 같은 오픈소스 라우팅 모델을 활용하여 벤더 종속성을 피하고, 팀의 특정 요구 사항에 맞춰 라우팅 로직을 유연하게 커스터마이징하고 개선할 수 있습니다.
*   **지속적인 개선 루프 적용**: 모델 라우팅을 단순히 한 번 설정하는 것으로 끝내지 않고, 라우팅 결과에 대한 평가, 캐싱 전략 최적화, 팀의 워크로드 패턴 학습을 통한 개인화 등 지속적인 개선 루프를 통해 라우터의 효율성을 높여야 합니다.
