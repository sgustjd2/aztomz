# Two Bugs That Hid in Plain Sight: A vLLM Debugging Detective Story — Asaf Gardin & Yuval Belfer

## 핵심 주장
- 널리 사용되는 성숙한 라이브러리에도 미묘한 버그가 숨어 있을 수 있으며, 이는 시스템의 안정성과 성능에 심각한 영향을 미칠 수 있습니다. vLLM과 같은 고성능 시스템에서도 이러한 버그가 발견되어 깊은 디버깅이 필요했습니다.
- GPU 메모리 누수는 `torch.empty`의 특정 사용 방식과 PyTorch의 캐싱 할당자 동작 방식 때문에 발생할 수 있습니다. 초기화되지 않은 작은 텐서가 반복적으로 할당될 때 메모리 단편화 및 누수를 유발하여 결국 OOM(Out Of Memory)을 초래할 수 있습니다.
- 성능 저하는 `torch.nn.functional.scaled_dot_product_attention` (SDPA) 내부의 불필요한 `cudaStreamSynchronize` 호출 때문에 발생했습니다. `is_causal=True`와 `dropout_p > 0` 조건이 동시에 충족될 때 동기화가 발생하며, 이는 드롭아웃이 실제로 적용되지 않아도 트리거되어 CPU-GPU 동기화 병목을 만듭니다.
- 이러한 버그를 해결하기 위해서는 `nsight systems`와 같은 고급 프로파일링 도구를 활용하고, PyTorch 및 CUDA와 같은 하위 시스템의 내부 동작에 대한 깊은 이해가 필수적입니다. 단순히 표면적인 동작만으로는 문제를 진단하고 효율적인 해결책을 찾기 어렵습니다.

## 세부 내용
발표는 Asaf Gardin과 Yuval Belfer가 vLLM에서 발견한 두 가지 미묘한 버그에 대한 디버깅 과정을 탐정 이야기 형식으로 공유했습니다. vLLM은 고처리량, 저지연 LLM 서빙 엔진입니다.

**첫 번째 버그: GPU 메모리 누수**
문제는 vLLM 서버를 장시간 실행할 때 GPU 메모리 사용량이 지속적으로 증가하여 결국 OOM(Out Of Memory) 오류가 발생하는 것이었습니다. 발표자들은 초기에는 vLLM의 핵심 기술인 PagedAttention이나 KV 캐시 관리 문제로 의심했지만, vLLM은 이 부분을 효율적으로 설계했기에 다른 원인을 찾기 시작했습니다.

디버깅 과정은 다음과 같았습니다.
1.  `nvidia-smi`를 통해 GPU 메모리 사용량의 지속적인 증가를 확인했습니다.
2.  `nvprof` (이후 `nsight systems`로 대체)를 사용하여 GPU 커널 호출을 추적했습니다. `nvprof --print-gpu-trace python -m vllm.entrypoints.api_server ...` 명령어를 사용해 `cudaMalloc` 호출을 분석했습니다.
3.  추적 결과, 많은 수의 작은 `cudaMalloc` 호출이 있었지만, 이에 상응하는 `cudaFree` 호출이 보이지 않았습니다. 이는 PyTorch가 메모리를 할당하고 캐싱하지만, 특정 상황에서 효율적으로 재사용하거나 해제하지 못하고 있음을 시사했습니다.
4.  원인은 `torch.empty` 사용 방식에 있었습니다. `torch.empty`는 초기화되지 않은 메모리를 할당하며, 만약 이 텐서가 즉시 사용되지 않거나 작은 크기로 반복적으로 할당될 경우, PyTorch의 캐싱 할당자가 이 메모리 블록들을 효율적으로 재사용하지 못하고 계속 보유하여 단편화와 누수를 유발했습니다. 발표자는 이를 "버그가 아니라 기능"이라고 표현하며 `torch.empty`의 의도된 동작이지만 사용에 주의가 필요하다고 설명했습니다.
5.  해결책은 `torch.zeros`를 사용하거나, 더 나은 방법으로 `torch.empty_like(..., out=...)`를 사용하여 기존 텐서의 메모리를 명시적으로 재사용하는 것이었습니다.
6.  이 수정으로 GPU 메모리 사용량이 안정화되었고, 특히 작은 배치 크기(예: 배치 크기 1, 4, 8)에서 상당한 메모리 절감 효과를 보였습니다.

**두 번째 버그: 성능 저하**
문제는 배치 크기가 증가할수록 vLLM의 추론 지연 시간이 선형적으로 증가하지 않고, 계단식으로 급격히 증가하는 현상이었습니다. 이는 대규모 배치 처리 시 성능 병목을 유발했습니다.

디버깅 과정은 다음과 같았습니다.
1.  `nsight systems`를 사용하여 시스템 전체의 성능 프로파일링을 수행했습니다. `nsight systems --trace cuda,nvtx,osrt,cudnn,cublas python -m vllm.entrypoints.api_server ...` 명령어를 사용해 GPU 및 CPU 활동을 상세히 분석했습니다.
2.  프로파일링 결과, GPU 타임라인에 많은 `cudaStreamSynchronize` 호출이 나타났고, 특히 어텐션 계산 중에 집중되어 있었습니다. 이는 CPU와 GPU 간의 불필요한 동기화가 성능 병목을 유발하고 있음을 의미했습니다.
3.  원인은 `torch.nn.functional.scaled_dot_product_attention` (SDPA) 내부 동작에 있었습니다. SDPA는 `is_causal=True`이고 `dropout_p > 0`일 때 내부적으로 `cudaStreamSynchronize`를 호출하도록 되어 있었습니다. vLLM 코드에서는 드롭아웃이 필요 없을 때 `dropout_p`를 0.0으로 설정하거나 기본값에 의존했지만, SDPA의 내부 로직이 여전히 `dropout_p > 0` 조건을 확인하고 동기화를 트리거했던 것입니다.
4.  해결책은 드롭아웃이 필요 없을 때 SDPA 호출 시 `dropout_p=0.0`을 명시적으로 전달하는 것이었습니다. 이렇게 하면 SDPA 내부의 동기화 로직이 활성화되지 않아 불필요한 `cudaStreamSynchronize` 호출을 방지할 수 있습니다.
5.  이 수정으로 지연 시간이 배치 크기에 따라 훨씬 더 선형적으로 스케일링되었고, 특히 큰 배치 크기(예: 배치 크기 64)에서 최대 2배의 성능 향상을 달성했습니다.

결론적으로 발표자들은 널리 사용되는 라이브러리도 버그가 있을 수 있으며, 하위 시스템(CUDA, PyTorch 내부)에 대한 깊은 이해와 `nsight systems`와 같은 프로파일링 도구의 활용이 버그 해결에 필수적이라고 강조하며 "Never trust, always verify"라는 메시지를 전달했습니다.

- **하위 시스템 동작 이해**: PyTorch, CUDA 등 AI 프레임워크 및 런타임의 메모리 관리, 스트림 동기화와 같은 하위 시스템 동작 방식을 깊이 이해하는 것이 복잡하고 미묘한 버그 디버깅에 필수적입니다.
- **라이브러리 기본값 및 조건부 로직 주의**: 라이브러리 함수의 기본 매개변수나 조건부 로직이 예상치 못한 성능 저하나 동작을 유발할 수 있으므로, 특히 중요한 성능 경로에서는 명시적으로 값을 설정하고 내부 동작을 확인해야 합니다.
