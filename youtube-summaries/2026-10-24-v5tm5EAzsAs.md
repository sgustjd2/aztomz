# Your Agent Fix Just Broke Something Else - Sofia Jakovcevic, Arize AI

🔗 https://youtu.be/v5tm5EAzsAs · 📅 2026-10-24 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트 개발에서 발생하는 회귀(regression) 문제를 해결하기 위해, 프로덕션 트레이스를 활용하여 에이전트의 런타임 동작을 관찰하고 평가하는 자동화된 회귀 루프를 CI/CD 파이프라인에 통합하는 방법을 제시합니다.

## 발표자·소속
Sofia Jakovcevic, Arize AI 소속 Forward Deployed Engineer

## 핵심 주장
- **에이전트의 실패는 런타임에서 발생:** 기존 소프트웨어와 달리 AI 에이전트의 로직은 코드 레벨보다는 런타임에서 발현되는 행동에 의해 결정되며, 코드 변경이 예상치 못한 런타임 동작을 유발하여 '조용한 실패(silent failures)'로 이어질 수 있습니다.
- **트레이스가 새로운 진실의 원천:** 에이전트의 실제 동작을 이해하기 위해서는 정적 코드 분석만으로는 부족하며, 런타임에 발생하는 모든 단계와 도구 호출을 기록하는 트레이스(traces)가 에이전트의 행동을 파악하는 핵심 정보원이 됩니다.
- **자동화된 회귀 루프 구축의 필요성:** 에이전트의 작은 정책 변경이 전체 시스템에 미치는 영향을 예측하기 어렵기 때문에, 프로덕션 트레이스 기반의 데이터셋과 평가자(evaluators)를 활용하여 변경 사항을 자동으로 테스트하고 검증하는 회귀 루프를 CI/CD에 통합해야 합니다.
- **에이전트의 자가 개선으로의 전환:** 현재는 엔지니어가 수동으로 에이전트의 문제를 디버깅하고 개선하지만, 궁극적으로는 에이전트 스스로 트레이스를 읽고, 평가하고, 자신의 행동을 개선하는 '에이전트 속도(agentic speed)'의 자가 개선 시스템으로 발전해야 합니다.

## 세부 내용

발표자는 Arize AI가 AI 시스템의 작동을 돕는 관찰 가능성(observability) 백엔드라고 소개하며, AI 시스템 구축의 어려움, 특히 에이전트의 '블랙박스' 특성으로 인한 디버깅의 어려움을 지적합니다. 관찰 가능성은 이 블랙박스에 빛을 비춰 시스템의 실제 동작을 이해하고, 성능을 평가하며, 에이전트를 반복적으로 개선하는 데 필수적입니다.

가장 큰 문제는 에이전트의 수정이 다른 기능을 망가뜨리는 '회귀(regression)' 현상입니다. 발표자는 가상의 '환불 정책 에이전트' 사례를 들어 설명합니다. 보안 엔지니어가 에이전트 정책에 "어떤 조치를 취하기 전에 사용자에게 확인을 요청하라"는 한 줄을 추가합니다. 이 변경은 '행동 안전(action safety)' 지표를 0.81에서 0.98로 17포인트 개선했지만, '작업 완료(task completion)' 지표는 0.89에서 0.72로 17포인트 하락시켰습니다. 결과적으로 두 지표의 평균은 0.85로 변화가 없었습니다. 이는 한 가지 차원에서의 개선이 전체 에이전트의 성능을 보장하지 않으며, 수치적 평가 없이 '감'으로 변경을 적용하는 것이 위험하다는 점을 보여줍니다.

발표자는 에이전트가 코드 레벨이 아닌 런타임에서 실패한다는 점을 강조합니다. 코드 리뷰에서는 한 줄의 정책 변경이 사소해 보이지만, 실제 프로덕션에서는 `llm.plan`, `tool.lookup_account`, `llm.decide_action`, `policy.check + ask user`, `llm.respond`와 같은 복잡한 실행 경로를 완전히 재구성할 수 있습니다. 이러한 런타임 동작은 정적 코드에 나타나지 않으며, 오직 트레이스(traces)를 통해서만 확인할 수 있습니다. 따라서 트레이스가 에이전트의 '새로운 진실의 원천'이 되며, '조용한 실패'를 포착하기 위해 트레이스 기반의 회귀 테스트가 필수적입니다.

이러한 이해를 바탕으로 자동화된 회귀 루프를 구축하는 5단계 프로세스를 제시합니다.
1.  **데이터셋 선택:** 실제 프로덕션 트레이스에서 실제 입력, 도구 호출, 결과, 일반적인 워크플로우, 알려진 실패 사례, 엣지 케이스, 그리고 보호해야 할 성공 사례를 포함하는 대표적인 데이터셋을 구성합니다.
2.  **평가자(Evaluators) 추가:** LLM을 '판사(judge)'로 활용하여 환각(hallucination), 정확도, 도구 궤적, 단계 효율성 등 주관적인 에이전트 성능 지표를 정량적인 점수(예: 0 또는 1)로 변환합니다. 결정론적 검사에는 코드 기반 평가자를 사용할 수 있습니다.
3.  **기준선(Baseline) 실험 실행:** 현재 에이전트를 변경하지 않은 상태로 데이터셋과 평가자를 사용하여 기준선 성능을 측정합니다. 이는 향후 변경 사항을 비교하는 통제 그룹이 됩니다.
4.  **변경 및 재실행:** 에이전트 정책을 변경(예: 프롬프트, 모델, 도구, 스킬, 정책 변경)하고, 동일한 데이터셋과 평가자로 실험을 다시 실행하여 변경 전후의 성능을 비교합니다. 원하는 트레이드오프를 얻을 때까지 이 과정을 반복합니다.
5.  **CI에 실험 통합:** 모든 프롬프트, 모델, 도구, 스킬 변경이 병합되기 전에 회귀 데이터셋과 평가자에 대해 실행되도록 CI/CD 파이프라인에 실험을 통합합니다. 각 중요한 차원에 대해 기준(예: 기준선 대비 0.02 이상 하락 금지)을 설정하고, 이 기준을 충족하지 못하면 병합을 차단합니다.

라이브 데모에서는 Arize 플랫폼에서 'refund-policy-regression' 실험을 시연합니다. 행동 안전과 작업 완료 지표의 변화를 그래프와 표로 보여주며, 여러 실험을 통해 최적의 트레이드오프를 찾는 과정을 설명합니다. 또한 프롬프트 플레이그라운드에서 단일 에이전트를 테스트하거나, 에이전트 플레이그라운드에서 복잡한 다중 에이전트 시스템을 테스트하는 방법을 보여줍니다. Arize의 평가자 허브에서 다양한 사전 구축된 평가자를 선택하거나 사용자 정의 평가자를 추가할 수 있으며, 원격 에이전트를 연결하여 IDE에서 작성된 코딩 에이전트의 동작을 프로덕션 데이터와 연결하여 평가할 수 있음을 강조합니다.

## 인상적인 대목
- "우리는 '감(vibes)'으로 코딩하고 싶지 않습니다. 우리는 수치적 평가 스위트와 데이터로 뒷받침되는 코딩을 하고 싶습니다."
- "코드 변경은 로컬이지만, 행동 효과는 그렇지 않습니다. 작은 변경이 전체 실행 경로를 재구성할 수 있습니다. Diff는 무엇이 변경되었는지 알려주지만, 트레이스는 무엇이 실제로 일어났는지 알려줍니다."
- "관찰 가능성의 미래는 스스로 보고, 평가하고, 자신의 행동을 개선할 수 있는 에이전트입니다."

## 실무 적용 포인트
- **프로덕션 트레이스 기반 회귀 데이터셋 구축:** 실제 사용자 쿼리, 도구 호출, 결과, 알려진 실패 및 성공 사례를 포함하는 프로덕션 트레이스를 수집하여 에이전트 회귀 테스트의 핵심 데이터셋으로 활용합니다.
- **LLM 기반 평가자 개발 및 활용:** 에이전트의 환각, 정확도, 효율성 등 주관적인 성능 지표를 LLM을 '판사'로 사용하여 정량적인 점수로 변환하는 평가자를 개발하고, 이를 통해 에이전트의 품질을 객관적으로 측정합니다.
- **CI/CD 파이프라인에 에이전트 회귀 테스트 자동화:** GitHub Actions와 같은 CI/CD 도구를 사용하여 모든 코드 변경(프롬프트, 모델, 도구 등)이 병합되기 전에 정의된 회귀 데이터셋과 평가자에 대해 자동으로 테스트되도록 설정하고, 특정 기준 미달 시 병합을 차단합니다.
- **에이전트의 자가 개선 루프 설계:** 에이전트가 프로덕션에서 발생한 실패 트레이스를 스스로 분석하고, 이를 바탕으로 자신의 프롬프트, 도구 사용 또는 정책을 수정하여 성능을 개선하는 피드백 루프를 구축하는 것을 목표로 합니다.
