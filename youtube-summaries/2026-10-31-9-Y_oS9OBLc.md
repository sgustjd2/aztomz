# When Running Your Own AI Models Beats Paying for APIs - Steven Latré, imec

🔗 https://youtu.be/9-Y_oS9OBLc · 📅 2026-10-31 · 🎙 AI Engineer

## 한 줄 요약
AI 모델을 자체 인프라에서 운영하는 것은 API를 사용하는 것보다 비용 효율적일 수 있지만, 하드웨어, 모델, 애플리케이션 및 하네스 간의 복잡한 비선형적 관계를 신중하게 관리해야 하며, 이를 통해 25% 이상의 비용 절감을 달성할 수 있습니다.

## 발표자·소속
Steven Latré, imec AI 부서장

## 핵심 주장
- API에서 자체 인프라로 AI 모델 운영을 전환하는 결정은 단순한 선형적 비용 비교가 아니며, 복잡한 요소들을 고려해야 합니다.
- 하드웨어 아키텍처, 모델 복잡성, 추론 엔진 선택, KV 캐시 최적화, GPU 가용성 등 다양한 요소들이 성능과 비용에 복합적으로 영향을 미칩니다.
- 특히, 하네스(harness) 선택은 애플리케이션 성능에는 큰 영향을 미치지 않을 수 있지만, GPU 사용량과 총 소유 비용에 상당한 영향을 미쳐 비용을 두 배로 만들 수도 있습니다.
- 대규모 토큰 배포의 경우, API 사용에서 벗어나 자체 인프라를 통합하고 최적화하는 단계로 나아가야 하며, 이를 통해 예측 가능성과 규제/보안 요구사항을 충족할 수 있습니다.
- 이러한 복잡한 관계를 신중하게 관리하면 25% 이상의 비용 절감을 달성할 수 있으며, imec은 이를 위한 벤치마킹 데이터셋을 구축하여 공개할 예정입니다.

## 세부 내용
발표자는 imec의 AI 부서장인 Steven Latré로, imec이 반도체 분야에서 40년 이상 차세대 기술을 개발해 온 숨겨진 보석 같은 연구 기관임을 소개했습니다. 그의 팀은 AI 워크로드와 인프라를 연결하는 연구를 담당하고 있습니다.

발표자는 AI 성숙도의 여러 단계를 설명했습니다. 초기에는 최신 프론티어 모델을 사용하는 데 집중했지만, 2024-2025년에는 토큰 비용이 비트코인 가치보다 더 변동성이 크다는 것을 깨달았습니다. 이에 따라 "모델 라우팅"과 같은 저비용 최적화(low-hanging fruit optimization)를 통해 특정 작업에 가장 적합한 모델을 찾는 단계로 진입했습니다.

그러나 대규모 토큰 배포의 경우, 인프라가 중요한 역할을 하기 시작합니다. 이는 부트스트래핑(폐쇄형 API 사용), 스케일링(모델 라우팅), 통합(인프라 임대), 최적화(인프라 소유)의 4단계로 나뉩니다. 인프라를 직접 관리하기 시작하면 작업 복잡성, 모델 평판, 하네스 복잡성, 모델 복잡성, 하드웨어 아키텍처, 추론 엔진 선택, KV 캐시 최적화, GPU 가용성 등 고려해야 할 설계 공간이 폭발적으로 증가합니다.

Steven Latré는 이러한 API와 자체 인프라 간의 격차를 해소하기 위한 벤치마킹 연구를 수행했다고 밝혔습니다. 이 연구는 64개의 장기 코딩 작업을 포함하는 SWE-Bench PRO 태스크를 사용했습니다. 다양한 코딩 하네스(Codex, PI, Claude Code)와 오픈웨이트 모델(Opus 4.8, Qwen 0.5-3.6B, DeepSeek V4, GLM-5.2, Kimi K3)을 다양한 하드웨어 복잡성(1x H200, 4x H200, 8x B200, 8x B300)에 매핑하여 해결률, 지연 시간, 비용을 측정했습니다.

연구 결과, 모델의 해결률은 모델 복잡도에 따라 증가했지만, 하드웨어 비용은 비선형적으로 증가했습니다. 예를 들어, Qwen과 DeepSeek은 비슷한 해결률을 보였지만, DeepSeek은 4배 더 비싼 GPU 임대 비용이 들었습니다. Kimi K3는 88.4%의 높은 해결률을 보였지만, Opus 4.8 API보다 1.15배 더 비싼 GPU 임대 비용이 들었습니다.

또한, 동시성(concurrency)이 중요한 요소로 부각되었습니다. 자체 인프라를 사용할 경우, 사용자 KV 캐시와 모델의 파라미터 크기가 GPU 메모리에 미치는 영향 때문에 얼마나 많은 사용자를 동시에 처리할 수 있는지가 중요해집니다. Qwen 3.6(H200)과 DeepSeek-V4-Flash는 48명의 동시 사용자를 처리할 수 있었지만, GLM-5.2는 8명, Kimi K3는 4명에 불과했습니다. 심지어 더 큰 하드웨어에서도 동시성이 크게 떨어졌으며, 모든 경우에 Claude Code API보다 2~3배 느렸습니다. 이는 정확도보다 동시성이 더 중요할 수 있음을 시사합니다.

API, 임대, 구매 간의 스위트 스팟 분석에서는, 낮은 티어의 하드웨어 시스템(예: 4x H200)의 경우 89%의 GPU 활용률이 필요하여 비현실적임을 보여주었습니다. 반면, GLM급 애플리케이션의 경우 API 대비 25%의 비용 절감이 가능했으며, 더 높은 티어의 하드웨어 시스템(예: 8x B200)의 경우 15%의 GPU 활용률만으로도 비용 효율성을 달성할 수 있어 현실적입니다.

하네스 선택은 해결률에는 큰 영향을 미치지 않았지만, 토큰 소비량에는 큰 차이를 보였습니다. 예를 들어, GLM-5.3-Flash 모델을 Codex 하네스와 함께 사용했을 때, Claude Code 또는 PI 하네스를 사용했을 때보다 토큰 소비량이 절반으로 줄었습니다. 이는 GPU 비용을 두 배로 만들 수 있는 중요한 요소이며, 자체 인프라를 관리할 때는 하네스 선택이 총 소유 비용에 큰 영향을 미친다는 것을 의미합니다.

결론적으로, API에서 자체 인프라로의 전환은 비선형적이며, 하네스, 모델, 애플리케이션, 인프라 간의 복잡한 관계를 이해해야 합니다. 이는 끊임없이 변화하는 목표이며, 신중하게 관리하면 25% 이상의 비용 절감이 가능합니다. imec은 이러한 통찰력을 바탕으로 벤치마킹 데이터셋을 구축하여 공개할 예정이며, AI 스택 얼라이언스(aistack alliance)를 통해 칩 공급업체, 시스템 통합업체, 모델 연구소, 인프라 공급업체 등 다양한 이해관계자들과 협력하여 이 문제를 해결하고자 합니다.

## 실무 적용 포인트
- **총 소유 비용(TCO) 분석의 중요성**: API 사용과 자체 인프라 구축/임대 간의 비용을 비교할 때, 단순히 토큰 비용을 넘어 하드웨어 활용률, 동시성, 하네스 선택 등 다양한 요소를 포함한 TCO 관점에서 접근해야 합니다.
- **하네스 선택의 전략적 고려**: 하네스(프레임워크, 런타임 등)가 모델의 해결률에 직접적인 영향을 미치지 않더라도, 토큰 소비량과 GPU 사용 시간에 큰 영향을 미칠 수 있으므로, 자체 인프라 운영 시 비용 최적화를 위해 하네스 선택을 신중하게 고려해야 합니다.
- **동시성(Concurrency) 관리**: 대규모 AI 모델을 자체 인프라에서 운영할 때는 GPU 메모리 제약으로 인해 동시성 문제가 발생할 수 있습니다. 모델의 파라미터 크기와 사용자 KV 캐시 요구 사항을 고려하여 적절한 하드웨어 아키텍처와 추론 엔진을 선택해야 합니다.
- **벤치마킹 데이터셋 활용**: imec이 구축하여 공개할 예정인 벤치마킹 데이터셋과 같은 자료를 활용하여 다양한 모델, 하네스, 인프라 조합에 대한 성능 및 비용 데이터를 얻고, 이를 바탕으로 최적의 AI 스택을 설계하는 데 참고할 수 있습니다.
