# How to Generate Mergeable Code with a Context Engine — Peter Werry, Unblocked

🔗 https://www.youtube.com/watch?v=qdAkxLoYNI8

## 개요
*   **발표자:** Peter Werry, Unblocked
*   **주제:** AI 에이전트가 병합 가능한 고품질 코드를 생성하기 위해, 조직의 고유한 지식과 히스토리를 제공하는 '컨텍스트 엔진'의 필요성과 작동 방식을 설명합니다.

## 발표 흐름

### 도입: 컨텍스트 엔진의 정의
발표자는 Unblocked가 구축하는 '컨텍스트 엔진'을 소개하며 발표를 시작합니다. 컨텍스트 엔진은 조직의 고유한 컨텍스트(지식, 맥락)를 인간 작업자뿐만 아니라, 점차 중요해지는 AI 에이전트에게도 제공하는 시스템이라고 정의합니다.

### 문제 정의 1: 인간은 어떻게 컨텍스트를 구축해왔는가?
과거 AI 에이전트가 없던 시절, 개발자 자신이 '컨텍스트 레이어' 역할을 해왔다고 설명합니다. 어떤 작업을 위해 필요한 정보를 얻으려면 개발자는 다음과 같은 여러 분산된 소스를 직접 뒤져야 했습니다.
*   **GitHub:** 오래된 변경 사항 확인
*   **Notion:** 오래된 아키텍처 문서 검색
*   **Datadog:** 시스템의 증상(원인이 아닌) 파악
*   **Jira:** 작업의 현재 상태 추적
*   **Slack:** 비공식적인 논의나 부족 지식(tribal knowledge) 탐색
*   **Confluence:** 서로 상충되는 정보 확인

이 과정은 비효율적이며, 정보는 낡았거나, 상충되거나, 중요한 부족 지식이 흩어져 있는 등 문제가 많았습니다.

### 문제 정의 2: AI 에이전트가 직면한 새로운 문제
이제 AI 에이전트가 이 문제를 그대로 물려받았다고 지적합니다. 하지만 문제는 더 심각한데, 비용이 '복리'로 증가하기 때문입니다. 발표자는 **"에이전트는 신입사원과 같다"**는 핵심 비유를 사용합니다. 에이전트는 새로운 작업을 시작할 때마다 지식이 초기화되어, 매번 처음부터 코드베이스, 테스트 방식, 배포 절차 등을 다시 학습해야 합니다. 이 과정에서 인간이 겪었던 컨텍스트 탐색의 비효율성이 반복되고 증폭됩니다.

### AI 성숙도 모델과 컨텍스트의 중요성
Bassim Eledin의 '엔지니어링 조직의 AI 성숙도 수준' 모델을 인용하며, 컨텍스트의 중요성을 강조합니다.
*   **1단계 (Tab complete):** 개발자 자신이 컨텍스트의 전부인 단계.
*   **2단계 (Agent IDE):** IDE 내에서 에이전트 활용.
*   **3단계 (Context engineering):** 선별된 컨텍스트를 제공하기 시작.
*   **4-5단계 (Parallel agents, MCP + skills):** 여러 에이전트를 활용하고 '컨텍스트 레이어'를 구축하는 단계. 대부분의 조직이 현재 이 단계에 머물러 있으며, 컨텍스트가 병목 현상임을 깨닫고 내부 위키 등을 만들려 노력합니다.
*   **6-8단계 (Harness engineering, Cloud agents, Software Factories):** 완전 자율적인 에이전트와 소프트웨어 팩토리를 향한 단계. 이 단계로 나아가려면 에이전트가 자율적으로 작동할 수 있도록 하는 강력한 컨텍스트 레이어가 필수적입니다.

### 핵심 문제: 접근(Access)은 이해(Understanding)가 아니다
단순히 정보에 접근 권한을 주는 것만으로는 충분하지 않다고 역설합니다. 발표자는 "접근 ≠ 이해"라는 공식을 제시하며, 방사선과 의사들의 '탐색 만족(satisfaction of search)' 편향을 예로 듭니다. 의사가 엑스레이에서 첫 번째 이상 징후를 발견하면 탐색을 멈춰 더 심각한 다른 문제를 놓칠 수 있는 것처럼, AI 에이전트도 처음 발견한 그럴듯한 정보에 만족하고 더 깊이 탐색하지 않아 최적이 아닌 결과를 낼 수 있습니다.

이는 '빙산의 일각'과 같습니다. 에이전트는 수면 위의 '컴파일되는 코드'는 볼 수 있지만, 수면 아래에 잠긴 거대한 **'알려지지 않은 미지(unknown unknowns)'**, 즉 다음과 같은 핵심 컨텍스트는 보지 못합니다.
*   코드의 원래 의도
*   팀의 코딩 컨벤션
*   과거에 내려진 중요한 결정들
*   아키텍처의 근거
*   과거 장애로부터 얻은 교훈

### 데모: 컨텍스트 엔진의 실제 작동 방식

1.  **Q&A 및 Slack 통합:**
    *   Unblocked의 웹 UI에서 "소스마크 엔진은 어떻게 작동하나요?"라고 질문하자, 시스템은 코드 조각, 자동 생성된 아키텍처 다이어그램, 그리고 답변의 근거가 된 소스 파일 및 문서 링크를 포함한 상세한 답변을 제공합니다. 이는 답변의 신뢰도를 높입니다.
    *   Slack 채널에서 "Unblocked의 사용자 참여 지표는 무엇이고 어떻게 작동하나요?"라고 질문하자, Unblocked 봇이 스레드 내에서 표와 데이터 흐름 다이어그램까지 포함된 체계적인 답변을 생성합니다. 이를 통해 개발자의 작업 흐름을 방해하지 않고 컨텍스트를 제공할 수 있음을 보여줍니다.

2.  **AI 에이전트 성능 비교 (Claude Code):**
    *   **컨텍스트 없이:** Claude Code 에이전트에게 '소스마크 계산기 최적화 계획'을 세우라고 지시합니다. 에이전트는 2분 35초 동안 $1.22를 소모하여 일반적인 최적화 계획을 생성합니다.
    *   **컨텍스트 포함:** 동일한 작업을 Unblocked 컨텍스트 엔진과 연동하여 실행합니다. 에이전트는 1분 18초 동안 $0.93을 소모하여 훨씬 더 정교한 계획을 생성합니다. 특히, **"과거로부터의 두 가지 경고"** 항목을 포함하며, "과거에 단순 git-diff 캐시를 시도했지만 작동하지 않았다"는 사실과 관련 PR(#1236)을 명시적으로 참조합니다. 이는 컨텍스트 엔진이 과거의 실패 경험이라는 '알려지지 않은 미지'를 에이전트에게 제공하여, 같은 실수를 반복하지 않게 함을 보여줍니다.

3.  **컨텍스트 기반 자동화:**
    *   **코드 리뷰:** Unblocked 봇이 GitHub PR에 자동으로 코드 리뷰 코멘트를 남깁니다. 이 코멘트는 과거 시니어 엔지니어(Richie)가 남겼던 코멘트들을 기반으로 생성되었으며, 근거가 된 과거 코멘트 링크를 함께 제공합니다.
    *   **작업 자동화:** 개발자가 Q&A 스레드에서 문제 분석 후 "고쳐줘(Fix it please)"라고 요청하자, Unblocked 에이전트가 자동으로 Jira 티켓을 생성하고, 문제를 해결하는 코드를 작성하여 PR을 제출합니다. 이 PR 설명에는 문제의 발단이 된 Slack 대화 링크까지 포함되어, 모든 작업이 컨텍스트 안에서 완벽하게 연결됩니다.

### 결론
컨텍스트 엔진을 사용하면 토큰 사용량과 작업 분류 시간을 줄일 뿐만 아니라, 노이즈에 묻히지 않은 더 나은 품질의 답변과 결과를 얻을 수 있다고 결론 내립니다. 발표자는 컨텍스트 엔진 시뮬레이터와 데모 예약을 위한 QR 코드를 공유하며 발표를 마칩니다.

## 구체 수치·데모·아키텍처
*   **AI 성숙도 모델:** Bassim Eledin의 8단계 모델 (1. Tab complete, 2. Agent IDE, 3. Context engineering, 4. Parallel agents, 5. MCP + skills, 6. Harness engineering, 7. Cloud agents, 8. Software Factories).
*   **Claude Code 에이전트 성능 비교 (최적화 계획 수립):**
    *   **컨텍스트 미사용:** 비용 $1.22, API 소요 시간 2분 35초.
    *   **컨텍스트 사용 (Unblocked):** 비용 $0.93, API 소요 시간 1분 18초. 약 24% 비용 절감, 약 49% 시간 단축.
*   **언급된 도구/제품:** Unblocked, Claude Code, GitHub, Jira, Slack, Notion, Datadog, Confluence.
*   **오픈소스 프로젝트:**
    *   `document-query-engine`: 자연어 쿼리를 MongoDB 집계 파이프라인으로 변환.
    *   `engineering-social-graph`: GitHub PR 히스토리에서 팀 구조, 전문가, 협업 패턴을 시각화.
*   **데모 아키텍처/기능:**
    *   **Q&A:** 자연어 질문에 대해 코드, 다이어그램, 참조 링크를 포함한 답변 생성.
    *   **Slack 통합:** Slack 내에서 봇을 통해 질문하고 스레드에서 답변 수신.
    *   **자동 코드 리뷰:** 과거 PR 리뷰 코멘트를 학습하여 새로운 PR에 자동으로 코멘트 작성.
    *   **자동 PR 생성:** "Fix it"과 같은 자연어 명령에 따라 Jira 티켓 생성 및 코드 수정 PR 자동 제출.

## 핵심 인용
*   "For years, **you** have been the context layer."
    > (수년간, **여러분 자신이** 컨텍스트 레이어였습니다.)
*   "Now your agents have the same problem. Only the cost compounds."
    > (이제 여러분의 에이전트도 같은 문제를 겪습니다. 단지 비용이 복리로 늘어날 뿐입니다.)
*   "The problem: access ≠ understanding"
    > (문제는 이것입니다: 접근이 이해를 의미하지는 않는다.)
*   "~50% fewer tokens, faster triage, and Unblocked's answer was actually **better** because it wasn't buried in noise."
    > (~50% 더 적은 토큰, 더 빠른 분류, 그리고 Unblocked의 답변은 노이즈에 묻히지 않았기 때문에 실제로 **더 나았습니다**.)

## 한 줄 결론
AI 에이전트가 조직의 '신입사원'처럼 매번 모든 것을 새로 배우는 비효율을 극복하고, 과거의 실수와 부족 지식까지 이해하여 진정으로 병합 가능한 코드를 생성하게 하려면, 조직의 모든 지식을 연결하고 제공하는 '컨텍스트 엔진'이 필수적이다.
