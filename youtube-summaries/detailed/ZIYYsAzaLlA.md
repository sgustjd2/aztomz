# Building the Engine While Flying the Plane: Launching the Figma MCP Server — Jesse Lumarie, Figma

🔗 https://www.youtube.com/watch?v=ZIYYsAzaLlA

## 개요
- **발표자:** Jesse Lumarie
- **소속:** Figma
- **한 줄 주제:** 피그마(Figma)는 기존 TypeScript 기반의 멀티플레이어 서버가 가진 성능 및 확장성 한계를 극복하기 위해, 서비스 중단 없이 새로운 Rust 기반의 MCP(Multiplayer Collaboration Protocol) 서버를 개발하고 성공적으로 마이그레이션했습니다.

## 발표 흐름

### ### 도입: 왜 비행 중에 엔진을 교체해야 했나?
발표는 "비행 중인 비행기의 엔진을 교체하는 것"이라는 유명한 비유로 시작합니다. 이는 피그마의 핵심 기능인 실시간 협업을 담당하는 멀티플레이어 서버를 사용자들이 서비스를 이용하는 도중에 교체해야 했던 상황을 설명합니다.

피그마의 멀티플레이어 서버는 사용자들이 같은 파일에서 동시에 작업할 때 모든 변경 사항을 동기화하는 매우 중요한 역할을 합니다. 기존 서버는 TypeScript와 Node.js로 작성되었는데, 피그마의 규모가 커지면서 심각한 성능 문제에 직면했습니다. 특히 사용자가 많고 매우 복잡한 디자인 파일의 경우, 서버의 CPU 사용량이 100%에 도달하며 병목 현상이 발생했습니다.

### ### 문제 정의: 기존 TypeScript 서버의 한계
기존 아키텍처는 '문서 하나당 하나의 Node.js 프로세스'를 할당하는 방식이었습니다. 이 구조는 처음에는 단순하고 격리가 잘 된다는 장점이 있었지만, 다음과 같은 명확한 한계를 드러냈습니다.

1.  **싱글 스레드 병목:** Node.js는 기본적으로 싱글 스레드 환경입니다. 따라서 아무리 좋은 서버(멀티 코어)를 사용해도, 한 문서에 대한 처리는 단일 CPU 코어의 성능에 의해 제한되었습니다. 복잡한 문서 하나가 서버의 코어 하나를 완전히 점유해버리는 문제가 발생했습니다.
2.  **가비지 컬렉션(GC) 문제:** TypeScript(JavaScript)는 가비지 컬렉터에 의해 메모리를 관리합니다. 문서가 크고 활동이 많아지면 GC가 자주 발생하고, 이로 인해 'Stop-the-world' 현상(GC 동안 모든 작업이 멈춤)이 일어나면서 응답 지연 시간(latency)이 급증했습니다. 이는 사용자 경험에 직접적인 악영향을 미쳤습니다.
3.  **높은 메모리 사용량:** JavaScript 객체의 오버헤드로 인해 메모리 사용량이 비효율적이었습니다.

이러한 문제들로 인해 서버 비용이 증가하고, 대규모 사용자들이 참여하는 협업 환경에서 안정적인 성능을 제공하기 어려워졌습니다.

### ### 해결책: Rust 기반의 새로운 MCP 서버 설계
이 문제를 해결하기 위해 피그마는 새로운 멀티플레이어 서버를 처음부터 다시 만들기로 결정했습니다. 새로운 서버의 핵심 목표는 다음과 같았습니다.

-   **멀티스레딩 활용:** 단일 프로세스가 여러 CPU 코어를 효율적으로 사용하여 여러 문서를 동시에 처리할 수 있어야 함.
-   **예측 가능한 성능:** GC로 인한 지연 시간 급증 없이, 일관되고 낮은 지연 시간을 보장해야 함.
-   **메모리 효율성:** 더 적은 메모리로 더 많은 작업을 처리할 수 있어야 함.

이 목표를 달성하기 위한 기술 스택으로 **Rust**를 선택했습니다. Rust는 GC가 없어 성능이 예측 가능하고, 메모리 안전성을 컴파일 시점에 보장하며, 뛰어난 동시성(concurrency) 처리 능력을 제공하기 때문에 이상적인 선택이었습니다.

새로운 아키텍처는 '하나의 Rust 프로세스가 워커 스레드 풀을 이용해 여러 문서를 동시에 처리'하는 모델로 변경되었습니다. 이를 통해 서버의 모든 CPU 코어를 효율적으로 활용할 수 있게 되었습니다.

### ### 마이그레이션 전략: 무중단 전환의 3단계
가장 어려운 과제는 수백만 명의 사용자가 실시간으로 사용하는 핵심 시스템을 중단 없이 교체하는 것이었습니다. 피그마는 다음과 같은 체계적인 3단계 전략을 사용했습니다.

1.  **1단계: 섀도잉 (Shadowing)**
    -   기존 TypeScript 서버와 새로운 Rust 서버를 동시에 운영했습니다.
    -   사용자 트래픽(요청)을 프록시(proxy)를 통해 양쪽 서버에 모두 보냈습니다.
    -   하지만 사용자에게 실제 응답을 보내는 것은 기존 TypeScript 서버의 역할이었습니다. 새로운 Rust 서버의 응답은 내부적으로 기록되고, 기존 서버의 응답과 비교 분석하는 데만 사용되었습니다.
    -   이 단계를 통해 새로운 Rust 서버의 구현이 기존 서버와 100% 동일하게 동작하는지(정합성) 검증하고, 버그를 찾아 수정할 수 있었습니다. 수많은 불일치 케이스를 발견하고 수정하는 과정을 거쳤습니다.

2.  **2단계: 내부 테스트 (Dogfooding)**
    -   섀도잉을 통해 안정성이 확보된 후, 피그마 내부 직원들(Figma employees)이 사용하는 문서 트래픽부터 새로운 Rust 서버로 보내기 시작했습니다.
    -   이를 '다크 론칭(Dark Launch)' 또는 '개밥 먹기(Dogfooding)'라고 부르며, 실제 사용 환경과 유사한 조건에서 발생할 수 있는 예외적인 문제나 성능 이슈를 미리 파악하는 데 큰 도움이 되었습니다.

3.  **3단계: 점진적 배포 (Gradual Rollout)**
    -   내부 테스트까지 성공적으로 마친 후, 기능 플래그(feature flag) 시스템을 이용해 실제 사용자 트래픽을 점진적으로 새로운 Rust 서버로 이전했습니다.
    -   처음에는 전체 트래픽의 1%만 새 서버로 보내고, 안정성과 성능 지표(CPU, 메모리, 지연 시간 등)를 면밀히 모니터링했습니다.
    -   문제가 없음을 확인한 후 5%, 10%, 25%, 50% 순으로 비율을 점차 늘려나갔고, 최종적으로 100% 전환을 완료했습니다.
    -   이 과정 덕분에 소수의 사용자에게만 영향을 미치는 엣지 케이스(edge case) 버그를 발견했을 때, 즉시 롤백하여 대규모 장애를 피할 수 있었습니다.

### ### 과정에서 마주한 도전과 교훈
-   **프로토콜 정합성 유지:** 두 개의 다른 언어(TypeScript, Rust)로 작성된 서버가 완전히 동일하게 동작하도록 만드는 것은 매우 어려웠습니다. 이를 위해 프로토콜 정의에 Protobuf(Protocol Buffers)를 사용하여 명확한 스키마를 공유하고, 두 구현 간의 차이를 줄였습니다.
-   **관측 가능성(Observability)의 중요성:** 새로운 Rust 서버의 상태를 정확히 파악하기 위해 로깅, 메트릭, 분산 추적(distributed tracing) 시스템을 철저하게 구축했습니다. 이는 문제 발생 시 원인을 신속하게 파악하고 디버깅하는 데 결정적인 역할을 했습니다.
-   **Rust의 학습 곡선:** Rust는 강력하지만 배우기 어려운 언어입니다. 팀원들이 Rust에 익숙해지고 생산성을 높이는 데 시간이 필요했습니다.
-   **성능의 함정:** Rust가 무조건 빠를 것이라고 생각했지만, 락 경합(lock contention)과 같은 동시성 문제로 인해 예상치 못한 성능 저하를 겪기도 했습니다. 프로파일링을 통해 병목 지점을 찾아내고 코드를 최적화하는 과정이 필수적이었습니다.

### ### 결과 및 성과: 새로운 엔진의 압도적인 성능
마이그레이션 완료 후, 새로운 Rust 기반 MCP 서버는 기대 이상의 성과를 보였습니다.

-   **CPU 사용량:** 이전 대비 **90% 이상 감소**했습니다. 기존에 수많은 서버가 처리하던 작업을 훨씬 적은 수의 Rust 서버가 감당할 수 있게 되었습니다.
-   **메모리 사용량:** 크게 감소하여 서버 효율성이 증대되었습니다.
-   **지연 시간 (Latency):** GC로 인한 스파이크(spike)가 완전히 사라져, p99 지연 시간이 매우 낮고 안정적으로 유지되었습니다. 이는 사용자 경험의 질을 크게 향상시켰습니다.
-   **비용 절감:** 더 적은 수의 서버로 더 많은 트래픽을 처리하게 되어 인프라 비용을 크게 절감할 수 있었습니다.

결론적으로, 피그마는 복잡하고 위험한 마이그레이션을 성공적으로 완수하여 서비스의 확장성과 안정성을 한 단계 끌어올렸습니다.

## 구체 수치·데모·아키텍처

-   **기존 서버 기술 스택:** TypeScript, Node.js
-   **신규 서버 기술 스택:** Rust
-   **프로토콜 정의 도구:** Protobuf (Protocol Buffers) - TypeScript와 Rust 간의 데이터 구조 일관성을 유지하기 위해 사용.
-   **통신 프로토콜:** gRPC (영상에서 명시적으로 언급되진 않았으나, Protobuf 사용 맥락상 gRPC 또는 유사한 RPC 프레임워크를 사용했을 가능성이 높음. 영상에서 불명)
-   **핵심 아키텍처 변화:**
    -   **이전 (As-is):** 1 Document : 1 Node.js Process (Single-threaded)
    -   **이후 (To-be):** 1 Rust Process : N Documents (Multi-threaded, using a worker pool)
-   **마이그레이션 전략:**
    -   **섀도잉 (Shadowing):** 트래픽을 구/신 서버에 모두 보내고 응답을 비교하여 정합성 검증.
    -   **점진적 배포 (Gradual Rollout):** 기능 플래그를 이용해 1% → 5% → ... → 100%로 트래픽 전환.
-   **핵심 성능 개선 수치:**
    -   **CPU 사용량:** 90% 이상 감소 (발표 슬라이드 그래프에서 극적인 감소를 시각적으로 보여줌).
    -   **p99 Latency:** GC로 인한 불규칙한 스파이크가 사라지고 매우 낮고 안정적인 그래프를 보임.
-   **언급된 내부 시스템/도구:**
    -   **MCP (Multiplayer Collaboration Protocol) Server:** 발표의 주제가 되는 실시간 협업 서버.
    -   **LiveGraph:** 피그마의 핵심 데이터 동기화 기술 스택의 일부로 추정 (영상에서 불명).

피그마는 체계적인 섀도잉 및 점진적 배포 전략을 통해, 서비스 중단 없이 기존 TypeScript 서버를 고성능 Rust 서버로 성공적으로 교체하여 확장성, 안정성, 비용 효율성을 극적으로 개선했습니다.
