## 발표 흐름

### 서론: LLM 게이트웨이의 필요성
발표자는 "문제가 발생했습니다. 다시 시도해 주세요."와 같은 오류 메시지를 본 경험이 있는지 물으며 발표를 시작합니다. 이러한 단순한 메시지 뒤에는, 모델 제공업체가 다운되더라도 서비스를 유지하려는 복잡한 시스템이 존재한다고 설명합니다. 이 시스템이 바로 **LLM 게이트웨이**이며, 이 발표는 LLM 게이트웨이를 프로덕션 환경에 안정적으로 적용하는 방법에 관한 것입니다.

### LLM 게이트웨이란 무엇인가?
LLM 게이트웨이는 애플리케이션/서비스와 여러 LLM 제공업체(Provider A, B, C 등) 사이에 위치하는 미들웨어 또는 단일 진입점(Entry Point)입니다. "하나의 API, 하나의 정책 적용 지점"으로 요약할 수 있습니다.
게이트웨이는 다음과 같은 다양한 기능들을 통합하여 관리합니다.
*   **라우팅(Routing):** 요청별로 최적의 모델 또는 제공업체를 선택합니다.
*   **인증 및 키 관리(Auth & Keys):** 단일 인증 경계를 제공하고, API 키를 중앙에서 관리 및 교체합니다.
*   **폴백(Fallback):** 특정 제공업체가 실패하거나 느려질 때 다른 제공업체로 요청을 자동 전환합니다.
*   **속도 제한 및 비용 관리(Rate Limits & Cost):** 호출자를 제어하고, 작업 부하별로 비용을 추적 및 할당합니다.
*   **가드레일(Guardrails):** 입출력 데이터에 대한 안전성 검사를 한 곳에서 수행합니다.
*   **관찰 가능성(Observability):** 모델별 토큰 사용량, 지연 시간, 오류 등을 추적합니다.

### 핵심 딜레마: 4가지 요소의 상충 관계
LLM 게이트웨이의 핵심에는 4가지 요소 간의 끊임없는 싸움이 존재합니다.
1.  **가용성 (Availability)**
2.  **지연 시간 (Latency)**
3.  **가드레일 (Guardrails) / 보안**
4.  **비용 (Cost)**

발표자는 특히 서비스 성능 저하 상황에서 이 네 가지를 동시에 최적화하는 것은 불가능하다고 강조합니다. 하나의 요소를 위해 안전장치를 추가하면(예: 가용성을 위한 폴백), 다른 요소(예: 지연 시간, 비용)에 부정적인 영향을 미치게 됩니다. 이 발표의 목표는 게이트웨이 사용자에게는 어떤 트레이드오프를 해야 할지, 게이트웨이 설계자에게는 어떤 선택지를 제공해야 할지를 알려주는 것입니다.

### 가용성: 올바른 폴백(Fallback) 설계
단일 제공업체에만 의존하면, 해당 제공업체의 장애가 곧 우리 서비스의 장애가 됩니다.
전통적인 소프트웨어 엔지니어링에서는 '재시도(Retry)'와 '회로 차단기(Circuit Breaker)' 패턴으로 불안정한 의존성을 다룹니다. 하지만 LLM에는 이 방식이 충분하지 않습니다.
*   **문제 1:** LLM API 호출은 느리고 비싸기 때문에, 장애가 발생한 동일 제공업체에 재시도하는 것은 지연 시간과 비용만 낭비합니다.
*   **문제 2:** 회로 차단기가 작동해 요청을 차단하면, 사용 가능한 다른 백업 제공업체가 있음에도 불구하고 서비스가 실패하게 됩니다.

더 나은 접근법은 **요청별 폴백(Per-request fallback)**과 **주요 제공업체 제외(Ejection) 기능이 있는 회로 차단기**를 결합하는 것입니다.
1.  요청이 들어오면 먼저 주 제공업체(Primary)를 호출합니다.
2.  실패 시, 해당 요청에 한해 즉시 보조 제공업체(Secondary)로 폴백합니다.
3.  주 제공업체의 실패가 누적되면 회로 차단기가 작동하여, 이후의 모든 요청을 한동안 보조 제공업체로 직접 보냅니다. (주 제공업체를 요청 경로에서 일시적으로 '제외'함)

이때 회로 차단기의 상태(실패 횟수)를 어디에 저장할지 결정해야 합니다.
*   **전역 상태(Fleet-wide):** Redis 등 공유 인프라에 저장. 한 번의 장애로 모든 인스턴스가 빠르게 반응하지만, 추가 인프라가 필요합니다.
*   **로컬 상태(Local):** 각 인스턴스 메모리에 저장. 추가 인프라는 불필요하지만, 모든 인스턴스가 개별적으로 장애를 겪어야 상태가 전파되므로 반응이 느립니다.

### 가용성 설계의 현실적 문제점
깔끔한 다이어그램만으로는 보이지 않는 실제 문제들이 있습니다.
*   **폴백의 비투명성:** 제공업체마다 도구 호출(Tool-calling) 스키마, 토큰 제한, 중단 이유(Stop reasons) 등이 다릅니다. 정규화(Normalization) 계층 없이는 폴백 시 응답 형식이 바뀌어 애플리케이션이 깨질 수 있습니다.
*   **스트리밍의 제약:** 스트리밍 응답 중에는 일단 첫 토큰이 전송되면 중간에 폴백, 재시도, 수정이 불가능합니다. 응답 중간에 실패하면 사용자는 그대로 오류를 보게 됩니다. 따라서 지연 시간이 극도로 중요한 경우가 아니라면 스트리밍을 사용하지 않는 것이 더 많은 제어권을 확보하는 길입니다.
*   **폴백 제공업체의 용량:** 많은 팀이 주 제공업체의 용량은 철저히 계획하지만, 폴백 제공업체의 용량은 간과합니다. 실제 장애로 모든 트래픽이 폴백 제공업체로 몰리면, 해당 제공업체가 과부하로 다운될 수 있습니다.

### 지연 시간(Latency): 조용한 장애
서비스 불능은 명확한 알림을 유발하지만, 높은 지연 시간은 '조용한 장애'처럼 서서히 서비스를 악화시킵니다.
특히 게이트웨이가 임베딩(0.3초), 분류(0.8초), 채팅(3초), 추론(35초) 등 다양한 작업을 처리할 때, 이들을 합친 **평균 지연 시간은 거짓말을 합니다.** 추론 모델의 정상적인 지연 시간(35초)이 채팅 모델의 장애 상황과 비슷해 보일 수 있기 때문입니다.
따라서 게이트웨이 전체의 단일 지연 시간 지표 대신, **모델 종류별, 라우트별로 P99 지연 시간을 추적하고 타임아웃을 설정**해야 합니다.

### 예측 불가능한 지연 시간의 원인과 해결책
*   **원인 1 (가변적인 '생각' 시간):** 추론 모델은 비결정적인 내부 처리 과정을 거치므로, 동일한 프롬프트라도 2초가 걸릴 수도, 60초가 걸릴 수도 있습니다.
*   **원인 2 (라우터 모델):** 제공업체 측에서 내부적으로 여러 모델 중 하나를 선택해 응답을 생성하는 '라우터 모델'을 사용하면, 지연 시간을 예측하기 더욱 어려워집니다.
*   **해결책:**
    1.  **정적 추론 수준 고정:** 특정 라우트에서는 사용할 모델을 고정하여 지연 시간 예측 가능성을 높입니다.
    2.  **꼬리 지연 시간 헤징(Hedge the tail):** 주 요청을 보낸 후 짧은 지연 시간 뒤에 백업 요청을 병렬로 보내, 먼저 도착하는 응답을 사용합니다. 이는 P99 지연 시간을 크게 줄여주지만, 비용 관리를 위해 이 전략을 사용하는 비율을 제한해야 합니다.

### 보안: 가드레일의 중요성과 딜레마
가드레일은 프롬프트 인젝션, 개인정보(PII) 유출, 유해성 콘텐츠 등을 방지하는 데 필수적입니다. 하지만 가드레일 자체도 또 하나의 의존성이며, 실패할 수 있습니다.
가드레일 시스템이 실패했을 때 두 가지 선택지가 있습니다.
*   **Fail Open (개방형 실패):** 가드레일 검사 없이 요청을 통과시킵니다. 가용성은 보호되지만 보안 위험을 감수해야 합니다.
*   **Fail Closed (폐쇄형 실패):** 요청을 차단합니다. 보안은 보호되지만 가용성에 타격을 줍니다.

정답은 없으며, 정책별로 위험을 판단해야 합니다. 예를 들어, 유해성 필터는 Fail Open 해도 괜찮을 수 있지만, PII 필터나 프롬프트 인젝션 방어는 반드시 Fail Closed 해야 합니다. 각 가드레일의 중요도에 따라 개별적으로 정책을 정하는 것이 중요합니다.

### 안정적인 가드레일 시스템 구축 방안
가드레일을 안정적으로 운영하기 위해 다음을 고려해야 합니다.
*   **시간 예산(Time Budget):** 각 가드레일에 엄격한 실행 시간 제한을 두어, 느린 검사가 전체 앱의 지연 시간을 좌우하지 않도록 합니다.
*   **폴백(Fallback):** 가드레일도 서비스이므로, 장애 시를 대비해 보조 검사 시스템이나 캐시된 결정을 활용하는 폴백 전략이 필요합니다.
*   **배치(Placement):** 가드레일을 언제 실행할지에 따라 사용자 경험이 달라집니다.
    *   **Pre-hook (모델 호출 전):** 입력 검사에 가장 안전하지만, 모든 요청에 직렬 지연 시간을 추가합니다.
    *   **In Parallel (모델 호출과 병렬, ★선호됨):** 모델 호출과 동시에 가드레일을 실행하고, 최종 응답 전에 결과를 취합합니다. 사용자가 체감하는 지연 시간이 거의 없습니다.
    *   **Post-hook (모델 호출 후):** 모델의 출력물을 검사하는 데 필요하며, 응답에 직렬 지연 시간을 추가합니다.

### 비용 및 속도 제한: 공유 인프라의 함정
*   **공유 속도 제한(Shared Rate Limits):** 하나의 '시끄러운 테넌트(noisy tenant)'가 전체 속도 제한을 소진하여 다른 모든 사용자를 방해할 수 있습니다. 이를 방지하려면 팀이나 작업 부하별로 별도의 API 키를 발급하여 사용량을 격리해야 합니다.
*   **부하 차단(Load Shedding):** 시스템에 과부하가 걸릴 때, 무한정 요청을 큐에 쌓아두면 재시도 폭풍(Retry Storm)으로 이어져 재앙이 됩니다. 반드시 **바운드 큐(Bounded Queue)**를 사용하고, 큐가 가득 차면 새로운 요청을 즉시 거부(Shed)하여 시스템을 안정적으로 유지해야 합니다.

### 결론: 중앙 집중식 게이트웨이의 위험과 대안
모든 트래픽을 처리하는 중앙 집중식 게이트웨이는 그 자체로 **단일 장애점(Single Point of Failure, SPOF)**이 됩니다. 잘못된 배포 한 번으로 모든 워크로드가 동시에 다운될 수 있습니다.
더 나은 모델은 **분산된 게이트웨이, 중앙 집중식 거버넌스(Decentralized gateway, centralized governance)**입니다.
*   **게이트웨이 분산:** 각 서비스가 자체적인 폴백, 타임아웃, 부하 차단 로직을 가집니다. 복원력과 관련된 로직은 로컬에 둡니다.
*   **거버넌스 중앙 집중:** 비용 할당, 가드레일 실패 이벤트, 속도 제한 정책 등은 중앙 거버넌스 플레인으로 전송하고 관리합니다. 이를 통해 SPOF 없이 중앙 통제의 이점을 누릴 수 있습니다.

마지막으로 발표자는 자신의 아들 생일임에도 불구하고 이 자리에 섰다며, 청중들이 이 발표를 통해 단 하나의 장애라도 예방할 수 있기를 바란다는 개인적인 소회를 밝히며 발표를 마쳤습니다.

## 구체 수치·데모·아키텍처
*   **LLM 게이트웨이 아키텍처:** [App/Service A, B] -> [LLM Gateway] -> [Provider A, B, C] 형태로, 게이트웨이가 중간에서 라우팅, 폴백, 가드레일 등을 처리하는 모델.
*   **4가지 상충 요소:** 가용성(Availability), 지연 시간(Latency), 가드레일(Guardrails), 비용(Cost)이 서로 트레이드오프 관계에 있음을 보여주는 다이어그램.
*   **폴백 및 회로 차단기 아키텍처:** 요청이 Breaker를 통해 Primary로 가고, 실패 시 Secondary로 폴백하며, Breaker가 열리면(open) 요청이 바로 Secondary로 가는 흐름을 보여주는 다이어그램.
*   **작업 부하별 P99 지연 시간 (예시):**
    *   Embeddings: 0.3초
    *   Classify: 0.8초
    *   Chat: 3초
    *   Reasoning: 35초
    *   Blended P99: 약 6~8초 (이 수치가 무의미함을 설명하기 위한 예시)
*   **바운드/언바운드 큐 다이어그램:** Unbounded Queue는 재시도 폭풍 시 재앙으로 이어지며, Bounded Queue는 부하를 차단(shed)하여 시스템을 안정적으로 유지함을 시각적으로 설명.
*   **분산 게이트웨이, 중앙 집중식 거버넌스 모델:** 복원력(resilience)은 로컬에 두고, 비용 및 가드레일 이벤트 등 거버넌스 데이터만 중앙 플레인으로 보내는 아키텍처를 제안.

## 핵심 인용
*   "A reasoning model's normal is a chat model's outage."
    > 추론 모델의 정상 상태는 채팅 모델의 장애 상태와 같다. (따라서 통합된 지연 시간 지표는 무의미하다는 의미)
*   "Decentralized gateway, centralized governance."
    > 게이트웨이는 분산시키고, 거버넌스는 중앙 집중화하라. (단일 장애점을 피하면서 중앙 통제를 유지하는 방법)
*   "Shared limits are a trap, shared infra is a risk."
    > 공유된 (속도) 제한은 함정이고, 공유된 인프라는 위험이다.
