# AI Agents Are Just Distributed Systems Now — Salman Munaf, TikTok

🔗 https://www.youtube.com/watch?v=hD9-V56FNRI

## 개요
*   **발표자:** Salman Munaf (TikTok)
*   **한 줄 주제:** AI 에이전트를 '분산 시스템(Distributed Systems)'이라는 익숙하고 검증된 엔지니어링 프레임워크로 바라보면, 복잡한 에이전트 시스템을 더 체계적이고 안정적으로 설계, 구축, 디버깅할 수 있다.

## 발표 흐름

### 들어가며: AI 에이전트의 '환멸의 계곡'
발표자는 AutoGPT, BabyAGI 같은 초기 AI 에이전트들이 등장했을 때의 엄청난 기대감과 흥분을 언급하며 발표를 시작합니다. 처음에는 에이전트가 모든 것을 자동화해줄 것처럼 보였지만, 곧 사람들은 이것이 매우 불안정하고, 디버깅이 어려우며, 실제 프로덕션 환경에 적용하기 어렵다는 것을 깨닫게 되었습니다. 이는 마치 가트너 하이프 사이클의 '환멸의 계곡(trough of disillusionment)'에 빠진 것과 같다고 비유합니다.

이러한 문제를 해결하기 위해, 발표자는 에이전트를 바라보는 새로운 '멘탈 모델(mental model)'을 제안합니다. 그것이 바로 "AI 에이전트는 분산 시스템이다"라는 관점입니다. 이 관점은 단순한 비유가 아니라, 지난 수십 년간 분산 시스템 분야에서 쌓아온 지식, 도구, 패턴을 AI 에이전트 개발에 직접 적용할 수 있게 해주는 실용적인 프레임워크라고 주장합니다.

### 핵심 주장: AI 에이전트는 분산 시스템이다
발표자는 분산 시스템을 "공통의 목표를 달성하기 위해 네트워크를 통해 메시지를 주고받으며 통신하는, 여러 컴퓨터에 위치한 자율적인 컴퓨팅 요소들의 집합"으로 정의합니다. 그리고 이 정의의 핵심 특징들(여러 구성요소, 네트워크 통신, 독립적인 실패 가능성)이 AI 에이전트 시스템의 특징과 정확히 일치한다고 설명합니다.

이러한 관점을 채택하면 다음과 같은 이점이 있다고 말합니다.
1.  **문제 정의:** 에이전트 개발 시 겪는 문제들을 분산 시스템의 용어(예: 지연 시간, 실패 처리, 상태 동기화)로 명확하게 정의하고 이해할 수 있습니다.
2.  **솔루션 재사용:** 에이전트를 위한 새로운 추상화나 도구를 발명하는 대신, 이미 성숙한 분산 시스템 생태계의 검증된 솔루션과 패턴을 가져와 재사용할 수 있습니다.

### 개념 매핑: 에이전트와 분산 시스템의 구성 요소 비교
발표자는 AI 에이전트 시스템의 각 구성요소를 분산 시스템의 개념과 일대일로 매핑하여 자신의 주장을 구체화합니다.

*   **노드/서비스 (Nodes/Services) ↔ LLM과 도구 (LLMs and Tools):** 분산 시스템의 개별 마이크로서비스나 노드는 AI 에이전트 시스템의 LLM, 검색 API, 코드 실행기, 데이터베이스 조회 도구 등과 같습니다. 각 요소는 독립적으로 작동하며 실패할 수 있습니다.
*   **네트워크 호출 (Network Calls) ↔ 프롬프트 (Prompts):** 서비스들이 API를 통해 통신하듯, 에이전트의 구성요소들은 '프롬프트'를 통해 통신합니다. LLM이 도구를 호출하기 위해 생성하는 JSON 형식의 프롬프트는 사실상 다른 서비스에 보내는 네트워크 API 요청과 구조적으로 동일합니다.
*   **독립적인 실패 (Independent Failures) ↔ 환각 및 도구 오류 (Hallucinations & Tool Errors):** 분산 시스템에서 특정 노드가 다운되거나 네트워크가 끊기는 것처럼, 에이전트 시스템에서는 LLM이 환각(hallucination)을 일으키거나(LLM 노드의 실패), 외부 API 도구가 타임아웃되거나 에러를 반환할 수 있습니다(도구 노드의 실패).

### 분산 시스템 원칙의 적용 1: 관찰 가능성(Observability)
분산 시스템에서 여러 서비스 간의 복잡한 상호작용을 이해하기 위해 로깅, 메트릭, 분산 추적(distributed tracing)이 필수적이듯, AI 에이전트에서도 '관찰 가능성'이 매우 중요하다고 강조합니다.

*   **문제:** 에이전트가 왜 특정 행동을 했는지, 어떤 도구를 어떤 순서로 호출했는지, 중간에 어떤 오류가 발생했는지 파악하기가 매우 어렵습니다.
*   **해결책:** LangSmith, LangFuse 같은 도구들이 바로 이 문제를 해결하기 위한 것입니다. 이들은 에이전트의 '생각의 연쇄(chain of thought)'를 시각적으로 추적하게 해주는데, 이는 분산 시스템에서 OpenTelemetry나 Jaeger 같은 도구로 마이크로서비스 간의 요청 흐름을 추적하는 것과 정확히 같은 개념입니다. 발표자는 데모에서 OpenTelemetry를 직접 사용하여 에이전트의 작동을 추적하는 모습을 보여줍니다.

### 분산 시스템 원칙의 적용 2: 상태 관리(State Management)
분산 시스템에서 여러 노드에 걸쳐 일관된 상태를 유지하는 것이 어려운 문제인 것처럼, AI 에이전트도 대화 기록, 중간 계산 결과(scratchpad), 장기 기억 등 다양한 '상태'를 관리해야 합니다.

*   **문제:** 간단한 데모에서는 파이썬 딕셔너리에 상태를 저장할 수 있지만, 실제 애플리케이션에서는 상태가 유실되거나 동기화되지 않는 문제가 발생합니다.
*   **해결책:** 분산 시스템에서 사용하는 Redis 같은 인메모리 캐시나 데이터베이스를 에이전트의 '메모리' 또는 '상태 저장소'로 활용할 수 있습니다. 이는 이미 검증된 안정적이고 확장 가능한 상태 관리 솔루션입니다.

### 분산 시스템 원칙의 적용 3: 오케스트레이션(Orchestration)
여러 마이크로서비스를 조율하여 하나의 비즈니스 로직을 완성하는 것을 '오케스트레이션'이라고 합니다. AI 에이전트에서도 여러 LLM과 도구들을 어떤 순서와 논리로 조율할 것인지가 핵심입니다.

*   **문제:** 간단한 ReAct (Reasoning and Acting) 루프만으로는 복잡한 다단계 작업을 수행하기 어렵습니다. 여러 에이전트가 협업하는 시나리오에서는 더욱 복잡해집니다.
*   **해결책:** Kubernetes, Airflow, Temporal 같은 워크플로우 오케스트레이션 도구들의 원리가 에이전트 프레임워크에 적용되고 있습니다. CrewAI나 Autogen 같은 라이브러리는 여러 에이전트(노드) 간의 작업 흐름과 통신 방식을 정의하는 '오케스트레이터' 역할을 합니다. 이는 중앙 컨트롤러가 서비스들을 조율하는 분산 시스템의 오케스트레이션 패턴과 동일합니다.

### 분산 시스템 원칙의 적용 4: 회복탄력성(Resilience)
분산 시스템은 일부 구성요소가 실패하더라도 전체 시스템은 계속 작동하도록 설계됩니다. 이를 '회복탄력성'이라고 합니다.

*   **문제:** LLM이 잘못된 형식의 JSON을 출력하거나, 외부 API 호출이 실패하면 에이전트 전체가 멈춰버립니다.
*   **해결책:** 분산 시스템의 재시도(retry) 로직, 서킷 브레이커(circuit breaker), 대체 작동(fallback) 등의 패턴을 에이전트에 적용해야 합니다. 예를 들어, 도구 호출이 실패하면 LLM에게 다른 방법을 시도하도록 요청하거나, LLM이 생성한 코드가 에러를 발생시키면 디버깅 정보를 포함하여 다시 수정을 요청하는 '자가 교정(self-correction)' 루프가 바로 회복탄력성 패턴의 한 예입니다.

### 실제 구현 데모: `magentic` 라이브러리와 OpenTelemetry
발표자는 이론을 실제로 보여주기 위해 자신이 기여하고 있는 파이썬 라이브러리 `magentic`을 사용한 라이브 코딩 데모를 진행합니다.

1.  **`magentic` 소개:** 파이썬의 타입 힌트와 데코레이터를 사용하여 LLM 함수와 도구를 매우 직관적으로 정의할 수 있게 해주는 라이브러리입니다.
2.  **`@prompt` 데코레이터:** 일반 파이썬 함수에 `@prompt` 데코레이터를 붙이면, 함수 시그니처(함수 이름, 설명, 파라미터, 반환 타입)가 자동으로 LLM 프롬프트로 변환됩니다. 함수를 호출하는 것이 곧 LLM API를 호출하는 것과 같아져 '프롬프트는 네트워크 호출'이라는 비유를 코드로 명확하게 보여줍니다.
3.  **`@tool` 데코레이터:** 도구로 사용될 함수에 `@tool` 데코레이터를 붙여 LLM이 호출할 수 있는 함수로 쉽게 등록합니다.
4.  **데모 시나리오:** GitHub 저장소의 스타 개수와 같은 정보를 알려주는 에이전트를 만듭니다.
    *   GitHub API를 호출하는 `get_repo_details` 함수를 `@tool`로 정의합니다.
    *   사용자의 질문을 받아 `get_repo_details` 도구를 사용하여 답변을 생성하는 `get_repo_info` 함수를 `@prompt`로 정의합니다.
5.  **관찰 가능성 시연:** 데모 코드에 OpenTelemetry 설정을 추가하자, 에이전트의 실행 과정이 분산 추적 시스템(Jaeger와 유사한 UI)에 시각적으로 표시됩니다. 사용자의 질문이 들어온 시점부터, LLM이 어떤 추론을 거쳐 `get_repo_details` 도구를 호출했는지, 도구의 반환 값은 무엇이었는지, 그리고 최종 답변을 생성하기까지의 모든 과정이 하나의 '트레이스(trace)'로 묶여 명확하게 보입니다. 이는 디버깅에 매우 강력한 기능임을 보여줍니다.

### 결론: 엔지니어링 관점으로 에이전트 바라보기
발표자는 AI 에이전트를 '마법'이 아닌 '엔지니어링'의 대상으로 봐야 한다고 다시 한번 강조하며 마무리합니다. 분산 시스템이라는 렌즈를 통해 AI 에이전트를 바라보면, 우리는 이미 수십 년간 쌓아온 강력한 도구와 원칙들을 활용하여 더 예측 가능하고, 안정적이며, 확장 가능한 시스템을 만들 수 있습니다. 이것이 '환멸의 계곡'을 지나 '생산성의 고원(plateau of productivity)'으로 나아가는 길이라고 주장합니다.

## 구체 수치·데모·아키텍처
*   **언급된 프레임워크/도구:**
    *   **초기 AI 에이전트:** AutoGPT, BabyAGI (에이전트의 초기 하이프와 한계를 설명하는 맥락에서 언급)
    *   **관찰 가능성 도구:** LangSmith, LangFuse, OpenTelemetry, Jaeger (에이전트의 작동을 추적하고 디버깅하기 위한 도구로 언급)
    *   **상태 관리 도구:** Redis (에이전트의 메모리/상태를 안정적으로 관리하기 위한 솔루션 예시로 언급)
    *   **오케스트레이션 도구/프레임워크:** Kubernetes, Airflow, Temporal (분산 시스템의 오케스트레이션 도구 예시), CrewAI, Autogen (AI 에이전트 오케스트레이션 프레임워크 예시)
*   **데모에서 사용된 라이브러리:**
    *   **`magentic`:** 발표자가 시연한 파이썬 라이브러리. 데코레이터 기반으로 LLM 함수와 도구를 쉽게 정의.
*   **데모 아키텍처/코드:**
    *   **개념 아키텍처:** 에이전트 시스템을 여러 노드(LLM, Tool)가 네트워크(Prompt)를 통해 통신하는 분산 시스템으로 묘사.
    *   **`magentic` 코드 조각:**
        ```python
        # LLM 함수를 정의하는 데코레이터
        @prompt("Describe the function of the {function_name} function.")
        def describe_function(function_name: str) -> str:
            ...

        # 도구를 정의하는 데코레이터
        @tool
        def get_repo_details(owner: str, repo: str) -> dict[str, Any]:
            """Returns details for a GitHub repository."""
            # ... GitHub API call logic ...

        # 도구를 사용하는 LLM 함수(에이전트)
        @prompt(
            "Answer the following question: {question}",
            tools=[get_repo_details]
        )
        def get_repo_info(question: str) -> str:
            ...
        ```
    *   **데모 결과:** `get_repo_info("how many stars does magentic have?")`를 실행했을 때, OpenTelemetry를 통해 생성된 트레이스(trace)를 시각적으로 보여줌. 이 트레이스에는 `get_repo_info` 호출, 내부적인 LLM 호출, `get_repo_details` 도구 호출, 도구의 결과 반환 등 모든 단계가 명확히 기록되어 있었음.

## 한 줄 결론
복잡하고 불안정한 AI 에이전트 개발 문제를, 이미 검증된 분산 시스템의 설계 원칙(관찰 가능성, 상태 관리, 오케스트레이션, 회복탄력성)과 도구를 적용하여 해결하자는 매우 실용적인 제안.
