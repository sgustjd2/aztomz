# How to avoid disaster when vibe-coding a billing engine — Andrew Garvin, Stripe

🔗 https://www.youtube.com/watch?v=mJqwmmOx4WA

## 개요
*   **발표자:** Andrew Garvin (Stripe)
*   **한 줄 주제:** 직관과 느낌에 의존하는 'Vibe-coding'으로 과금 엔진을 만들 때 발생하는 재앙적인 문제들을 살펴보고, 상태 머신(State Machine), 이벤트 기반 아키텍처, 멱등성(Idempotency)이라는 엔지니어링 원칙을 통해 이를 어떻게 피할 수 있는지 설명합니다.

## 발표 흐름

### ### 도입: 과금 시스템, 생각보다 복잡하다
발표자는 과거 한 회사에서 과금 시스템을 처음 만들었던 경험으로 발표를 시작합니다. 당시에는 "매달 한 번씩 모든 고객에게 청구하는 간단한 크론잡(cron job)" 정도로 문제를 매우 단순하게 생각했습니다. 이러한 접근법, 즉 문제의 복잡성을 깊이 이해하지 않고 직관과 느낌에만 의존해 코드를 작성하는 것을 'Vibe-coding'이라고 지칭합니다.

초기 버전의 코드는 매우 간단했습니다. 청구 대상 고객 목록을 가져와 루프를 돌며 `bill_customer` 함수를 호출하는 식이었습니다. 이 코드는 처음에는 잘 작동하는 것처럼 보였지만, 시스템이 복잡해지고 예외 상황이 발생하면서 재앙의 시작이 되었습니다.

### ### 첫 번째 재앙: 중복 과금과 멱등성의 부재
첫 번째 문제는 스크립트가 실행 도중 멈췄을 때 발생했습니다. 예를 들어 1000명의 고객 중 500명에게만 청구하고 스크립트가 멈췄다고 가정해봅시다. 가장 간단한 해결책은 스크립트를 다시 실행하는 것입니다. 하지만 이렇게 하면 이미 청구된 500명의 고객에게 또다시 요금이 부과되는 '중복 과금' 문제가 발생합니다.

이 문제의 근본 원인은 작업이 **멱등성(Idempotency)**을 갖추지 않았기 때문입니다. 멱등성이란 동일한 작업을 여러 번 수행하더라도 결과가 한 번 수행한 것과 같은 성질을 의미합니다. `bill_customer` 함수는 멱등성이 없었기 때문에 재실행 시 중복 과금을 유발했습니다.

이를 해결하기 위한 첫 시도는 고객 데이터베이스에 `billed_at` 같은 타임스탬프 필드를 추가하는 것이었습니다. 청구 전에 이 필드가 비어있는지 확인하고, 청구 후에 현재 시간을 기록하는 방식입니다. 이렇게 하면 이미 청구된 고객은 건너뛰게 되어 중복 과금을 막을 수 있습니다.

### ### 두 번째 재앙: 경쟁 상태와 상태 머신의 도입
`billed_at` 필드를 추가했지만 더 교묘한 문제가 발생했습니다. `bill_customer` 함수는 실제로는 여러 단계로 이루어져 있습니다.
1.  고객의 신용카드에 요금을 청구한다.
2.  데이터베이스의 `billed_at` 필드를 업데이트한다.
3.  고객에게 영수증 이메일을 보낸다.

만약 1번(카드 청구)과 2번(DB 업데이트) 사이에서 스크립트가 멈춘다면 어떻게 될까요? 고객에게 돈은 청구되었지만, `billed_at`은 여전히 비어있으므로 스크립트를 재시작하면 또다시 중복 과금이 발생합니다. 이처럼 여러 단계로 이루어진 작업이 원자적(atomic)으로 처리되지 않을 때 경쟁 상태(race condition) 문제가 발생합니다.

발표자는 이 문제를 해결하기 위해 접근 방식을 근본적으로 바꿔야 한다고 주장합니다. 과금 프로세스를 단순히 '작업의 목록'으로 보는 대신, **상태 머신(State Machine)**으로 모델링해야 한다는 것입니다. 예를 들어, '청구서(Invoice)'라는 객체를 도입하고, 이 객체가 가질 수 있는 상태를 `due`(청구 예정), `paid`(지불 완료), `error`(오류) 등으로 정의합니다.

이제 과금 스크립트의 역할은 '고객에게 요금을 청구하는 것'이 아니라, **'due 상태의 청구서를 paid 상태로 전환하는 것'**이 됩니다. 스크립트는 `due` 상태의 모든 청구서를 가져와 결제를 시도하고, 성공하면 상태를 `paid`로 바꿉니다. 만약 결제 성공 직후 DB 업데이트 전에 시스템이 멈추더라도, 재시작된 스크립트는 여전히 `due` 상태인 해당 청구서에 대해 결제를 '재시도'할 뿐입니다. 여기서 결제 게이트웨이(예: Stripe)가 멱등성을 보장한다면 중복 결제 없이 안전하게 상태를 `paid`로 전환할 수 있습니다.

### ### 핵심 원칙 1: 상태 전이 로직과 부수 효과(Side Effect)의 분리
상태 머신을 도입했지만, 상태를 바꾸는 핵심 로직(결제 시도)과 그에 따른 부수 효과(이메일 발송, 분석 데이터 전송, 회계 시스템 업데이트 등)가 한 함수 안에 섞여 있으면 코드가 복잡해지고 테스트가 어려워집니다. 예를 들어 이메일 시스템이 다운되면 핵심적인 결제 로직까지 실패할 수 있습니다.

이를 해결하기 위한 원칙은 **상태 전이 로직과 부수 효과를 분리**하는 것입니다. 이는 **이벤트 기반 아키텍처(Event-driven Architecture)**를 통해 구현할 수 있습니다.
1.  **상태 머신 실행기(State Machine Runner):** 오직 청구서의 상태를 `due`에서 `paid`로 바꾸는 책임만 집니다.
2.  **이벤트 발행(Event Emission):** 상태 전환에 성공하면, `invoice.paid`와 같은 이벤트를 이벤트 버스(Event Bus)로 발행합니다.
3.  **이벤트 리스너(Event Listeners):** 각각의 부수 효과를 처리하는 별도의 서비스(이메일 서비스, 분석 서비스 등)들이 이 이벤트를 구독(subscribe)합니다. `invoice.paid` 이벤트가 발생하면, 이메일 서비스는 영수증을 보내고 분석 서비스는 데이터를 기록합니다.

이 아키텍처는 각 컴포넌트의 책임을 명확히 분리(decoupling)하여 시스템의 유연성과 안정성을 크게 높입니다. 이메일 서버에 문제가 생겨도 핵심 결제 로'직은 영향을 받지 않으며, 나중에 이메일 서버가 복구되었을 때 이벤트를 재처리하여 이메일을 보낼 수 있습니다.

### ### 핵심 원칙 2: 멱등성 키를 이용한 재시도 안정성 확보
이벤트 기반 아키텍처를 도입해도 멱등성 문제는 여전히 존재합니다. 예를 들어, 이메일 리스너가 `invoice.paid` 이벤트를 받고 이메일을 성공적으로 보냈지만, 이벤트 버스에 '처리 완료'라고 알리기 직전에 다운되었다고 가정해봅시다. 시스템이 복구되면 이벤트 버스는 해당 이벤트를 '미처리'로 간주하고 다시 전달할 것이고, 고객은 동일한 영수증 이메일을 두 번 받게 됩니다.

이 문제를 해결하기 위해 **멱등성 키(Idempotency Key)**를 사용합니다.
1.  이벤트를 발행하는 쪽(상태 머신 실행기)에서 각 이벤트마다 고유한 ID(예: UUID)를 생성하여 '멱등성 키'로 함께 보냅니다.
2.  이벤트를 수신하는 쪽(이메일 리스너 등)에서는 처리한 이벤트의 멱등성 키를 데이터베이스에 저장합니다.
3.  이벤트를 처리하기 전에, 수신한 멱등성 키가 이미 DB에 저장되어 있는지 확인합니다.
4.  이미 저장된 키라면, 이전에 처리가 완료되었지만 확인 신호만 못 보낸 것으로 간주하고 현재 작업을 건너뜁니다.

이 방식은 Stripe API가 실제로 작동하는 방식과 동일합니다. API 요청 시 `Idempotency-Key` 헤더에 고유한 값을 담아 보내면, 네트워크 오류 등으로 동일한 요청을 재시도하더라도 Stripe 서버는 이를 한 번의 요청으로 처리하여 중복 결제를 방지합니다.

### ### 결론: Vibe-Coding을 넘어서
발표자는 안정적인 과금 시스템을 구축하기 위해 'Vibe-coding'에서 벗어나 다음과 같은 세 가지 핵심 엔지니어링 원칙을 따라야 한다고 강조하며 발표를 마무리합니다.

1.  **비즈니스 프로세스를 상태 머신으로 모델링하라:** 문제의 상태와 상태 간의 전이를 명확히 정의하라.
2.  **상태 전이와 부수 효과를 분리하라:** 이벤트 기반 아키텍처를 사용해 핵심 로직과 부가적인 작업을 분리하여 시스템을 유연하고 안정적으로 만들어라.
3.  **모든 것을 멱등적으로 만들어라:** 멱등성 키를 사용하여 네트워크 오류나 시스템 장애 발생 시에도 재시도가 안전하게 이루어지도록 보장하라.

이러한 원칙들은 과금 시스템뿐만 아니라 신뢰성이 중요한 모든 분산 시스템에 적용될 수 있는 강력한 설계 패턴입니다.

## 구체 수치·데모·아키텍처
*   **초기 코드 (Vibe-coding):**
    *   **맥락:** 멱등성이 고려되지 않은 가장 단순한 형태의 과금 스크립트.
    ```python
    # This is a simplification
    for customer in customers_to_bill:
        bill_customer(customer)
    ```

*   **상태 머신 도입 후 코드:**
    *   **맥락:** '청구서(Invoice)' 객체와 그 상태를 기반으로 동작하는 개선된 스크립트.
    ```python
    # Also a simplification
    for invoice in invoices_in_due_state:
        # This function is idempotent
        charge_invoice(invoice)
    ```

*   **이벤트 기반 아키텍처 다이어그램 (개념 설명):**
    *   **맥락:** 상태 전이 로직과 부수 효과를 분리하는 구조를 설명.
    *   **흐름:**
        1.  **State Machine Runner** (상태 머신 실행기)가 상태 전이를 처리함.
        2.  성공 시 **Event Bus** (이벤트 버스)로 `invoice.paid` 같은 이벤트를 발행함.
        3.  이벤트를 구독하는 여러 **Listeners** (리스너)들이 각자의 작업을 수행함.
            *   `Email Service` -> 영수증 발송
            *   `Analytics Service` -> 데이터 기록
            *   `Accounting Sync` -> 회계 정보 동기화

*   **도구 및 개념:**
    *   **Idempotency Key:** API 요청이나 이벤트 처리의 멱등성을 보장하기 위해 사용되는 고유 식별자. Stripe API의 `Idempotency-Key` 헤더가 대표적인 예시로 언급됨.
    *   **State Machine (상태 머신):** 비즈니스 로직을 유한한 상태와 상태 간의 전이로 모델링하는 방법. `due` -> `paid` 상태 전환이 예시로 사용됨.
    *   **Event-driven Architecture (이벤트 기반 아키텍처):** 시스템의 컴포넌트들이 이벤트를 통해 비동기적으로 통신하는 방식.

*   **멱등성 키를 사용한 이벤트 핸들러 (의사 코드):**
    *   **맥락:** 이벤트 리스너가 중복 처리를 방지하는 로직을 설명.
    ```
    function handle_event(event):
        # DB에서 idempotency_key를 조회
        if processed_keys.contains(event.idempotency_key):
            return # 이미 처리됨, 무시
        
        # 실제 작업 수행
        send_receipt_email(event.customer_id)

        # DB에 idempotency_key 저장
        processed_keys.add(event.idempotency_key)
    ```

## 핵심 인용
*   "Billing systems are just distributed state machines."
    > "과금 시스템은 그저 분산 상태 머신일 뿐입니다." (과금 시스템의 본질을 상태 머신으로 정의하며)
*   "Your job is not to bill the customer. Your job is to move the invoice from the 'due' state to the 'paid' state."
    > "당신의 일은 고객에게 요금을 청구하는 것이 아닙니다. 당신의 일은 청구서를 'due' 상태에서 'paid' 상태로 옮기는 것입니다." (문제 해결의 관점을 바꾸는 것의 중요성을 강조하며)
*   "Model your business process as a state machine. Separate your state transitions from your side effects. And make everything idempotent."
    > "비즈니스 프로세스를 상태 머신으로 모델링하고, 상태 전이와 부수 효과를 분리하며, 모든 것을 멱등적으로 만드십시오." (발표의 세 가지 핵심 원칙을 요약하며)

## 한 줄 결론
직관에 의존하는 과금 시스템 개발은 재앙을 초래하므로, 상태 머신, 이벤트 기반 분리, 멱등성 키라는 엔지니어링 원칙을 적용하여 예측 가능하고 안정적인 시스템을 구축해야 한다.
