# Your Code Has Bugs. Lean4 Has Proofs: Formal Verification for Engineers — Varun Pant, AWS

🔗 https://www.youtube.com/watch?v=lRa9sPaMyy4

## 개요
*   **발표자:** Varun Pant, AWS
*   **한 줄 주제:** AI 코딩 에이전트가 대량의 코드를 생성하는 시대에, 형식 검증(Formal Verification)과 Lean 같은 증명 보조기(Proof Assistant)를 사용하여 모든 입력에 대해 수학적으로 '증명 가능하게 올바른' 소프트웨어를 구축하는 방법을 소개합니다.

## 발표 흐름

### ### 문제 제기: AI 시대의 코드 정확성 검증의 한계
발표자는 AI 코딩 에이전트가 그 어느 때보다 많은 코드를 생성하고 있다고 지적하며, 이 코드의 정확성을 어떻게 보장할 수 있는지 질문을 던집니다. 기존의 방법들에는 명확한 한계가 있습니다.

*   **LLM을 심판으로 사용 (LLM-as-judge):** LLM의 판단은 확률적(probabilistic)이므로 결정론적인 정확성을 보장할 수 없습니다.
*   **테스트 (Tests):** 테스트는 일부 대표적인 입력값에 대해서만 동작을 확인할 뿐, 모든 가능한 입력에 대한 정확성을 증명하지는 못합니다.
*   **인간의 코드 리뷰 (Human code review):** AI 에이전트가 코드를 생성하는 속도를 인간이 따라가며 검토하는 것은 현실적으로 불가능(doesn't scale)합니다.

결론적으로, 위 방법 중 어느 것도 "모든(ALL) 입력에 대해 이 코드는 올바르다"라고 단언할 수 없습니다.

### ### 해결책: 형식 검증 (Formal Verification)
발표자는 이 문제의 해결책으로 형식 검증을 제시합니다. 형식 검증은 코드가 **모든 가능한 입력**에 대해 올바르게 동작한다는 것을 **수학적으로 증명**하는 기술입니다.

그 과정은 다음과 같습니다.
1.  개발자는 '올바름'이 무엇을 의미하는지 명세(specification, spec)로 작성합니다.
2.  형식 검증 도구가 코드가 이 명세를 만족하는지 증명합니다.
3.  증명이 성공하면, 코드는 모든 가능한 입력에 대해 명세를 만족함이 보장됩니다.

### ### 형식 검증의 활용법: 명세 기반 개발 (Spec-Driven Development)
형식 검증을 실제 개발 과정에 적용하는 방법으로 '명세 기반 개발' 워크플로우를 제안합니다.

1.  **명세(SPEC) 작성:** '올바름'이 무엇인지 정의합니다. Lean과 같은 형식 언어로 직접 작성하거나, 자연어로 의도를 기술하고 AI가 이를 형식적인 명세로 자동 변환(autoformalize)하게 할 수 있습니다.
2.  **명세 검증(Validate the spec):** 이 단계가 매우 중요합니다. 명세 자체가 살아있는 핵심 산출물이므로, 인간이 직접 리뷰하거나 일부 입력값으로 테스트하여 명세가 의도한 바를 정확히 담고 있는지 확인해야 합니다.
3.  **AI 코딩 에이전트의 구현:** 검증된 명세를 바탕으로 AI 에이전트가 코드를 구현합니다.
4.  **증명(PROVE):** 형식 검증 도구를 사용해 AI가 구현한 코드가 명세와 일치함을 증명합니다.

이 워크플로우는 **"인간은 명세를 소유하고, 기계는 코드와 증명을 소유한다 (Humans own the spec. Machines own the code and proof.)"**는 역할 분담으로 요약할 수 있습니다.

### ### 증명 보조기 'Lean' 소개
Lean은 프로그래밍 언어이자 증명 보조기(proof assistant)입니다. 주요 특징은 다음과 같습니다.
*   **통합된 언어:** 코드(정의)와 증명을 같은 언어로 작성하므로 별도의 변환 계층이 필요 없습니다.
*   **확장성:** Lean 자체가 Lean으로 구현되어 있어 확장성이 매우 뛰어납니다.
*   **작고 신뢰할 수 있는 커널:** Lean의 핵심에는 작고 신뢰할 수 있는 커널(small trusted kernel)이 있습니다. 이를 통해 생성된 증명은 외부로 내보내져 독립적으로 검증될 수 있습니다.

발표자는 Lean으로 작성된 리스트 뒤집기(`reverse`) 함수와, `reverse(A ++ B) = reverse(B) ++ reverse(A)`라는 속성을 증명하는 `theorem` 코드를 예시로 보여줍니다. 이 증명은 모든 가능한 리스트 A, B에 대해 성립합니다.

### ### Lean 증명 과정의 비유: 체스
Lean의 증명 과정을 체스 게임에 비유하여 설명합니다.
*   **목표:** 체스에서 상대방을 체크메이트 시키는 것이 목표이듯, Lean에서는 증명하고자 하는 정리(theorem)를 증명하는 것이 목표입니다.
*   **전술(Tactics):** 체스에서 말을 움직이는 행위는 Lean에서 '전술(tactic)'을 적용하는 것과 같습니다.
*   **과정:** 증명은 체스판처럼 상호작용적인 환경에서 이루어집니다. 다양한 전술을 시도하고, 막히면 다른 경로를 탐색(backtrack)하며 증명 트리를 탐색합니다. LLM은 이 과정에서 최적의 전술을 찾는 역할을 할 수 있습니다.
*   **검증:** 최종적으로 증명이 완료되면, 신뢰할 수 있는 작은 '커널'이 전체 증명 과정이 유효한지 검증합니다. 마치 체스 심판이 게임 규칙을 확인하는 것과 같습니다.

### ### 적용 사례
1.  **C 라이브러리를 Lean으로 변환:** AI를 사용하여 널리 쓰이는 C 압축 라이브러리인 `zlib`을 Lean 코드로 변환하고, "압축 후 해제하면 원본 데이터가 나온다"는 핵심 속성을 Lean으로 증명한 실제 오픈소스 사례를 소개합니다. 이 과정에서 약 1,100개의 정리와 32,000줄의 증명 코드가 생성되었습니다.
2.  **Rust 코드와 Lean 명세 (Cedar):** AWS의 오픈소스 권한 정책 언어인 Cedar는 프로덕션 코드는 Rust로, 동작에 대한 형식 명세(모델)는 Lean으로 작성되었습니다. 매일 밤 약 1억 건의 무작위 차등 테스팅(differential random testing)을 통해 Rust 구현과 Lean 모델의 동작이 일치하는지 검증합니다. 이 검증을 통과하지 못하면 새로운 버전을 릴리스하지 않는 '릴리스 게이트'로 활용됩니다.
3.  **다양한 Rust 검증 도구 (Verus, Aeneas):**
    *   **Verus:** Rust 코드 내에 `requires` (사전조건), `ensures` (사후조건) 같은 어노테이션으로 명세를 직접 추가하여 Z3 같은 SMT 솔버로 검증하는 도구입니다. 이 명세는 런타임에는 제거되는 '유령 코드(ghost code)'입니다.
    *   **Aeneas:** Rust 코드를 중간 표현(IR)으로 변환한 뒤, 이를 다시 Lean 코드로 변환하여 Lean의 증명 기능을 활용하는 도구입니다.

### ### 미래 비전: 모든 언어를 위한 검증 프레임워크 'Strata'
궁극적으로 어떤 프로그래밍 언어든 검증할 수 있는 프레임워크를 목표로, AWS에서 개발 중인 오픈소스 프로젝트 **Strata**를 소개합니다. Strata는 컴파일러와 유사한 구조를 가집니다.
*   다양한 언어(Python, Java, Rust 등)를 입력받는 프론트엔드.
*   각 언어를 공통의 중간 표현(IR)으로 변환하는 '다이얼렉트(Dialect)'.
*   이 중간 표현을 SMT 솔버, 모델 체커, Lean 증명 등 다양한 분석 엔진(백엔드)으로 보내 검증을 수행합니다.

### ### 결론 및 시작하기
발표자는 청중에게 지금 바로 형식 검증을 시작해볼 것을 권합니다.
1.  자신의 코드베이스에서 가장 중요한(critical) 코드를 선택합니다.
2.  그 코드의 '올바른' 동작이 무엇인지 명세로 작성합니다.
3.  코딩 에이전트가 이를 구현하고, 형식 검증 도구로 증명하게 합니다.

이를 통해 우리는 '아마도 올바른(probably correct)' 소프트웨어가 아닌, '증명 가능하게 올바른(provably correct)' 소프트웨어의 시대로 나아갈 수 있다고 강조하며 발표를 마칩니다.

## 구체 수치·데모·아키텍처
*   **도구 및 언어:**
    *   **형식 검증 도구:** Z3, CVC5, Dafny
    *   **증명 보조기:** Lean (Lean Theorem Prover)
    *   **Rust 검증 도구:** Verus (Z3 솔버 사용), Aeneas (Lean으로 변환)
    *   **권한 정책 언어:** Cedar (AWS)
    *   **통합 검증 프레임워크 (WIP):** Strata (AWS)
*   **수치:**
    *   **zlib 변환:** 약 1,100개의 정리(theorems)와 32,000줄의 증명(proof) 코드 생성.
    *   **Cedar 차등 테스팅:** 매일 밤 약 1억(100M) 건의 무작위 테스트 실행.
*   **아키텍처 다이어그램:**
    *   **Lean 증명 과정:** LLM이 전술(tactic) 트리를 탐색하고, 목표(Goal)가 증명되면 커널(Kernel)이 확인하는 흐름도.
    *   **Cedar 모델 vs. 프로덕션:** 무작위 입력 생성기가 Lean 모델과 Rust 프로덕션 코드에 동일한 입력을 제공하고, 두 결과가 일치하는지 비교하는 차등 테스팅 아키텍처.
    *   **Strata 프레임워크:** 다양한 프론트엔드 언어 → Strata 다이얼렉트 → 공통 중간 표현(Core) → 다양한 분석 엔진(SMT 솔버, 모델 체커, Lean 증명)으로 이어지는 컴파일러 형태의 아키텍처.
*   **코드 조각:**
    *   **Lean:** 리스트를 뒤집는 `reverse` 함수와 `theorem reverse_append` 증명 코드.
    *   **Rust (Verus):** `requires`와 `ensures` 키워드를 사용하여 사전/사후 조건을 명시한 `vec_update_at_idx` 함수.

## 핵심 인용
*   "Humans own the spec. Machines own the code and proof." (인간은 명세를 소유하고, 기계는 코드와 증명을 소유한다.)
*   "Tactics do the work, kernel checks." (전술이 작업을 수행하고, 커널이 이를 검증한다.)
*   "...software and systems that are not probably correct, but provably correct." (아마도 올바른 소프트웨어가 아닌, 증명 가능하게 올바른 소프트웨어와 시스템.)

## 한 줄 결론
AI가 생성한 코드의 신뢰성을 확보하기 위해, 형식 검증과 Lean 같은 증명 보조기를 활용하여 모든 경우에 대해 수학적으로 올바름이 증명된 소프트웨어를 구축하는 시대로 나아가야 한다.
