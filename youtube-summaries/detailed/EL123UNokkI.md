# Building uReview, Uber's Multi-Agent Code Review Engine — Will Bond & Ameya Ketkar, Uber

🔗 https://www.youtube.com/watch?v=EL123UNokkI

## 개요
- **발표자:** 윌 본드(Will Bond), 아메야 케트카르(Ameya Ketkar) / 우버(Uber)
- **주제:** 우버가 개발한 멀티 에이전트 코드 리뷰 엔진 'uReview'를 통해 어떻게 대규모 엔지니어링 조직의 코드 리뷰 병목 현상을 해결하고, 개발자 생산성을 향상시키고 있는지 상세히 소개합니다.

## 발표 흐름

### 도입: 우버의 코드 리뷰 문제
발표는 우버의 소프트웨어 엔지니어링 규모를 설명하며 시작합니다. 수천 명의 엔지니어, 수백 개의 팀, 12개의 글로벌 오피스, 6개의 언어별 모노레포(monorepo)를 운영하고 있습니다. 이 규모에서 코드 리뷰는 개발 속도의 주요 병목 지점이 되었습니다.

특히 '첫 리뷰까지 걸리는 시간(Time to First Review)'이라는 핵심 지표가 악화되었습니다. 2024년에는 3시간 이내였던 이 시간이 2026년(발표 시점)에는 9시간으로 3배나 증가했습니다. 이는 AI 기반 코드 생성 도구의 보급으로 풀 리퀘스트(PR)의 양과 크기가 급증했기 때문입니다. 결국, 인간 리뷰어의 처리 용량이 한계에 다다랐고, 자동화된 코드 리뷰 시스템의 필요성이 대두되었습니다.

### 왜 자체 개발했나? uReview의 6가지 요구사항
시중에도 여러 코드 리뷰 자동화 도구가 있지만, 우버는 다음과 같은 특수한 요구사항 때문에 자체 시스템인 'uReview'를 구축하기로 결정했습니다.

1.  **Phabricator 지원:** 우버는 오랫동안 Phabricator를 코드 리뷰 도구로 사용해왔고, 점진적으로 GitHub로 마이그레이션 중이었습니다. 대부분의 상용 도구는 Phabricator를 지원하지 않아 두 플랫폼을 모두 지원하는 시스템이 필요했습니다.
2.  **이너 루프(Inner-Loop) 워크플로우:** 개발자가 로컬 환경에서 코드를 작성하는 '이너 루프' 단계에서도 일관된 코드 리뷰 경험을 제공해야 했습니다. 이는 인간 개발자뿐만 아니라 코드를 생성하는 AI 에이전트에게도 동일하게 적용되어야 했습니다.
3.  **팀 소유권(Team Ownership):** 수백 개 팀의 리뷰 규칙을 중앙에서 관리하는 것은 불가능합니다. 각 팀이 자신들의 코드베이스에 맞는 리뷰 규칙과 커스터마이제이션을 직접 소유하고 관리할 수 있는 분산된 구조가 필요했습니다.
4.  **내부 컨텍스트(Internal Context):** 우버 내부의 방대한 도메인 지식과 내부 시스템 시그널을 리뷰에 활용해야 했습니다.
5.  **튜닝(Tuning):** 모든 코드 변경에 동일한 리뷰를 적용하는 것은 비효율적입니다. 코드 변경의 리스크 프로파일, 복잡도 등을 고려하여 리뷰의 강도와 종류를 동적으로 조절(튜닝)할 수 있어야 했습니다.
6.  **일관성(Consistency):** 보안, 규정 준수와 같은 전사적인 규칙은 모든 코드에 일관되게 적용되어야 했습니다. 팀의 자율에만 맡길 수 없는 부분이었습니다.

### uReview 시스템 아키텍처
uReview는 여러 컴포넌트로 구성된 복합적인 시스템입니다.

-   **입력 소스:** GitHub, Phabricator, 그리고 AI 에이전트가 코드를 작성하는 '에이전트 루프(Agent Loop)'에서 리뷰 요청을 받습니다.
-   **uReview 서비스 (중앙 허브):**
    -   **디스패치(Dispatch):** 리뷰 요청과 사용자 피드백을 받아 적절한 생성기(Generator)로 라우팅합니다.
    -   **생성기(Generators):** 다양한 종류의 리뷰를 생성합니다.
        -   **일반(General):** 단일 파일에 대한 일반적인 로직 검사.
        -   **AI 린터(AI Linters):** 팀별로 정의된 간단한 규칙 기반의 린팅.
        -   **심층 리뷰(Deep Reviews):** 여러 파일에 걸친 복잡한 리뷰를 수행하는 에이전트.
        -   **커스텀 에이전트(Custom Agents):** 특정 도메인에 특화된 맞춤형 에이전트.
    -   **평가 데이터셋(Eval Dataset):** 사용자의 반응(이모지), 댓글, 감성 분석 결과 등 모든 피드백을 저장하여 시스템 개선에 활용합니다.
-   **후처리(Post-Process):** 여러 생성기에서 나온 리뷰 결과들을 취합하여 평가(Rate), 분류(Categorize), 중복 제거(Deduplicate) 등의 과정을 거쳐 개발자에게 가장 유용하고 신뢰도 높은 코멘트만 전달합니다.

### 포커스 1: 관찰 가능성(Observability)과 평가 기반 진화
uReview는 처음부터 복잡한 시스템이 아니었습니다. 초기에는 단일 프롬프트와 에이전트로 구성된 단순한 구조였습니다. 시스템을 진화시킨 핵심은 '관찰 가능성'과 '평가'였습니다.

-   **초기 단계:** 비용 대비 품질(Cost vs. Quality) 그래프에서 결과가 무작위로 흩어져 있었습니다.
-   **1단계 (사용자 피드백):** 리뷰 코멘트에 대한 개발자의 반응(sentiment)을 수집하고 분석하기 시작했습니다. 이를 통해 어떤 리뷰가 유용하고 어떤 것이 그렇지 않은지 파악하여 시스템을 개선했고, 비용 대비 품질 그래프에서 결과가 '저비용-고품질' 영역으로 모이기 시작했습니다.
-   **2단계 (런타임 프로파일링):** 더 깊은 관찰을 위해 두 가지 지표를 추가했습니다.
    -   **수용률(Addressal Rate):** AI가 제안한 코멘트를 개발자가 실제로 얼마나 반영하는지 측정.
    -   **에이전트 궤적(Agent Trajectory):** 에이전트가 리뷰를 생성하기까지의 생각 과정, 호출한 도구 등을 추적.

이러한 상세한 데이터는 모델이 왜 잘못된 리뷰를 생성하는지 근본적으로 이해하고 시스템을 정교하게 튜닝하는 데 결정적인 역할을 했습니다. 여기서 얻은 교훈은 "모델은 자신이 틀렸다는 것을 모른다"는 것입니다. 따라서 에이전트가 올바른 방향으로 작동하도록 명확한 가이드와 가드레일을 제공하는 것이 매우 중요합니다.

### 포커스 2: 팀 커스터마이제이션
수백 개 팀의 다양한 요구를 충족시키기 위해 '리뷰 스택(The Review Stack)'이라는 개념을 도입했습니다.

-   **제네릭 스택 (Generic):**
    -   **범용 리뷰:** 단일 파일에 대한 기본적인 로직 버그 검사.
    -   **심층 리뷰:** 여러 파일에 걸친 언어별 특화 리뷰.
-   **커스텀 스택 (Customized):**
    -   **AI 린터:** 팀이 퓨샷(few-shot) 방식으로 쉽게 정의할 수 있는 간단한 규칙.
    -   **커스텀 에이전트:** RAG, 내부 지식 베이스, 특정 스킬을 활용해 복잡한 도메인 특화 리뷰를 수행하는 에이전트.

이러한 커스터마이제이션을 구현하기 위해, 팀별 설정 파일을 코드와 함께 관리하고(Ownership), 코드 소유권과 리스크 프로파일에 따라 리뷰 요청을 적절한 생성기로 보내는 지능적인 라우팅(Dispatch) 시스템을 구축했습니다. 또한, 각 팀이 자신들의 커스텀 규칙의 성능을 직접 확인하고 개선할 수 있도록 상세한 관찰 가능성(Observability) 데이터를 대시보드 형태로 제공했습니다.

### 포커스 3: 이너 루프 vs. 아우터 루프
uReview는 개발 워크플로우의 두 가지 다른 단계, 즉 '이너 루프'와 '아우터 루프'에 맞춰 다르게 작동합니다.

-   **이너 루프 (Inner Loop):** AI 에이전트가 코드를 생성하고 스스로 리뷰하는 단계.
    -   **특징:** 빠른 API 응답, 높은 정확도(Precision)가 중요. 잘못된 피드백으로 에이전트가 무한 루프에 빠지는 '캐비테이션(cavitation)'을 방지해야 함.
-   **아우터 루프 (Outer Loop):** 인간 개발자가 PR을 생성하고 리뷰를 받는 단계.
    -   **특징:** 네이티브 UI(GitHub/Phabricator 봇)를 통해 제공. 높은 재현율(Recall)이 중요. 개발자가 놓칠 수 있는 문제를 최대한 많이 찾아주는 것이 목표.

### 결론: 아우터 루프의 확장
AI 에이전트가 코드 작성과 리뷰의 많은 부분을 자동화함에 따라 "인간의 코드 리뷰(아우터 루프)가 사라질 것인가?"라는 질문이 제기됩니다. 우버의 비전은 '아우터 루프를 죽이는 것(Kill the Outer Loop)'이 아니라, '아우터 루프를 확장하는 것(Expand the Outer Loop)'입니다.

즉, 인간 엔지니어의 역할이 저수준의 코드 스타일이나 자잘한 버그를 찾는 것에서 벗어나, 더 높은 차원의 문제에 집중하도록 진화할 것이라는 의미입니다. AI가 구현의 세부사항을 처리하는 동안, 인간은 **아키텍처(Architecture), 도메인(Domain), 제품(Product)**에 대한 깊은 고민과 의사결정에 더 많은 시간을 쏟게 될 것입니다.

## 구체 수치·데모·아키텍처

-   **우버 엔지니어링 규모:** 수천 명의 엔지니어, 수백 개의 팀, 12개 사이트, 6개 언어별 모노레포.
-   **'첫 리뷰까지 걸리는 시간' 지표:** 2024년 3시간 → 2026년 9시간으로 3배 증가.
-   **uReview 처리량:** 주당 약 25,000개의 코멘트 생성.
-   **사용자 피드백 비율:** 생성된 코멘트의 10% (2,500개)에 대해 사용자가 피드백을 남김.
-   **부정적 피드백 비율:** 전체 PR 중 4%만이 부정적인 피드백을 받음.
-   **수용률(Addressal Rate):** 전체 코멘트의 67%가 개발자에 의해 수용됨. 심각도 높은(High-severity) 코멘트의 경우 74%가 수용됨.
-   **성능 향상:** 단순한 구현 대비 비용은 60% 이상 절감하고, 정확도는 70% 이상 향상됨.
-   **uReview 아키텍처:** (발표 흐름 섹션에 상세히 기술됨) GitHub/Phabricator/Agent Loop → Dispatch → Generators (General, Deep, AI Linters, Custom Agents) → Post-Process → Output. 전체 과정에서 Eval Dataset과 Feedback Loop가 시스템을 지속적으로 개선.
-   **리뷰 스택:** 제네릭(범용, 심층 리뷰)과 커스텀(AI 린터, 커스텀 에이전트)으로 구성된 계층적 리뷰 구조.

## 한 줄 결론
우버는 uReview라는 자체 AI 코드 리뷰 엔진을 통해 대규모 조직의 개발 병목을 해결하고 있으며, 이는 단순 자동화를 넘어 관찰 가능성과 팀별 커스터마이제이션을 통해 인간 엔지니어의 역할을 저수준의 코드 검토에서 고수준의 아키텍처 및 제품 설계로 확장시키는 방향으로 진화하고 있다.
