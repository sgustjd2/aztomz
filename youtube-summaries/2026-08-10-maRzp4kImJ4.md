# Taking Reinforcement Learning Cross Datacenter — Nan Jiang, Modal

🔗 https://youtu.be/maRzp4kImJ4 · 📅 2026-08-10 · 🎙 AI Engineer

## 한 줄 요약
본 발표는 강화 학습(RL)의 롤아웃(rollout) 단계를 훈련 클러스터에서 분리하여 전 세계에 분산된 GPU 자원을 활용함으로써, RL 훈련의 확장성과 효율성을 크게 향상시키는 '스파스 델타(sparse delta)' 프로토콜과 '스티치(stitch)' 구현을 제안합니다.

## 발표자·소속
Nan Jiang, Modal

## 핵심 주장
- **RL 롤아웃 단계의 분리 가능성:** RL 훈련 루프에서 백프로파게이션(backpropagation)은 긴밀하게 연결된 클러스터가 필요하지만, 롤아웃 단계는 본질적으로 병렬적이며 독립적인 궤적을 생성하므로 훈련 클러스터에서 분리하여 전 세계에 분산된 컴퓨팅 자원을 활용할 수 있습니다.
- **가중치 업데이트의 희소성(Sparsity):** BF16과 같은 낮은 정밀도 형식으로 가중치를 서비스할 때, Adam 옵티마이저의 작은 업데이트 단계와 유한한 정밀도(finite precision)로 인해 대부분의 가중치(99% 이상)는 BF16 가시성 경계(visible boundary)를 넘지 않아 실제 변경되는 가중치는 매우 희소합니다.
- **델타 기반 가중치 동기화 프로토콜:** 전체 체크포인트를 전송하는 대신, 변경된 가중치 부분(패치)만 전송하는 델타 기반 프로토콜을 사용하면 전송량을 500GB에서 500MB로 획기적으로 줄여 클러스터 간 가중치 동기화 시간을 분-시간 단위에서 초 단위로 단축할 수 있습니다.
- **탄력적인 RL 훈련 인프라 구축:** 이러한 분리 및 희소 델타 프로토콜을 통해 유휴 GPU 자원을 RL 롤아웃에 활용할 수 있게 되어, 추론(inference) 용량이 곧 RL 용량이 되는 탄력적이고 확장 가능한 RL 훈련 인프라를 구축할 수 있습니다.

## 세부 내용

발표는 강화 학습(RL) 훈련의 확장성 문제를 다루며 시작됩니다. 현재 RL 훈련은 GPU 용량, 동일 지역, 빠른 패브릭, 즉시 사용 가능성이라는 네 가지 조건을 동시에 충족하는 단일 클러스터에 의존하는 경향이 있습니다. 특히 RDMA(Remote Direct Memory Access)와 같은 빠른 상호 연결이 필요한 훈련 단계는 단일 클러스터에 묶여 있으며, 이는 RL 훈련의 확장성을 제한합니다.

발표자는 RL 훈련 루프를 두 부분으로 나눕니다:
1.  **트레이너(Trainer):** 정책을 업데이트하고 백프로파게이션을 수행하는 부분. 이는 긴밀하게 연결된 GPU 클러스터(카테드랄)가 필요합니다.
2.  **롤아웃(Rollout) 또는 샘플러(Sampler):** 정책을 사용하여 궤적을 생성하고 환경과 상호작용하여 보상과 관찰을 수집하는 부분. 롤아웃은 본질적으로 병렬적이며, 각 롤아웃 워커는 독립적인 궤적을 생성하므로 서로 간의 동기화가 필요 없습니다.

핵심 아이디어는 롤아웃 단계를 훈련 클러스터에서 분리하여 전 세계에 분산된 컴퓨팅 자원(스프롤)을 활용하는 것입니다. 롤아웃은 훈련 클러스터(트레이너)와 동일한 지역이나 빠른 패브릭에 있을 필요가 없습니다. 롤아웃은 단지 최신 정책 가중치(fresh weights)를 받고 궤적과 메타데이터를 트레이너에게 다시 보내기만 하면 됩니다.

이러한 분리 아키텍처에서 가장 중요한 문제는 **가중치 동기화(weight sync)**입니다. 트레이너가 정책을 업데이트할 때마다 롤아웃 엔진은 새로운 가중치 버전을 받아야 합니다. 전통적인 방식대로 전체 체크포인트(수백 GB)를 전송하면 네트워크 지연으로 인해 몇 분에서 몇 시간이 걸릴 수 있습니다.

발표자는 이 문제를 해결하기 위해 **가중치 업데이트의 희소성**에 주목합니다.
-   **BF16 정밀도:** 롤아웃 엔진이 BF16과 같은 낮은 정밀도로 가중치를 서비스할 때, 유한한 정밀도로 인해 가중치 값 사이에는 '바닥(floor)'이 존재합니다. 즉, 가중치 업데이트가 이 바닥을 넘어서지 않으면 BF16으로 표현된 가중치 값은 변경되지 않습니다.
-   **Adam 옵티마이저의 작은 단계:** Adam 옵티마이저는 학습률(learning rate)에 비례하는 작은 업데이트 단계를 수행합니다. 이 '푸시(push)'가 BF16의 '바닥'보다 작으면, 가중치 값은 BF16 관점에서 변경되지 않고 '흡수(absorbed)'됩니다.
-   **실험 결과:** PULSE 논문 및 내부 실험에 따르면, 대부분의 가중치(99% 이상)는 각 훈련 단계에서 BF16 가시성 관점에서 변경되지 않습니다.

이러한 희소성을 활용하여, 발표자는 **델타 기반의 가중치 동기화 프로토콜**을 제안합니다.
-   **패치(Patch) 전송:** 전체 체크포인트 대신, 변경된 가중치의 위치(indices)와 새로운 값(replacement values)으로 구성된 '패치'만 전송합니다. 이는 선택적 덮어쓰기(selective overwrite) 또는 XOR 비트 연산을 통해 비트 단위로 정확하게 재구성될 수 있습니다.
-   **LoRA(Low-Rank Adaptation)와의 유사성:** LoRA와 같은 기법은 설계상(by construction) 어댑터 가중치가 작지만, 이 방식은 흡수(by absorption)를 통해 전체 파라미터 모델에서도 델타가 희소해지는 것을 보여줍니다.
-   **성능 향상:** 500GB의 전체 체크포인트 대신 500MB의 패치만 전송하면, 클러스터 간 전송 시간이 몇 시간에서 몇 초로 단축됩니다.

이러한 프로토콜을 구현한 것이 Modal의 **스티치(stitch)**입니다.
-   **프로토콜:** 트레이너는 업데이트된 가중치 버전을 '게시판(bulletin board)'에 게시합니다. 롤아웃 엔진은 이 게시판에서 최신 버전을 가져와 로컬에서 구체화(materialize)하고 서비스합니다.
-   **사이드카(Sidecar):** 롤아웃 엔진 옆에서 실행되는 사이드카는 엔진이 어떤 버전의 가중치를 서비스해야 하는지 관리하고, 필요한 경우 누락된 트랜지션(패치)을 적용하여 가중치를 업데이트합니다.
-   **탄력성:** 이 설계를 통해 유휴 GPU는 언제든지 롤아웃 엔진으로 활용될 수 있으며, 훈련 클러스터와 지리적으로 분리되어 있어도 효율적으로 작동합니다. 이는 추론 용량이 곧 RL 훈련 용량이 되는 것을 의미합니다.

발표자는 몇 가지 **오픈 문제**도 제시합니다.
-   MoE(Mixture of Experts) 모델에서도 이러한 희소성이 유지되는가?
-   완전 비동기(asynchronous) RL 훈련을 대규모로 구현할 수 있는가?
-   이러한 델타 압축 기법이 사전 훈련(pre-training), 중간 훈련(mid-training), SFT(Supervised Fine-Tuning)와 같은 RL 이외의 다른 훈련 단계에도 적용될 수 있는가?

## 인상적인 대목
-   "Backprop stays in the cluster. Rollout can leave." (백프로파게이션은 클러스터에 머물지만, 롤아웃은 떠날 수 있다.) - RL 훈련의 핵심 구성 요소를 분리하여 확장성을 확보하는 아이디어를 명확하게 전달하는 문장입니다.
-   "A weight is visible only if the push clears the floor." (가중치는 푸시가 바닥을 넘어서야만 가시적이다.) - 낮은 정밀도 가중치 업데이트의 희소성을 설명하는 핵심 원리입니다.

## 실무 적용 포인트
-   **RL 롤아웃 분산 처리:** RL 훈련의 롤아웃 단계를 지리적으로 분산된 저렴한 GPU 자원(예: 스팟 인스턴스)에 배포하여 훈련 비용을 절감하고 확장성을 확보할 수 있습니다.
-   **델타 기반 가중치 동기화 구현:** 대규모 모델의 경우, 전체 모델 체크포인트를 전송하는 대신 변경된 가중치 부분만 패치 형태로 전송하는 방식을 도입하여 클러스터 간 가중치 동기화 지연 시간을 최소화할 수 있습니다.
-   **낮은 정밀도 서비스 가중치 활용:** BF16, FP8, FP4와 같은 낮은 정밀도 형식으로 롤아웃 엔진의 가중치를 서비스함으로써, 가중치 업데이트의 희소성을 높여 전송량을 더욱 줄일 수 있습니다.
-   **사이드카 패턴 적용:** 롤아웃 엔진 옆에 사이드카를 두어 가중치 버전 관리 및 패치 적용을 담당하게 함으로써, 롤아웃 엔진 자체의 복잡성을 줄이고 다양한 백엔드 및 GPU 유형에 대한 유연성을 확보할 수 있습니다.
