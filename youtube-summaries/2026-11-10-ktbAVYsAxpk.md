# The Agents Were Fine. Everything Around Them Broke. - Joey Wang, Harvey

🔗 https://youtu.be/ktbAVYsAxpk · 📅 2026-11-10 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트 플랫폼인 Spectre를 구축하면서 에이전트 자체보다 에이전트가 작동하는 주변 환경(하네스)을 구축하고 관리하는 것이 더 중요하며 어려웠다는 경험을 공유한다.

## 발표자·소속
Joey Wang, Harvey 엔지니어링 리드

## 핵심 주장
- **에이전트 자체보다 하네스가 핵심 제품이다:** 에이전트가 코드를 작성하는 것은 시작에 불과하며, 내구성, 공유 가시성, 재시도, 비용 회계, 다중 공급자 지원, 협업 표면 등 에이전트 주변의 모든 인프라(하네스)가 제품의 핵심이 된다.
- **에이전트 인터페이스는 다양해야 한다:** 개발자들은 각자 선호하는 에이전트 인터페이스(Claude Code, Cursor, ChatGPT Dots 등)를 사용하므로, Spectre는 이 모든 인터페이스를 하부에서 지원하여 에이전트가 어떤 방식으로든 작업을 시작하고 완료할 수 있도록 한다.
- **에이전트가 모든 작업을 주도할 수 있어야 한다:** 사람이 클릭할 수 있는 모든 작업은 에이전트도 호출할 수 있도록 설계하여, 에이전트가 태스크 생성, PR 관리, 아티팩트 발행 등 다양한 작업을 CLI를 통해 직접 수행할 수 있게 한다.
- **확장성 문제를 해결하기 위한 인프라 개선이 필수적이다:** 에이전트의 작업량이 폭증했을 때, 모델의 성능이 아닌 Git 클론 시간, 노드 풀 한계, PR 병합 지연과 같은 인프라 문제가 병목 현상을 일으켰으며, 이를 해결하기 위한 시스템 개선이 중요했다.
- **자동화된 에이전트의 자율적인 작업 시작이 중요하다:** 사람이 직접 요청하는 작업 외에, 스케줄이나 이벤트에 따라 스스로 작업을 시작하는 자동화 에이전트가 빠르게 성장하고 있으며, 이들의 무분별한 작업 폭주를 막기 위한 가드레일(예: 5회 실패 시 자동 중단, 예산/만료일 설정)이 필요하다.

## 세부 내용

발표자는 지난달에 매분 한 개 이상의 에이전트 태스크가 플랫폼에서 시작되었다는 통계로 발표를 시작했다. 10,000개 이상의 에이전트 PR(Pull Request)이 생성된 후, 문제가 된 것은 에이전트 자체가 아니라 그 주변 환경이었다고 강조했다.

Spectre 플랫폼은 2026년 5월부터 10월까지 월별 태스크 수가 약 10,000개에서 45,000개로 4.5배 증가했다. 이 태스크들은 코드 작성 및 수정, 데이터 분석, 트리아지 및 모니터링, 심지어 마케팅을 위한 스토리보드 및 비디오 그래픽 제작과 같은 다양한 종류의 작업을 포함했다. 이는 에이전트가 단순히 코드를 넘어 다양한 업무에 활용되고 있음을 보여준다.

발표자는 "얇은 래퍼(Thin wrapper)는 내구성, 공유 가시성, 재시도 의미론, 비용 회계, 다중 공급자 지원, 협업 표면이 필요하기 전까지는 괜찮다. 그 시점에서 하네스가 제품이 된다"는 Harvey 블로그 글을 인용하며, 에이전트 모델 자체보다 그 주변의 하네스(Harness)가 중요함을 역설했다.

Spectre는 Claude Code, Codex, Cursor와 같은 기존 도구들을 대체하는 것이 아니라, 그 위에서 실행되는 플랫폼이다. Spectre는 비밀 관리, 실제 스택 검증, 트리거(알림, 스케줄, PR 이벤트), 단일 정책, 공정한 용량 할당 등의 기능을 제공하여 에이전트가 클라우드 환경에서 확장 가능하게 작동하도록 돕는다.

**세 가지 이야기:**

1.  **코드 작성 이후의 작업 관리:** 에이전트가 코드를 작성한 후에도 실제 작업은 계속된다. PR의 하루를 예로 들면, 새벽 2시에 슬랙에 알림이 발생하면 에이전트가 이를 감지하여 수정 코드를 작성하고, 실제 스택에 대한 증명을 PR에 게시한다. CI(Continuous Integration)가 실패하면 에이전트가 실패를 읽고 다른 수정 사항을 푸시한다. 아침이 되면 PR은 검토 대기열에 들어가고, 담당자가 승인하면 에이전트가 자동으로 병합한다. 10월에 병합된 에이전트 PR의 4개 중 1개는 이러한 후속 루프를 거쳤다. Spectre 프로젝트는 차터(사람이 작성), 메모리(에이전트가 작성), 스킬(팀이 고정), 아티팩트(재사용 가능한 페이지), 공유(역할별), 히스토리(누가 무엇을 실행했는지)를 포함하여 에이전트가 필요로 하는 모든 지식을 한곳에 모아 관리한다.
2.  **모든 에이전트가 작업을 주도할 수 있게 함:** "클릭할 수 있다면, 에이전트도 호출할 수 있다"는 규칙을 만들었다. CLI를 통해 에이전트가 태스크 생성, PR 자동 병합, 아티팩트 게시 등의 작업을 수행할 수 있게 했다. 10월에는 CLI를 통해 시작된 태스크가 약 6,500개에 달했으며, 웹 앱에서 시작된 태스크보다 더 많은 PR을 병합했다. 심지어 앱을 전혀 열지 않고 수백 개의 태스크를 시작하는 새로운 유형의 사용자도 나타났다. 이로 인해 에이전트가 작업을 구동하는 방식이 다양해졌지만, 동시에 새로운 문제가 발생했다. 가장 느린 단계는 모델의 사고가 아니라 Git이었다. 모든 레포를 체크아웃하는 데 평균 1분 이상이 걸렸고, 이를 해결하기 위해 각 노드에 레포의 베어 클론을 유지하고 태스크가 이를 빌려 쓰는 방식으로 5초 이내로 단축했다.
3.  **시스템이 고장 났을 때:** 8월 중순, 버그가 포함된 릴리스가 배포되면서 워크스페이스당 한 번씩 알림이 발생했고, 이 알림이 수백 개의 에이전트 태스크를 트리거했다. 약 900개의 에이전트가 동시에 동일한 버그를 추적하면서 노드 풀이 한계에 도달하여 시스템이 멈췄다. 2개월 후, 한 엔지니어가 명령줄에서 약 950개의 태스크를 3시간 만에 시작하면서 다시 클러스터가 가득 차고 다른 모든 작업이 대기열에 갇히는 문제가 발생했다. 이는 사용자 문제가 아닌 플랫폼 문제였다. 4일 후, "공정한 실행 대기열(Fair launch queue)"을 도입하여 이 문제를 해결했다. 대화형 작업이 우선순위를 갖고, 개인당 동시 태스크 수를 25개로 제한하며, 대기열의 위치를 시각적으로 보여주었다. 이 개선으로 300개 태스크 부하 테스트에서 태스크 목록 로딩 시간이 2초에서 70밀리초로 단축되었다. 이후 월별 태스크 수는 4.5배 증가했고, 94-97%의 태스크가 완료되었다. 그러나 병합(Merging)이 새로운 병목 현상이 되었다. PR 병합 시간이 15~30분에서 1시간 이상으로 늘어났고, 60% 더 많은 PR이 한 달 만에 생성되었다. 이 문제는 아직 해결 중이다.

**추가 사항:**
사람이 요청하는 작업 외에, 스케줄이나 이벤트에 따라 스스로 작업을 시작하는 자동화 에이전트가 빠르게 성장하고 있다. 10월에는 약 110명이 290개의 자동화를 실행하여 약 13,000개의 태스크를 시작했다. 이들은 알림 트리아지, PR 검토, 보고서 작성, 테스트 및 CI, 정리 작업 등을 수행했다. 에이전트가 무분별하게 작업을 시작하는 것을 막기 위해, 5회 연속 실패 시 자동 중단, 비용 예산, 만료일 설정 등의 가드레일을 도입했다.

**향후 과제:**
- 모든 슬랙 채널에 항상 로그인되어 대화를 추적하고 스스로 작업을 시작하는 에이전트를 두는 것.
- 모든 PR이 사람이 검토하기 전에 작동함을 증명하는 것.
- 에이전트가 끊임없이 PR을 생성할 때 어떻게 대량으로 병합할 것인가.

## 인상적인 대목
- "The thing that broke wasn't the agents. It was everything around them." (문제가 된 것은 에이전트가 아니었다. 그것은 에이전트 주변의 모든 것이었다.)
- "A thin wrapper is fine until you need durability, shared visibility, retry semantics, cost accounting, multi-provider support, and collaboration surfaces. At that point the harness becomes the product." (얇은 래퍼는 내구성, 공유 가시성, 재시도 의미론, 비용 회계, 다중 공급자 지원, 협업 표면이 필요하기 전까지는 괜찮다. 그 시점에서 하네스가 제품이 된다.)
- "If you can click it, an agent can call it." (클릭할 수 있다면, 에이전트도 호출할 수 있다.)
- "The slowest step wasn't the model. It was git." (가장 느린 단계는 모델이 아니었다. Git이었다.)
- "That's not a user problem. That's our problem." (그것은 사용자 문제가 아니다. 그것은 우리의 문제다.)
- "Engineers will write code with whichever agent they like. The lasting work is the harness that runs it, checks it and gets it merged." (엔지니어는 자신이 좋아하는 에이전트로 코드를 작성할 것이다. 지속적인 작업은 코드를 실행하고, 확인하고, 병합하는 하네스이다.)

## 실무 적용 포인트
- **에이전트 인프라(하네스)에 투자하라:** 에이전트 모델 자체의 성능 향상만큼이나, 에이전트가 안정적으로 작동하고 확장하며 협업할 수 있는 플랫폼과 도구를 구축하는 데 집중해야 한다.
- **다양한 에이전트 인터페이스를 통합하라:** 개발자들이 선호하는 다양한 에이전트 도구를 Spectre와 같은 하네스 아래에서 원활하게 사용할 수 있도록 통합된 백엔드 시스템을 제공해야 한다.
- **에이전트의 자율성을 높이고 CLI를 활용하라:** 에이전트가 사람의 개입 없이도 태스크를 시작하고, PR을 관리하며, 아티팩트를 발행할 수 있도록 CLI 기반의 자동화 기능을 적극적으로 개발하고 활용해야 한다.
- **확장성 병목 현상을 예측하고 해결하라:** 에이전트의 작업량이 증가할 때 Git 클론 시간, 노드 풀 용량, 코드 병합 프로세스 등 예상치 못한 인프라 문제가 발생할 수 있으므로, 초기부터 이러한 병목 현상을 식별하고 해결하기 위한 아키텍처적 개선을 고려해야 한다.
- **자동화 에이전트에 대한 가드레일을 설정하라:** 스케줄이나 이벤트에 따라 자율적으로 작동하는 에이전트의 경우, 무한 루프나 리소스 고갈을 방지하기 위해 실패 시 자동 중단, 예산 제한, 만료일 설정 등과 같은 안전장치를 반드시 마련해야 한다.
