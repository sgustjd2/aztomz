# SonarQube + OpenAI: Agentic Development — Killian Carlsen-Phelan, Sonar

🔗 https://youtu.be/bI8WyG9YB0I · 📅 2026-10-11 · 🎙 AI Engineer

## 한 줄 요약
SonarQube와 OpenAI를 활용한 에이전트 중심 개발(AC/DC) 방법론을 소개하며, AI 에이전트가 생성한 코드의 신뢰성, 일관성, 투명성을 보장하기 위한 가이드, 생성, 검증, 해결의 4단계 개발 주기를 강조합니다.

## 발표자·소속
킬리안 칼슨-펠런 (Killian Carlsen-Phelan), Sonar 개발 콘텐츠 엔지니어

## 핵심 주장
-   **"완료(Done)"의 정의**: 작업이 완료되었다는 것은 단순히 "수정됨"이라고 말하는 것이 아니라, 검토 가능한 변경 사항과 도구 증거를 포함한 명확한 증거가 있어야 합니다.
-   **격리는 정확성이 아니다**: 에이전트의 실행 환경(격리)은 에이전트가 수행하는 작업의 정확성을 보장하지 않으므로, 다층적인 제어와 검증이 필수적입니다.
-   **피드백 계약은 루프 안에 속한다**: 에이전트의 작업 흐름 내에서 피드백 계약(가이드라인, 규칙, 아키텍처 등)을 통합하여 에이전트가 관련 컨텍스트를 기반으로 작업을 수행하고, 즉각적인 검증을 통해 문제를 해결하도록 해야 합니다.

## 세부 내용
발표는 AI 엔지니어링 컨퍼런스의 소개와 스폰서 목록으로 시작됩니다. 첫 번째 발표자는 Codex의 배포 엔지니어링 팀 소속으로, 에이전트가 작업을 완료했다는 것의 의미와 신뢰 경계에 대한 질문을 던지며 세 가지 핵심 주장을 소개합니다.

첫 번째 주장은 **"완료(Done)"의 정의**입니다. 작업이 완료되었다는 것은 검토 가능한 차이점(diff)과 도구 증거를 포함해야 하며, 단순히 "수정됨"이라고 말하는 것을 넘어 사실을 뒷받침하는 증거를 제공해야 합니다. 저렴한 구현 방식은 병목 현상을 사양 및 검증으로 옮기는 경향이 있으며, 이는 바람직하지 않습니다. 에이전트의 일반적인 실패 모드는 불완전한 컨텍스트, 전역 불변성을 위반하는 로컬 수정, 또는 동일한 문제를 전파하는 생성된 테스트로 귀결됩니다. 자체 비판은 유용하지만 독립적인 오라클이 아니며, 에이전트와 검증자의 결과가 직교하는 경우가 많아 양쪽을 모두 봐야 합니다.

두 번째 주장은 **격리는 정확성이 아니다**입니다. 에이전트의 실행 계층(도구 접근 권한, 범위, 승인)과 아티팩트 계층(결과 평가, 테스트, 분석, 정책, 의도)을 구분해야 합니다. 샌드박스는 쓰기를 격리할 수 있지만 쿼리가 안전하다는 것을 증명할 수는 없습니다. 어떤 오라클도 증명이 될 수 없으므로, 여러 경계에 걸쳐 제어 계층을 두는 "심층 방어" 접근 방식이 필요합니다.

세 번째 주장은 **피드백 계약은 루프 안에 속한다**입니다. 에이전트의 작업 루프는 모델 액션, 실행, 변경 사항 관찰, 계획 업데이트의 예측 가능한 패턴을 따릅니다. 각 개별 작업에는 결과, 불변성, 정의된 범위, 승인 기준이 있습니다. 피드백 계약은 에이전트의 역량을 최대한 활용하기 위해 루프 내부에 있어야 합니다. 이는 기술(절차), MCP(구조화된 도구 및 컨텍스트), 훅(hook)을 통한 라이프사이클 검사(예: 하드코딩된 비밀 탐지)를 포함합니다. 궁극적으로 인간은 의도, 예외, 배포 결정을 소유하며, 완전한 CI/CD 및 인간 검토 프로세스가 핵심이 되어야 합니다.

두 번째 발표자인 Sonar의 킬리안 칼슨-펠런은 "SonarQube + OpenAI를 이용한 에이전트 중심 개발"이라는 주제로 발표를 이어갑니다. 그는 AI 에이전트가 생성한 코드의 안전성과 검증을 보장하는 방법을 다루며, Sonar의 에이전트 중심 개발 주기(AC/DC)를 소개합니다. 1,000명 이상의 개발자를 대상으로 한 설문조사에서 커밋된 코드의 42%가 AI에 의해 생성되거나 지원되었지만, 96%의 개발자는 이를 완전히 신뢰하지 않는다는 결과가 나왔습니다. 이는 코드 생성에서 코드 검증으로 병목 현상이 이동했음을 의미합니다.

AC/DC는 가이드(Guide), 생성(Generate), 검증(Verify), 해결(Solve)의 네 가지 주요 단계로 구성됩니다. Sonar는 가이드, 검증, 해결 단계를 담당합니다.
-   **가이드**: 에이전트에게 적절한 컨텍스트, 가이드라인, 규칙, 아키텍처를 주입하여 고품질의 출력을 보장합니다. 이는 토큰 비용을 줄이는 데도 도움이 됩니다.
-   **생성**: Codex와 같은 코드 생성 도구를 사용합니다.
-   **검증**: 생성된 코드에 보안, 코드 품질, 유지보수성 등의 문제가 없는지 확인합니다.
-   **해결**: 탐지된 문제를 신속하고 효율적으로 수정하여 반복적인 코딩 시스템을 만듭니다.

AC/DC는 내부 루프(에이전트가 계획을 달성하기 위해 반복적으로 가이드-검증-해결을 수행)와 외부 루프(에이전트가 작업을 완료한 후 더 포괄적인 검증을 수행)로 나뉩니다. 발표자는 데모를 통해 Sonar의 도구를 사용하여 이러한 개념을 시연합니다.

데모에서는 VS Code 환경에서 `apply-sonar.sh` 스크립트를 실행하여 SonarQube Cloud 프로젝트를 생성하고 초기 스캔을 수행합니다. 이 과정에서 하드코딩된 OpenAI API 키(블로커 심각도)와 SQL 인젝션 취약점(주요 심각도)이 발견됩니다. SonarQube 대시보드에서 보안 등급이 "E"로 표시되고, 발견된 문제들이 시각적으로 표시됩니다. 발표자는 SonarQube가 어떻게 데이터 흐름 분석과 오염 분석을 통해 SQL 인젝션 취약점을 탐지하는지 보여줍니다.

이후 발표자는 Codex에게 SQL 인젝션 취약점(S8702)을 수정하도록 요청합니다. Codex는 매개변수화된 쿼리를 사용하여 문제를 해결하고, SonarQube는 수정된 코드를 재분석하여 문제가 해결되었음을 확인합니다. 또한, SonarQube의 비밀 스캐닝 훅(Secret Scanning Hook)이 어떻게 LLM 컨텍스트로 비밀이 유출되는 것을 방지하고, 에이전트가 비밀이 포함된 파일을 읽는 것을 차단하는지 보여줍니다. 에이전트가 코드를 수정하거나 파일을 변경할 때마다 Agentic Analysis 훅이 즉시 실행되어 서버 측 분석을 수행하고 새로운 취약점이 도입되지 않았음을 자동으로 확인합니다.

발표자는 SonarQube의 CLI 도구가 에이전트 중심 개발 워크플로우를 어떻게 지원하는지 강조하며, SonarQube Cloud, Server, Enterprise 및 무료 등급에서 이러한 기능에 접근할 수 있다고 언급합니다.

-   "Time is money at enterprises, and your engineers save a lot of money on therapy bills as well." (기업에서 시간은 돈이며, 엔지니어들은 치료비도 많이 절약할 수 있습니다.)

## 실무 적용 포인트
-   **명확한 "완료" 기준 설정**: AI 에이전트가 작업을 완료했다고 판단할 때, 단순히 "수정됨"이라는 메시지 대신 검토 가능한 코드 변경 사항(diff)과 관련 도구의 증거를 요구하여 작업의 실제 완료 여부를 명확히 해야 합니다.
-   **다층적 보안 및 검증 도입**: AI 에이전트의 실행 환경(샌드박스)만으로는 코드의 정확성과 안전성을 보장할 수 없으므로, 코드 생성 전 컨텍스트 가이드라인 주입, 생성 후 정적/동적 분석, 런타임 검증 등 여러 계층의 보안 및 검증 도구를 통합해야 합니다.
-   **개발 루프 내 피드백 계약 통합**: SonarQube의 Agentic Analysis 훅과 같은 도구를 활용하여 에이전트가 코드를 수정할 때마다 즉시 서버 측 분석을 실행하고, 새로운 취약점이 도입되지 않았는지 자동으로 확인하는 시스템을 구축하여 개발 시간을 단축하고 엔지니어의 피로도를 줄일 수 있습니다.
-   **비밀 관리 강화**: 하드코딩된 API 키와 같은 비밀 정보가 LLM 컨텍스트나 코드베이스에 유출되지 않도록 비밀 스캐닝 훅을 사용하여 프롬프트 단계에서부터 비밀을 탐지하고 차단하는 것이 중요합니다.
