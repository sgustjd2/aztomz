# Is Speculative Decoding Worth It? Profiling vLLM on NVIDIA Blackwell — Akamai

🔗 https://youtu.be/XTpyNrEgJQ4 · 📅 2026-10-06 · 🎙 AI Engineer

## 한 줄 요약
추론 속도 향상을 위한 투기적 디코딩(Speculative Decoding)은 추가 GPU 자원과 교환하여 디코딩 지연 시간을 줄이는 최적화 기법으로, 그 가치는 워크로드 유형과 GPU 활용도에 따라 달라지므로 실제 트래픽에 대한 측정이 필수적입니다.

## 발표자·소속
Sheila Kiarie, Senior Developer Advocate, Akamai

## 핵심 주장
-   **투기적 디코딩의 기본 원리:** 대규모 언어 모델(LLM)의 느린 토큰 생성(디코딩) 속도를 개선하기 위해, 작은 드래프트 모델이 여러 토큰을 예측하고 대규모 타겟 모델이 이를 한 번에 검증하여 효율성을 높입니다.
-   **성능 향상과 비용:** 투기적 디코딩은 디코딩 지연 시간을 크게 줄여 처리량을 향상시키지만, 두 개의 모델(타겟 및 드래프트)을 호스팅하고 추가 KV 캐시를 관리하기 위한 추가 GPU 메모리 및 자원이 필요합니다.
-   **워크로드에 따른 효과:** JSON 생성, 코드 작성, 정보 추출(RAG)과 같이 구조화되고 예측 가능한 출력에는 높은 토큰 수용률로 인해 투기적 디코딩이 매우 효과적입니다. 반면, 시나리오 작성이나 브레인스토밍과 같은 창의적인 작업에는 수용률이 낮아 효과가 제한적입니다.
-   **컨텍스트 길이와 동시성 고려:** 프롬프트 길이가 길어 모델이 컨텍스트를 처리하는 데 많은 시간을 할애하는 경우(Prefill), 디코딩 속도 개선 효과가 전체 지연 시간에 미치는 영향은 줄어듭니다. 또한, 높은 동시성 환경에서는 추가 드래프트 모델의 오버헤드가 속도 향상을 상쇄할 수 있으므로 주의해야 합니다.

## 세부 내용

발표는 LLM 추론이 느린 이유를 설명하는 것으로 시작됩니다. LLM은 일반적으로 두 가지 단계로 작동합니다. 첫 번째는 '프리필(Prefill)' 단계로, 모델이 프롬프트를 완전히 읽고 입력 토큰을 처리하여 KV 캐시(모델의 작업 메모리)를 구축합니다. 이 단계는 요청당 한 번 발생합니다. 두 번째는 '디코딩(Decode)' 단계로, 모델이 답변을 작성하기 시작하며, 각 토큰이 이전 토큰에 의존하기 때문에 일반적으로 한 번에 하나씩 순차적으로 발생합니다. 예를 들어 500개의 토큰을 생성하려면 모델이 500번의 순방향 패스를 수행해야 하므로 사용자 체감 지연 시간이 길어집니다.

이러한 지연 문제를 해결하기 위해 '투기적 디코딩(Speculative Decoding)'이 제안됩니다. 이 기법은 대규모 타겟 모델이 모든 토큰을 직접 생성하는 대신, 더 작은 드래프트 모델이 몇 개의 토큰(일반적으로 3~5개)을 즉시 예측(추측)하도록 합니다. 그런 다음 타겟 모델은 이 예측된 토큰들을 한 번의 순방향 패스로 병렬적으로 검증합니다. 예측이 정확하면 여러 토큰이 한 번의 비용으로 효과적으로 생성된 것이며, 예측이 틀리면 타겟 모델이 해당 토큰부터 다시 생성합니다. 이 과정은 타겟 모델이 최종 권한을 가지므로 출력 품질은 동일하게 유지됩니다.

하지만 투기적 디코딩은 "공짜가 아니다"라고 발표자는 강조합니다. 주요 트레이드오프는 다음과 같습니다.
1.  **두 번째 모델:** 드래프트 모델을 호스팅하기 위한 추가 GPU 자원이 필요합니다. (작은 모델이므로 가중치 메모리 요구 사항은 크지 않음)
2.  **추가 GPU 메모리:** 드래프트 모델의 가중치와 활성화에 필요한 추가 GPU 메모리가 할당되어야 합니다.
3.  **두 번째 KV 캐시:** 타겟 모델과 드래프트 모델 간에 KV 캐시를 분할해야 하므로 메모리 관리가 복잡해집니다.
결론적으로 투기적 디코딩은 낮은 디코딩 지연 시간을 위해 추가 GPU 자원을 사용하는 것입니다.

드래프트 모델 선택 시 고려 사항은 '비용 대 수용률(Cost vs. Acceptance)'입니다. 드래프트 모델은 타겟 모델보다 훨씬 작고(10~50배) 빨라야 하며, 높은 수용률(타겟 모델이 드래프트 모델의 예측을 수용하는 비율)을 보여야 합니다. 발표자의 데모 환경에서는 Llama 3 70B 모델을 타겟으로, Llama 3 1.5B 모델을 드래프트로 사용했습니다. NVIDIA RTX 6000 Blackwell GPU(96GB VRAM)에서 70B 모델은 70GB, 1.5B 모델은 2.5GB의 가중치 메모리를 사용했습니다.

라이브 데모에서는 두 가지 워크로드 유형에 따른 성능을 비교했습니다.
1.  **구조화된 출력(JSON):** API 요청 태그 배열을 생성하는 작업.
    *   기존(Baseline) 엔진: 총 요청 시간 6.39초, 출력 토큰/초 60.1, 토큰당 시간 16.6ms.
    *   투기적 가속(Speculative Accelerated) 엔진: 총 요청 시간 3.78초, 출력 토큰/초 101.7, 토큰당 시간 9.7ms.
    *   결과: 투기적 디코딩이 1.69배 빨랐으며, 드래프트 모델의 토큰 수용률은 82%였습니다.
2.  **개방형 창의적 생성(단편 소설):** 엔지니어에 대한 짧은 미스터리 스토리를 작성하는 작업.
    *   기존 엔진: 총 요청 시간 6.39초, 출력 토큰/초 60.1, 토큰당 시간 16.6ms.
    *   투기적 가속 엔진: 총 요청 시간 5.09초, 출력 토큰/초 75.3, 토큰당 시간 13.3ms.
    *   결과: 투기적 디코딩이 1.25배 빨랐으며, 드래프트 모델의 토큰 수용률은 51%였습니다.
이 데모는 구조화된 작업에서 투기적 디코딩의 성능 향상이 더 크다는 것을 보여주었습니다.

두 번째 데모(컨텍스트 길이 대 이점)는 시각 자료로만 설명되었으며, 디코딩이 시간의 대부분을 차지하지 않는 경우(예: 긴 프롬프트 처리) 투기적 디코딩의 이점이 줄어든다고 설명합니다. 투기적 디코딩은 주로 디코딩 단계의 속도를 높이므로, 프롬프트 처리(Prefill) 시간이 지배적인 경우에는 전체적인 지연 시간 개선 효과가 미미합니다.

세 번째 데모(생산 환경 동시성) 역시 시각 자료로만 설명되었으며, 동시성이 증가하면 GPU가 더 바빠지고, 추가 드래프트 모델의 오버헤드가 속도 향상을 감소시키거나 심지어 없앨 수도 있다고 경고합니다.

발표자는 투기적 디코딩을 언제 활성화해야 하는지에 대한 요약표를 제시합니다.
-   **구조화된 출력(JSON, 코드, 추출, RAG):** 좋은 후보 (Good candidate)
-   **창의적 생성(스토리텔링, 개방형):** 덜 유익함 (Less beneficial)
-   **긴 컨텍스트 요청(RAG, 긴 문서):** 덜 유익함 (Less beneficial)
-   **낮은 동시성(실시간, 단일 사용자 LLM):** 일반적으로 유익함 (Usually beneficial)
-   **높은 동시성(다중 테넌트 공유 API 노드):** 활성화 전 측정 필요 (Measure before enabling)
발표자는 투기적 디코딩이 단순히 켜고 끄는 것이 아니라 워크로드에 따라 그 가치가 달라지는 최적화 기법이며, 자신의 트래픽에 대해 측정하는 것이 가장 좋은 방법이라고 결론지었습니다.

## 인상적인 대목
-   "투기적 디코딩은 단순히 켜고 끄는 것이 아닙니다. 이는 워크로드에 따라 그 가치가 달라지는 최적화 기법입니다. 이것이 가치 있는지 아는 가장 좋은 방법은 자신의 트래픽에 대해 측정하는 것입니다."

## 실무 적용 포인트
-   **워크로드 특성 분석:** LLM 애플리케이션이 주로 구조화된 출력을 생성하는지(예: JSON, 코드) 아니면 창의적이고 개방형 출력을 생성하는지 파악하여 투기적 디코딩의 잠재적 이점을 평가합니다. 구조화된 작업에 더 효과적입니다.
-   **GPU 자원 및 메모리 고려:** 투기적 디코딩은 추가 드래프트 모델과 KV 캐시를 위해 추가 GPU 메모리를 요구하므로, 현재 GPU 자원 활용도를 확인하고 여유 공간이 충분한지 검토해야 합니다.
-   **프롬프트 길이와 디코딩 시간 비중 평가:** LLM 호출 시 프롬프트 처리(Prefill) 시간이 디코딩 시간보다 훨씬 길다면, 디코딩 속도만 개선하는 투기적 디코딩의 전체적인 지연 시간 단축 효과는 제한적일 수 있습니다.
-   **생산 환경에서 측정:** 높은 동시성 환경에서는 추가 모델의 오버헤드가 속도 향상을 상쇄할 수 있으므로, 실제 운영 환경의 트래픽 패턴과 동시성 수준에서 투기적 디코딩의 성능을 반드시 측정하여 최적화 여부를 결정해야 합니다.
