# Your Self-Hosted LLM Needs to Say No - Harshul Jain & Parv Khatri, Audible & SAP

🔗 https://youtu.be/ntVpbyDTYaQ · 📅 2026-11-09 · 🎙 AI Engineer

## 한 줄 요약
LLM 추론 인프라에서 코딩 에이전트의 과도한 요청으로 인한 시스템 과부하를 방지하기 위해, GPU 메모리 할당 전에 요청을 선별적으로 처리하는 '입장 제어(Admission Control)'의 필요성과 구현 전략, 벤치마킹 방법을 제시한다.

## 발표자·소속
*   **Harshul Jain**: Audible 선임 소프트웨어 엔지니어
*   **Parv Khatri**: SAP 선임 개발자

## 핵심 주장
*   **LLM 추론 시스템의 한계**: LLM 추론은 GPU 메모리를 많이 사용하며, 각 토큰 생성은 이전 토큰에 의존하여 순차적으로 이루어진다. 모델은 응답의 길이를 미리 알 수 없으므로, 모든 요청을 무조건 수락하면 GPU 메모리 고갈 및 성능 저하로 이어질 수 있다.
*   **입장 제어(Admission Control)의 필요성**: OpenAI나 Anthropic과 같은 대규모 LLM 제공업체들도 과도한 트래픽으로 인한 서비스 중단을 겪었으며, 이들의 사후 분석은 더 빠른 엔진이 아닌 '요청을 일찍 결정하는 것'의 중요성을 강조한다. GPU 메모리가 할당되기 전에 요청을 선별하는 입장 제어 계층이 필수적이다.
*   **코딩 에이전트의 트래픽 변화**: 기존 사용자 채팅은 요청이 순차적이고 간격이 있었지만, 코딩 에이전트는 하나의 작업을 위해 수십 개의 API 호출을 동시에 발생시키고 타임아웃 시 재시도하는 등 예측 불가능하고 폭발적인 트래픽 패턴을 보인다. 이는 기존 인프라 스택에 큰 부담을 준다.
*   **입장 제어 정책 구축 및 벤치마킹**: 효과적인 입장 제어 정책은 요청 단위(단일 요청, 에이전트 세션, 테넌트), 감시할 신호(KV 압력, 큐 깊이, 마감 시간 지연), 결정 규칙(임계값, 이중 게이트, 최적화 도구, 형식적 바운드), 클라이언트에게 반환할 액션(허용, 연기, 거부)을 명확히 정의해야 한다. 또한, 정책의 효과를 검증하기 위해 실제 트래픽 패턴을 반영한 벤치마킹을 수행하고, '제공된 모든 요청 대비 실제 처리된 유용한 요청'인 굿풋(goodput) 지표를 사용해야 한다.

## 세부 내용

발표는 LLM 추론 시스템의 기본 원리와 한계, 그리고 이를 해결하기 위한 입장 제어(Admission Control)의 필요성에 대해 설명한다.

**1. 동기 (Motivation)**

*   **LLM 추론의 작동 방식**: 사용자가 프롬프트를 입력하면 LLM 모델은 한 번에 하나의 토큰을 생성하며 응답을 스트리밍한다. 각 토큰은 이전 토큰에 의존하므로 병렬 처리가 어렵다. 중요한 점은 모델이 응답의 총 길이를 미리 알 수 없다는 것이다.
*   **추론 파이프라인**: 사용자 앱/에이전트에서 시작된 요청은 API 게이트웨이(인증, 속도 제한), 라우터(로드 밸런싱), 추론 엔진(GPU에 모델 로드, 요청 배치 처리, KV 캐시 유지)을 거친다. KV 캐시는 요청이 응답을 생성하는 동안 GPU 메모리에 저장되는 데이터로, 응답이 길수록 더 많은 메모리를 차지한다.
*   **인프라의 한계**: 인프라는 품질(Quality), 지연 시간(Latency), 처리량(Throughput) 중 일부만 최적화할 수 있다. 예를 들어, 대화형 챗봇은 품질과 지연 시간을 중시하고 처리량을 희생하며, 비동기 에이전트는 품질과 처리량을 중시하고 지연 시간을 허용한다.
*   **실제 사례**: OpenAI와 Anthropic의 서비스 중단 사례는 과도한 트래픽으로 인한 메모리 부족 및 컴퓨팅 자원 부족이 원인이었음을 보여준다. 이들은 모두 '엔진이 요청을 처리하기 전에' 결정을 내리는 것이 중요하다고 결론 내렸다.
*   **입장 제어의 역할**: GPU 메모리가 할당되기 전에 요청을 수락(Admit), 보류(Hold), 거부(Reject)할지 결정하는 것이 입장 제어의 핵심이다. 요청이 일단 GPU에 들어가면 메모리를 차지하고, 과부하 시 엔진은 요청을 강제 종료(Evict), 디스크로 스왑(Swap), 또는 오류 반환(Preempt)해야 하는데, 이 모든 작업은 이미 자원을 낭비한 후의 조치이다.
*   **자체 호스팅의 문제**: 클라우드 LLM API를 사용할 때는 공급업체가 입장 제어를 관리하지만, 자체 LLM을 호스팅할 경우 개인 정보 보호, 비용 예측 가능성, 모델 제어 등의 이점과 함께 입장 제어의 책임도 직접 져야 한다.
*   **코딩 에이전트의 영향**: 코딩 에이전트는 하나의 작업을 위해 수십 개의 툴 호출을 동시에 실행하고, 타임아웃 시 재시도하며, 응답이 느리면 전체 계획을 지연시키는 등 예측 불가능한 트래픽 패턴을 보인다. 이는 기존 인프라가 설계된 방식과 달라 시스템 과부하를 유발한다.

**2. 입장 제어 (Admission Control)**

*   **결정 지점**: 입장 제어는 추론 파이프라인의 가장 앞단인 '인그레스(Ingress)'에서 이루어져야 한다. 이 단계에서는 요청을 거부해도 GPU 메모리나 엔진 스케줄러에 영향을 주지 않는다.
*   **정책의 결과**: 입장 제어 정책은 요청의 특징과 시스템 상태를 기반으로 다음 세 가지 중 하나를 반환한다.
    *   **허용(Admit)**: 요청이 엔진에 진입하고 GPU 메모리가 할당된다.
    *   **연기(Defer)**: 요청을 잠시 보류하고, 일정 시간(τ) 후 재시도하도록 클라이언트에 알린다. 이는 일시적인 트래픽 급증(burst)에 유용하다.
    *   **거부(Reject)**: 요청을 즉시 거부하고, 429(너무 많은 요청) 또는 529(서버 과부하)와 같은 오류 코드를 반환하여 클라이언트가 적절히 대응하도록 한다.
*   **클라이언트의 역할**: 클라이언트는 200 OK 응답을 받으면 스트림을 주시하고, 503(연기) 응답을 받으면 `Retry-After` 헤더에 명시된 시간만큼 기다린 후 재시도해야 한다(재시도 폭주를 막기 위해 지터(jitter)를 추가하는 것이 좋다). 429/529(거부) 응답을 받으면 요청 수를 줄이거나 다른 모델/프로바이더로 전환하는 등 적절히 대응해야 한다.

**3. 전략 (Strategies)**

*   **요청 수 vs 비용**: 단순히 요청 수를 세는 방식(예: 속도 제한, 고정 용량)은 실제 GPU 부하를 정확히 측정하지 못한다. 짧은 요청과 긴 요청이 동일하게 카운트되거나, GPU 용량이 배치 처리량에 따라 변동하는 것을 반영하지 못한다.
*   **비용 인식 정책(Cost-aware policy)**: 각 요청이 KV 캐시와 토큰에 얼마나 많은 비용을 발생시키는지 지속적으로 측정하고, 실시간 엔진 상태를 기반으로 요청을 거부하거나 연기하는 것이 더 효과적이다.
*   **정책 구축의 4가지 선택**:
    1.  **단위(Unit)**: 무엇을 허용할 것인가? (단일 요청, 에이전트 세션 전체, 테넌트 전체) 코딩 에이전트는 세션 단위로 요청을 보내므로, 세션 단위로 입장 제어를 하는 것이 더 효율적이다.
    2.  **신호(Signal)**: 무엇을 감시할 것인가? (KV 압력, 큐 깊이, 마감 시간 지연) 시스템 부하에 따라 움직이는 지표를 선택해야 한다.
        *   KV 압력: 캐시 오버플로우 방지.
        *   KV 사용량 + 캐시 적중률: 재계산 낭비 방지.
        *   큐 깊이 또는 시간: 대기 시간 단축.
        *   마감 시간 지연: 지연 시간 목표 달성.
        *   예측된 출력 길이: 긴 응답 계획.
    3.  **규칙(Rule)**: 어떻게 결정할 것인가? (저렴한 것부터 비싼 것 순)
        *   **임계값(Threshold)**: 단일 지표를 한계와 비교 (예: KV 사용량). 구현 비용이 저렴하지만, 성능 향상 폭이 작다 (10-20%).
        *   **이중 게이트(Dual gate)**: 두 가지 지표가 모두 동의해야 행동 (예: KV 사용량 + 캐시 적중률). 구현 비용이 낮고, 성능 향상 폭이 더 크다 (4배 이상).
        *   **최적화 도구(Optimizer)**: 선형 프로그래밍으로 최적의 입장 결정 (예: 모든 큐에 대한 QLM). 구현 비용이 높고, 결정 시간이 길지만 (5초), 성능 향상 폭이 가장 크다 (40-90%).
        *   **형식적 바운드(Formal bound)**: 최악의 경우 응답 시간 테스트 (예: Chronos). 구현 비용이 매우 높고, 지연 시간이 매우 짧다 (마이크로초), 마감 시간 미달률을 99%에서 0%로 줄인다.
*   **코딩 에이전트에 적합한 정책**: 현재 공개된 연구 중 자체 호스팅 코딩 에이전트에 완벽하게 맞는 정책은 없다. 대부분의 정책은 단일 요청에 초점을 맞추거나, 오프라인 테스트만 진행되었다. 따라서 기존 정책을 수정하거나 직접 구축해야 한다.

**4. 벤치마킹 (Benchmarking)**

*   **벤치마킹의 중요성**: 자체 구축하거나 수정한 입장 제어 정책이 실제로 작동하는지 증명해야 한다.
*   **벤치마킹 설정**:
    1.  **클러스터**: 입장 제어 없이 복제본이 감당할 수 있는 최대 부하를 측정하여 시스템의 기본 용량을 파악한다.
    2.  **정책**: 감시할 신호, 한계, 그리고 '거부' 시 행동을 명확히 정의한다.
    3.  **트레이스**: 실제 코딩 에이전트 트래픽(0.5x ~ 2x 용량)을 재현하여 사용한다.
    4.  **점수(Score)**: '제공된 모든 요청(거부된 요청 포함) 대비 SLO를 충족한 요청'인 굿풋(goodput)을 측정한다. 단순히 허용된 요청만으로 SLO 달성률을 계산하면, 실제 시스템 성능을 왜곡할 수 있다.
*   **워크로드**: 실제 트래픽(에이전트 트레이스, 용량 대비 부하, 실제 부하에서 마감 시간)으로 벤치마킹해야 한다. 용량 이하의 벤치마크는 정책을 제대로 테스트하지 못한다.
*   **보고**: 입장 제어 결과는 7가지 항목을 공개해야 한다. (용량 대비 부하, 보정된 마감 시간, 신호 활성도, 반복 및 확산, 매개변수 출처, 지표 정의, 구성)
*   **AdmitPerf**: 발표자들은 이러한 벤치마킹을 용이하게 하기 위해 AdmitPerf라는 도구를 개발했다. 이는 프로덕션 환경과 벤치마크 환경에서 동일한 정책 코드를 사용하여 일관된 측정을 가능하게 한다.

## 인상적인 대목
*   "Say no early. Say it clearly. Check that your no ever fires." (일찍 거부하라. 명확하게 거부하라. 당신의 거부가 실제로 작동하는지 확인하라.) - 입장 제어의 핵심 원칙을 간결하게 요약한 문장.
*   "A benchmark that stays below capacity never exercises the policy." (용량 이하로 유지되는 벤치마크는 정책을 전혀 실행하지 않는다.) - 벤치마킹의 현실적인 중요성을 강조하는 문장.

## 실무 적용 포인트
1.  **입장 제어 계층 구축**: LLM 추론 시스템에 GPU 메모리 할당 전에 요청을 선별하는 별도의 입장 제어 계층을 반드시 구축한다. API 게이트웨이 또는 프록시 단에서 구현하는 것이 엔진 수정 없이 가장 효율적이다.
2.  **비용 인식 정책 채택**: 단순히 요청 수를 세는 대신, 각 요청이 GPU 메모리(KV 캐시)와 토큰 생성에 얼마나 많은 자원을 사용하는지 추정하는 '비용 인식 정책'을 도입하여 실제 부하를 정확히 관리한다.
3.  **벤치마킹을 통한 정책 검증**: 실제 트래픽 패턴(에이전트 트레이스)을 재현하고, 시스템 용량을 초과하는 부하를 주어 정책을 벤치마킹한다. '굿풋(goodput)' 지표를 사용하여 거부된 요청까지 포함한 실제 유용한 처리량을 측정하여 정책의 효과를 객관적으로 평가한다.
4.  **오픈소스 도구 활용**: AdmitPerf (github.com/harshuljain13/AdmitPerf)와 같은 오픈소스 도구를 활용하여 입장 제어 정책을 개발하고 벤치마킹한다. 이는 정책 개발 및 검증에 필요한 시간과 노력을 줄여줄 수 있다.
