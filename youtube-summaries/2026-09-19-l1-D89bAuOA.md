# Are LLM Performance Benchmarks Reliable? — Ashok Chandrasekar & Jason Kramberger, Google

🔗 https://youtu.be/l1-D89bAuOA · 📅 2026-09-19 · 🎙 AI Engineer

## 한 줄 요약
LLM 성능 벤치마크의 신뢰성 문제를 제기하고, Inference Perf와 같은 다중 프로세스 아키텍처, 선언적 구성, 실제 워크로드 시뮬레이션, 정확한 지표 측정을 통해 재현 가능한 프로덕션 규모 벤치마크를 달성하는 솔루션을 제시합니다.

## 발표자·소속
*   **Ashok Chandrasekar**: Google Staff Software Engineer, Kubernetes Inference Perf Project Lead / llm-d SIG Benchmarking Co-lead
*   **Jason Kramberger**: Google Software Engineer, Inference Perf Co-maintainer

## 핵심 주장
*   **LLM 벤치마크의 신뢰성 부족**: 기존 벤치마크는 프로덕션 규모의 정확성, 지표 가시성, 재현성, 입력 데이터셋 품질 측면에서 중대한 결함이 있어 실제 성능을 왜곡합니다.
*   **측정 편향 문제**: 인프라 문제로 진단되는 경우가 많지만, 실제로는 벤치마크 도구 자체에서 발생하는 측정 편향으로 인해 성능 지표가 부정확하게 보고됩니다.
*   **Inference Perf 아키텍처의 해결책**: Inference Perf는 다중 프로세스 로드 제너레이터, 선언적 구성, 클라이언트 및 서버 지표의 충실한 보고를 통해 Python GIL과 같은 제약을 극복하고 프로덕션 규모에서 정확하고 재현 가능한 벤치마크를 가능하게 합니다.
*   **실제 워크로드 시뮬레이션의 중요성**: 단순한 합성 워크로드가 아닌, 실제 사용 사례를 반영하는 컨텍스트 인식 데이터셋과 다양한 부하 패턴을 사용하여 벤치마크가 실제 프로덕션 환경을 정확하게 모방해야 합니다.

## 세부 내용

발표자들은 LLM 성능 벤치마크의 신뢰성 문제를 다루며, 현재 벤치마크 생태계를 네 가지 유형으로 분류합니다: 모델 서버 프레임워크, 경쟁 분석 도구, 웹 벤치마크, 그리고 프로덕션 규모 LLM 벤치마크. 이 발표는 특히 프로덕션 규모 LLM 벤치마크에 초점을 맞춥니다.

일반적인 벤치마크 실행은 특정 모델, 데이터셋, 입출력 시퀀스 길이, 요청률 등을 지정하는 명령줄 스크립트를 통해 이루어지며, 결과는 주로 입출력 토큰 처리량과 시간당 첫 토큰(TTFT), 시간당 출력 토큰(TPOT)과 같은 지연 시간 지표로 보고됩니다.

그러나 프로덕션 규모의 LLM 환경은 훨씬 복잡합니다. 온라인 서빙과 배치 워크로드가 공존하고, Prefill/Decode Disaggregation, 워크로드 오토스케일링 등 복잡한 구성이 필요하며, 규모가 훨씬 커집니다. 이러한 환경에서는 높은 부하와 동시성, 실제 워크로드 시뮬레이션, 정확한 지표 및 백분위수 기반 SLA, 그리고 비즈니스 SLO를 보장하는 굿풋(Goodput)이 중요합니다.

발표자들은 벤치마킹의 네 가지 주요 함정을 지적합니다.
1.  **프로덕션 규모 정확성**: 기존 벤치마크는 고동시성 프로덕션 환경을 시뮬레이션하지 못하고, 요청을 묵묵히 드롭하거나 시스템 한계를 왜곡합니다.
2.  **지표 가시성**: Python GIL(Global Interpreter Lock)과 같은 클라이언트 측 오버헤드가 지연 시간 측정치를 부풀려 서버 성능 데이터를 오도할 수 있습니다.
3.  **재현성 및 확률성**: 확률적 매개변수, 실행 간 편차, 시드되지 않은 무작위 모델 생성으로 인해 벤치마크 결과가 매우 일관성이 없어집니다. 예를 들어, 모델 온도를 0으로 설정하면 결정론적 디코딩이 강제되어 토큰 생성이 인위적으로 가속화될 수 있습니다.
4.  **입력 데이터셋 품질**: 합성적이고 비대표적인 프롬프트 분포 및 특정 샘플링 기법은 실제 사용자 행동을 모방하지 못하여 비현실적인 캐시 적중률과 토큰률로 이어집니다. 동일한 데이터셋을 사용하더라도 벤치마크 도구마다 프롬프트 자르기 및 시퀀싱 방식이 달라 입력 토큰 수에 33%의 차이가 발생할 수 있습니다.

이러한 문제에 대한 해결책으로 Inference Perf 프레임워크를 제시합니다. Inference Perf는 CNCF(Cloud Native Computing Foundation) 프로젝트로, 다음과 같은 특징을 가집니다.
*   **선언적 구성**: 사용자 정의 부하 및 데이터셋 정의를 통해 명확한 재현성을 제공합니다.
*   **로드 제너레이터**: 사용자 정의 부하 패턴에 따라 요청을 대기열에 넣고, 워커가 여러 프로세스에 걸쳐 동적으로 작업을 풀링하여 asyncio 루프를 vCPU에 분산함으로써 Python GIL 문제를 효과적으로 우회합니다.
*   **지표 충실도**: 클라이언트가 관찰한 지표와 서버 지표를 모두 보고하여 충실한 보고 및 가시성을 제공합니다. 이를 통해 클라이언트가 트래픽을 조용히 제한하지 않았음을 수학적으로 보장합니다.

Inference Perf의 다중 프로세스 아키텍처는 메인 프로세스가 QPS/동시성을 관리하고 로드 제너레이터를 통해 요청 큐/채널을 워커 프로세스에 분배하는 방식으로 작동합니다. 각 워커 프로세스는 자체 asyncio 이벤트 루프를 가지고 동시 작업을 처리합니다. 이를 통해 5,000 QPS와 같은 높은 부하에서도 Locust(Python, 1,634 QPS)나 MLPerf(C++/Py, 1,944 QPS)와 같은 다른 도구보다 훨씬 높은 부하 충실도(4,998 QPS)를 달성하며, Go native k6(5,000 QPS)와 거의 동일한 성능을 보여줍니다.

Inference Perf는 또한 상세한 에이전트 로드 구성(YAML 형식)을 제공하여, 시스템 프롬프트, 멀티턴, 모델 온도, 입출력 시퀀스 길이 분포 등 다양한 변수를 정확하게 설정할 수 있습니다. LLM-D 프로젝트의 일부인 Workload Catalog와 Prism UI를 통해 표준화된 실제 워크로드(예: 코드 생성 에이전트, 대화형 챗봇, 배치 요약 등)를 제공하고, 벤치마크 결과를 시각화하여 최적화 전후의 성능 변화를 명확하게 보여줍니다.

## 인상적인 대목
*   "What is frequently diagnosed as an infrastructure issue is, in reality, a measurement bias induced by the benchmark itself." (인프라 문제로 자주 진단되는 것이 실제로는 벤치마크 자체에 의해 유발된 측정 편향입니다.)

## 실무 적용 포인트
*   **다중 프로세스 벤치마크 도구 사용**: Python GIL과 같은 언어적 제약으로 인한 클라이언트 측 병목 현상을 피하기 위해, 프로덕션 규모 벤치마크에서는 항상 Inference Perf와 같이 다중 프로세스 아키텍처를 사용하는 도구를 활용해야 합니다.
*   **지표 가시성 확보**: 벤치마크 클라이언트의 행동(예: 요청 드롭 또는 지연 시간 인플레이션)을 명확히 관찰할 수 있도록 클라이언트 및 서버 양쪽의 지표를 모두 측정하고 보고하는 도구를 사용해야 합니다.
*   **확률적 변수 통제**: 모델 온도와 같은 확률적 매개변수를 실제 워크로드의 특성을 반영하도록 신중하게 설정하고, 벤치마크 간 재현성을 위해 가능한 한 고정하거나 명확히 문서화해야 합니다.
*   **실제와 유사한 데이터셋 및 워크로드 사용**: 합성 데이터나 단순한 프롬프트 대신, 실제 프로덕션 사용 사례를 모방하는 컨텍스트 인식 데이터셋과 프롬프트 구조를 사용하고, 필요하다면 LLM-D Workload Catalog와 같은 표준화된 워크로드를 활용하여 벤치마크의 유효성을 높여야 합니다.
