# How Many Credentials Should Your AI Agent Have? Zero. — Jim Clark, Docker

🔗 https://youtu.be/ZUZVNKFSmTM · 📅 2026-10-06 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트의 안전성을 높이기 위해 에이전트의 역할을 분리하고, 필요한 도구와 리소스를 적시에 최소한으로 노출하며, 자격 증명을 에이전트 하네스에서 분리하여 게이트웨이 계층에서 관리하는 '프로그레시브 디스클로저(Progressive Disclosure)' 접근 방식을 사용해야 한다.

## 발표자·소속
Jim Clark, Docker 엔지니어

## 핵심 주장
- **에이전트 역할 분리:** 하나의 AI 에이전트를 여러 역할로 분리하여 각 역할에 필요한 최소한의 기능과 리소스만 부여함으로써, 에이전트가 오작동하거나 악의적인 행동을 할 경우 발생할 수 있는 '블래스트 반경(blast radius)'을 줄일 수 있습니다. 이는 뉴스룸에서 기자, 팩트체커, 편집자의 역할을 분리하는 것과 유사합니다.
- **자격 증명 없는 하네스:** 에이전트 하네스(agent harness) 자체는 자격 증명(credentials)을 직접 보유하지 않고, 오직 도구 호출(tool calls)만 생성해야 합니다. 모든 자격 증명은 MCP(Managed Credential Provider) 게이트웨이 계층에서 관리되어야 하며, 이를 통해 에이전트의 보안 위험을 최소화할 수 있습니다.
- **점진적 공개(Progressive Disclosure) 게이트웨이:** MCP 게이트웨이는 에이전트가 특정 작업을 수행하는 데 필요한 도구, 리소스 및 프롬프트만 '적시(just in time)'에 공개하는 제어 지점 역할을 합니다. 이는 에이전트가 불필요한 정보나 기능에 접근하는 것을 방지하여 컨텍스트 크기를 줄이고 에이전트의 행동을 의도한 범위 내로 제한합니다.

## 세부 내용

발표자는 AI 에이전트가 점점 더 많은 작업을 자율적으로 수행하게 되면서, 에이전트의 안전성(AI safety)이 중요해지고 있다고 강조했습니다. 에이전트가 적은 감독으로 더 많은 일을 할수록, 잠재적인 위험도 커지기 때문입니다.

발표자는 이 문제를 해결하기 위한 세 가지 핵심 요소를 제시했습니다: 에이전트 하네스, 샌드박스, 그리고 MCP(Managed Credential Provider)입니다.

**1. 에이전트 하네스:**
에이전트 하네스는 기본적으로 '컨텍스트를 읽고 → 도구 호출을 내보내고 → 반복하는' 역할을 합니다. 하네스는 빠르게 진화할 것으로 예상되므로, 장기 실행 작업에 효과적으로 작동하도록 설계되어야 하며, 하네스 주변의 '경계(boundaries)'가 중요합니다. 하네스 자체는 '죽은 방(dead room)'에 있는 것과 같아서, 외부의 컨텍스트나 작업을 요청할 뿐입니다.

**2. MCP (Managed Credential Provider):**
MCP는 에이전트가 새로운 작업을 수행하기 위해 외부 도구, 프롬프트, 리소스에 접근할 수 있도록 돕는 역할을 합니다. 발표자는 안전성을 확보하기 위해 두 가지 질문에 자신 있게 답할 수 있어야 한다고 말했습니다: "어떤 컨텍스트가 모델로 들어가는가?"와 "에이전트가 실제로 무엇을 호출할 수 있는가?" 이 두 가지를 제어하면 '블래스트 반경(blast radius)'을 제어할 수 있습니다.

**3. 샌드박스:**
샌드박스는 에이전트가 작업을 수행하는 공간입니다. 발표자는 "왜 우리가 부엌에 전기톱을 보관하지 않는가"라는 비유를 들며 샌드박스의 중요성을 설명했습니다. 현재 에이전트 하네스 런타임은 이미 샌드박스화되어 있지만, 실제로는 종종 코드 샌드박스와 함께 배치되거나 노트북에서 실행되어 위험이 발생할 수 있습니다.

발표자는 '뉴스룸 비유'를 통해 에이전트의 역할을 분리하는 방법을 설명했습니다.
- **리서처(Researcher) 샌드박스:** 웹에 접근하여 정보를 수집하고, 임시 디렉토리에 연구 결과를 작성합니다. 이 샌드박스는 네트워크 접근 권한을 가지지만, 출판(publishing) 권한은 없습니다.
- **팩트체커(Fact-checker) 샌드박스:** 네트워크 접근 권한 없이 리서처가 작성한 연구 결과를 읽고, 팩트 데이터베이스에 접근하여 사실을 확인합니다.
- **리포터(Reporter) 샌드박스:** 네트워크 접근 권한 없이 필터링된 연구 결과를 읽고, 노션(Notion)이나 다른 출판 MCP를 통해 기사를 발행합니다.

이처럼 한 에이전트를 세 가지 역할로 분리하고 각 역할에 필요한 최소한의 기능만 부여함으로써, 에이전트가 잘못된 행동을 하더라도 그 영향이 제한됩니다.

**코드 커밋 시나리오:**
장기 실행 코딩 작업의 경우, 각 단계 사이에 '커밋(commit)' 작업을 삽입할 수 있습니다. 커밋 작업 샌드박스는 오직 Git 작업 트리만 볼 수 있으며, 그 유일한 임무는 커밋을 만드는 것입니다. 따라서 서명 키(signing key)는 이 샌드박스에만 존재하며, 필요한 아주 짧은 시간 동안만 노출됩니다. 핵심은 '에이전트는 무언가를 커밋할 때만 서명 키가 필요하다'는 것입니다.

**MCP 게이트웨이 설계:**
Docker의 'sbx' 도구는 이 개념을 구현합니다. 에이전트 하네스는 자격 증명 없이 `mcp-gateway.docker.internal`과 같은 내부 URL과 플레이스홀더 토큰(placeholder token)만 가집니다. MCP 게이트웨이는 실제 자격 증명을 관리하고, GitHub, Notion, Linear와 같은 외부 서비스와의 통신을 중재합니다. 게이트웨이는 각 샌드박스가 어떤 도구, 리소스, 프롬프트를 볼 수 있는지 정확히 관리하는 '제어 지점'입니다. 이를 통해 하네스는 MCP에 구애받지 않게(harness-agnostic) 되어, MCP 카탈로그를 하네스 간에 쉽게 이동할 수 있습니다.

**SSO (Single Sign-On) for agents - Cross-App Access (XAA):**
기업의 기존 SSO 시스템을 활용하여 에이전트의 접근 권한을 관리할 수 있습니다. 에이전트 샌드박스와 MCP 게이트웨이는 기업의 기존 ID 공급자(IdP)와 상호 작용하여 에이전트의 ID 클레임(identity claims)을 교환하고, 이를 통해 리소스 서버(예: Notion, GitHub)에 접근할 수 있는 액세스 토큰(access token)을 얻습니다. 에이전트는 사용자를 대신하여 행동하며, 기존 SSO 인프라를 재활용하여 보안을 강화합니다.

**결론:**
MCP 게이트웨이는 '점진적 공개(progressive disclosure)' 원칙을 MCP에 적용합니다. 필요한 도구와 리소스만 적시에 공개하여 컨텍스트 크기를 줄이고, 에이전트에게 문제 해결을 위한 충분한 공간을 제공하며, 모든 샌드박스가 동일할 필요가 없도록 합니다. 오케스트레이터(orchestrator)는 에이전트의 의도를 파악하여 적절한 기능을 가진 샌드박스를 구축합니다.

이 모든 것은 다음과 같이 요약됩니다:
- **역할 분리(Role separation):** 어떤 단계도 위험한 조합 전체를 보유하지 않습니다.
- **하네스 내 자격 증명 없음(No creds in the harness):** 하네스는 오직 도구 호출만 내보냅니다.
- **점진적으로 공개하는 게이트웨이(A gateway that discloses progressively):** 최소한의 기능만 적시에 부여됩니다.
- **의도를 나타내는 샌드박스(Sandboxes that represent Intent):** 기능이 작업과 일치합니다.
- **-> 더 안전한 에이전트(safer agents)**

Docker는 `sbx`라는 도구를 통해 이러한 개념을 구현하고 있으며, `brew install sbx` 및 `sbx run claude` 명령어를 통해 에이전트가 샌드박스 환경에서 실행되는 것을 시연했습니다.

## 인상적인 대목
- "Less supervision raises the stakes on safety. Is there a world where agents become more useful without becoming more dangerous?" (감독이 줄어들면 안전에 대한 위험이 높아집니다. 에이전트가 더 위험해지지 않으면서 더 유용해지는 세상이 있을까요?)
- "Creds belong at the MCP layer, not the harness." (자격 증명은 하네스가 아닌 MCP 계층에 속합니다.)
- "Expose capability to a sandbox just in time, not just in case." (샌드박스에 기능을 '만약을 대비해서'가 아니라 '필요할 때만' 노출하세요.)

## 실무 적용 포인트
- **에이전트 설계 시 역할 분리:** 복잡한 AI 에이전트를 개발할 때, 단일 에이전트가 모든 기능을 수행하게 하기보다는, 뉴스룸 비유처럼 '리서처', '팩트체커', '리포터'와 같이 명확히 분리된 역할과 책임을 가진 여러 에이전트로 나누어 설계합니다.
- **최소 권한 원칙 적용:** 각 에이전트(또는 샌드박스)에 필요한 최소한의 도구, 리소스, 네트워크 접근 권한만 부여합니다. 특히 자격 증명은 에이전트 하네스 내부에 직접 저장하지 않고, 별도의 보안 계층(MCP 게이트웨이)에서 관리하도록 합니다.
- **점진적 공개 메커니즘 도입:** 에이전트가 특정 작업을 수행할 때만 필요한 기능이나 리소스에 대한 접근 권한을 동적으로 부여하고, 작업이 완료되면 회수하는 '점진적 공개' 방식을 구현합니다. 이는 에이전트의 컨텍스트 크기를 최적화하고 불필요한 위험 노출을 줄입니다.
- **기존 SSO 인프라 활용:** 에이전트의 인증 및 권한 부여를 위해 기업의 기존 SSO(Single Sign-On) 및 ID 관리 시스템을 활용합니다. 이를 통해 에이전트별로 개별적인 인증 시스템을 구축하는 복잡성을 피하고, 중앙 집중식으로 에이전트의 접근 권한을 관리할 수 있습니다.
