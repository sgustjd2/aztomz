# No, That's Not a Software Factory — Ryan Cooke, WorkOS

🔗 https://youtu.be/HvboD89DyQ8 · 📅 2026-09-27 · 🎙 AI Engineer

## 한 줄 요약
WorkOS는 소프트웨어 팩토리가 단순한 코드 생성 도구를 넘어, 조직의 엔지니어링 문화와 프로세스를 AI 에이전트에 인코딩하여 실제 비즈니스 성과를 창출하는 시스템이 되어야 한다고 주장합니다.

## 발표자·소속
Ryan Cooke, Product Engineering - WorkOS

## 핵심 주장
-   **출력(Output)보다 성과(Outcomes)에 집중**: 업계는 AI가 생성하는 코드의 양(PR 병합 수, AI 작성 코드 비율 등)에 초점을 맞추지만, WorkOS는 기능 배포 시간 단축, 결함률 안정화, 엔지니어 생산성 향상 등 실제 비즈니스 성과를 측정하는 것이 중요하다고 강조합니다.
-   **인프라스트럭처는 필요하지만 불완전함**: 샌드박스, 모델, 레포지토리와 같은 기본 인프라는 소프트웨어 팩토리에 필수적이지만, 이것만으로는 엔지니어가 로컬에서 AI를 사용하는 것보다 더 나은 결과를 내기 어렵습니다.
-   **엔지니어링 프로세스 인코딩의 중요성**: 소프트웨어 팩토리의 진정한 가치는 단순히 코드를 생성하는 것을 넘어, 조직의 제품 엔지니어링 문화, 계획, 기능 범위 설정, 검증 및 컨벤션과 같은 제도적 지식을 AI 에이전트에 인코딩하여 실행 가능하게 만드는 데 있습니다.
-   **PM 에이전트와 컨텍스트 엔진 구축**: WorkOS는 PM 에이전트(기획 프로세스 인코딩)와 컨텍스트 엔진(내부 도구 및 데이터 연결)을 구축하여 AI가 프로젝트 계획을 수립하고, 작업을 분할하며, 기존 시스템과 상호작용하고, 심지어 팩토리 자체를 개선하도록 합니다.

## 세부 내용
발표자는 AI 엔지니어링 컨퍼런스에서 소프트웨어 팩토리에 대한 WorkOS의 접근 방식을 설명합니다.

**표준 플레이북의 한계**: 발표자는 Ramp, Spotify, Stripe 등 여러 기업이 AI를 활용해 PR(Pull Request)을 생성하고 병합하는 "표준 플레이북"을 따르고 있음을 언급합니다. 이 플레이북은 샌드박스에서 AI 모델이 코드를 생성하고, 레포지토리에 PR을 열어 병합하는 과정을 포함합니다. 하지만 발표자는 이러한 접근 방식이 주로 "출력 지표(Output metrics)"에만 초점을 맞춘다고 지적합니다.

**출력 대 성과**: 발표자는 업계가 PR 병합 수, AI가 작성한 코드의 비율, 코드 생성량, 에이전트 처리량 등 "출력 지표"에만 집중하고 있다고 비판합니다. WorkOS는 대신 "성과 지표(Outcome metrics)"를 측정해야 한다고 주장합니다. 여기에는 기능 배포 시간 개선, 대규모 결함률 안정화, 엔지니어 생산성 향상, 문제 해결 시간 단축 등이 포함됩니다. "더 빠르고 많은 코드는 더 빠르고 많은 가치와 같지 않다"는 것이 핵심 메시지입니다.

**WorkOS의 접근 방식: Horizon / TARS**: WorkOS는 이러한 성과를 달성하기 위해 두 가지 핵심 시스템을 구축했습니다.
-   **TARS (The Product)**: 사용자가 Slack, Linear, GitHub, 웹 UI를 통해 AI 에이전트와 상호작용하는 제품입니다. 지시를 받고, PR을 열고, 상태를 보고합니다.
-   **Horizon (The Infrastructure)**: Cloudflare 컨테이너, 웹훅 기반 오케스트레이션, OpenCode 런타임, 웜-풀드 샌드박스로 구성된 인프라스트럭처입니다. Linear에서 레포지토리로, 다시 돌아오는 이벤트 루프를 관리합니다.

**인프라스트럭처를 넘어선 엔지니어링 프로세스 인코딩**: 발표자는 인프라스트럭처만으로는 충분하지 않다고 강조합니다. WorkOS는 엔지니어링 프로세스 자체를 AI 에이전트에 인코딩했습니다.
-   **PM 에이전트**: WorkOS는 "PM 에이전트"라는 AI 에이전트를 개발하여 기획 프로세스를 인코딩했습니다. 이 에이전트는 "Hilltop 문서"라는 제품 요구사항 문서를 읽고, 이를 명시적인 의존성 체인을 가진 이슈(Linear 티켓)로 나눕니다. 인간 엔지니어는 이 이슈들을 검토하고 추가 컨텍스트를 제공하여 실제 의사결정을 반영합니다. 이후 구현 에이전트가 이슈가 언블록되는 순서대로 작업을 수행하고 PR을 엽니다. PR이 병합되면 Horizon이 자동으로 다음 종속성 이슈를 언블록하여 작업이 즉시 시작됩니다.
-   **데모**: 발표자는 Slack에서 `/project create` 명령어로 "Vault Internal KEK API" 프로젝트를 시작하는 데모를 보여줍니다. TARS는 자동으로 Linear 프로젝트, Notion의 Hilltop 문서 초안, 의사결정 로그 등을 생성합니다. 이 Hilltop 문서는 경쟁사 분석, 디자인 스크린, 주요 마일스톤 등을 포함하며, AI가 초안을 작성하여 엔지니어의 초기 작업 부담을 줄여줍니다.
-   **컨텍스트 엔진**: WorkOS는 내부 시스템을 연결하고 AI 에이전트에게 도구 사용법과 정보 구조를 알려주는 "컨텍스트 엔진"을 구축했습니다. 이는 데이터 파이프라인이 아니라 "문화 인코딩"입니다. 일관된 명명 규칙, Snowflake와 같은 데이터 소스 연결, Sentry 오류나 Slack 컨텍스트와 같은 패턴을 에이전트에 제공하여 에이전트가 최소한의 컨텍스트로도 작업을 수행할 수 있도록 합니다. 이 MCP(Multi-Cloud Platform) 서버는 이제 WorkOS의 다른 내부 팀에서도 데이터 분석 및 고객 분석을 위해 직접 쿼리하는 데 사용됩니다.

**소프트웨어 팩토리의 차별점**: 발표자는 소프트웨어 팩토리가 단순히 샌드박스, 모델, 레포지토리의 조합을 넘어, 조직의 제도적 지식(작업 계획 방식, 기능 범위 설정 방식, 검증 방식, 컨벤션)을 실행 가능하게 만드는 것이 진정한 차별점이라고 결론짓습니다. 궁극적인 목표는 플랫폼이 실패를 반복하는 것보다 더 빠르게 학습하여 지속적으로 개선되는 것입니다.

## 인상적인 대목
-   "More code, faster, is not the same as more value, faster." (더 빠르고 많은 코드는 더 빠르고 많은 가치와 같지 않다.)
-   "Infrastructure is only half the story. Encoding how we build software did." (인프라스트럭처는 이야기의 절반에 불과합니다. 우리가 소프트웨어를 구축하는 방식을 인코딩하는 것이 중요했습니다.)
-   "The unlock isn't infrastructure. It's institutional knowledge, made executable." (진정한 해제는 인프라스트럭처가 아닙니다. 그것은 실행 가능하게 만들어진 제도적 지식입니다.)

## 실무 적용 포인트
-   **성과 중심의 AI 도입**: AI 도구 도입 시 PR 수나 코드 라인 수 같은 출력 지표보다는 기능 배포 속도, 결함률, 엔지니어 생산성 등 실제 비즈니스 성과에 미치는 영향을 측정하고 개선하는 데 집중해야 합니다.
-   **엔지니어링 프로세스 자동화**: AI 에이전트를 단순한 코드 생성 도구로만 활용하는 것을 넘어, 조직의 고유한 기획, 설계, 검토, 배포 프로세스를 에이전트에 인코딩하여 자동화 수준을 높이는 것을 고려해야 합니다.
-   **컨텍스트 엔진 구축**: AI 에이전트가 조직의 내부 시스템(이슈 트래커, 데이터 웨어하우스, 커뮤니케이션 도구 등)과 원활하게 상호작용하고, 조직의 컨벤션과 지식을 이해하도록 돕는 컨텍스트 엔진 또는 MCP 게이트웨이를 구축하는 것이 중요합니다.
-   **지속적인 학습 및 개선**: AI 에이전트가 생성하는 코드와 수행하는 작업의 결과를 지속적으로 모니터링하고, 이를 통해 에이전트의 성능을 개선하고 조직의 엔지니어링 문화를 발전시키는 "자기 개선(self-improving)" 루프를 구축해야 합니다.
