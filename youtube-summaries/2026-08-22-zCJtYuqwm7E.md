# Coding Agents Don't Scale Themselves. Neither Do Your Teams. — Patrick Debois, Tessl

🔗 https://youtu.be/zCJtYuqwm7E · 📅 2026-08-22 · 🎙 AI Engineer

## 한 줄 요약
AI 코딩 에이전트가 스스로 확장되지 못하며, 이는 개발 팀의 확장 문제와 유사하므로, 데브옵스(DevOps) 원칙을 적용하여 에이전트의 작업 흐름, 피드백, 지속적인 학습을 체계적으로 관리해야 합니다.

## 발표자·소속
Patrick Debois, Tessl

## 핵심 주장
-   **프롬프트 엔지니어링만으로는 복잡한 AI 에이전트의 확장이 불가능합니다.** 현재의 프롬프트 엔지니어링은 단일 지시로 완벽한 결과물을 기대하는 것과 같아, 복잡하고 다단계적인 문제 해결에는 한계가 있으며, 에이전트가 스스로 학습하고 개선하는 데 필요한 구조를 제공하지 못합니다.
-   **AI 에이전트도 인간 개발팀처럼 '흐름(Flow)', '피드백(Feedback)', '지속적인 학습(Continuous Learning)'이 필요합니다.** 에이전트가 문제를 이해하고, 계획하고, 실행하고, 테스트하고, 개선하는 일련의 과정을 체계적인 흐름으로 설계하고, 각 단계에서 명확하고 즉각적인 피드백을 받아 스스로 오류를 수정하고 학습할 수 있는 환경을 구축해야 합니다.
-   **AI 에이전트는 단일 LLM 호출이 아닌, 여러 LLM 호출과 도구의 '오케스트레이션(Orchestration)'입니다.** 에이전트의 지능은 단순히 대규모 언어 모델(LLM) 하나에서 나오는 것이 아니라, LLM을 활용하여 계획을 세우고, 코드를 작성하고, 테스트를 실행하고, 디버깅하며, 외부 도구와 상호작용하는 복합적인 시스템 설계에서 비롯됩니다.
-   **데브옵스 원칙은 AI 에이전트 및 이를 개발하는 팀의 확장에 직접 적용될 수 있습니다.** 데브옵스가 소프트웨어 개발 및 운영의 효율성을 높이는 데 중점을 두는 것처럼, 에이전트의 모듈화, 테스트, 버전 관리, 지속적인 통합 및 배포, 관측 가능성 등의 원칙을 적용하여 에이전트의 성능과 안정성을 향상시키고, 팀의 생산성을 높일 수 있습니다.

## 세부 내용
발표는 AI 코딩 에이전트가 스스로 확장되지 못하는 문제점을 지적하며 시작됩니다. 발표자는 AI 에이전트가 마치 주니어 개발자와 같아서, 복잡한 문제를 해결하고 스스로 확장하기 위해서는 명확한 지시, 도구, 피드백, 그리고 구조화된 환경이 필요하다고 강조합니다. 현재의 '프롬프트 엔지니어링' 방식은 단일 지시로 완벽한 결과물을 기대하는 것과 같아 한계가 명확하다고 주장합니다.

발표자는 데브옵스(DevOps)의 핵심 원칙인 '흐름(Flow)', '피드백(Feedback)', '지속적인 학습(Continuous Learning)'을 AI 에이전트 개발에 적용해야 한다고 제안합니다.
1.  **흐름**: 에이전트가 문제를 해결하는 과정을 단일 프롬프트가 아닌, 문제 이해 → 계획 수립 → 코드 작성 → 테스트 → 디버깅 → 개선의 일련의 흐름으로 설계해야 합니다.
2.  **피드백**: 에이전트가 작성한 코드에 대한 즉각적이고 구체적인 피드백(예: 테스트 결과, 오류 메시지)을 제공하여 스스로 오류를 인지하고 수정할 수 있도록 해야 합니다.
3.  **지속적인 학습**: 에이전트가 실패와 성공으로부터 학습하고, 새로운 정보에 적응하며, 시간이 지남에 따라 성능을 개선할 수 있는 시스템을 구축해야 합니다.

발표자는 Tessl 플랫폼을 통해 이러한 원칙이 어떻게 구현되는지 시각적으로 설명합니다. Tessl의 접근 방식에서 '에이전트'는 단일 LLM이 아니라, 여러 LLM 호출과 외부 도구들의 정교한 오케스트레이션입니다.
*   **문제 정의**: 사용자가 고수준의 문제(예: "X를 수행하는 파이썬 스크립트 생성")를 제공합니다.
*   **에이전트 오케스트레이션**:
    *   **플래너(Planner)**: 문제를 받아 더 작고 실행 가능한 단계로 분해합니다 (LLM 호출).
    *   **실행자(Executor)**: 플래너가 세운 단계를 실행합니다. 이 과정에서 여러 구성 요소가 사용됩니다.
        *   **코더(Coder)**: 특정 단계에 따라 코드를 작성합니다 (LLM 호출).
        *   **테스터(Tester)**: 생성된 코드에 대해 테스트를 실행합니다 (도구 호출, 예: 파이썬 인터프리터, 단위 테스트 프레임워크).
        *   **디버거(Debugger)**: 테스트 실패를 분석하고 수정 사항을 제안합니다 (LLM 호출).
        *   **리파이너(Refiner)**: 피드백/수정 사항을 통합하여 코드를 개선합니다 (LLM 호출).
        *   **서처(Searcher)**: 필요한 경우 정보를 수집합니다 (도구 호출, 예: 웹 검색).
*   **피드백 루프**: 테스터의 출력(성공/실패, 오류 메시지)은 디버거/리파이너에게 전달되어 코더나 플래너에게 다시 피드백을 제공합니다.
*   **도구 활용**: 에이전트는 파이썬 인터프리터, 파일 시스템, 웹 검색, 단위 테스트 프레임워크 등 다양한 도구를 사용하여 환경과 상호작용하고 작업의 유효성을 검사합니다.
*   **컨텍스트 관리**: 시스템은 여러 단계와 상호작용에 걸쳐 컨텍스트를 유지하여 에이전트가 이전 작업과 피드백을 기억할 수 있도록 합니다.
*   **휴먼 인 더 루프(Human in the Loop)**: 복잡한 문제나 에이전트가 막혔을 때 인간이 개입하여 피드백을 제공할 수 있는 지점을 마련하여 에이전트의 확장성을 높입니다.

발표자는 이러한 에이전트 시스템을 인간 개발 팀에 비유하며, 주니어 개발자(AI 에이전트)가 명확한 작업, 도구, 피드백, 멘토링, 그리고 구조화된 환경(버전 관리, CI/CD)을 필요로 하는 것과 같다고 설명합니다. 결론적으로, AI 에이전트는 강력하지만 확장하기 위해서는 구조화된 접근 방식이 필요하며, 데브옵스 원칙이 에이전트와 이를 구축하는 팀을 확장하는 데 핵심적인 역할을 한다고 강조합니다. 미래는 LLM에 프롬프트를 던지는 것을 넘어, 에이전트가 효과적으로 작동하고, 학습하며, 확장할 수 있는 시스템을 설계하는 '에이전트 엔지니어링'의 시대가 될 것이라고 전망합니다.

## 인상적인 대목
-   "프롬프트 엔지니어링만으로는 충분하지 않습니다." (Prompt engineering is not enough.)
-   "에이전트는 스스로 확장되지 않습니다." (Agents don't scale themselves.)
-   "에이전트는 LLM 자체가 아니라, 오케스트레이션입니다." (The agent is not the LLM, the agent is the orchestration.)
-   "우리는 에이전트를 위한 운영 체제를 구축해야 합니다." (We need to build an operating system for agents.)

## 실무 적용 포인트
-   **에이전트 개발에 소프트웨어 엔지니어링 원칙 적용**: AI 에이전트를 개발할 때 일반적인 소프트웨어 개발처럼 모듈화, 버전 관리, 테스트 주도 개발(TDD) 등의 원칙을 적용하여 에이전트의 안정성과 유지보수성을 높여야 합니다.
-   **명시적인 피드백 루프 설계**: 에이전트의 최종 결과물에 대한 평가뿐만 아니라, 각 작업 단계에서 에이전트가 스스로 오류를 감지하고 수정할 수 있도록 구체적이고 즉각적인 피드백 메커니즘(예: 단위 테스트, 린터)을 시스템 내에 구축해야 합니다.
-   **복잡한 작업을 작은 단계로 분해**: 에이전트에게 복잡한 단일 작업을 지시하기보다, '계획(Planner)' 구성 요소를 통해 작업을 더 작고 관리 가능한 순차적 단계로 분해하여 에이전트가 체계적으로 문제를 해결하도록 유도해야 합니다.
-   **에이전트에게 외부 도구 제공**: 에이전트가 코드 실행 환경, 파일 시스템, 웹 검색 등 다양한 외부 도구와 상호작용하여 작업을 수행하고 스스로 결과를 검증할 수 있도록 도구 접근성을 설계해야 합니다.
