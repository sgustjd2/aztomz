# Stop Guessing Your vLLM Config: Benchmarking LLMs on Runpod - Chris Vela, Runpod

🔗 https://youtu.be/P_0_Th_ZzIg · 📅 2026-10-28 · 🎙 AI Engineer

## 한 줄 요약
Runpod의 Chris Vela는 vLLM 모델을 프로덕션 환경에 배포할 때 추측에 의존하지 않고, BenchPod라는 템플릿을 통해 모델 벤치마킹 및 최적화된 구성을 데이터 기반으로 빠르게 찾아내는 방법을 제시합니다.

## 발표자·소속
Chris Vela, Runpod의 Forward Deployed Engineer

## 핵심 주장
- **LLM 서빙 설정은 추측에 의존하는 경향이 있습니다.** 개발자들이 vLLM 버전, 모델 길이, 병렬 처리 등 다양한 설정값을 추측하여 사용하며, 이로 인해 프로덕션 환경에서 문제가 발생하거나 불필요한 최적화에 시간을 낭비하게 됩니다.
- **데이터 기반의 벤치마킹을 통해 최적의 구성을 찾아야 합니다.** 단순히 최신 모델이나 기본 설정을 사용하는 대신, 실제 워크로드에 맞는 GPU, vLLM 버전, KV 캐시 활용 등 다양한 요소를 벤치마킹하여 성능 지표(TTFT, TPoT, 처리량 등)를 확인하고 최적의 구성을 선택해야 합니다.
- **Runpod의 BenchPod는 모델 배포 및 벤치마킹 과정을 간소화합니다.** Docker 이미지 기반의 템플릿을 통해 vLLM 모델을 빠르게 배포하고, 실시간 메트릭 대시보드, 설정 관리, 자가 치유 기능, A/B 테스트 기능을 제공하여 R&D부터 프로덕션까지의 과정을 효율적으로 지원합니다.

## 세부 내용
발표자는 vLLM 모델을 프로덕션 환경에 배포할 때 겪는 어려움, 특히 "추측에 의존하는 설정" 문제를 지적합니다. 최신 모델을 사용하려 해도 적절한 vLLM 버전(예: Kimi K3는 CUDA 13.0 필요), 컨텍스트 윈도우 크기, 병렬 처리 방식 등을 알기 어렵고, 이는 결국 프로덕션에서 성능 문제로 이어진다는 것입니다.

Runpod는 GPU 대여를 간소화하는 클라우드 플랫폼으로, R&D부터 서버리스 프로덕션 워크플로우까지 지원합니다. 발표자는 이러한 문제를 해결하기 위해 BenchPod라는 템플릿을 소개합니다. BenchPod는 vLLM 위에 구축된 메트릭 시스템으로, 모델 벤치마킹을 매우 쉽게 만듭니다.

**BenchPod의 작동 방식:**
1.  **RunPod Pod 생성:** 8개의 GPU를 사용하는 Pod에 `skim-vllm-tag-image` (vLLM Docker 이미지)를 배포합니다.
2.  **부트 페이로드:** Python 스크립트가 패키지를 설치합니다.
3.  **Watchdog:** vLLM 설정을 적용하고 자가 치유 기능을 제공합니다.
4.  **vLLM 서버:** Kimi K3 모델(1M 컨텍스트, fp8 KV 캐시)을 서빙합니다.
5.  **대시보드 (Grafana):** GPU 메트릭, CUDA 버전, 에러 스캔, KV 캐시 사용량, 요청 수, 토큰 처리량, TTFT(Time To First Token), TPoT(Time Per Output Token), 프리픽스 캐시 히트율 등 실시간 및 저장된 메트릭을 제공합니다.
6.  **Nginx (FastAPI):** 모델 엔드포인트를 제공합니다.
7.  **영구 볼륨:** 모델 가중치 캐시를 저장합니다.

**데모 시연:**
발표자는 Runpod UI에서 BenchPod 템플릿을 선택하고, Kimi K3 모델을 배포하는 과정을 보여줍니다. 현재 B300 GPU는 품절 상태이지만, 이미 실행 중인 Kimi K3 인스턴스를 통해 대시보드를 시연합니다. 대시보드에는 GPU 활용률, 메모리, 디스크, CUDA 버전 등 상세한 호스트 메트릭이 표시됩니다. 특히, 지난 주말 GPU 장애가 발생했을 때 Watchdog이 자가 치유하여 서비스 중단 없이 복구된 사례를 언급합니다. Kimi K3의 콜드 스타트 시간은 약 9분으로 측정되었습니다.

**설정 비교:**
발표자는 "Serving" 탭에서 vLLM의 YAML 설정 파일을 직접 수정하여 `max-num-batched-tokens` 값을 변경하고 벤치마크를 실행하는 과정을 보여줍니다. 벤치마크 결과는 "Benchmarks" 탭에서 비교할 수 있습니다.
-   `max-num-batched-tokens`를 늘렸을 때:
    -   Median TTFT @ c1: -2.2% 감소 (216.59ms -> 211.83ms)
    -   Median TPoT @ c8: +3.7% 증가 (13.44ms -> 13.94ms)
    -   TTFT med @ c64 (ms): +19.4% 증가 (1966ms -> 2348ms)
    -   Output tok/s @ c64: +1.7% 증가 (2004 -> 2048)
    -   ITL p99 @ c64 (ms): -60% 더 부드러워짐 (195ms -> 78ms)
    이러한 수치를 통해 `max-num-batched-tokens`를 늘리면 전체 작업 완료 시간이 빨라지고, 특히 긴 작업의 경우 인터-토큰 지연 시간이 크게 줄어드는 것을 확인할 수 있습니다.

**Kimi K3 사용 이유:**
Kimi K3는 1M 토큰 디자인을 가지며, Runpod의 8xB300 GPU에서 실행 가능합니다. fp8 KV 캐시를 활용하여 더 많은 동시 장문 컨텍스트 세션을 처리할 수 있습니다. 발표자는 Kimi K3가 코딩 에이전트와 같은 장문 작업에 매우 효과적이라고 언급합니다.

## 실무 적용 포인트
-   **모델 배포 전 벤치마킹 필수:** 새로운 LLM 모델을 프로덕션에 적용하기 전에, BenchPod와 같은 도구를 활용하여 다양한 설정(vLLM 버전, 배치 토큰 수, 컨텍스트 길이 등)에 따른 TTFT, TPoT, 처리량, 지연 시간 등의 메트릭을 벤치마킹하여 최적의 구성을 찾아야 합니다.
-   **설정 변경의 영향 분석:** 단순히 기본 설정을 따르지 말고, 특정 설정 변경(예: `max-num-batched-tokens` 조정)이 모델 성능에 미치는 영향을 정량적으로 분석하여 실제 워크로드에 가장 적합한 구성을 선택해야 합니다.
-   **자가 치유 및 모니터링 시스템 구축:** 프로덕션 환경에서는 모델 서버의 자가 치유 기능(Watchdog)과 실시간 메트릭 대시보드(Grafana)를 통해 시스템 상태를 지속적으로 모니터링하고, 문제 발생 시 자동으로 복구되도록 하여 안정성을 확보해야 합니다.
-   **비용 효율성 고려:** 항상 최신 또는 가장 큰 모델이 최적의 선택은 아닐 수 있습니다. 실제 필요한 성능과 비용(예: B300 노드의 월 4만 달러 비용)을 고려하여 더 작은 모델이나 GPU로도 충분한지 벤치마킹을 통해 검증해야 합니다.
