# Why 99% Accurate Browser Agents Still Fail — Derek Meegan, Browserbase

🔗 https://youtu.be/5xi_S1f9sDU · 📅 2026-10-02 · 🎙 AI Engineer

## 한 줄 요약
브라우저 에이전트의 생산성을 높이기 위해서는 모델의 불확실성을 줄이고, 반복 가능한 작업을 도구와 스킬로 추상화하며, 인증과 같은 결정론적 프로세스를 분리하여 성능, 비용, 유지보수성을 최적화해야 합니다.

## 발표자·소속
Derek Meegan, Browserbase 소프트웨어 엔지니어

## 핵심 주장
- **데모와 생산 환경의 차이 이해:** 브라우저 에이전트 데모는 한 번의 실행으로 성공할 수 있지만, 생산 환경에서는 수천 번의 무인 실행이 필요하며 웹사이트 변경이나 모델 오류로 인해 실패할 수 있어 근본적으로 다릅니다.
- **모델 출력의 확률적 특성 관리:** 모델의 출력은 확률 분포이며, 가장 가능성 있는 동작을 선택하여 브라우저와 상호작용합니다. 브라우저의 복잡한 인터페이스(DOM, 스크린샷, 접근성 트리, 브라우저 상태, JS 런타임)를 효과적으로 다루는 것이 중요합니다.
- **비용 누적과 가치 실현의 불균형 해소:** 브라우저 에이전트의 각 단계는 비용과 실패 위험을 누적시키지만, 가치는 전체 작업이 완료될 때만 실현됩니다. 99%의 신뢰도를 가진 100단계 에이전트도 전체 성공률은 36%에 불과하므로, 부분적인 성공이 아닌 전체 트랜잭션 성공률을 높이는 데 집중해야 합니다.
- **성능, 비용, 유지보수성 최적화:** 에이전트의 가치는 고객을 위해 작업을 반복적으로, 동일한 방식으로 완료하는 능력에 있습니다. 이를 위해 성능(가치 전달), 비용(실행당 비용), 유지보수성(시간 경과에 따른 비용)의 세 가지 차원을 고려하여 에이전트를 설계하고 개선해야 합니다.
- **실제 시나리오를 통한 에이전트 구축 전략:** 건강보험 포털 로그인 및 EOB(Explanation of Benefits) 다운로드와 같은 실제 작업을 예시로, 복잡한 작업을 사용자 정의 도구로 캡슐화하고, OCR을 통한 결정론적 검증을 추가하며, 인증 로직을 모델에서 분리하고, 반복적인 경로를 스킬로 전환하는 단계별 접근 방식을 통해 에이전트의 견고성을 높일 수 있습니다.

## 세부 내용

발표는 브라우저 에이전트를 배포하는 것과 관련된 도전 과제를 다루며 시작됩니다. 데모는 한 번의 실행으로 성공할 수 있지만, 수천 번의 무인 실행이 필요한 생산 환경에서는 웹사이트 변경이나 모델의 '컨디션 난조'로 인해 실패할 수 있다는 점을 강조합니다.

발표는 네 부분으로 구성됩니다.
1.  **혼돈에 질서 부여하기 (에이전트가 웹과 상호작용하는 방식):**
    *   모델의 출력은 확률 분포로, 입력 토큰(페이지 상태, 목표, 이전 실행 기록)을 받아 가능한 동작의 분포를 탐색하고 가장 가능성 있는 동작을 제안합니다. 이 동작은 구조화된 도구 호출로 변환되어 브라우저에서 결정론적으로 실행됩니다.
    *   브라우저 인터페이스는 복잡하며, 네트워크 요청/응답, DOM(HTML), 스크린샷(렌더링된 픽셀), 접근성 트리(역할 및 이름), 브라우저 상태(저장소, 쿠키, URL 등) 및 JavaScript 런타임(임의의 JS 또는 CDP 실행)과 같은 여러 계층을 포함합니다.
    *   에이전트를 브라우저에 연결하는 세 가지 주요 전략이 있습니다: 1) 구조화된 표현(DOM + 접근성 트리), 2) 컴퓨터 비전(스크린샷 기반), 3) 에이전트 분리(임의의 JS 또는 CDP를 통한 동적 코드 실행). 대부분의 생산 시스템은 첫 번째 또는 두 번째, 혹은 이 둘의 조합을 사용합니다.
    *   에이전트의 '에이전트성(agenticness)' 스펙트럼이 존재합니다. '덜 에이전트적'인 것은 특정 작업을 위해 설계된 목적 지향적 흐름(예: 벤더 인보이스 지불)이며, '더 에이전트적'인 것은 임의의 요청에 대해 즉석에서 추론하는 방식(예: 항공편 체크인)입니다. 중간에는 브라우저를 구현 세부 사항으로 활용하여 페이지를 추출하거나 판단하는 간접적인 브라우저 궤적(예: 심층 연구 수행)이 있습니다.
    *   대규모 워크플로우는 일반적으로 트랜잭션적입니다. 즉, 단위 작업을 처음부터 끝까지 완료해야 합니다. 브라우저 에이전트는 이러한 트랜잭션에서 발생하는 모호성을 처리할 수 있는 유연한 실행 환경을 제공합니다.

2.  **불가능 정의하기 (브라우저 에이전트의 딜레마):**
    *   생산 환경에서 브라우저 에이전트가 어려운 이유는 '비용 누적은 연속적이고, 가치 실현은 종결적'이기 때문입니다. 각 단계마다 비용과 실패 위험이 누적되지만, 가치는 모든 단계가 완료될 때만 실현됩니다. 부분적인 성공은 인정되지 않습니다.
    *   예를 들어, 각 단계가 99% 신뢰할 수 있는 100단계 브라우저 에이전트는 전체 성공률이 36%에 불과합니다 (0.99^100 = 0.36). 이는 생산 환경에서 신뢰할 수 있는 결과를 제공하기에 충분하지 않습니다.
    *   하지만 이 수학적 계산이 전부는 아닙니다.

3.  **중요한 것 생각하기 (에이전트가 가치를 전달하는 방식):**
    *   에이전트의 가치 제안은 "고객을 위해 작업을 동일한 방식으로, 매번 완료하는 것"입니다.
    *   에이전트의 성공을 측정하는 세 가지 차원이 중요합니다 (중요도 순서):
        *   **성능:** 에이전트가 전달하는 가치. 성공은 작업 완료 후 남는 구체적인 아티팩트(예: 확인 이메일, 주문 ID, 시스템의 새 기록)로 정의됩니다.
        *   **비용:** 각 완료에 드는 비용(COGS). 모델 비용, 인프라 및 컴퓨팅, 통합 및 도구화가 포함됩니다. 모델 비용은 시간이 지남에 따라 감소하는 경향이 있습니다.
        *   **유지보수성:** 시간이 지남에 따라 작동 상태를 유지하는 데 드는 비용. 관찰 가능성, 개발자 시간(고장 수리), 모델 및 사이트 변경 시 재평가가 필요합니다.
    *   에이전트가 올바르게 작동하는 빈도를 측정하는 방법도 중요합니다. 개별 실행 성공률이 50%라도, 트랜잭션당 몇 번의 재시도를 허용하면(예: 4번) 성공률은 94%까지 올라갈 수 있습니다. 고객이 느끼는 성공률에 맞춰 최적화해야 합니다.
    *   작동하는 에이전트를 침식시키는 위험 요소는 다음과 같습니다: 환경의 반격(봇 방어, 레이아웃 변경), 작업 변경(기본 작업의 변화), 더 나은 방법의 출현(더 저렴하거나 간단한 접근 방식), 모델의 작업 이탈(실행마다 이상적인 궤적을 따르지 않음).

4.  **주주 가치 창출 (대규모 배포를 위한 구체적인 조치):**
    *   목표는 비용을 낮추고, 성능과 유지보수성을 높이는 것입니다. 건강보험 포털 에이전트 구축을 예시로 5단계의 진화 과정을 설명합니다:
        *   **V1: 에이전트만으로 시작:** 요청을 받아 모델과 도구 계층을 통해 브라우저에서 동작을 수행하는 최소한의 시스템.
        *   **V2: 취약한 시퀀스를 사용자 정의 도구로 래핑:** EOB 다운로드와 같이 프로그래밍 방식의 브라우저 상호작용과 클라우드 스토리지 파일 검색이 필요한 복잡한 시퀀스를 단일 도구 호출로 캡슐화합니다. 이는 모델이 즉석에서 결정을 내릴 필요성을 줄여줍니다.
        *   **V3: OCR로 결정론적 검증:** 에이전트가 OCR 도구를 사용하여 다운로드된 EOB에서 핵심 필드를 추출하고 이를 시스템 기록 데이터베이스와 비교하여 작업의 정확성을 결정론적으로 검증할 수 있도록 합니다.
        *   **V4: 모델의 손에서 인증을 분리:** 서버리스 인증 함수를 사용하여 로그인 및 MFA(다단계 인증)를 결정론적으로 수행하고, 인증된 브라우저를 에이전트에 전달합니다. 이 인증 함수는 동일한 포털의 다른 비즈니스 로직 궤적에서도 재사용할 수 있습니다. 이는 에이전트가 성공적으로 작업을 완료하는 데 필요한 단계 수를 줄여 비용을 낮추고 성능을 높이며 유지보수성을 향상시킵니다.
        *   **V5: 수렴된 경로를 스킬로 전환:** 에이전트를 충분히 실행하여 수렴된 '핵심 경로'를 식별한 다음, 이 경로를 '스킬'로 문서화합니다. 에이전트는 런타임에 이 스킬을 호출하여 핵심 경로를 더 잘 따르도록 유도하고, 모호성을 줄입니다. 스킬은 과거의 표준 운영 절차(SOP)와 유사하지만 에이전트를 위한 것입니다.

최종 결과는 서버리스 인증, 스킬 호출, 도구를 사용한 다운로드, 검증을 포함하는 복잡하지만 잘 정의된 시스템입니다. 이 시스템은 모델의 책임에서 불필요한 단계를 제거하여 유지보수성과 성능을 향상시키고, 브라우저 에이전트의 딜레마를 극복합니다.

발표는 "생산 환경에 오신 것을 환영합니다. 축하합니다, 이제 당신은 온콜입니다."라는 말로 마무리됩니다.

## 인상적인 대목
- "A demo != production" (데모는 생산 환경과 같지 않다)
- "Cost accumulation is continuous, Value realization is terminal" (비용 누적은 연속적이고, 가치 실현은 종결적이다)
- "No partial credit. The vast majority of web automations only pay off on total completion." (부분적인 성공은 없다. 대부분의 웹 자동화는 전체 완료 시에만 가치를 발휘한다.)
- "0.99 ^ 100 = 36%. 100 steps. Each 99% reliable. A near-perfect agent completes barely a third of the time." (100단계, 각 단계 99% 신뢰도. 거의 완벽한 에이전트도 겨우 3분의 1만 완료한다.)
- "profits = revenue - costs. Your agent should give you more than it takes." (이익 = 수익 - 비용. 당신의 에이전트는 가져가는 것보다 더 많이 주어야 한다.)
- "Welcome to production. Congrats, now you're on-call." (생산 환경에 오신 것을 환영합니다. 축하합니다, 이제 당신은 온콜입니다.)

## 실무 적용 포인트
- **트랜잭션 성공률 최적화:** 개별 실행 성공률보다는 재시도 메커니즘을 포함한 '트랜잭션당 성공률'을 핵심 지표로 삼아 고객 관점에서 에이전트의 신뢰도를 높여야 합니다.
- **결정론적 작업 분리 및 캡슐화:** 인증, 파일 다운로드, 데이터 검증과 같이 모호성이 적고 반복 가능한 작업은 모델의 책임에서 분리하여 사용자 정의 도구(custom tool)나 서버리스 함수(serverless function)로 캡슐화하여 에이전트의 복잡성을 줄이고 효율성을 높입니다.
- **OCR 기반 검증 도입:** 에이전트가 생성하거나 처리한 문서(예: PDF, 이미지)의 내용을 OCR 도구를 통해 추출하고, 이를 신뢰할 수 있는 시스템(예: 데이터베이스)과 비교하여 작업의 정확성을 결정론적으로 검증하는 메커니즘을 구축합니다.
- **'스킬'을 통한 핵심 경로 강화:** 에이전트가 반복적으로 수행하는 안정적인 작업 흐름을 '스킬'로 정의하고 문서화하여 에이전트 런타임에 제공합니다. 이는 에이전트가 예측 가능한 경로를 따르도록 유도하여 불확실성을 줄이고 성능을 향상시킵니다.
