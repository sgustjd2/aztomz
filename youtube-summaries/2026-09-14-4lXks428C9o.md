# We let an AI agent execute Bash and lived to talk about it — Sarah Sanders, PostHog

🔗 https://youtu.be/4lXks428C9o · 📅 2026-09-14 · 🎙 AI Engineer

## 한 줄 요약
PostHog의 AI 에이전트 '위자드'는 Bash 명령 실행을 통해 프로젝트 설정을 자동화하여 개발자 온보딩 시간을 단축하지만, 이 과정에서 발생할 수 있는 보안 위협에 대응하기 위해 '워록'이라는 결정론적 탐지 엔진과 '트리아지'라는 비결정론적 LLM 레이어를 포함한 다층 방어 체계를 구축했습니다.

## 발표자·소속
사라 샌더스(Sarah Sanders), PostHog 컨텍스트 엔지니어

## 핵심 주장
-   **AI 에이전트의 효율성**: PostHog의 '위자드' 에이전트는 복잡한 프로젝트 설정(SDK 설치, 이벤트 계측, 대시보드 생성)을 몇 시간에서 5~6분으로 단축하여 개발자 온보딩 경험을 혁신합니다.
-   **보안 위협 인식**: Bash 명령을 실행하는 에이전트의 특성상 잠재적인 '악성코드'와 유사한 보안 위험이 존재하며, 이는 개발자의 코드베이스에 직접적인 영향을 미칠 수 있습니다.
-   **다층 방어 전략**: 초기에는 시스템 프롬프트와 허용 목록에 의존했지만, 이후 결정론적 탐지 엔진인 '워록'과 비결정론적 LLM 기반의 '트리아지' 레이어를 추가하여 방어 깊이(Defense in Depth)를 강화했습니다.
-   **결정론적 보안의 중요성**: 보안 규칙은 결정론적으로 강제되어야 하며, 프롬프트는 지시 역할만 해야 합니다. 모델의 비결정적 특성에 보안을 의존하는 것은 위험합니다.
-   **공급망 입력 스캔**: 에이전트에 공급되는 모든 입력(사용자 입력, 코드베이스, 문서 등)은 잠재적인 위협이 될 수 있으므로, 소스와 사용 시점 모두에서 철저히 스캔해야 합니다.

## 세부 내용

사라 샌더스는 PostHog의 '위자드'라는 AI 에이전트를 소개하며 발표를 시작했습니다. 위자드는 개발자의 코드베이스를 분석하여 적절한 SDK를 설치하고, 이벤트를 계측하며, 대시보드를 설정하는 CLI 도구입니다. 이 과정은 과거에 1~2시간이 걸리던 작업을 5~6분으로 단축시킵니다. 발표자는 위자드가 개발자에게 강력한 경험을 제공하지만, Bash 명령을 실행하는 에이전트의 특성상 보안에 대한 우려가 제기되었다고 설명했습니다.

위자드의 아키텍처는 일반적인 에이전트와 유사하게 모델, 시스템 프롬프트, 도구를 포함합니다. 하지만 PostHog 팀은 자체 개발한 컨텍스트 엔진(일명 '위자드의 두뇌'), 커스텀 TUI 인터페이스, 그리고 보안 스캐너인 '워록'을 추가했습니다. 발표자는 Bash 명령을 실행하는 에이전트가 환경 변수 접근, SSH 실행, 외부 서버로 데이터 전송 등 악성코드와 유사한 기능을 수행할 수 있음을 지적하며, 이러한 에이전트를 구축할 때 보안에 대한 깊은 고민이 필요하다고 강조했습니다.

초기 보안 체계는 '레이어 0: 시스템 프롬프트', '레이어 1: 허용 목록', '레이어 2: 정규식 스캐너'로 구성되었습니다. 시스템 프롬프트는 PII(개인 식별 정보) 공유 금지 등 에이전트의 행동을 '제안'하는 역할이었으나, 이는 실제 보안 조치가 아니었습니다. 허용 목록은 Bash가 특정 도구만 실행하도록 제한했지만, 여전히 우려가 있었습니다. 정규식 스캐너는 에이전트의 입력 및 출력 컨텍스트에서 위협 패턴을 찾으려 했으나, '매우 해킹스러운(extremely hacky)' 수준이었다고 인정했습니다.

보안 감사 결과, 몇 가지 중요한 교훈을 얻었습니다. 첫째, "Start with"는 "is"가 아닙니다. 즉, 허용 목록이 특정 명령어로 시작하는 것을 허용한다고 해서 그 명령어가 안전하다고 맹신해서는 안 됩니다. 둘째, 두 가지 안전한 것이 하나의 열린 문을 만들 수 있습니다. 개별적으로는 안전해 보이는 두 가지 기능이 결합될 때 취약점이 발생할 수 있다는 것입니다. 셋째, 허용된 도구도 개발자가 작성하지 않은 코드를 실행할 수 있습니다. 예를 들어, 오염된 설정 파일은 신뢰하는 도구를 통해 임의의 코드 실행으로 이어질 수 있습니다. 가장 큰 위협은 에이전트의 '두뇌'에 공급되는 '도움이 되는 것처럼 보이는' 컨텍스트 자체였습니다.

이러한 위협에 대응하기 위해 '워록'이 개발되었습니다. 워록은 YARA 규칙을 기반으로 하는 결정론적 탐지 엔진으로, OWASP Top 10과 같은 위협 패턴에 맞춰 구축되었습니다. 워록은 문제를 '탐지'할 뿐, 직접 '조치'하지는 않습니다. 탐지된 문제에 대한 조치(차단 등)는 개발자의 결정에 따릅니다. 워록은 서브 에이전트가 비밀 정보를 유출하려 하거나, PII를 이벤트에 포함시키거나, '이전 지시를 무시하라'와 같은 주입된 명령어를 탐지했습니다. 또한, 재귀적 삭제나 덮어쓰기 같은 위험한 행동을 무심코 실행하는 '지나치게 자신감 있는' 에이전트의 행동도 포착했습니다.

발표자는 결정론적인 보안 도구에 비결정적인 LLM 레이어를 추가하는 것에 대한 고민을 공유했습니다. LLM을 '보안관'으로 둘 것인가, 아니면 '조언자'로 둘 것인가의 문제였습니다. 최종적으로 LLM은 '트리아지' 레이어로서 오탐(false positives)을 분류하고 노이즈를 줄이는 역할만 하도록 결정했습니다. 즉, 탐지 및 강제(enforcement)는 결정론적이고 기계적인 방식으로 유지되며, LLM은 문제가 차단되지 않았을 경우에만 사후에 개입하여 노이즈를 제거하는 역할을 합니다.

현재 PostHog의 방어 깊이(Defense in Depth)는 다음과 같습니다:
-   **프롬프트**: 오직 에이전트의 방향을 '조정'하는 역할만 합니다.
-   **샌드박스**: 쓰기 권한이 작업 디렉토리와 임시 디렉토리로 제한됩니다.
-   **게이트**: 기본적으로 모든 것을 '거부'합니다.
-   **볼트**: 비밀 정보가 모델에 직접 도달하지 않도록 합니다.
-   **워록**: 결정론적인 위협 탐지를 수행합니다.
-   **트리아지**: 노이즈 제거 역할만 합니다.
-   **텔레메트리**: 전체 프로세스를 모니터링하여 모든 것을 파악합니다.

발표자는 이러한 다층 방어 체계가 각 레이어가 자신의 역할에 충실함으로써 견고한 보안을 제공한다고 결론지었습니다.

## 인상적인 대목

-   "이것은 악성코드처럼 생겼습니다." (It sounds kind of malware-shaped.)

-   "위험한 입력은 당신이 공급하는 것입니다." (The dangerous input is what you feed it)
-   "만약 결정론적으로 강제되지 않는다면, 그것은 강제되지 않는 것입니다. 프롬프트 규칙은 스티커 메모에 불과합니다." (If it isn't enforced deterministically, it isn't enforced. Prompt rules are a sticky note.)

## 실무 적용 포인트
-   **결정론적 보안 계층 분리**: 에이전트의 핵심 보안 기능(예: 명령 실행 허용/거부)은 예측 가능하고 결정론적인 방식으로 구현해야 합니다. LLM은 판단이나 조언 역할에 사용하되, 직접적인 강제 역할은 피해야 합니다.
-   **공급망 전체 스캔**: 에이전트에 입력되는 모든 데이터(코드, 설정 파일, 문서, 사용자 프롬프트 등)는 잠재적인 위협이 될 수 있으므로, 데이터의 소스(예: Git 리포지토리)와 에이전트가 데이터를 사용하는 시점 모두에서 보안 스캔을 수행해야 합니다.
-   **방어 깊이(Defense in Depth) 전략 채택**: 단일 보안 메커니즘에 의존하지 않고, 샌드박스, 허용 목록, 비밀 관리(Vault), 결정론적 탐지(Warlock), 노이즈 제거(Triage), 그리고 상세한 텔레메트리(Telemetry)와 같은 여러 계층의 방어를 구축하여 전체 시스템의 견고성을 높여야 합니다.
-   **명확한 규칙 및 테스트**: 보안 규칙은 명확하고 구체적이어야 하며, 오탐을 줄이기 위해 긍정적 및 부정적 테스트 케이스를 포함하여 규칙의 효과를 검증해야 합니다.
