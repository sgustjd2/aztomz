# Your Team's Agents Are All Shipping to the Same Code at Once - Patrick Debois, Tessl

🔗 https://youtu.be/fTUinMqA1XQ · 📅 2026-11-10 · 🎙 AI Engineer

## 한 줄 요약
AI 에이전트가 소프트웨어 개발에 통합되면서 발생하는 동시성 문제를 해결하기 위해, 코드와 의사결정 모두에서 동시성을 지원하는 '멀티플레이어 소프트웨어 팩토리'로의 전환이 필요하며, 이는 사람과 에이전트가 함께 일하는 새로운 개발 패러다임을 요구한다.

## 발표자·소속
패트릭 드부아 (Patrick Debois), 테슬 (Tessl)

## 핵심 주장
-   **연속 전달(Continuous Delivery)의 한계와 동시 전달(Concurrent Delivery)의 필요성:** 기존의 연속 전달 파이프라인은 빌드, 테스트는 병렬로 진행되지만, 메인 브랜치로의 통합은 여전히 한 번에 하나의 변경만 허용하는 직렬 지점(serial point)을 가지고 있어, AI 에이전트가 생성하는 수많은 변경 사항을 처리하는 데 병목 현상이 발생한다. 따라서 충돌이 예외가 아닌 일상이 되는 동시 전달을 위해 시스템을 설계해야 한다.
-   **에이전트 간 작업 분할 및 충돌 관리:** 에이전트들이 코드를 변경할 때 발생하는 병합 충돌과 리베이스 지연 문제를 해결하기 위해, 작업 단위를 에픽, 모듈, 파일, 함수, 심지어 키스트로크 수준으로 세분화하여 분할하고, 에이전트가 작업을 시작하기 전에 미리 선점하며, 충돌 발생 시 에이전트가 스스로 계획을 재조정하거나 재실행하여 수동 병합을 최소화해야 한다.
-   **에이전트의 '현실' 포크 및 의도 확인:** 에이전트가 독립적으로 작업할 수 있도록 공유된 환경(실행 중인 머신, API, 데이터베이스, 테스트 데이터 등)의 스냅샷을 생성하여 각 에이전트에게 자신만의 '현실' 뷰를 제공한다. 또한, 단순한 코드 충돌을 넘어 에이전트의 변경 의도를 확인하여, 코드는 병합 가능하지만 의도상 충돌하는 문제를 방지해야 한다.
-   **사람과 에이전트의 협업을 위한 '하나의 보드' 개념:** 에이전트가 사람의 개입을 최소화하면서도 필요한 경우 적절한 질문을 던지고, 사람은 에이전트가 제시하는 선택지 중에서 의사결정을 내리는 방식으로 협업한다. 이 과정에서 모든 의사결정은 팀의 원장(ledger)에 기록되어 투명성과 추적성을 확보하고, 에이전트가 이를 학습하여 루틴한 작업을 자동화하는 데 기여한다.
-   **위험 기반 코드 리뷰 및 컨텍스트 공유:** 모든 변경 사항을 사람이 일일이 검토하는 대신, 변경의 위험도에 따라 자동화된 검토(낮은 위험)부터 사람의 승인(치명적인 위험)까지 다양한 수준의 리뷰를 적용한다. 또한, 에이전트가 각 팀원(엔지니어, 지원, 영업, 마케팅 등)의 역할과 언어에 맞춰 변경 사항의 컨텍스트를 업데이트하고 전달하여 정보 격차를 해소한다.

## 세부 내용

발표는 '멀티플레이어 소프트웨어 팩토리'라는 주제로, AI 에이전트가 소프트웨어 개발 파이프라인에 통합되면서 발생하는 문제점과 해결책을 제시한다.

**연속 전달의 현주소**
기존의 연속 전달(Continuous Delivery) 파이프라인은 여러 개발자가 병렬로 빌드 및 테스트를 수행하지만, 메인 브랜치로의 병합(merge to main)은 한 번에 하나의 변경만 허용하는 직렬 지점(serial point)이 존재한다. 이는 자동화와 견고한 전달에 기여했지만, 에이전트가 도입되면서 새로운 병목 현상을 야기한다.

**솔로 팩토리의 등장**
개발자들은 개인 노트북이나 시스템에서 여러 코딩 에이전트를 활용하는 '솔로 팩토리'를 구축하고 있다. 이 경우 개발자 자신이 병합 큐와 메모리 역할을 하며, 에이전트의 의도를 모두 알고 있어 충돌이 드물고 직접 해결한다. 하지만 팀 단위로 확장되면 문제가 발생한다.

**싱글 플레이어, 공유, 멀티플레이어**
개발 환경은 세 가지 단계로 진화한다.
1.  **싱글 플레이어:** 개발자와 에이전트가 개인 환경에서 작업하는 '솔로 팩토리'.
2.  **공유:** 사람들이 서로의 설정(스킬, 규칙, 플레이북)을 재사용하지만, 각자 독립적으로 작업한다.
3.  **멀티플레이어:** 여러 사람과 에이전트가 하나의 실행 중인 작업, 공유된 코드베이스, 팀 경계를 넘어 적극적으로 협력한다.

**발표의 구성**
발표는 두 가지 주요 부분으로 나뉜다.
1.  **에이전트와 함께: 하나의 메인(One main).** 모든 에이전트가 하나의 코드베이스에서 팀처럼 협력하는 방식. (분할 -> 선점 -> 격리 -> 적응 -> 재실행 -> 읽기 확인 -> 검증)
2.  **사람과 에이전트: 하나의 보드(One board).** 사람들이 에이전트가 수행하는 작업을 계획, 지시, 검토, 인계하는 방식. (시작 -> 참여 -> 결정 -> 검토 -> 지시)

**에이전트와 함께: 하나의 메인**
*   **'불 뿜는 호스(firehose)'의 도래:** AI 에이전트가 활성화되면, Anthropic의 사례처럼 하루에 병합되는 변경 사항이 2,500개에서 30,000개 이상으로 급증한다. 이러한 가속화는 모든 곳에서 병목 현상을 노출시킨다.
*   **끝없는 병합 충돌:** 에이전트가 동일한 코드 라인을 변경하면 병합이 중단되고 사람이 개입해야 한다. 또한, 에이전트들이 서로 상충되는 목표를 가지고 작업할 경우 '영역 싸움(turf wars)'이 발생하여 한 에이전트가 변경한 것을 다른 에이전트가 되돌리는 상황이 반복된다.
*   **리베이스, CI 재실행, 반복:** 하나의 PR이 메인에 병합되면 다른 모든 PR은 오래된(stale) 상태가 되어 리베이스하고 CI를 재실행해야 한다. 이는 CI 시스템을 매우 느리게 만들고 비용을 증가시킨다.
*   **PR 큐의 증가:** 기능 티켓 외에도 에이전트 충돌 해결 및 팩토리 유지보수(스킬, 루프 개선) 작업으로 인해 PR 큐가 계속해서 늘어난다. "병렬 에이전트는 리뷰어를 추가하지 않는다. 그들은 큐를 추가한다."
*   **패러다임 전환:** 연속 전달에서는 충돌이 '예외'였지만, 동시 전달에서는 충돌이 '일상'이 된다. 따라서 이를 염두에 두고 시스템을 설계해야 한다.

**에이전트가 작업을 분할하여 엉킴을 방지하는 방법**
에이전트들은 작업을 분할하여 충돌 가능성을 줄인다.
*   **에픽:** 큰 작업 단위를 정의한다.
*   **모듈:** 코드베이스를 모듈 단위로 분할하여 에이전트에게 할당한다.
*   **임포트 그래프:** 코드의 의존성 그래프를 기반으로 작업을 분할한다.
*   **파일:** 특정 파일에 대한 작업을 할당한다.
*   **함수:** 특정 함수에 대한 작업을 할당한다.
*   **키스트로크:** 가장 세분화된 단위로, 특정 코드 라인 변경에 집중한다.
이러한 분할은 에이전트가 작업을 시작하기 전에 계획 단계에서 이루어지며, 사람이 승인한다.

**작업을 작성하기 전에 선점하기**
에이전트는 작업을 시작하기 전에 해당 작업을 선점(claim)한다. 이는 중복 PR을 방지하고, 에이전트가 변경할 파일 목록을 미리 공개하여 다른 에이전트나 사람이 잠재적인 충돌을 미리 감지할 수 있도록 한다.

**Git 브랜치가 코드를 포크하듯, 에이전트는 현실의 뷰를 포크한다.**
각 에이전트에게는 공유된 세계(실행 중인 머신, API, 데이터베이스)의 스냅샷이 제공되어 자신만의 독립적인 환경에서 작업할 수 있다. 이는 외부 세계의 영향을 받지 않고 작업을 수행할 수 있게 한다.

**두 에이전트가 충돌할 때, 멈추는 대신 재계획한다.**
에이전트 간 충돌이 발생하면, 단순히 기다리거나 작업을 버리고 재시도하는 대신, 에이전트가 계획을 수정하거나 작업 범위를 재협상하여 해결한다.

**충돌 시 에이전트가 재실행하여 수동 병합을 없앤다.**
에이전트가 코드 충돌을 감지하면, 사람이 수동으로 병합하는 대신 에이전트가 새로운 메인 브랜치에서 작업을 재실행한다. 에이전트는 함수 단위 병합이나 변경 의도 병합과 같은 더 스마트한 병합 전략을 사용하며, 심지어 잠재적인 충돌을 미리 감지하여 회피할 수도 있다.

**에이전트는 단순한 충돌이 아닌 의도를 확인한다.**
에이전트는 코드 변경이 기술적으로 충돌하지 않더라도, 변경의 의도(예: 금액 단위를 달러에서 센트로 변경)가 다른 에이전트의 가정(예: 금액이 달러라고 가정)과 상충될 경우 이를 감지하고 경고하거나 PR을 수정한다.

**병합 트레인은 병렬로 테스트하여 메인이 계속 움직이게 한다.**
'투기적 큐(speculative queue)'를 사용하여 여러 PR 조합을 병렬로 테스트한다. 만약 한 PR 조합이 실패하더라도 다른 호환 가능한 PR 조합은 계속해서 메인에 병합될 수 있어, 메인 브랜치의 흐름이 끊기지 않는다.

**에이전트 아래에서 새로운 인프라 계층이 성장하고 있다.**
코딩 에이전트를 위한 새로운 인프라 계층이 구축되고 있다. 이는 소스 제어, CI, 리베이스, 병합, 티켓 관리 등 개발 프로세스의 다양한 측면을 지원하며, 여러 개발자가 동시에 작업하는 환경에 최적화되어 있다.

**사람과 에이전트: 하나의 보드**
*   **에이전트가 채팅에 참여한다. 상태는 티켓에 기록된다.** 에이전트는 슬랙과 같은 채팅 채널에 참여하여 사람들의 대화에서 단서를 얻고, 제약 조건과 의사결정을 바탕으로 티켓을 정제한다. 이는 에이전트가 단순히 프롬프트에 반응하는 것이 아니라, 대화에 능동적으로 참여하여 작업의 컨텍스트를 이해하도록 돕는다.
*   **에이전트가 세 가지 질문을 던져, 모든 에이전트가 하나의 목표를 향해 빌드한다.** 에이전트는 작업을 시작하기 전에 '누구를 위한 것인가?', '어떤 기간인가?', '환불은 어떻게 처리하는가?'와 같은 핵심 질문을 던져 요구사항을 명확히 한다. 이 질문에 대한 답변은 티켓에 체크리스트 형태로 기록되어 에이전트들이 추측이 아닌 명확한 목표를 가지고 작업하게 한다.
*   **문제를 가진 누구든 뛰어들어 빌드할 수 있다.** 과거에는 비기술 직군(영업, 마케팅, 지원)이 엔지니어링에 티켓을 제출하고 몇 주를 기다려야 했다. 이제는 멀티플레이어 팩토리 덕분에 문제를 가진 사람이 직접 에이전트와 협력하여 기능을 실험하고, 개선하고, 심지어 빌드할 수 있으며, 엔지니어링은 이를 검토하는 흐름으로 바뀐다.
*   **에이전트가 불확실할 때, 사람이 실행 중인 작업에 참여한다.** 에이전트가 작업 수행 중 막히거나 불확실한 상황에 처하면, 사람이 에이전트의 코딩 IDE에 직접 뛰어들어 컨텍스트를 파악하고 에이전트를 돕는다. 사람이 올바른 선택을 하거나 실험을 마치면, 에이전트에게 다시 작업을 인계하여 계속 진행하게 한다.
*   **실제 의사결정만 사람에게 옵션으로 제시된다.** 에이전트는 대부분의 사소한 질문을 스스로 해결하고, 실제 중요한 의사결정만 사람에게 여러 옵션 형태로 제시한다. 이는 사람이 에이전트에게 일일이 지시하는 수고를 덜어준다.
*   **모든 의사결정은 팀의 원장(ledger)에 기록된다.** 사람이 내린 모든 의사결정은 변경 불가능한 원장(decision log)에 기록된다. 이는 에이전트와 사람이 과거의 의사결정을 추적하고, 새로운 에이전트가 학습하며, 컨텍스트를 공유하는 데 활용된다.
*   **리뷰를 읽기 쉽게 만든다: 작은 조각들, 증거와 함께.** 47개 파일, 2,881줄의 대규모 PR은 사람이 리뷰하기 어렵다. 대신, 작은 PR 단위로 쪼개고, 각 PR에 논리 테스트, UI 미리보기, 비디오 등 변경에 대한 증거를 첨부하여 리뷰어가 빠르게 이해하고 검토할 수 있도록 돕는다.
*   **위험이 있는 곳에 사람의 리뷰를 집중한다.** 팩토리는 모든 변경 사항을 위험도에 따라 분류한다. 낮은 위험(문서 변경)은 자동으로 배포하고, 중간 위험(카나리 배포)은 추가 검사를 거치며, 높은 위험은 더 많은 검증을 요구하고, '치명적인(critical)' 변경(인증, 결제)만 사람이 직접 승인하도록 한다. 이는 위험을 줄이는 동시에 리뷰 효율성을 높인다.
*   **모든 사람의 컨텍스트를 그들의 언어로 업데이트한다.** 멀티플레이어 팩토리에서는 코드가 너무 많이 생성되어 각 부서(엔지니어, 지원, 영업, 마케팅)가 변경 사항을 따라잡기 어렵다. '리더 에이전트(reader agent)'는 각 부서의 청중과 관심사에 맞춰 변경 사항을 그들의 언어로 번역하여 전달함으로써 정보 격차를 해소한다.

**종합: 루틴을 위한 스킬, 예외를 위한 사람**
대부분의 루틴한 작업은 에이전트가 소유한 스킬(UI 패턴, 인증 규칙 등)을 통해 자동화된다. 개인과 에이전트가 필요한 스킬을 활용하여 작업을 수행하며, 사람이 개입할 필요가 없다. 반면, 새로운 스킬이 필요하거나, 다른 팀의 약속과 충돌하거나, 치명적인 변경인 경우와 같은 '예외' 상황에만 사람이 개입한다. 모든 답변은 기록되고, 반복되는 답변은 테스트된 스킬로 승격되어 에이전트가 활용한다.

**일부 팀은 이제 제품이 아닌 팩토리를 구축한다.**
이제 팀의 일부는 제품(기능, 버그 수정)이 아닌 '팩토리' 자체를 구축하는 데 집중한다. 팩토리 작업에는 스킬 개발, 리뷰 정책, 워크플로우 개선 등이 포함된다. 개인적인 프롬프트가 팀 규칙으로 승격되고, 이를 소유하고 유지보수하는 팀이 생기며, 팩토리 팀은 예산과 함께 플랫폼 팀처럼 운영된다.

**결론: 대비하라. 당신이 판단자다.**
과거에는 개발자가 잠금(lock), 병합 큐(merge queue), 메모리(memory) 역할을 했다. 이제 팩토리가 이 역할을 대신하며, 개발자는 '판단자(judgment)'가 된다. 병목 현상은 항상 이동하므로, 이 변화의 흐름을 즐겨야 한다.

**다음 단계: 개인 에이전트**
현재 OpenClaw, OpenAI Dots, Claude Duet과 같은 개인 에이전트가 이미 존재한다. 미래에는 에이전트가 '당신'으로서 리뷰 요청에 응답하고, 당신의 이름으로 위험을 수용하며, 다른 에이전트와 인계를 협상할 것이다. "그것은 모든 규모의 작업을 수행하고, 당신이 자리를 비운 동안 계속 작업하며, 중요할 때 당신의 승인을 기다린다."

## 인상적인 대목
-   "Understanding emerges from the interaction, not from a well-organized folder." (이해는 잘 정리된 폴더에서 나오는 것이 아니라 상호작용에서 나온다.)
-   "That level of acceleration exposes bottlenecks everywhere." (그러한 수준의 가속화는 모든 곳에서 병목 현상을 노출시킨다.)
-   "Parallel agents do not add reviewers. They add queue." (병렬 에이전트는 리뷰어를 추가하지 않는다. 그들은 큐를 추가한다.)
-   "Pipeline delivery: conflict is the exception -> Concurrent delivery: conflict becomes routine. So design for it." (파이프라인 전달: 충돌은 예외 -> 동시 전달: 충돌은 일상. 그러니 이를 위해 설계하라.)
-   "The code is the easy part. Fork the machine, branch the data, twin the APIs, keep context private." (코드는 쉬운 부분이다. 머신을 포크하고, 데이터를 브랜치하고, API를 트윈하고, 컨텍스트를 비공개로 유지하라.)
-   "They work in parallel, but my attention doesn't." (그들은 병렬로 일하지만, 나의 주의력은 그렇지 않다.)
-   "Support asks in Slack what shipped, then leadership schedules more meetings to stay informed." (지원팀은 슬랙에서 무엇이 배포되었는지 묻고, 리더십은 정보를 얻기 위해 더 많은 회의를 잡는다.)
-   "Skills for the routine. People for the exceptions." (루틴을 위한 스킬. 예외를 위한 사람.)
-   "You were the lock, the merge queue and the memory. Now the factory is. You're the judgment." (당신은 잠금, 병합 큐, 그리고 메모리였다. 이제 팩토리가 그렇다. 당신은 판단자다.)

## 실무 적용 포인트
-   **작업 단위를 세분화하고 에이전트에게 명확히 할당:** 코드베이스를 모듈, 파일, 함수 단위로 나누고, 에이전트가 작업을 시작하기 전에 어떤 영역을 담당할지 명확히 선점하도록 하여 충돌 가능성을 줄인다.
-   **에이전트의 작업 환경 격리 및 의도 확인:** 각 에이전트에게 독립적인 실행 환경(스냅샷, 디지털 트윈)을 제공하여 외부 영향 없이 작업하게 하고, 코드 변경뿐 아니라 변경의 '의도'까지 확인하여 잠재적인 논리적 충돌을 미리 방지하는 시스템을 구축한다.
-   **위험 기반의 자동화된 리뷰 프로세스 도입:** 모든 PR에 동일한 수준의 사람 리뷰를 적용하는 대신, 변경의 위험도(예: 문서 변경, 기능 플래그, 결제 로직)에 따라 자동화된 검증, 카나리 배포, 사람의 승인 등 차등적인 리뷰 전략을 적용하여 효율성을 높인다.
-   **에이전트를 활용한 의사결정 지원 및 지식 공유:** 에이전트가 사람의 대화에 참여하여 요구사항을 명확히 하고, 중요한 의사결정 시 여러 옵션을 제시하도록 훈련시킨다. 또한, 모든 의사결정을 기록하는 공유 원장(ledger)을 구축하여 팀의 지식 기반을 강화하고 에이전트의 학습 데이터로 활용한다.
