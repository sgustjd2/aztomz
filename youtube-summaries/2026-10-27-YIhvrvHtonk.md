# We Kept Rebuilding Our AI Agent. Here's What Survived - Fuad Ali, Arize AI

🔗 https://youtu.be/YIhvrvHtonk · 📅 2026-10-27 · 🎙 AI Engineer

## 한 줄 요약
Arize AI는 2년간 프로덕션 AI 에이전트 'Alyx'를 개발하며 모델의 발전과 함께 에이전트의 '하네스 코드'를 지속적으로 재구축하고 최적화했으며, 이 과정에서 계획, 턴 종료, 메모리 관리, 에이전트 구조, 기본 모델 선택, 테스트 방식 등 다양한 핵심 결정들을 내렸고, 여전히 인간의 판단이 필요한 영역이 존재함을 발견했습니다.

## 발표자·소속
푸아드 알리 (Fuad Ali), Arize AI 제품 담당 (Product, Arize)

## 핵심 주장
- **하네스 코드의 중요성**: 모델 자체의 발전 외에도, 에이전트의 계획, 턴 종료 규칙, 메모리 관리, 안전 장치 등 대부분의 핵심 로직은 '하네스 코드'로 구축하고 재구축해야 하며, 이는 엔지니어링의 중요한 영역입니다.
- **계획 소유권의 진화**: 초기에는 모델이 계획을 직접 관리했으나, 모델이 계획 수립에 너무 많은 리소스를 소모하는 문제를 겪은 후, 계획 관리와 상태 추적을 하네스 코드로 옮겨 모델의 효율성을 높였습니다.
- **메모리 관리의 실용성**: 장기 메모리 구현에 있어 복잡한 지식 그래프나 벡터 검색 대신, 사용자당 8,000자 제한의 간단한 마크다운 파일을 사용하는 것이 더 효과적이고 감사(audit)하기 쉬웠습니다.
- **에이전트 구조의 단순화**: 여러 전문 에이전트(specialist agents)로 시작했으나, 결국 하나의 에이전트가 필요에 따라 스킬과 도구를 로드하는 방식으로 통합하여 복잡성을 줄였습니다.
- **최신 모델이 항상 최선은 아님**: 새로운 모델이 출시될 때마다 무조건 기본 모델로 채택하는 것이 아니라, 특정 작업에 가장 빠르고 충분히 좋은 모델을 선택하고, 경우에 따라서는 에이전트 루프 자체가 필요 없는 경우도 있음을 확인했습니다.
- **인간 중심의 디버깅 및 평가**: AI 에이전트의 버그는 명시적인 오류로 나타나기보다 미묘한 성능 저하로 나타나는 경우가 많으므로, 실제 프로덕션 세션을 테스트 케이스로 활용하고 인간의 판단(골드 라벨링)을 통해 에이전트의 성능을 평가하는 것이 필수적입니다.

## 세부 내용

발표는 Arize AI의 프로덕션 에이전트 'Alyx'를 2년간 개발하며 얻은 교훈에 초점을 맞췄습니다. Alyx는 Arize AX 내의 에이전트로, 트레이스를 읽고, 발견 사항을 테스트로 전환하며, 다단계 작업을 계획하고 실행합니다. 초기 프로토타입(2023년 말, GPT-3.5 모델 사용)은 "50% 환각, 50% 유용"한 수준이었으나, 현재는 훨씬 발전했습니다.

**Alyx 개발 타임라인:**
- **2023년 말 (프로토타입)**: GPT-3.5 모델 기반. 수학 계산 등은 코드에서 처리.
- **2024년 7월 (코파일럿 출시)**: 스킬 세트 위에 라우터 구조. 의사결정 트리를 사용.
- **2025년 8월 (재작성)**: 의사결정 트리를 없애고, 반복적인 도구 호출(iterative tool calling)과 투두(todo) 도구 도입.
- **2026년 2월 (Alyx 2.0)**: 계획 기능 출시. Claude Sonnet 4.5가 기본 모델이 됨.
- **2026년 6월 (One Alyx)**: 전문 에이전트들을 하나로 통합. 필요에 따라 스킬 로드.
- **2026년 9월 (메모리)**: 사용자별 장기 메모리 기능 도입. 백그라운드에서 기록.

**하네스 코드의 패턴:**
발표자는 모델 자체의 발전과 별개로, 에이전트의 '하네스 코드'를 구축하고 재구축하는 것이 중요하다고 강조했습니다. 계획, 턴 종료 규칙, 메모리, 가드레일 등은 모두 하네스 코드의 영역입니다. Arize는 에이전트 프레임워크를 사용하지 않고, 모델 호출에는 LiteLLM을 사용하며, 루프, 계획, 중지 규칙, 메모리 등을 직접 구현했습니다.

**주요 결정 사항:**

1.  **누가 계획을 소유하는가?**
    *   초기에는 모델에게 투두(todo) 도구를 주어 계획을 직접 작성하고 업데이트하게 했으나, 모델이 계획 업데이트에 너무 많은 LLM 호출(27회)을 사용하고, 여러 도구 호출 후 집중력을 잃는 문제가 발생했습니다.
    *   해결책: 계획 관리를 하네스 코드로 옮겼습니다. 하네스가 계획 상태를 유지하고, 매 호출마다 모델에게 계획을 메시지로 렌더링하여 전달했습니다. 현재는 투두 도구 없이 계획과 상태를 인라인으로 관리하며, 하네스가 상태와 완료 여부를 추적합니다.
    *   교훈: "하네스가 추론할 수 있다면, 모델이 그것을 유지할 필요는 없다."

2.  **무엇이 턴을 종료하는가?**
    *   초기에는 도구 호출이 없는 텍스트 출력을 턴 종료로 간주했으나, 모델이 다음 턴에 호출할 스텝을 미리 알리는 경우 문제가 발생했습니다.
    *   해결책: 하네스가 턴 종료를 강제하는 게이트를 도입했습니다.
        *   계획 항목이 열려 있을 때 명시적인 `finish` 호출이 세 번까지 실패하면 다시 시도.
        *   모델이 도구 호출을 일반 텍스트로 입력하면 힌트 제공.
        *   진행이 없을 경우 턴 종료.
        *   반복 제한 직전에 경고 후 강제 종료.
    *   교훈: "프롬프트는 제안이고, 코드는 제약이다."

3.  **메모리 관리 (네 가지 문제)**
    *   **하나의 도구 결과**: 너무 큰 도구 결과(10MB+ JSON)는 컨텍스트 창을 초과.
        *   해결책: 미리보기(preview)와 ID를 제공하고, 전체 복사본은 서버 측에 저장하여 `jq` 같은 도구로 쿼리하게 함.
    *   **하나의 턴**: 에이전트의 자체 궤적이 컨텍스트 창을 초과.
        *   해결책: 토큰 임계값을 넘으면 하네스가 모델에게 체크포인트를 작성하게 하고, 이전 내용을 삭제.
    *   **하나의 세션**: 대화가 길어지면서 히스토리가 너무 빨리 증가.
        *   해결책: 히스토리에 고정된 토큰 예산 할당.
    *   **세션 간**: 메모리 쓰기가 사용자 요청과 충돌.
        *   해결책: 백그라운드 작업이 사용자당 하나의 작은 파일을 편집.
    *   교훈: "데이터에 대한 구조적 절단. 에이전트의 자체 작업 상태에 대한 모델 작성 요약." 복잡한 솔루션보다 간단한 파일 기반 메모리가 더 효과적이었고, 인간이 감사하기 쉬웠습니다.

4.  **하나의 에이전트인가, 여러 에이전트인가?**
    *   초기에는 하나의 트레이스 에이전트에서 시작.
    *   2026년 초에는 10개의 전문 에이전트(페이지당 하나, 약 100개 도구)로 분할. 프롬프트 토큰이 36k에서 22k로 감소.
    *   2026년 6월에는 다시 하나의 Alyx로 통합. 에이전트가 필요에 따라 스킬 지침과 도구를 로드.
    *   전문 에이전트는 범위가 지정된 작업(scoped jobs)에 남아있지만, 계획은 하지 않음.

5.  **기본 모델 선택:**
    *   새로운 모델이 항상 최고의 기본 모델은 아니었습니다. 2026년 8월, 새로운 모델로 기본값을 변경했을 때, 모델이 행동을 확신하기 전에 동일한 도구를 여러 번 호출하여 사용자 대기 시간이 길어졌고, 결국 이전 모델로 돌아갔습니다.
    *   해결책: 빠르고 충분히 좋은 모델을 기본값으로 설정. 작업별로 모델을 선택. 특정 좁은 영역에서는 루프 자체가 필요 없는지 테스트.

6.  **테스트 방법:**
    *   좋은 프로덕션 세션이 테스트가 되었습니다.
    *   **레벨 1 (하나의 결정)**: 단일 결정까지 히스토리를 재구성하고, 실제 오케스트레이터를 실행하며 답변의 사실을 확인.
    *   **레벨 2 (전체 세션)**: 실제 세션을 턴별로 오늘날의 코드에 대해 재생. LLM 심사위원이 어떤 경로로든 동일한 결과에 도달했는지 판단.
    *   결과를 Arize의 실험으로 기록하고, 점수 하락 시 빌드가 실패하도록 설정.

**에이전트 디버깅:**
- 에이전트에서 버그는 명시적인 오류로 거의 나타나지 않습니다. 대신, "OK" 상태임에도 불구하고 43개의 동일한 도구 호출, 227초의 응답 대기 시간, 192개의 스팬 같은 미묘한 지표로 나타납니다.
- Alyx.Signal이라는 리뷰어 에이전트가 Alyx 자신의 트레이스를 읽어 30일 만에 34개의 숨겨진 재시도 루프(retry loops) 문제를 발견했습니다.

**우리가 거의 스스로를 속였던 네 가지 방법:**
- **상태 코드는 거짓말을 한다**: 처리되지 않은 예외가 루트 스팬을 오류로 바꾸어, 한 쿼리가 모든 깨진 턴을 찾게 함.
- **수정은 다음 버그가 될 수 있다**: 반복되는 계획 업데이트를 실패로 간주하는 가드레드가 모델이 예산 소진까지 재시도하게 만들었고, 에이전트가 작성한 PR은 성공으로 처리됨.
- **텔레메트리에 아티팩트가 있다**: 한 제공업체가 스트리밍 도구 호출에서 0개의 완료 토큰을 보고했는데, 이는 지연처럼 보였지만 실제로는 로깅 문제였음.
- **심사위원은 인간 기준선이 필요하다**: 심사위원의 점수를 신뢰하기 전에, 사람들이 골드 세트를 라벨링하고 두 의견이 다른 부분을 확인.

**여전히 인간의 역할이 필요한 부분:**
- **작성 (Writes)**: Alyx는 생성/변경 전에 항상 묻습니다. 자동 수락은 변경 유형에 따라 옵트인(opt-in).
- **병합 (Merges)**: Signal 및 관리형 에이전트가 PR을 열지만, 실제 커밋 작성자(사람)가 모든 PR을 병합.
- **정답 (Ground truth)**: 심사위원의 골드 라벨은 사람에게서 나옴.
- **모델 기본값 (Model defaults)**: 속도 대 품질은 인간의 판단.
- **메모리 안전성 (Memory safety)**: 잘못된 메모리 항목은 프롬프트 주입이 될 수 있으므로, 쓰기 작업은 게이트를 통과.
- 교훈: "아무도 보고 있지 않을 때, 하네스가 쓰기 권한을 가져야 한다."

**우리가 유지한 여섯 가지:**
- 자체 제품으로 트레이싱 (2024년 5월부터 Alyx 디버깅에 사용).
- 코드 내 수학 및 데이터 (코드가 집계를 계산하고, 모델은 읽고 설명).
- CI의 골든 데이터셋 (모델 또는 프롬프트 변경으로 평가 점수가 떨어지면 빌드 실패).
- 명확한 수정이 있는 오류 (복구 가능한 오류는 모델에게 다음 할 일을 알려줌. 다른 모든 것은 크게 실패).
- 스트리밍 및 지속성 (2024년 스레드 및 스토리지 계층은 세 가지 에이전트 설계보다 오래 지속).
- "스킬"이라는 단어 (2024년에는 라우터 브랜치. 이제는 에이전트가 스스로 지침과 도구를 로드).

## 인상적인 대목
- "It's agents all the way down." (0:56) - 에이전트가 에이전트를 만들고 디버깅하는 메타적인 상황을 위트 있게 표현.
- "50% hallucinations, 50% something useful." (3:20) - 초기 AI 에이전트의 현실적인 성능을 솔직하게 인정하는 부분.
- "Prompts are suggestions; code is constraints." (9:19) - 프롬프트 엔지니어링과 하네스 코드의 역할을 명확히 구분하는 통찰력 있는 문장.
- "If the harness can infer it, the model shouldn't have to maintain it." (7:30) - 모델의 부담을 줄이고 하네스 코드의 역할을 강조하는 핵심 원칙.
- "Once nobody is watching, the harness has to own the write." (18:29) - AI 시스템의 안전성과 신뢰성을 확보하기 위한 중요한 철학.

## 실무 적용 포인트
- **하네스 코드에 집중**: LLM 모델 자체의 성능 향상에만 의존하지 말고, 에이전트의 계획, 턴 관리, 메모리, 가드레일 등 핵심 로직을 견고한 하네스 코드로 구현하는 데 엔지니어링 노력을 기울이세요.
- **모델의 역할 재정의**: 모델에게 모든 것을 맡기기보다, 모델은 추론과 설명에 집중하고, 반복적인 작업이나 상태 관리는 하네스 코드가 담당하도록 역할을 분리하여 효율성을 높이세요.
- **간단한 메모리 솔루션 우선 고려**: 장기 메모리 구현 시 복잡한 지식 그래프나 벡터 데이터베이스 대신, 간단한 파일 기반의 구조(예: 사용자별 마크다운 파일)가 성능과 감사 용이성 측면에서 더 나을 수 있습니다.
- **프로덕션 데이터를 활용한 테스트**: 실제 사용자 세션을 테스트 케이스(골든 데이터셋)로 활용하고, LLM 심사위원을 통해 에이전트의 행동을 평가하는 시스템을 구축하여 미묘한 버그를 탐지하고 회귀를 방지하세요.
- **인간의 역할 명확화**: AI 에이전트가 스스로 결정을 내리는 영역과 인간의 승인, 판단, 라벨링이 필요한 영역을 명확히 구분하고, 특히 쓰기(writes)나 병합(merges) 같은 중요한 작업에는 인간의 개입을 유지하는 안전 장치를 마련하세요.
