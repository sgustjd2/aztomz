# Grep or Embeddings? Agentic Search Over Company Documents — George He, LlamaIndex

## 한 줄 요약
LlamaIndex의 조지 허(George He)는 기업 문서 검색을 위한 에이전트 기반 검색 시스템에서 'grep' 방식과 '임베딩' 방식의 장단점을 비교하고, 데이터 규모에 따라 두 방식을 결합한 하이브리드 접근 방식이 신뢰할 수 있는 결과를 제공한다고 주장합니다.

## 핵심 주장
-   **검색 결과의 중요성**: 많은 사람들이 검색 방법에 대해 이야기하지만, 실제로는 신뢰할 수 있는 검색 결과가 더 중요하며, 이를 위해 에이전트가 문맥(context)을 효과적으로 활용해야 합니다.
-   **'grep' 방식의 한계**: Anthropic의 Claude Code에서 RAG(Retrieval-Augmented Generation)를 제거하고 일반 파일 검색(glob, grep, read)을 사용한 사례는 코드와 같이 작고 구조화된 평문 데이터에 효과적이지만, 기업 문서와 같이 규모가 크고, 자주 변경되며, 보안이 중요하고, 다양한 형식의 데이터에는 적합하지 않습니다.
-   **하이브리드 접근 방식의 필요성**: 데이터의 양에 따라 순수 'grep' 방식, 하이브리드 방식, 또는 시맨틱 검색 중심의 접근 방식을 선택해야 하며, 에이전트에게 미리 정해진 레시피가 아닌 다양한 도구를 제공하여 스스로 최적의 검색 방법을 선택하도록 해야 합니다.
-   **다섯 가지 핵심 도구**: 에이전트가 신뢰할 수 있는 결과를 생성하도록 돕기 위해 하이브리드 검색(벡터 + 키워드), 파일 목록 조회, grep, 파일 읽기, 페이지 스크린샷 획득의 다섯 가지 도구를 활용하는 하네스(harness)를 구축해야 합니다.
-   **엔터프라이즈 데이터 관리의 복잡성**: 파일 시스템을 벗어나 기업 데이터를 관리할 때는 테넌시(tenancy), 권한(permissions), 최신성(freshness)과 같은 요소들을 직접 구축해야 하며, 이는 동기화 및 파싱 프로세스를 분산 처리하고 계층화된 스토리지 시스템을 통해 효율적으로 관리해야 합니다.

## 세부 내용
발표는 LlamaIndex의 엔지니어링 책임자인 조지 허가 AI 엔지니어 월드 페어에서 진행되었습니다. 그는 LlamaIndex가 문서 파싱, 오케스트레이션 및 지식 관리에 중점을 둔 시리즈 A 스타트업이라고 소개했습니다.

발표의 핵심은 기업 에이전트를 위한 검색, 특히 검색 결과의 품질을 높이는 방법에 대한 논의였습니다. 그는 에이전트가 언제, 왜 벡터 인덱스 문맥(context)을 필요로 하는지에 대한 질문을 던졌습니다. 잘못된 답변은 모델의 문제가 아니라 잘못된 문서 검색의 문제이며, 이는 두 가지 주요 해결책, 즉 'grep' 방식과 '임베딩' 방식이 있다고 설명했습니다.

**'grep' 방식의 강점과 한계**:
Anthropic이 Claude Code에서 RAG를 제거하고 'glob', 'grep', 'read'와 같은 일반 파일 검색을 사용한 사례를 언급했습니다. 이는 코드가 작고, 구조화되어 있으며, 평문 텍스트이고, 로컬 디스크에 존재한다는 특성 때문에 가능했습니다. 이러한 방식은 보안, 개인 정보 보호, 최신성, 신뢰성 측면에서 이점을 제공합니다.
그러나 기업 데이터는 코드와 다릅니다. 수백만 개의 파일이 수천 명의 고객(계약서, 서류, 스캔된 PDF, 스프레드시트, 슬라이드 덱)에 걸쳐 존재하며, 다음과 같은 문제가 발생합니다.
-   **규모(Scale)**: 서버에 존재하며 너무 커서 검색을 실행하기 어렵습니다.
-   **최신성(Freshness)**: 문서가 계속 변경되므로 인덱스가 오래될 수 있습니다.
-   **보안(Security)**: 모든 사람이 모든 것을 볼 수 없으므로 각 검색은 권한을 존중해야 합니다.
-   **형식(Format)**: 평문 텍스트가 아니며, 레이아웃, 표, 스캔된 페이지, 차트 등이 포함됩니다.

**하이브리드 접근 방식**:
조지 허는 Anthropic의 자체 플레이북도 이미 하이브리드 방식을 사용하고 있다고 지적했습니다. Claude.md 파일은 미리 로드하고, 'glob'과 'grep'은 필요할 때 검색하는 방식입니다. 그는 "더 똑똑한 검색이 아니라, 에이전트에게 모든 도구를 제공하고 질문에 따라 선택하도록 하는 하네스(harness)가 중요하다"고 강조했습니다.

데이터의 양에 따라 적절한 접근 방식이 달라집니다.
-   **적은 데이터(수십~수백 개 파일)**: 'grep'과 'read'만으로 충분하며, 인덱스는 방해가 될 수 있습니다.
-   **중간 데이터(수천 개 파일)**: 'grep'이 한계를 보이기 시작하면 시맨틱 검색을 추가하는 하이브리드 방식이 필요합니다.
-   **많은 데이터(수백만 개, 멀티테넌트)**: 너무 커서 전체를 검색하기 어려우므로 시맨틱 검색으로 범위를 좁혀야 합니다.

**비용 문제**:
더 많은 문맥(context)은 더 많은 비용을 초래합니다. 모든 토큰은 GPU 메모리와 컴퓨팅 비용을 발생시키며, 전체 코퍼스를 문맥으로 사용하는 것은 가장 비싼 방법입니다. 모델의 문맥 길이가 늘어나도 토큰 비용과 첫 토큰 생성 시간은 증가합니다. 따라서 검색은 필요한 청크만 찾아 비용을 절감하는 방향으로 가야 합니다.

**하네스(The Harness)와 다섯 가지 도구**:
LlamaIndex는 에이전트가 스스로 선택할 수 있도록 하네스를 구축합니다. 이 하네스는 다섯 가지 도구와 다섯 가지 질문에 답합니다.
1.  **"어디를 봐야 할까?" (Where do I even look?) - Retrieval**: 전체 인덱스에서 광범위하게 검색하는 하이브리드 검색(벡터 + 키워드)을 사용합니다. 시맨틱 및 브레드스(breadth) 검색을 결합합니다.
    -   **벡터 검색**: 의미와 의역을 찾지만, 정확한 용어를 놓칠 수 있습니다.
    -   **키워드 검색 (BM25)**: 정확한 용어를 찾지만, 관련 없는 결과를 반환할 수 있습니다.
    -   `retrieval`은 상호 순위 융합(reciprocal rank fusion)을 통해 두 신호를 결합하고 상위 결과를 재순위화하여 검색 품질을 48% 향상시킵니다(Azure AI 검색 벤치마크, 2023).
2.  **"이 폴더에 뭐가 있지?" (What's in this folder?) - `list_files`**: 디렉토리 내 파일을 페이징 및 이름 매칭으로 나열합니다. 파일 시스템 탐색에 사용됩니다.
3.  **"정확히 어떤 줄이지?" (Where's the exact line?) - `grep`**: 주변 문맥과 함께 파일 내에서 정규식 검색을 수행합니다. 어휘적 증명에 사용됩니다.
4.  **"정확히 뭐라고 쓰여 있지?" (What does it actually say?) - `read`**: 파일을 청크 단위로 읽고 얼마나 남았는지 알려줍니다. 어휘적 증명에 사용됩니다.
5.  **"페이지가 어떻게 생겼지?" (What does the page look like?) - `get_page_screenshot`**: 레이아웃이나 차트 이미지를 위해 실제 페이지 이미지를 불러옵니다. 멀티모달 처리에 사용됩니다.

**LlamaParse와 파싱 품질**:
LlamaParse는 레이아웃, 표, 차트 등 복잡한 실제 문서를 읽고 각 페이지를 텍스트, 페이지 이미지, 레이아웃 스팬(bbox 포함), 파싱 품질 점수와 같은 풍부한 객체로 반환합니다. `get_page_screenshot` 도구는 이미지를 모델에 직접 전달하여, 'grep'이 차트를 읽을 수 없는 문제를 해결합니다. LlamaParse Agent0은 ParseBench에서 14개 파서 중 84.9%의 점수를 기록하며, 텍스트 유사성이나 TEDS(Text Edit Distance)가 부족한 에이전트의 요구 사항을 충족합니다.

**엔터프라이즈 데이터의 '세금'**:
파일 시스템을 벗어나면 'grep'이 무료로 제공하던 기능들을 직접 구축해야 합니다.
-   **테넌시(Tenancy)**: 각 쿼리는 호출자의 프로젝트에 잠겨 다른 테넌트의 데이터에 접근할 수 없습니다.
-   **권한(Permissions)**: 모든 결과는 호출자의 권한에 대해 확인되어 허용된 것만 볼 수 있습니다.
-   **최신성(Freshness)**: 문서가 변경되면 다시 파싱되고 이전 항목은 교체되어 인덱스가 항상 최신 상태를 유지합니다.

**인덱스 내부 - 동기화(Sync)**:
문서가 계속 변경되므로 '모든 것을 재구축하는' 인덱스는 오래됩니다. LlamaIndex는 동기화를 세 가지 독립적이고 점진적인 작업으로 나눕니다.
1.  **수집(Ingest)**: 소스를 지문화하고 새로 변경된 것만 가져옵니다.
2.  **파싱(Parse)**: 변경된 파일만 LlamaParse를 실행합니다. 파싱은 파이프라인에서 가장 느리고 비용이 많이 드는 단계이므로 분산 처리됩니다.
3.  **내보내기(Export)**: 청크화, 임베딩, 삭제 후 인덱스에 삽입합니다.

**인덱스 내부 - 스토리지(Storage)**:
수천 개의 테넌트를 위한 벡터를 저장하려면 스토리지가 저렴하고, 격리되어 있으며, 빨라야 합니다. LlamaIndex는 SSD/RAM 캐시와 S3와 같은 객체 스토리지를 결합하여 이 문제를 해결합니다. 벡터는 필요할 때만 캐시로 로드되어 비용을 절감하고, 각 테넌트는 격리된 네임스페이스를 가집니다.

**인덱스 내부 - 권한(Permissions)**:
권한은 벡터와 함께 이동합니다. 파일이 수집될 때 권한을 캡처하여 벡터 스토어에 임베딩 바로 옆에 저장합니다. 검색 시 호출자의 그룹을 기반으로 필터링하여 권한 없는 데이터가 노출되지 않도록 합니다.

**라이브 데모**:
발표자는 Alphabet의 재무 보고서(135개 파일)를 사용하여 에이전트가 "2021-2025년 현금 흐름 또는 수입을 표로 제공"하는 쿼리에 어떻게 응답하는지 시연했습니다. 에이전트는 검색 명령을 발행하고, 스크린샷과 문맥을 검토하며, 특정 파일을 읽고, 쿼리를 재조정하여 여러 파일에서 데이터를 추출하고, 최종적으로 깔끔한 표 형식의 답변을 제공했습니다.

## 인상적인 대목
-   "Search finds it. The harness makes it a result you can trust." (검색은 찾아내고, 하네스는 신뢰할 수 있는 결과를 만듭니다.)
-   "It was never either/or. Let the amount of data decide." (그것은 결코 '이것 아니면 저것'이 아니었습니다. 데이터의 양이 결정하게 하십시오.)
-   "Give the agent tools, not a recipe." (에이전트에게 레시피가 아닌 도구를 주십시오.)
-   "The index handles the enterprise parts — tenancy, permissions, freshness, formats." (인덱스는 테넌시, 권한, 최신성, 형식과 같은 엔터프라이즈 부분을 처리합니다.)

## 실무 적용 포인트
-   **데이터 규모에 따른 검색 전략 선택**: 로컬 파일 시스템 검색(grep), 하이브리드 검색, 시맨틱 검색 중 어떤 방식을 사용할지 데이터의 양과 특성(코드 vs 기업 문서)에 따라 유연하게 결정해야 합니다.
-   **에이전트 도구 상자 구축**: 에이전트가 스스로 최적의 검색 방법을 선택하도록 `list_files`, `grep`, `read`, `get_page_screenshot`과 같은 다양한 도구를 제공하는 '하네스' 아키텍처를 고려해야 합니다.
-   **문서 파싱 품질의 중요성**: 복잡한 문서(표, 차트, 스캔 이미지 포함)의 경우, 텍스트뿐만 아니라 레이아웃, 이미지 등 멀티모달 정보를 정확하게 파싱하는 것이 에이전트의 추론 품질에 결정적인 영향을 미치므로 LlamaParse와 같은 전문 파싱 도구 사용을 검토해야 합니다.
-   **엔터프라이즈급 인덱스 관리**: 멀티테넌시, 권한 관리, 데이터 최신성 유지를 위해 3단계 동기화(수집, 파싱, 내보내기) 파이프라인과 계층화된 스토리지(SSD/RAM 캐시 + 객체 스토리지)를 구축하여 효율성과 확장성을 확보해야 합니다.
