# Your AI Agents Shouldn't Care Where They Run - Nikhil Harithas, Factory

🔗 https://youtu.be/XIHZpZtYCzo · 📅 2026-11-03 · 🎙 AI Engineer

## 한 줄 요약
에이전트가 실행되는 인프라에 구애받지 않도록, 컴퓨트 라이프사이클을 추상화하는 오픈소스 프로젝트인 OpenCompute를 통해 엔터프라이즈 환경에서 에이전트 배포의 복잡성을 해결하고 유연성을 제공한다.

## 발표자·소속
Nikhil Harithas, Factory (Lead Forward Deployed Engineering)

## 핵심 주장
- 에이전트는 애플리케이션이며, 애플리케이션은 인프라가 필요하지만 에이전트가 실행되는 인프라에 대해 신경 쓸 필요가 없어야 한다.
- 엔터프라이즈 환경의 복잡성(규제, 보안, BYO 컴퓨트/추론/ID, 단일 테넌트)은 에이전트 배포에 큰 어려움을 초래한다.
- OpenCompute는 에이전트의 컴퓨트 라이프사이클을 추상화하여, 고객이 원하는 인프라(EC2, Kubernetes 등)에서 에이전트를 배포하고 관리할 수 있도록 지원한다.
- OpenCompute는 고객의 환경 내에서 모든 작업을 수행하며, Factory는 고객의 인프라에 대한 인바운드 연결 없이 아웃바운드 연결을 통해 제어 계층을 유지한다.

## 세부 내용
발표자는 Factory에서 포워드 배포 엔지니어링을 이끌고 있으며, Factory는 코딩 에이전트(Droid)를 사용하여 소프트웨어 엔지니어링에 자율성을 부여하는 회사라고 소개했습니다. 이 발표는 현장에서 얻은 경험, 특히 복잡한 엔터프라이즈 고객과의 협업에서 얻은 교훈을 바탕으로 합니다.

가장 복잡한 고객 중 하나로 Blackstone을 예로 들었습니다. Blackstone은 1조 달러 규모의 자산을 운용하는 대형 금융 기관으로, 엄격한 규제, 보안 제약, 그리고 비결정론적 소프트웨어(에이전트) 배포 방식에 대한 강한 의견을 가지고 있습니다. 이들의 환경에서는 모든 기본 설정이 의문시되었는데, 예를 들어 에이전트를 기업 노트북에서 실행할 수 없고, 자체 컴퓨트, 추론, ID를 사용하며, 모든 것이 단일 테넌트여야 한다는 요구사항이 있었습니다.

Factory의 에이전트(Droid)는 티켓을 자동으로 처리하는 자동 위임(Auto-delegation) 작업을 수행합니다. 예를 들어, Jira 티켓을 Droid에 할당하면 Droid가 PR을 생성하여 작업을 완료합니다. 이러한 작업은 많은 권한을 필요로 합니다.

지난 3개월간의 경험을 통해 두 가지 핵심 질문이 반복적으로 제기되었습니다: "이 에이전트는 누구를 대신하여 작동하는가?" (ID)와 "어디에서 실행되는가?" (인프라). 발표자는 에이전트가 사용자의 ID를 계속 빌릴 수 없으며, 궁극적으로 에이전트는 애플리케이션일 뿐이고 애플리케이션은 인프라가 필요하다고 강조했습니다.

과거에는 "Bring Your Own Compute" 제품을 제공했지만, 고객이 여전히 컴퓨트 라이프사이클을 직접 관리해야 하는 문제가 있었습니다. 이를 해결하기 위해 Factory는 OpenCompute라는 오픈소스 프로젝트를 개발했습니다. OpenCompute는 어떤 에이전트든 고객의 클라우드 환경에서 컴퓨트 라이프사이클을 추상화하여 관리할 수 있도록 설계되었습니다.

OpenCompute의 아키텍처는 Factory 클라우드와 고객 클라우드로 나뉩니다.
- **Factory 클라우드**: CLI, Jira/Slack, 자동화, 데스크톱/웹과 같은 클라이언트가 백엔드와 통신합니다. 백엔드는 컴퓨트 게이트웨이(Compute Gateway)와 릴레이(Relay)라는 두 가지 핵심 구성 요소를 포함합니다.
- **고객 클라우드**: OpenCompute 컨트롤 플레인(스케줄러, 클린, 루프, 테스트, REST API, 서명된 챌린지)과 실제 컴퓨트(EC2, GCP, Azure, 온프레미스 등에서 실행되는 Droid 데몬)가 있습니다.

**작동 방식 (세션 시작 및 실행)**:
1.  클라이언트(CLI)가 백엔드에 `start session` 요청을 보냅니다.
2.  백엔드는 컴퓨트 게이트웨이를 통해 OpenCompute에 `CreateCompute` 요청을 보냅니다.
3.  OpenCompute는 고객 클라우드 내에서 EC2 인스턴스(또는 다른 컴퓨트)를 `deliver`하고 Droid 데몬을 시작합니다.
4.  Droid 데몬은 Factory 클라우드의 릴레이로 아웃바운드 연결을 설정합니다.
5.  클라이언트가 "hello world"와 같은 명령을 릴레이로 보내면, 릴레이는 이 요청을 Droid 데몬으로 전달하고, Droid 데몬은 작업을 수행한 후 결과를 다시 릴레이를 통해 클라이언트로 스트리밍합니다.
이 과정에서 고객의 개인 키는 고객 클라우드를 떠나지 않으며, Factory는 고객의 환경으로 인바운드 연결을 만들지 않고, 모든 연결은 고객이 아웃바운드로 시작합니다.

OpenCompute는 컴퓨트 라이프사이클을 관리하는 API를 제공하며, 각 인프라 제공업체는 이 API를 구현하는 드라이버를 개발합니다. 이 API는 컴퓨트 생성, 가져오기, 일시 중지, 재개, 파괴, 스냅샷 생성/로드, 포크 등의 기능을 포함합니다. 드라이버는 특정 컴퓨트 유형(예: EC2, Kubernetes)에 대한 래퍼 역할을 합니다.

발표자는 OpenCompute가 세션이 아닌 **컴퓨터**를 관리하는 프로젝트라고 강조했습니다. 이는 에이전트가 실행되는 환경(빌드)을 Docker 이미지, 환경 변수, 설정 스크립트 등으로 구성된 "고정된 환경"으로 정의하고, 이 환경을 기반으로 컴퓨트(컴퓨터)를 생성하고 관리하는 방식입니다. 에이전트 자체는 이 컴퓨터 내에서 실행되며, OpenCompute는 에이전트의 태스크에 관여하지 않습니다.

이러한 접근 방식은 AWS MicroVM의 8시간 세션 제한과 같은 문제를 해결하는 데 도움이 됩니다. 에이전트가 여러 날 동안 실행되어야 하는 경우, OpenCompute는 스냅샷을 생성하고 새로운 인스턴스에서 재개하는 방식으로 세션 제한을 우회할 수 있습니다. 또한, 사용자 정의 베이스 이미지, 비밀 주입, Terraform을 통한 인프라 관리 등 엔터프라이즈 고객의 복잡한 요구사항을 충족시킵니다.

Factory는 Droid가 드라이버를 작성하도록 하여 이 시스템을 구축했습니다. Droid에게 특정 제공업체에 대한 지원을 구축하도록 지시하고, Droid는 계약을 구현하고 테스트를 통과하여 드라이버를 생성합니다. 이 과정은 8주 만에 프로토타입이 완성되었고, 첫 번째 핸드오버는 1일 만에 이루어졌습니다.

## 인상적인 대목
- "An agent can't keep borrowing your identity." (에이전트가 당신의 신원을 계속 빌릴 수는 없다.) - 에이전트의 독립적인 ID 관리의 중요성을 강조하는 문장.
- "Agents are applications. Applications need infrastructure." (에이전트는 애플리케이션이다. 애플리케이션은 인프라가 필요하다.) - 에이전트를 기존 소프트웨어 엔지니어링 패러다임에 통합하려는 실용적인 접근 방식.
- "Nothing connects in. The deployer's private key never leaves it." (아무것도 안으로 연결되지 않는다. 배포자의 개인 키는 절대 외부로 나가지 않는다.) - 엔터프라이즈 고객의 보안 우려를 해소하는 핵심 원칙.

## 실무 적용 포인트
- **컴퓨트 라이프사이클 추상화**: 에이전트 개발 시, 에이전트가 특정 인프라에 종속되지 않도록 컴퓨트 라이프사이클을 추상화하는 드라이버 기반 아키텍처를 고려한다.
- **보안 및 규정 준수**: 에이전트가 고객의 VPC 내에서 실행되고, 모든 연결이 아웃바운드로 이루어지며, 민감한 정보(개인 키, 비밀)가 고객 환경을 벗어나지 않도록 설계하여 엔터프라이즈 보안 요구사항을 충족시킨다.
- **에이전트 ID 관리**: 에이전트가 개별적인 서비스 계정 또는 역할(BYO Identity)을 사용하여 작업을 수행하도록 하여, 개인 사용자 ID에 의존하지 않도록 한다.
- **복원력 있는 프로비저닝**: 인프라 프로비저닝이 단일 API 호출이 아님을 인지하고, 연결 실패, 스로틀링, 서버 재시작 등 다양한 실패 시나리오에 대비하여 재시도 로직과 상태 관리를 포함하는 견고한 시스템을 구축한다.
