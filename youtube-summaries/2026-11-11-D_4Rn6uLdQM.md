# 225,000 Lines of Tests, Written and Merged by Agents - Kush Agrawal, Duolingo

🔗 https://youtu.be/D_4Rn6uLdQM · 📅 2026-11-11 · 🎙 AI Engineer

## 한 줄 요약
Duolingo는 AI 에이전트를 활용하여 iOS 코드베이스에 225,000줄 이상의 유닛 테스트 코드를 작성하고 병합했으며, 이를 통해 테스트 커버리지를 크게 향상시키고 개발 워크플로우의 병목 현상을 해결했습니다.

## 발표자·소속
Kush Agrawal, Staff Software Engineer, iOS Platform at Duolingo

## 핵심 주장
- **AI 에이전트가 테스트 작성의 병목 현상을 해결:** Duolingo의 모바일 코드베이스는 1.86M 라인에 달하며, 주간 앱 스토어 릴리스와 600개 이상의 동시 실험을 진행하는 등 빠르게 성장하고 있습니다. AI 코딩 도구의 도입으로 코드 작성 속도가 빨라지면서, 코드 검증(테스트)이 새로운 병목 현상이 되었고, AI 에이전트가 이 문제를 해결하는 데 핵심적인 역할을 했습니다.
- **MVVM 아키텍처에 집중하여 효율적인 테스트 커버리지 달성:** 코드베이스의 약 50%가 MVVM(Model-View-ViewModel) 패턴을 따르며, 이 부분이 테스트하기 가장 쉬운 영역으로 판단되어 에이전트의 테스트 작성 대상이 되었습니다. 이를 통해 MVVM 컴포넌트의 테스트 커버리지를 9%에서 59%로, 전체 앱 커버리지를 11%에서 24%로 끌어올렸습니다.
- **지속적인 개선을 위한 5단계 반복 루프 구축:** 에이전트 기반 테스트 작성 파이프라인은 '식별(Identify)', '작성(Write)', '검증(Verify)', '해결(Resolve)', '반복(Iterate)'의 5단계 루프를 따릅니다. 각 단계의 피드백은 다음 실행을 개선하여 에이전트의 성능과 코드 품질을 지속적으로 향상시킵니다.
- **Temporal을 활용한 견고한 워크플로우 오케스트레이션:** 에이전트 세션은 수 시간 동안 실행될 수 있고 GitHub, CI, S3, Claude와 같은 외부 도구를 호출하며, 사람의 개입, 타임아웃, 플래키(flaky) 테스트에도 안전하게 대처해야 하므로, Temporal의 스케줄, 자식 워크플로우, 재시도 및 타임아웃, 멱등성(idempotency)과 같은 내장 기능을 활용하여 복잡한 워크플로우를 안정적으로 오케스트레이션했습니다.

## 세부 내용

**1. 배경**
Duolingo의 모바일 앱은 주간 앱 스토어 릴리스를 진행하며, 600개 이상의 동시 실험을 운영하는 실험 중심의 회사입니다. iOS 및 Android 앱은 10년 이상 서비스되어 왔으며, iOS 저장소의 실행 가능한 앱 코드 라인 수는 2019년 약 20만 줄에서 현재 1.86M 줄로 급증했습니다. AI 보조 코딩 도구의 도입으로 코드 작성 속도가 빨라지면서, 코드베이스 기여자 수도 2019년 66명에서 2026년 현재 259명으로 늘었습니다. 이 중에는 iOS 엔지니어 외에도 백엔드, Android 엔지니어, 심지어 PM과 디자이너도 포함됩니다.

코드베이스의 약 50%는 MVVM 아키텍처 패턴(View → ViewModel → Repository → DataSource)을 따르고 있으며, 나머지 50%는 레거시 코드입니다. 테스트하기 쉬운 MVVM 부분에 집중하여 프로젝트를 진행했습니다. 2026년 3월 기준으로 전체 유닛 테스트 커버리지는 11%였으며, MVVM 컴포넌트별로는 Repository 11%, ViewModel 9%, DataSource 5%로, MVVM 전체는 9%였습니다.

코드 작성 속도가 빨라지면서, 코드를 작성하는 것보다 검증하는 것이 병목 현상이 되었습니다. 유닛 테스트는 테스트 피라미드의 가장 아래를 구성하며, 빠르고 저렴하게 작성 및 실행할 수 있고, 에이전트의 안전장치 역할을 하며, 코드의 의도를 명확히 하는 살아있는 문서 역할을 합니다. 8개월 후인 2026년 11월에는 전체 유닛 테스트 커버리지가 24%로, MVVM 컴포넌트 커버리지는 Repository 72%, ViewModel 58%, DataSource 41%로, MVVM 전체는 59%로 크게 증가했습니다.

**2. 구축 내용**

**개념적 워크플로우 (On Paper):**
1.  **식별 (Identify):** 테스트가 필요한 파일을 찾습니다.
2.  **작성 (Write):** 에이전트가 테스트를 작성합니다.
3.  **검증 (Verify):** 테스트가 품질이 좋고 CI를 통과하는지 확인합니다.
4.  **해결 (Resolve):** 엔지니어가 PR을 검토하고 병합합니다.
5.  **반복 (Iterate):** 피드백을 통해 다음 PR 배치를 개선합니다.

**프로덕션 시스템 (In Production):**
시스템은 Temporal 워크플로우 오케스트레이션 엔진을 중심으로 구축되었습니다. Temporal은 스케줄, 자식 워크플로우, 재시도 및 타임아웃, 멱등성 등의 기능을 제공하여 에이전트 세션이 수 시간 동안 실행되고 외부 도구(GitHub, CI, S3, Claude)를 호출하며 안전하게 실패할 수 있도록 합니다. S3는 워크플로우 간의 공유 상태를 저장하는 데 사용되며, GitHub는 액션, 레이블, PR 관리에 활용됩니다. Datadog은 파이프라인의 상태를 모니터링하는 데 사용됩니다.

**네 가지 마일스톤:**

1.  **로컬 검증 (Local Validation):**
    *   목표는 에이전트가 작업을 잘 수행하고 확장 가능성이 있는지 확인하는 것이었습니다.
    *   Claude Code Orchestrator가 로컬에서 코드 커버리지 리포트를 생성하고, 테스트 선택 스크립트를 통해 파일을 선택한 후, `write-tests` 에이전트와 `create-test-pr` 에이전트에게 전달하여 GitHub에 PR을 생성했습니다.
    *   두 번의 배치 실행 결과, 약 47-48%의 PR 병합률을 보였습니다. 이 단계의 목표는 많은 PR을 병합하는 것이 아니라 에이전트의 실패 모드를 학습하고 프로덕션화 전에 문제를 해결하는 것이었습니다.
    *   **주요 실패 모드 및 해결책:**
        *   Swift Testing과 XCTest 혼용: 에이전트에게 각 테스트 프레임워크를 언제 사용할지 명확한 규칙을 제공했습니다.
        *   구체적인 UserClient 클래스: 코드베이스를 프로토콜 기반으로 마이그레이션하고 린트 규칙을 추가하여 테스트 용이성을 높였습니다.
        *   Swift 6 Sendable 오류: 프롬프트 가이드를 개선하고 `@MainActor`로 모의 객체를 주석 처리했습니다.
        *   접근 제어 누락, 타이밍 기반 테스트: 더 나은 규칙과 예제를 테스트 스킬에 추가했습니다.

2.  **스케줄된 백필 워크플로우 (Scheduled Backfill Workflow):**
    *   코드 커버리지가 낮았기 때문에, 이미 병합된 코드에 대한 테스트를 백필하는 것이 가장 큰 효과를 가져올 것으로 판단했습니다.
    *   **식별 (Identify):** 매주 GitHub Actions가 PR 병합 시 XCode 커버리지 리포트를 생성하여 S3에 업로드합니다. 백필 워크플로우는 이 리포트를 가져와 선택 스크립트를 통해 다음 테스트할 파일을 선택합니다. 선택 스크립트는 파일 유형(MVVM 컴포넌트 2.5배 가중치), 커버리지 격차, 모듈 우선순위, 파일 크기(페널티)를 기준으로 파일을 평가하여 에이전트가 테스트를 잘 작성할 수 있는 파일을 우선시합니다. UI 코드는 현재 스냅샷 테스트가 더 적합하다고 판단하여 제외했습니다.
    *   **작성 (Write):** 선택된 파일들은 각각 병렬로 실행되는 자식 워크플로우에 할당됩니다. 각 에이전트는 저장소를 클론하고, 테스트 스킬(테스트 작성 방법 명시)을 읽고, 테스트와 필요한 모의 객체/가짜 객체를 작성한 후, `generated-test` 레이블이 붙은 PR을 생성합니다.
    *   에이전트는 Duolingo의 클라우드 코딩 에이전트 플랫폼에서 실행되며, 이는 Claude Code/Codex 위에 추상화된 것입니다. 처음에는 Linux EC2에서 실행되었으나, 나중에 macOS 러너로 전환되었습니다.

3.  **PR 라이프사이클 워크플로우 (PR Lifecycle Workflow):**
    *   백필 워크플로우가 프로덕션에서 실행되면서 수십에서 수백 개의 PR이 열렸고, 이를 수동으로 관리하는 것은 불가능했습니다.
    *   이 워크플로우는 상태 머신처럼 작동하며, 몇 시간마다 실행되어 열려 있는 모든 `generated-test` PR을 검토하고 정확히 하나의 작업을 수행합니다.
    *   **의사 결정 트리:**
        1.  병합 충돌이 있거나 PR이 오래된 경우(3주 이상): PR을 닫습니다.
        2.  CI가 보류 중이거나 이미 검토자가 할당된 경우: 건너뜁니다.
        3.  CI가 통과했지만 검토자가 없는 경우: 검토자를 할당합니다 (Git blame을 통해 해당 파일의 주요 기여자를 찾아서 할당하고 자동 병합을 켭니다).
        4.  CI가 실패했거나 사전 커밋 실패가 있는 경우: CI를 자동 수정합니다 (사전 커밋 실패는 GitHub Action으로, 유닛 테스트 실패는 에이전트가 로그를 읽고 수정사항을 푸시하며, 5회 시도 후에도 실패하면 PR을 닫습니다).
        5.  검토자가 PR을 거부한 경우: 30일 쿨다운 기간을 둡니다.

4.  **레이블 트리거 (Label trigger):**
    *   기존 코드에 대한 테스트 백필이 완료된 후, 엔지니어가 새로 작성하는 코드에 대해서도 쉽게 테스트를 생성할 수 있도록 했습니다.
    *   이제 어떤 엔지니어든 자신의 PR에 `write-tests` 레이블을 추가하면, 동일한 Temporal 인프라가 PR의 diff와 설명을 바탕으로 테스트를 작성하고, 원래 PR에 링크된 드래프트 테스트 PR을 생성합니다.

**3. 도전 과제 및 해결책**

**SwiftLint 실패:**
*   **문제:** 에이전트가 XCode나 SwiftLint가 설치되지 않은 Linux 머신에서 실행되었기 때문에, PR을 열기 전에 린트 오류를 잡을 수 없었습니다. 이로 인해 13.6%의 PR이 린트 실패로 CI 시간을 낭비했고, 이 중 62%는 단 두 개의 린트 규칙에서 발생했습니다.
*   **해결책:**
    1.  **프롬프트 업데이트:** 에이전트에게 좋은 예시와 피해야 할 함정을 프롬프트에 추가했습니다.
    2.  **CI에서 자동 수정:** CI 린트 오류를 자동 수정하는 GitHub Action을 트리거했습니다.
    3.  **수정 불가능한 린트 제거:** 자동 수정할 수 없는 린트 규칙 중 중요도가 낮은 것들을 제거했습니다.
    4.  **Mac 러너 사용:** 에이전트를 macOS 러너로 옮겨 PR을 열기 전에 로컬에서 코드를 빌드하고 린트 검사를 수행할 수 있도록 했습니다.

**PR 품질:**
*   **문제:** 에이전트가 CI를 통과하기 위해 때때로 최단 경로를 택하여, 생산 코드 수정, 기존 테스트 수정/삭제, 테스트에 긴 대기 시간 추가(CI를 불안정하게 만듦)와 같은 바람직하지 않은 행동을 보였습니다.
*   **해결책:**
    1.  **결정론적 규칙 기반 필터링:** 테스트, 모의 객체, 가짜 객체, 스텁 파일이 아닌 다른 파일을 건드리는 PR은 자동으로 닫는 규칙을 적용했습니다.
    2.  **봇 댓글 해결사 (Bot Comment Resolver):** Claude 및 Codex 리뷰 봇이 남긴 P0 댓글을 사람이 PR을 보기 전에 에이전트가 자동으로 해결하도록 했습니다.
    3.  **LLM을 심판으로 (AI Diff Reviewer):** PR diff를 읽고 다음 거부 기준을 적용하는 검토자 에이전트를 구축했습니다: 생산 코드 수정, 테스트 수정 또는 삭제, 비활성화된 테스트, 긴 대기 시간 추가. 이 에이전트는 현재까지 1,200개의 PR을 검토하여 73개를 거부했으며, 각 거부에는 명확한 이유가 포함된 댓글을 남깁니다. 이 피드백은 에이전트의 프롬프트와 스킬에 반영되어 동일한 실수를 반복할 가능성을 줄입니다.

**4. 결과**
*   총 701개의 PR이 병합되었고, 225,000줄의 테스트 코드가 추가되었습니다.
*   657개의 클래스가 테스트되었습니다.
*   MVVM 테스트 커버리지는 9%에서 59%로 증가했습니다.
*   전체 테스트 커버리지는 11%에서 24%로 증가했습니다.
*   2026년 3월 이후, 파이프라인은 전체 새 테스트 파일의 34%, 새 테스트 케이스의 44%, 전체 Swift 코드 라인 추가의 10%를 작성했습니다.
*   최근 몇 주 동안 에이전트의 코드 작성 비율이 감소했는데, 이는 엔지니어들이 직접 더 많은 테스트를 작성하기 시작했기 때문이며, 이는 궁극적인 목표이기도 합니다.
*   테스트 커버리지 성장 그래프는 백필이 스케줄에 따라 실행되기 시작한 4월 이후 꾸준히 상승했으며, 6월과 7월에 파이프라인이 본격적으로 가동되면서 가파른 상승세를 보였습니다.

## 인상적인 대목
- "As agents and humans write more code, verification becomes the bottleneck." (에이전트와 인간이 더 많은 코드를 작성함에 따라, 검증이 병목 현상이 됩니다.)
- "Unit tests as guardrails... agents check their own work... living documentation." (유닛 테스트는 안전장치 역할을 하며... 에이전트가 자신의 작업을 확인하고... 살아있는 문서 역할을 합니다.)
- "The pattern generalizes... Any job that fits this shape can run on the same infrastructure." (이 패턴은 일반화됩니다... 이 형태에 맞는 어떤 작업이든 동일한 인프라에서 실행될 수 있습니다.)
- LLM을 단순한 코드 생성기가 아닌, PR 품질을 검토하고 거부 기준을 적용하는 "심판(Judge)"으로 활용하여 에이전트의 행동을 제어하는 접근 방식이 인상 깊습니다.

## 실무 적용 포인트
- **AI 에이전트 워크플로우를 5단계 루프로 설계:** '식별-작성-검증-해결-반복'의 루프는 AI 에이전트가 코드를 생성하고 개선하는 데 효과적인 프레임워크를 제공합니다. 이는 테스트 작성 외에도 다양한 코드 변환 및 마이그레이션 작업에 적용될 수 있습니다.
- **Temporal과 같은 내구성 있는 워크플로우 엔진 활용:** AI 에이전트 작업은 장시간 실행되거나 외부 시스템과 상호작용하며 실패할 수 있습니다. Temporal과 같은 내구성 있는 워크플로우 엔진은 이러한 복잡한 작업을 안정적으로 오케스트레이션하고, 재시도, 타임아웃, 상태 관리를 통해 시스템의 견고성을 보장합니다.
- **점진적인 도입과 피드백 기반 개선:** 처음부터 완벽한 시스템을 구축하기보다는, 로컬 검증을 통해 에이전트의 실패 모드를 학습하고, 이를 바탕으로 프롬프트, 규칙, 인프라를 개선하는 반복적인 접근 방식이 중요합니다. AI 에이전트의 피드백(예: AI Diff Reviewer의 거부 사유)을 다시 시스템에 반영하여 에이전트의 성능을 지속적으로 향상시켜야 합니다.
- **CI/CD 파이프라인과의 긴밀한 통합 및 자동화된 품질 관리:** 에이전트가 생성한 코드의 품질을 보장하기 위해 SwiftLint 자동 수정, 규칙 기반 필터링, AI 기반 PR 검토와 같은 자동화된 품질 관리 메커니즘을 CI/CD 파이프라인에 통합하는 것이 필수적입니다. 특히, PR을 열기 전에 로컬에서 린트 및 빌드 검사를 수행하도록 에이전트 환경을 구성하는 것이 CI 시간 낭비를 줄이는 데 효과적입니다.
