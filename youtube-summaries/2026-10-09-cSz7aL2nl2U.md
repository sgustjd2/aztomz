# Why Your Company Needs a Context Graph (and How to Build It) — Gil Feig, Merge

🔗 https://youtu.be/cSz7aL2nl2U · 📅 2026-10-09 · 🎙 AI Engineer

## 한 줄 요약
기업의 AI 애플리케이션을 성공적으로 구축하기 위해서는 단순히 도구를 연결하는 것을 넘어, 회사 전체의 데이터를 통합하고, 지식과 프로세스를 반영하며, 추적 가능한 답변을 제공하는 '컨텍스트 그래프'를 구축하는 것이 필수적입니다.

## 발표자·소속
*   **발표자**: 길 페이그(Gil Feig)
*   **소속**: Merge 공동 창립자 겸 CTO

## 핵심 주장
*   **도구만으로는 충분하지 않다**: AI 에이전트가 효과적으로 작동하려면 단순히 외부 도구(API)에 연결하는 것을 넘어, 회사 전체의 데이터, 지식, 프로세스를 통합하는 컨텍스트 그래프가 필요합니다.
*   **데이터의 양보다 질과 구조가 중요하다**: 모든 데이터를 실시간으로 조회하는 것은 비효율적이며, 필요한 데이터만 선별하여 캐시하고 적절히 구조화해야 에이전트가 빠르고 정확하게 추론할 수 있습니다.
*   **모든 답변은 추적 가능해야 한다**: AI 에이전트가 내린 결정에 대한 디버깅, 감사 가능성, 그리고 신뢰할 수 있는 근거를 제공하기 위해 데이터의 출처, 접근 방식, 변환 여부 등이 명확히 기록되어야 합니다.

## 세부 내용

발표자는 AI 엔지니어링 컨퍼런스에서 기업이 컨텍스트 그래프를 구축해야 하는 이유와 방법을 설명했습니다. 발표자는 Merge의 공동 창립자 겸 CTO이며, Merge는 기업이 프로덕션 AI를 쉽게 구축할 수 있도록 돕는 연결 인프라를 제공합니다.

**Merge 소개**
Merge는 2020년에 설립되었으며, OpenAI, Netflix 등 400개 이상의 기업 고객을 보유하고 있습니다. Merge Unified(220개 이상의 SaaS 통합), Merge Agent Handler(5,000개 이상의 도구), Merge Gateway(모든 LLM 제공자를 위한 1개 API) 세 가지 제품을 통해 내부 및 고객 대면 AI 활용 사례를 지원합니다.

**컨텍스트 그래프의 의미**
발표자는 컨텍스트 그래프를 "회사 두뇌(company brain)"에 비유하며, 이는 단순한 그래프 데이터베이스를 넘어 여러 구성 요소를 포함한다고 설명했습니다.
*   **서드파티 데이터(3rd-party data)**: NetSuite, Jira와 같은 외부 시스템의 데이터.
*   **구조화된 컨텍스트(Structured context)**: 항상 에이전트에 전달되어야 하는 정적 문서나 구조화된 데이터.
*   **메모리(Memories)**: 에이전트가 사용되면서 형성되거나, 에이전트가 스스로 기억해야 한다고 판단하는 정보.
*   **스킬(Skills)**: 에이전트가 특정 작업을 수행하는 방법이나 회사 고유의 비즈니스 로직.
*   **LLM(Large Language Model)**: 컨텍스트를 이해하고 추론하는 핵심 모델.

**컨텍스트 그래프의 필요성: 고객 불만 사례**
발표자는 "고객 A가 지난주에 왜 화가 났나요?"라는 질문을 예로 들었습니다. 에이전트는 Zendesk와 같은 티켓팅 시스템에 접근하여 고객 A가 API 동기화 문제로 3개의 지원 티켓을 제출했고, 이 중 2개는 SLA 내에 응답이 없었다는 정보를 얻을 수 있습니다.

하지만 "다른 어떤 고객이 이 문제를 경험했나요?"와 같은 질문은 훨씬 어렵습니다. 에이전트가 지난주 또는 지난 1년 동안 Zendesk의 모든 티켓을 실시간으로 조회해야 하는데, 이는 API의 효율성 문제(예: 타임아웃)로 인해 불가능합니다. 또한, 외부 플랫폼들은 이러한 대규모의 의미론적 조회를 지원하도록 인센티브가 없습니다.

**동기화 계층(Syncing Layer)의 필요성**
이러한 문제를 해결하기 위해 동기화 계층이 필요합니다. 에이전트가 의미론적으로 질문하거나 방대한 데이터셋을 분석해야 하는 경우, 데이터를 로컬에 동기화(캐시)해야 합니다. 단순한 단일 조회는 라이브 API 호출로 충분하지만, 복잡한 분석을 위해서는 동기화된 데이터가 필수적입니다.

**라우팅 및 요약(Routing and Summarization)**
*   **라우터(Router)**: 사용자 프롬프트가 들어오면, 에이전트가 어떤 데이터 소스나 스킬을 사용해야 할지 결정하여 적절한 곳으로 보냅니다.
*   **요약기(Summarizer)**: 동기화된 컨텍스트와 라이브 컨텍스트에서 수집된 모든 데이터를 통합하여 에이전트가 이해할 수 있는 형태로 요약합니다.
*   **메모리 및 스킬의 중요성**: "고객이 행복한지 어떻게 판단하나요?"와 같은 질문은 회사마다 다른 기준(예: 티켓 수, 설문조사 데이터)을 가질 수 있습니다. 이러한 회사 고유의 비즈니스 로직과 판단 기준이 바로 '스킬'이며, 에이전트는 스킬을 먼저 확인한 후 데이터 조회를 시작해야 합니다.

**컨텍스트 선택 전략**
발표자는 컨텍스트 선택 전략을 위한 플로우차트를 제시했습니다.
1.  **쿼리 수신**: 사용자 프롬프트가 들어옵니다.
2.  **스킬/메모리 일치 여부 확인**: 에이전트가 프롬프트와 관련된 스킬이나 기억을 가지고 있는지 확인합니다.
    *   **일치**: 스킬을 실행합니다.
    *   **스킬이 외부 데이터를 필요로 하는가?**
        *   **아니오**: 응답을 생성합니다.
        *   **예**: 캐시된 데이터가 최신인지 확인합니다.
    *   **불일치**: 캐시된 데이터가 최신인지 확인합니다.
3.  **캐시된 데이터가 최신인지 확인**: SLA(서비스 수준 협약) 내에서 데이터가 유효한지 확인합니다.
    *   **최신**: 캐시된 컨텍스트를 사용합니다.
    *   **충분한 컨텍스트인가?**
        *   **예**: 메모리에 저장(선택 사항) 후 응답을 생성합니다.
        *   **아니오**: 라이브 API를 호출합니다.
    *   **최신 아님**: 라이브 API를 호출합니다.
4.  **라이브 API 호출**: 필요한 경우 외부 시스템에서 실시간 데이터를 가져옵니다.
    *   **충분한 컨텍스트인가?**
        *   **예**: 메모리에 저장(선택 사항) 후 응답을 생성합니다.
        *   **아니오**: (추가적인 전략 필요, 영상에서 명시적으로 실패 경로를 보여주지는 않음)

**추적 가능성 및 출처(Traceability and Provenance)**
모델에 전달되는 모든 컨텍스트 노드는 다음 질문에 답할 수 있어야 합니다.
*   어디에서 왔는가?
*   언제, 어디서 가져왔는가?
*   어떤 ID와 범위(권한)로 접근했는가?
*   변환되었는가? (원래 모습은 어떠했는가?)
*   무엇이 이 데이터를 무효화해야 하는가? (예: 데이터의 경과 시간)
이는 비즈니스에 중요한 의사결정을 내릴 때, 디버깅, 감사, 그리고 오래된 데이터로 인한 잘못된 판단을 방지하는 데 필수적입니다.

**모든 것을 통합하는 예시**
"Acme에 대한 한 단락짜리 상태 업데이트를 제공하고, 갱신 위험과 마지막 지원 상호작용을 포함해 주세요."라는 프롬프트에 대한 처리 과정은 다음과 같습니다.
1.  Acme의 캐시된 "계정 요약" 노드 확인 (최신 유지 기간 15분) -> `캐시`
2.  만약 오래되었거나 누락된 경우: CRM에서 기회 단계 + 갱신 날짜 호출 -> `라이브 API`
3.  마지막 지원 상호작용을 위해 티켓팅 시스템 조회 (SLA 내 캐시된 경우) -> `캐시`
4.  마지막 5개 티켓만 가져오고, 전체 기록은 가져오지 않음 (타임아웃 방지) -> `라이브 API`
5.  원본 티켓 ID, 가져온 타임스탬프, 사용자 범위가 태그된 파생 요약 생성 -> `파생 컨텍스트`

**핵심 요약**
1.  **도구는 컨텍스트가 아니다**: 컨텍스트 그래프는 회사 전체에 걸쳐 추론하는 데 도움이 됩니다. 이는 프로세스, 데이터, 스킬, 그리고 도구의 총체입니다.
2.  **더 많은 데이터가 항상 좋은 것은 아니다**: 필요한 것만 가져오고 적절하게 구조화해야 합니다. 신선하고 고품질의 데이터에 집중해야 합니다.
3.  **모든 답변은 추적 가능해야 한다**: 디버깅, 감사 가능성, 그리고 근거 있는 답변은 이에 달려 있습니다. AI가 잘못된 결정을 내렸을 때 그 이유를 알 수 없는 상황을 피해야 합니다.

Merge는 Gateway(LLM 라우터), Unified(서드파티 데이터 동기화), Agent Handler(라이브 MCP 연결)를 통해 이러한 엔터프라이즈 AI를 지원합니다.

## 인상적인 대목
*   "No magic here, only physics." (마법은 없고, 오직 물리학만 있을 뿐입니다.) - AI 시스템의 복잡성이 실제로는 논리적이고 구조적인 문제 해결에 달려 있음을 강조하는 부분.
*   "Getting context is actually a set of company principles and processes in and of itself." (컨텍스트를 얻는 것은 사실 그 자체로 회사 원칙과 프로세스의 집합입니다.) - 컨텍스트가 단순한 데이터가 아니라, 기업의 고유한 운영 방식과 지식을 담고 있음을 지적하는 통찰.

## 실무 적용 포인트
*   **컨텍스트 그래프의 다층적 접근**: AI 에이전트의 '두뇌'를 구성할 때, 프롬프트/스킬/메모리, 라이브 API 호출, 캐시된 데이터, 파생 컨텍스트 등 다양한 계층의 컨텍스트를 고려하여 설계해야 합니다.
*   **데이터 동기화 전략 수립**: 복잡한 의미론적 조회나 대규모 데이터 분석이 필요한 경우, 실시간 API 호출의 한계를 인지하고 로컬 벡터 데이터베이스에 데이터를 동기화(캐시)하는 전략을 반드시 포함해야 합니다.
*   **컨텍스트 선택 로직 정의**: 에이전트가 어떤 컨텍스트(스킬, 메모리, 캐시, 라이브 API)를 언제, 어떤 순서로 활용할지 명확한 플로우차트나 로직을 수립하여 효율성과 정확성을 높여야 합니다.
*   **데이터 추적 및 출처 관리**: AI 모델에 전달되는 모든 데이터에 대해 출처, 페치 시점, 접근 권한, 변환 이력, 무효화 조건 등의 메타데이터를 철저히 관리하여 디버깅, 감사, 그리고 신뢰성 있는 의사결정을 보장해야 합니다.
