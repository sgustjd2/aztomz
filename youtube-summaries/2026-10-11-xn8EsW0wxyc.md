# How Secrets Leak Through AI Agents (and How to Stop It) — Venice AI

🔗 https://youtu.be/xn8EsW0wxyc · 📅 2026-10-11 · 🎙 AI Engineer

## 한 줄 요약
AI 모델 자체는 프라이빗할 수 있지만, 이를 둘러싼 시스템은 데이터 유출에 취약하며, 베니스 AI는 아키텍처 및 하드웨어 수준의 프라이버시를 통해 이를 해결하고자 합니다.

## 발표자·소속
Joshua Mo, Venice AI의 Lead DevRel Eng.

## 핵심 주장
*   데이터 유출은 피할 수 없는 현실이며, 민감한 데이터는 보안 사고의 영향을 심화시킵니다. 사용자 데이터를 적게 저장하는 것이 위험을 줄이는 직접적인 방법입니다.
*   베니스 AI는 프롬프트나 대화를 저장하지 않고, 사전 정의된 프라이버시 계층을 제공하며, TEE(Trusted Execution Environment) 호스팅 모델과 종단 간(E2E) 암호화를 통해 프라이버시를 보장합니다.
*   LLM(대규모 언어 모델)은 AI 시스템의 중요한 부분이지만, 전체 시스템의 일부일 뿐이며, LLM 주변에 구축된 시스템은 데이터 유출 및 침해에 훨씬 더 취약합니다.
*   관찰 가능성(observability) 로깅은 디버깅에 유용하지만, 부주의할 경우 개인 식별 정보(PII)와 비밀을 포함한 프롬프트 및 대화를 실수로 저장할 수 있습니다.
*   비밀 정보는 LLM 추론 계층에서 분리하여 에이전트 런타임에 연결함으로써 모델이 훈련 데이터로 사용되는 것을 방지해야 합니다.
*   샌드박싱 에이전트와 권한 모니터링은 중요하지만, 외부 API 접근은 여전히 데이터 유출 위험이 있으므로 주의가 필요합니다.
*   하드웨어 수준의 프라이버시(기밀 컴퓨팅)와 검증 가능한 증명은 에이전트를 암호학적으로 격리할 수 있습니다.

## 세부 내용
발표자는 AI 시스템에서 프라이버시가 중요한 이유에 대해 설명하며 강연을 시작했습니다. 데이터 유출은 피할 수 없는 일이며, 민감한 데이터가 유출될 경우 기업의 평판과 재정적 손실이 막대할 수 있다고 강조했습니다. 사용자 데이터를 적게 저장하는 것이 보안 사고의 영향을 줄이는 가장 효과적인 방법입니다.

베니스 AI는 프라이버시를 최우선으로 하는 접근 방식을 채택하고 있습니다. 첫째, 어떠한 프롬프트나 대화도 저장하지 않아 사용자 디지털 발자국을 0으로 만듭니다. 둘째, Open AI와 호환되는 OpenRouter 스타일 모델 API를 통해 GLM 5.2, Kimmy 2.7과 같은 최신 오픈소스 모델을 호스팅하며, 이 모델들은 100% OpenAI 호환성을 가집니다. 셋째, TEE(Trusted Execution Environment)에 모델을 호스팅하여 추론 과정이 완전히 프라이빗하게 실행됨을 검증 가능하게 증명합니다. 넷째, 분할 키 관리(split key custody)를 사용하는 종단 간(E2E) 암호화를 통해 데이터를 암호화하고 접근 불가능한 인클레이브에 저장하여 공격자나 심지어 베니스 AI 팀조차 데이터에 접근할 수 없도록 합니다.

발표자는 "모든 시스템이 동등하게 만들어진 것은 아니다"라고 지적하며, LLM이 시스템의 핵심이지만 전체 시스템은 아니라고 강조했습니다. LLM 주변에 구축된 시스템은 데이터 유출 및 침해에 훨씬 더 취약합니다. 예를 들어, 관찰 가능성 로깅은 디버깅에 필수적이지만, 실수로 프롬프트나 대화에 포함된 PII 및 비밀 정보를 저장할 수 있습니다. 베니스 AI는 이러한 위험을 제거합니다.

에이전트를 통한 비밀 정보 흐름에 대한 다이어그램을 통해 일반적인 에이전트 시스템에서 사용자 요청이 에이전트 런타임, 비밀 저장소(예: 1Password/Vault), LLM 추론 계층을 거쳐 외부 API로 전달되는 과정을 설명했습니다. 이 과정에서 비밀 정보가 LLM 추론 계층으로 직접 전달되어 훈련 데이터로 사용될 수 있는 위험이 있습니다.

프라이버시를 보존하는 패턴으로 다음을 제안했습니다: 직접적인 데이터 대신 ID를 나타내는 해시를 저장하고, 분할 키 관리를 통해 데이터를 암호화하고 접근 불가능한 인클레이브에 저장하며, 쉽게 취소할 수 있는 핸들(handles)과 같은 디자인 패턴을 사용하고, 프라이버시를 염두에 두고 프롬프트를 설계해야 합니다.

에이전트 처리 데이터 보호를 위해 에이전트 범위를 좁혀 위험을 줄이고, 프롬프트 주입(prompt injection)을 확인하기 위한 분류 계층을 에이전트 앞에 두어 데이터 유출을 방지하고 프롬프트가 범위 내에 있는지 확인해야 합니다. 또한, 컨텍스트 루프를 타이트하게 유지하여 컨텍스트 윈도우 성능을 향상시킬 수 있습니다.

모델에서 비밀 정보를 분리하는 아키텍처를 제시했습니다. 사용자 요청은 LLM 추론 계층으로 가지만, 비밀 저장소는 에이전트 런타임에 직접 연결됩니다. 이로써 LLM은 비밀 정보에 직접 접근하지 않고, 에이전트 런타임이 필요할 때 비밀 저장소에서 정보를 가져와 외부 API 호출에 사용합니다. 이는 LLM 계층에서 프라이버시 및 보안상의 이유로 할 수 없었던 많은 작업을 가능하게 합니다.

에이전트 샌드박싱은 블래스트 반경을 크게 줄일 수 있지만, 외부 API 접근은 여전히 데이터 유출을 일으킬 수 있으므로 권한 모니터링이 필수적입니다. 발표자는 자체 에이전트 런타임을 구축하여 실행 계층과 추론 계층을 완전히 소유하는 것을 제안했습니다.

하드웨어 수준의 프라이버시인 "기밀 컴퓨팅(Confidential Compute)"에 대해서도 언급했습니다. TEE(Trusted Execution Environments)를 사용하여 에이전트의 추론 과정을 암호학적으로 완전히 격리하고 이를 증명할 수 있습니다. 검증 가능한 증명(verifiable attestation)을 통해 이러한 격리를 확인할 수 있습니다. 기밀 도구 호출(Confidential tool calls)은 아직 진행 중인 과제이지만, 공급자가 도구 호출이 실행되는 컴퓨팅 계층을 소유하도록 허용하는 것이 신뢰할 수 있는 해결책이 될 수 있다고 언급했습니다.

## 인상적인 대목
*   "Your model is private. Your system isn't." (당신의 모델은 프라이빗하지만, 당신의 시스템은 그렇지 않습니다.)
*   "Data breaches are an eventuality – reputational risk matters." (데이터 유출은 필연적이며, 평판 위험이 중요합니다.)
*   "Storing less user data directly reduces the blast radius." (사용자 데이터를 적게 저장하는 것이 블래스트 반경을 직접적으로 줄입니다.)

## 실무 적용 포인트
*   **데이터 최소화 및 해싱**: 사용자 식별을 위해 직접적인 개인 데이터를 사용하는 대신, 해시된 ID와 같은 대표 값을 저장하여 데이터 유출 시의 위험을 줄입니다.
*   **보안 아키텍처 설계**: LLM 추론 계층이 민감한 비밀 정보에 직접 접근하지 않도록 에이전트 런타임과 비밀 저장소를 분리하는 아키텍처를 구현합니다.
*   **TEE 활용**: Trusted Execution Environments(TEE)를 사용하여 에이전트의 추론 과정을 암호학적으로 격리하고, 검증 가능한 증명(verifiable attestation)을 통해 이 격리를 증명하여 하드웨어 수준의 프라이버시를 확보합니다.
*   **에이전트 범위 제한 및 모니터링**: 에이전트의 기능을 필요한 최소한으로 제한(narrow agent scope)하고, 외부 API 접근 권한을 철저히 모니터링하여 데이터 유출 위험을 줄입니다. 프롬프트 주입을 방지하기 위한 분류 계층을 에이전트 앞에 두는 것을 고려합니다.
