# MCP Tasks (async): Why Aren't Any Agents Supporting Them? — Cornelia Davis, Temporal

🔗 https://youtu.be/s4r6nk5WsZw · 📅 2026-08-02 · 🎙 AI Engineer

## 한 줄 요약
MCP(Multi-Agent Communication Protocol) 태스크는 장기 실행 및 비동기 작업에 필수적이지만, 분산 시스템에서 내구성(durability)과 확장성(scalability)을 확보하기 위한 복잡한 프로토콜 설계가 필요하며, MCP 태스크 v2는 프로토콜을 스테이트리스(stateless)하게 만들어 클라이언트 측 구현을 단순화하고 있다.

## 발표자·소속
Cornelia Davis, Principal Technologist, Temporal

## 핵심 주장
-   **MCP 태스크는 본질적으로 복잡하다:** 장기 실행 및 비동기 특성으로 인해 네트워크 불안정성, 사용자 지연, 프로세스 충돌 등 다양한 장애 상황에서도 작업을 지속할 수 있는 내구성이 필수적이다.
-   **MCP 태스크 v1 프로토콜은 확장성 문제가 있었다:** `tasks/list`와 같은 스테이트풀(stateful) 엔드포인트는 수많은 에이전트가 동시에 작업을 처리할 때 심각한 성능 저하를 초래하며, 클라이언트 측에서 장기 실행 연결을 관리하는 것이 복잡했다.
-   **MCP 태스크 v2는 프로토콜을 스테이트리스하게 개선했다:** `tasks/list`를 제거하고 `tasks/update`를 도입하여 클라이언트가 서버에 상태 변경을 알리는 방식을 단순화했으며, 이는 대규모 분산 환경에서 에이전트 간의 상호작용을 더 효율적으로 만든다.
-   **클라이언트 측 내구성 확보가 중요하다:** 클라이언트는 태스크 ID를 내구성 있는 스토리지에 저장하여 충돌이나 재시작 후에도 작업을 재개할 수 있도록 해야 하며, 이는 "SHOULD"가 아닌 "MUST" 요구사항으로 간주되어야 한다.

## 세부 내용

발표는 "왜 어떤 에이전트도 MCP 태스크를 지원하지 않는가?"라는 질문으로 시작하며, 그 답은 "빌더들이 똑똑하기 때문"과 "매우 복잡하기 때문"이라고 제시한다. 발표자는 20년 이상의 웹 아키텍처, 클라우드 네이티브, 쿠버네티스 경험을 가진 분산 시스템 전문가임을 소개한다.

**1. 구체적인 예시: 구매 주문(PO) 처리**
발표자는 구매 주문 처리 과정을 예시로 들어 MCP 태스크의 필요성을 설명한다.
-   구매 주문 접수 → 상품 수령 기록 → 재고 업데이트 및 요청자 알림 (백오피스 작업)
-   동시에, 인보이스 처리 (MCP 서버를 통한 작업)
인보이스 처리 과정은 ERP 검증, 승인 요청(인간 개입), ERP 재검증, 비용 센터 차감, 품목 결제 등의 여러 단계를 포함하며, 이는 장기 실행 비동기 작업이다. Temporal 워크플로우를 사용하여 이러한 인보이스 처리 과정을 코드로 구현한 스니펫을 보여주며, `workflow.signal`을 통해 장기 실행 프로세스에 비동기적으로 신호를 보낼 수 있음을 강조한다.

**2. MCP 태스크 프로토콜 개요**
MCP 태스크는 툴을 호출하고 태스크 핸들을 받아 비동기적으로 상호작용하는 방식이다. 이는 겉보기에는 간단해 보이지만, 실제로는 네트워크 불안정성, 인간의 개입 지연, 에이전트나 서버의 충돌 등 다양한 복잡성을 내포한다. 발표자는 "태스크는 요청의 기본 실행 상태에 대한 정보를 전달하는 내구성 있는 상태 머신이다"라고 정의하며, 내구성의 중요성을 강조한다.

**3. MCP 태스크 v1의 문제점**
발표자는 MCP Dev Summit에서 발표했던 서버 측 내구성 관련 내용을 언급하며, 이번 발표는 클라이언트 측에 초점을 맞춘다고 설명한다.
-   **데모:** 구매 주문 처리 데모를 통해 서버가 실행되지 않은 상태에서도 구매 주문이 제출되고, 서버가 시작된 후에도 인보이스 처리가 진행되는 것을 보여준다. 인보이스 처리는 "input_required" 상태에서 인간의 승인을 기다리며, 승인 후 나머지 단계가 완료된다.
-   **태스크 시맨틱스 (v1):** `tools/call`, `tasks/get`, `tasks/cancel`, `tasks/list`는 단기 실행 요청/응답 방식이며, `tasks/result`는 장기 실행 상태 저장 연결을 설정한다.
-   **주요 문제점:**
    -   `tasks/list`: 이 엔드포인트는 스테이트풀 프로토콜이며, 필터링 기능이 없어 수많은 태스크가 있을 경우 모든 태스크를 나열해야 하는 비효율성이 있다. 발표자는 "그냥 할 수 있다고 해서 해야 하는 것은 아니다!"라고 강조하며 이 엔드포인트를 비판한다.
    -   `tasks/result`: 이 엔드포인트는 클라이언트가 서버로부터 필요한 입력을 받아오기 위해 장기 실행 연결을 유지해야 하는 세션 중심 프로토콜로, 연결이 끊어지면 복잡한 재연결 및 상태 복구 로직이 필요하다.

**4. MCP 태스크 v2의 개선점**
발표자는 Agentic AI Foundation의 Angie Jones가 발표한 "MCP Is Growing Up" 블로그 게시물을 언급하며, MCP 프로토콜이 스테이트리스하게 변화하고 있음을 강조한다.
-   **스테이트리스 코어:** 일반 HTTP 인프라에서 확장 가능한 스테이트리스 코어를 지향한다.
-   **확장성:** 서버 렌더링 UI 및 태스크 확장을 통한 장기 실행 작업 등 확장을 지원한다.
-   **인증:** OAuth 및 OpenID Connect 배포와 더 밀접하게 연동되는 인증 기능을 제공한다.
-   **공식적인 폐기 정책:** 프로토콜이 기존 빌드를 손상시키지 않고 진화할 수 있도록 한다.
-   **태스크 시맨틱스 (v2):**
    -   `tasks/list`가 제거되었다.
    -   `tasks/update`가 새로 추가되어 클라이언트가 서버에 상태 업데이트를 보낼 수 있게 되었다. 이는 이전 `tasks/result`의 복잡한 입력 처리 방식을 대체한다.
    -   `tasks/result`는 여전히 존재하지만, 더 이상 세션 기반의 입력 처리에는 사용되지 않는다.
-   **클라이언트 측 내구성:** "클라이언트는 태스크 ID를 내구성 있는 스토리지에 저장하여 충돌 또는 재시작 후에도 폴링을 재개할 수 있도록 해야 한다." (Clients SHOULD persist task IDs to durable storage so that polling can resume after a crash or restart.) 발표자는 여기서 "SHOULD"가 "MUST"가 되어야 한다고 지적한다.
-   **여전한 확장성 도전:** v2 프로토콜이 개선되었음에도 불구하고, 수백만 개의 클라이언트가 모두 개별 태스크를 폴링하는 방식은 여전히 확장성 문제를 야기한다. 이를 해결하기 위해 "무언가 변경되었는지"를 묻는 단일 엔드포인트와 같은 알림 프로토콜이 필요하다.

## 인상적인 대목
-   "태스크는 요청의 기본 실행 상태에 대한 정보를 전달하는 내구성 있는 상태 머신이다." (Tasks are durable state machines that carry information about the underlying execution state of the request they wrap.) - 내구성의 중요성을 명확히 정의한 부분.
-   "그냥 할 수 있다고 해서 해야 하는 것은 아니다!" (Just because you can, doesn't mean you should!) - `tasks/list` 엔드포인트의 비효율성을 지적하며 개발자의 현명한 선택을 강조하는 부분.

## 실무 적용 포인트
-   **내구성 있는 시스템 설계:** 장기 실행 비동기 작업을 다룰 때는 네트워크 장애, 프로세스 충돌, 인간 개입 지연 등 다양한 실패 시나리오를 고려하여 내구성을 최우선으로 설계해야 한다.
-   **스테이트리스 프로토콜 활용:** 가능한 한 스테이트리스한 프로토콜을 사용하여 분산 시스템의 복잡성을 줄이고 확장성을 높이는 것이 좋다. MCP 태스크 v2의 `tasks/update`와 같은 패턴을 참고할 수 있다.
-   **클라이언트 측 상태 관리:** 클라이언트 애플리케이션은 태스크 ID와 같은 중요한 상태 정보를 내구성 있는 스토리지에 반드시 저장하여, 클라이언트 자체의 장애 발생 시에도 작업을 안전하게 재개할 수 있도록 해야 한다.
-   **확장성 고려한 알림 메커니즘:** 대규모 에이전트 환경에서는 개별 태스크 폴링 대신, 변경 사항 발생 시 에이전트에게 알림을 보내는 효율적인 메커니즘을 구현하여 서버 부하를 줄이고 확장성을 확보해야 한다.
